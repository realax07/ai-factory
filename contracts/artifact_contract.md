# Контракт артефактов между сабагентами конвейера

> Обязательный документ. Определяет интерфейсы передачи работы между этапами. Сабагент вправе принять артефакт только при выполнении условий входа и обязан отдать артефакт, удовлетворяющий условиям выхода.

## Общие правила

1. Передача работы — **только через файлы в репозитории проекта**, не через контекст диалога.
2. Каждая роль проверяет входной артефакт по чеклисту «Условия входа». Несоответствие — эскалация проектному менеджеру, не «доделывание за предыдущего».
3. Выходной артефакт должен проходить чеклист самовалидации агента-автора (см. инструкцию агента).
4. Форматы фиксированы; изменение формата — изменение настоящего контракта через коммит и согласование.

## Диаграмма потока

```
Заказчик ⇄ [ba_agent] → requirements.md → [sa_agent] → openspec/* + sdd.md
                                                              │
        [qa_automation] ← approved/* ← [qa_case_reviewer] ⇄ new/* ← [qa_case_author] ← checklists ← [qa_checklist]
```

## Контракт 3: Системный аналитик → QA-аналитик чеклистов (`openspec/`)

| Поле | Значение |
|---|---|
| Производитель | `sa_agent` (выход контракта 2) |
| Потребитель | `qa_checklist_agent` |

**Условия входа:** те же, что в контракте 2 (покрытие Must-требований, сценарии GIVEN/WHEN/THEN, отсутствие реализации в specs). Дополнительно: спека доступна для чтения, change-id проставлен.

## Контракт 4: QA чеклисты → QA автор кейсов (`test-model/checklists/`)

| Поле | Значение |
|---|---|
| Производитель | `qa_checklist_agent` |
| Потребитель | `qa_case_author_agent` |
| Путь | `test-model/checklists/<change-id>.md` |

**Условия входа:**
- [ ] Каждый Requirement спеки покрыт ≥1 пунктом чеклиста
- [ ] Каждый пункт имеет ID (CHK-N), источник (Requirement + FR-N), тип, приоритет
- [ ] Есть негативные/граничные пункты для требований с валидацией
- [ ] Дефекты спеки либо отсутствуют, либо эскалированы (в чеклисте есть раздел «Дефекты спеки»)

## Контракт 5: Автор ⇄ Ревьюер (`test-model/new/` ↔ `test-model/reviews/`)

| Поле | Значение |
|---|---|
| Производитель | `qa_case_author_agent` |
| Потребитель | `qa_case_reviewer_agent` (и обратно на доработку) |
| Пути | кейсы: `test-model/new/<change-id>/*.md`; ревью: `test-model/reviews/<change-id>/review-NNN.md` |

**Цикл:** автор кладет кейсы в `new/` → ревьюер пишет вердикт в `reviews/` → «вернуть» = автор исправляет и обновляет файлы в `new/` → повторное ревью (следующая итерация NNN) → «одобрить» = ревьюер переносит кейсы в `test-model/approved/<change-id>/`.

**Условия входа ревью (проверяет ревьюер):**
- [ ] Все пункты чеклиста покрыты кейсами, ID чеклиста указаны
- [ ] Каждый кейс: предусловия, атомарные шаги, проверяемый результат, конкретные данные
- [ ] Негативные кейсы ожидают явную ошибку
- [ ] Ожидаемые результаты не противоречат Scenario спеки

**Условия выхода ревью:** вердикт «одобрить» только при отсутствии blocker/major замечаний.

## Контракт 6: Ревьюер → Автоматизатор (`test-model/approved/`)

| Поле | Значение |
|---|---|
| Производитель | `qa_case_reviewer_agent` (переносом в approved/) |
| Потребитель | `qa_automation_agent` |

**Условия входа:**
- [ ] Кейсы лежат в `test-model/approved/<change-id>/` (наличие в `new/` = работа не начата)
- [ ] Кейсы прошли ревью (существует review-файл с вердиктом «одобрить»)
- [ ] Для API-кейсов: контракты в `sdd.md` достаточны для формирования запросов
- [ ] Для web-кейсов: известны UI-локаторы или сценарии навигации воспроизводимы

**Условия выхода автоматизатора:** тесты покрывают все одобренные кейсы, трассировка кейс → тест заполнена, прогон выполнен, падения оформлены баг-репортами в `test-model/bugs/`.

## Контракт 1: Заказчик → БА → Системный аналитик (`requirements.md`)

| Поле | Значение |
|---|---|
| Производитель | `ba_agent` (при участии Заказчика) |
| Потребитель | `sa_agent` |
| Путь | `requirements.md` в корне репозитория проекта |

**Условия входа (проверяет системный аналитик):**
- [ ] Присутствуют все 7 разделов структуры ТЗ (описание, аудитория, FR, NFR, приоритеты MoSCoW, ограничения, открытые вопросы)
- [ ] Каждое FR/NFR имеет уникальный идентификатор (`FR-N`, `NFR-N`)
- [ ] Раздел «Приоритеты» заполнен; требования без приоритета отсутствуют
- [ ] Нет оценочных формулировок без критерия («быстро», «удобно»)
- [ ] Открытые вопросы либо закрыты Заказчиком, либо явно помечены и не блокируют FR с приоритетом Must

**При нарушении:** системный аналитик возвращает ТЗ проектному менеджеру со списком дефектов. Не интерпретирует требования за БА.

## Контракт 2: Системный аналитик → Разработка (OpenSpec + SDD)

| Поле | Значение |
|---|---|
| Производитель | `sa_agent` |
| Потребитель | агент-разработчик (будущая роль) |
| Пути | `openspec/` в репозитории проекта + `sdd.md` в корне |

**Структура выхода:**
```
openspec/
├── specs/                  # источник правды: поведение системы по доменам
│   └── <domain>/spec.md    # Requirement + Scenario (GIVEN/WHEN/THEN)
└── changes/
    └── <change-id>/        # пакет изменений
        ├── proposal.md     # зачем и что (intent, scope, approach)
        ├── specs/          # дельты: ADDED / MODIFIED / REMOVED
        ├── design.md       # как: техрешения, архитектура
        └── tasks.md        # чеклист реализации
sdd.md                      # системный дизайн: стек, компоненты, контракты API, данные
```

**Условия входа (проверяет разработчик / валидатор):**
- [ ] Каждое Must-требование из `requirements.md` покрыто Requirement в spec или дельте (трассировка FR-N → Requirement)
- [ ] Каждое Requirement имеет хотя бы один тестируемый Scenario в формате GIVEN/WHEN/THEN
- [ ] Модальность по RFC 2119 (MUST/SHALL/SHOULD/MAY) использована осознанно
- [ ] В spec.md отсутствует реализация (имена классов, библиотеки, шаги кода) — только наблюдаемое поведение
- [ ] `tasks.md` покрывает все дельты; задачи атомарны (одна сессия = одна задача)
- [ ] `sdd.md` фиксирует: стек, компоненты, контракты API, модель данных, решения по НФТ
- [ ] Открытые вопросы ТЗ либо закрыты, либо отражены в proposal.md (Out of scope / допущения)

**При нарушении:** разработчик возвращает пакет проектному менеджеру со списком дефектов.

## Трассировка

Матрица трассировки FR/NFR → Requirement ведется в `sdd.md` (раздел «Трассировка»). Правило полноты: нет Requirement без источника в ТЗ; нет Must-требования без Requirement.
