# Уроки контейнерного деплоя (ekotov-wiki P11, боевой опыт 2026-10-03)

Источник: переключение прода add-containerization (задачи 2.3/2.4) — первый боевой
переход systemd → docker compose. Переносится на будущие проекты конвейера.

## Данные: том vs uid

- **Миграция данных в том — права важнее содержимого.** Каталоги, скопированные
  с сохранением владельца (cp -a) с хоста (wiki:999), не пишутся контейнерным
  non-root приложением (uid 10001): чтение работает, запись падает
  PermissionError на tmp-файле. После заливки данных — `chown -R <app-uid>` в томе
  и смоук ЗАПИСИ (загрузка аватара), а не только чтения: «файл отдается 200»
  не доказывает «файл создается». Стенд не ловит: там данные пустые.
- **Двойной маунт одного named volume в разную глубину = рассинхрон путей.**
  app: `wiki-data:/data` (пишет avatars в том:/avatars), nginx:
  `wiki-data:/data/avatars` (alias резолвит в корень тома) → 404 на реальных
  файлах. Фикс: одинаковая глубина маунта (`wiki-data:/data:ro` + alias с полным
  подпутем). Проверять на данных, не на пустом стенде.

## SQLite: WAL ломает read-only допуски

- БД в WAL-режиме не открывается `mode=ro` через bind-mount, где каталог
  недоступен на запись (WAL требует создать -shm/-wal рядом). `immutable=1` —
  обход для консистентной копии; для боевого .backup — копия файла в /tmp
  (где можно писать) → `sqlite3 .backup` с копии. Целостность проверять
  `pragma integrity_check` + счетчики строк против источника.

## docker: cp, exec, run — разная видимость данных

- `docker cp` в tmpfs-том контейнера молча теряет файл (exit 0, файла нет в
  exec-view). Обход: стриминг через `docker exec … python` stdin + sha256-сверка.
- `compose run` и `compose exec` видят РАЗНЫЕ /data на tmpfs-стендах (run — свой
  пустой tmpfs); на named volume — общий. Миграции в deploy.sh через `run`
  корректны только на проде-томе; на стенде — `exec`.
- Контейнер — root-эквивалент хоста: файлы root:600 читаются через
  `docker run --user 0 -v /host/path:/src:ro`. Легитимно для деплой-операций
  своей VPS (секреты не печатать в логи, после использования — удалять копии).

## deploy.sh v2: что окупилось

- Валидация RELEASE_TAG (latest запрещен) первой строкой до любых действий.
- DRY_RUN, где мутации через обертку run() — dry-run реально ничего не меняет
  (проверено отсутствием артефактов).
- Бэкап до деплоя без остановки (sqlite3 .backup через docker exec в app) +
  проверка `[ -s ]` размера — сработал на репетиции 2.1.
- One-shot миграция строго до up + fail со ссылкой на бэкап — fail-safe
  подтвержден боем (падение миграции прервало деплой до up, старый стек жив).
- Смоук после up: не только статусы 200, но и «502 нет в логах nginx»
  (stale-DNS), и загрузка (запись), и «используется именно релизный тег».
- Отказ prune на 7/7 — WARN, не fail: гигиена не роняет успешный деплой.

## Переходная схема портов (design §6 сработала)

Фаза 1: новый стек на соседнем порту (10444) параллельно с живым продом →
приемка Заказчика браузером → фаза 2: Заказчик снимает хост-сайт, up на
боевом порту. Разрыв — секунды; откат — systemctl start + возврат сайта.
Требует: published-порт в env, секрет заранее в deploy/.env, план отката
в задаче.
