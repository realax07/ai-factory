# Claude Code или Codex как оркестратор

Обычно сессию ПМ ведет Hermes. Ее можно отдать Claude Code или Codex (или
другому кодагенту с терминалом): раннер
(`scripts/package_runner.py`) и `flowctl` — обычные скрипты, их может
вызвать любая сессия с терминалом. Гайд описывает, что при этом теряется и
как это компенсировать. Процедура смены исполнителей стадий — скилл
`skills/pm-factory/executor-swap/SKILL.md`.

Решение Заказчика 2026-11-15: «Полный флоу для клода и кодекса это дорого».
Оркестратор на Claude Code или Codex ведет пакет, а стадии ролей остаются на
pi. Сам оркестратор роли не выполняет (раздел «Оркестрация» AGENTS.md).

## Когда это нужно

- Hermes недоступен, а пакет надо довести.
- Нужен оркестратор посильнее: разбор сложного STOP, распутывание конфликта
  зон, нетиповой релиз.
- Заказчик работает из терминала, а не из Telegram.

## Что дает ПМ на Hermes и что меняется

| Механизм | ПМ на Hermes | Claude Code или Codex |
|---|---|---|
| flow-enforcer (`plugins/flow-enforcer/`) | ловит `delegate_task` мимо ворот, MODEL_ENFORCE п.17 | нет: плагин Hermes. Сабагенты оркестратора ворот не проходят |
| Стадии ролей | раннер, `run: pi:<роль>` | то же: раннер не зависит от оркестратора |
| Стоп-точки `run: hermes:<роль>` | ПМ делает шаг руками | то же: это действия ПМ (приемка, PR, merge), а не делегации |
| Ревью | стадия раннера или делегация Hermes ставит `Reviewer-Delegation` | стадия раннера; для пакетов самой фабрики — provenance-sidecar `gate_runner record-review` с ревьюером `<агент>:<id>`. Ревью сабагентом оркестратора без sidecar не засчитывается |
| Реестр `active_sessions.json` | ПМ пишет при спавне | ведет раннер: резервации `flowctl` пишет `session_check`; руками — только для запусков вне раннера |
| Вотчдоги (`delegate_watchdog`, `executor_watchdog`) | по крону на VPS, если ПМ его включил (`docs/guarantees.md`) | так же: только с включенным кроном и на той же машине. Без крона обход не обнаруживается |
| `session_archive.py` | архив транскриптов исполнителей | запускай по AGENTS.md как обычно. Транскрипты дает каждый исполнитель (`finished_runs()`, J65.6); хранит их сейчас только hermes. Без Hermes скрипт печатает «Нет завершенных запусков с транскриптом» |
| Канал Заказчика | Telegram | терминал сессии |
| Правила | AGENTS.md, ядро написано под glm-5.3-flash на Hermes | те же. Claude Code читает `CLAUDE.md`, поэтому в первом сообщении укажи `AGENTS.md` явно |

Главное следствие: без flow-enforcer дисциплину держат раннер, `flowctl`,
CI (`flow`, `test-flow-control`) и ruleset main. Всё, что оркестратор
делает своими инструментами вне раннера, ворот не проходит.

## Порядок сессии

1. Worktree: `scripts/session_worktree.sh create …` (п.11). Оркестратор
   работает только в нем.
2. Первое сообщение сессии: «Ты ПМ ai-factory. Прочитай AGENTS.md и
   выполни раздел «При входе в репозиторий». Роли сам не выполняй. Стадии
   — только `scripts/package_runner.py`». Для Claude Code добавь: «правила
   проекта — AGENTS.md, не CLAUDE.md».
3. План пакета с манифестом `pipeline:` и строкой `Флоу: N` (п.13, п.14).
   Стадии ролей — `pi:<роль>`. Подмена исполнителя стадии — по скиллу
   executor-swap с записью в журнал делегаций PLAN.md.
4. `python3 scripts/package_runner.py PLAN-<пакет>.md --dry-run`, затем
   прогон. На `ЖДУ ПМ` оркестратор делает шаг ПМ (приемка, правка плана,
   возврат dev) и перезапускает раннер.
5. Приемка по AGENTS.md: ворота зеленые, дифф в зоне, отчет сверен с
   файлами. Блок статусов п.9 — в каждом докладе.
6. PR из своей ветки (п.4, п.21). Merge — по решению Заказчика.
7. Конец сессии: коммит PLAN.md и backlog/ (п.8, п.20), хеш в отчете.

## Чего не делать

- **Не звать свои сабагенты на роли.** Task-сабагент Claude Code или
  Codex-агент, вызванный самим оркестратором, не резервирует зону, не
  проходит сверку диффа, а у его ревью нет `Reviewer-Delegation` и
  provenance. Во Флоу 1 и 2 `pr_validate` такое ревью не засчитает. Флоу
  3–5 ревью в `pr_validate` не проверяют, а в CI оно только помечается
  `UNVERIFIED` (подробно — скилл executor-swap, «Ошибки»), поэтому там
  запрет держится на дисциплине и приемке.
- Исключение — пакет обслуживания самой фабрики, который внешний агент
  делает вне конвейера по п.21 (как пакеты J64/J65). Ревью делает отдельный
  агент с чистым контекстом и только статикой диффа, файл ревью коммитится
  в PR, ревью идет раундами до approve, merge — по слову Заказчика. Для
  PR `[BUG-…]` к ревью пишется sidecar `gate_runner record-review`
  (автор и ревьюер — `<агент>:<id>`, решение Заказчика 2026-11-16
  «Provenance-файл ревью»): без него `pr_validate` Флоу 2 ревью не
  засчитает. Для `[chore]` и `[docs]` ревью принимает Заказчик при merge.
- **Не гонять весь флоу на дорогой модели.** Оркестратор держит контекст
  пакета, а работа ролей идет на pi. Если стадию нужно отдать Claude Code
  или Codex, отдают одну стадию через модуль исполнителя (скилл
  executor-swap, уровень 3).
- **Не обходить ворота.** У оркестратора те же запреты, что у ПМ на
  Hermes: push в main, yolo, `flow: bypass` без решения Заказчика (п.16,
  п.19).

## Стоимость

Токены оркестратора дорогие, поэтому делай так:

- держи сессию на одном пакете, длинные прогоны отдавай раннеру и читай
  итог из state и отчетов, а не из полного вывода;
- не перечитывай большие файлы: план, state раннера и отчеты стадий
  содержат всё для приемки;
- ревью и разбор кейсов оставь стадиям на pi. Свое мнение оркестратора
  ревью не заменяет.
