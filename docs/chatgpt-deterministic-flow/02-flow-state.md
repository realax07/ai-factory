# ТЗ 02. `flow_state.py`: read-only снимок состояния

**Flow:** 4. **Зависимость:** 01. **Результат:** библиотека и CLI `inspect` с машинным JSON и читаемым выводом.

## Что собрать

Нормализовать факты из `requirements.md`, `openspec/changes/`, `openspec/specs/`, `sdd.md`, `tasks.md`, `code-reviews/`, `test-model/`, Git, результатов gates и `~/.hermes/state/active_sessions.json`. Состояние строится для указанного scope. Реестр вне Git является оперативным источником, но его отсутствие/битый JSON нельзя трактовать как «активных сессий нет».

## Модель

Каждый факт: `key`, `value`, `source` (repo-relative path, commit SHA либо registry locator), `observed_at`, `fingerprint`, `confidence` (`verified` или `unknown`). Snapshot: `schema_version`, `scope`, `repo_head`, `dirty_paths`, `registry_digest`, `facts`, `problems`, `snapshot_digest`. Для артефактов фиксировать наличие и пригодность раздельно: файл существует ≠ утверждён/прошёл gate. Метка `approved` выводится только по действующему контракту и evidence конкретной версии.

Снимок может содержать независимые состояния нескольких task ID внутри change. `current_stage` не обязан быть единственным. Если нужно показать «что дальше», отдавать набор кандидатов, вычисляемый отдельным validator.

## Поведение

1. `python scripts/flow_state.py inspect --repo PATH --project ID --flow N --change ID [--task ID] [--json]`; выбор имён ключей и модуля можно уточнить в 01, сохранив смысл.
2. Никаких записей, fetch, checkout, запуска агентов, изменения Git и реестра. Вызов дважды на неизменном вводе даёт эквивалентный JSON; временные поля исключены из digest.
3. Канонизировать пути и проверить, что читаемые проектные пути лежат внутри заданного repo/worktree. Не следовать symlink за пределы доверенной области при вычислении evidence.
4. Отличать `missing`, `invalid`, `unknown` и `ready`. Не выводить `ready` из одного имени файла либо чекбокса `tasks.md`.
5. При ошибке чтения Git/файла/реестра вернуть структурированную проблему и ненулевой код CLI; библиотека не скрывает ошибку пустым списком.
6. Проверять наличие обязательного идентификатора выбранного Flow: change для 1, BUG для 2/3, маркер обслуживания для 4, решение об экспресс-режиме и ретроспективных артефактах для 5. Конкретные форматы брать из актуальных спецификаций.

## Приёмка

- Тестовые фикстуры: пустой репозиторий, активный change с двумя задачами разного статуса, QA, архив, некорректный реестр, отсутствующий Git ref, чужой symlink.
- Снимок содержит ссылки на проверяемые факты и не меняет ни один файл.
- Для неоднозначного review или отсутствующего реестра статус `unknown`, без ложного разрешения следующего шага.
