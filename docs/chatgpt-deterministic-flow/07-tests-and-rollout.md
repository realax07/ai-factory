# ТЗ 07. Проверки обходов и поэтапное внедрение

**Flow:** 4. **Результат:** регрессионные тесты фабрики, миграция и наблюдаемый пилот.

## Тестирование

Создать временные Git-репозитории и независимые fixture-реестры; не использовать реальный `~/.hermes/state/` или пользовательские проекты. Проверять как библиотечные решения, так и exit code/JSON CLI. Тестировать отказ при:

1. Нет требований/утверждения заказчика для Flow 1; dev пытаются запустить до спеки или архитектурного review.
2. Зависимая задача стартует до merge предшественницы; task `[P]` пересекается с активной зоной.
3. Автор сам проводит review; approve относится к другому task/SHA или устарел после изменения входа.
4. QA-автоматизация стартует без approved кейсов; архив создают без слияния дельт master-spec.
5. Flow 2 используют для нового поведения; Flow 5 закрывают без ретроспективных артефактов; hotfix объявляют завершённым без последующего PR-цикла.
6. Отсутствует/битый реестр; неверный worktree/branch/SESSION.md; symlink уводит запись за зону; два конкурентных reservation пересекаются.
7. Gate возвращает FAIL, таймаут, отсутствующую команду или невалидный вывод; snapshot устаревает между `check` и `run`.
8. Runner падает после reservation и после записи файлов; recovery сохраняет данные и не стартует делегацию повторно.
9. Внешняя защита main неизвестна или отключена: отчёт честно показывает границу локального enforcement; локальные `PASS` не называют защиту main доказанной.

Каждый обнаруженный реальный обход workflow добавлять как отдельный regression test с минимальной фикстурой.

## Внедрение

**Шаг A, shadow mode:** `inspect/check/next` дают решения и диагностику без блокировки действующего ПМ. На реальном change сравнить результаты с решениями ПМ, записать ложные разрешения и ложные запреты.

**Шаг B, preflight enforcement:** заблокировать запуск делегации при `DENY/UNKNOWN`, включить atomic reservation и boundary check. Вход PM-agent и human approvals сохраняются.

**Шаг C, postflight enforcement:** до приёмки проверить diff, review provenance и gates. В CI оставить независимые существующие проверки; новые проверки подключать с явным статусом required и подтверждённой branch protection.

**Шаг D, orchestration MVP:** один поддерживаемый путь и ручной режим подготовки; автоматический adapter только после отдельного живого прогона. `factory_init.py` обновить так, чтобы новые скрипты, контракты и CI попадали в новые проекты без перезаписи пользовательских правок. Для установленных проектов документировать миграцию.
