# ТЗ 01. Контракт Flow Control и границы процесса

**Flow:** 4 (обслуживание фабрики; изменение правил конвейера оформить change-пакетом по решению заказчика). **Результат:** новая спека OpenSpec и контракт компонентов, не исполняющий агентов.

## Контекст

`flow_check.py` валидирует порядок уже созданных артефактов. `pm_bounds_check.py` проверяет отдельные границы ПМ и реестр. `pr_validate.py` проверяет PR. ПМ сегодня выбирает следующий шаг по инструкциям и фактам. В `AGENTS.md` существуют Flow 1–5, этапные согласования заказчика, независимые роли и ограничения зон записи. Новый слой должен выразить эти правила без дублирования противоречащей логики.

## Требования

1. Описать в `openspec/specs/` требования и сценарии для `Flow State`, `Transition Validator`, `Session Admission`, `Gate Runner`, `Orchestrator`, human gate и восстановления. Не объявлять текущие декларативные правила автоматически обеспеченными программой.
2. Задать общий интерфейс: `inspect(repo, scope) -> FlowSnapshot`; `check_action(snapshot, action) -> Decision`; `admit_session(decision, request) -> Reservation`; `run_gates(scope, phase) -> GateReport`. Отдельно документировать side effects: первые две операции чистые, reservation/runner меняют состояние.
3. Scope содержит канонический путь repo, project ID, Flow 1–5, идентификатор change/BUG/chore и при необходимости task ID. Неизвестный Flow и неоднозначный scope блокируют действие.
4. Описать граф действий, а не один `State(Enum)` для всего репозитория: утверждение требований, создание change, architecture review, dev task, code review, merge, QA stages, archive, release; для bug/hotfix/chore/express — собственные условия и исключения из действующих контрактов.
5. Запрос действия всегда содержит `actor_role`, `project`, `scope`, `requested_action`, ссылку на решение заказчика, если оно обязательно, и ожидаемую версию входного snapshot. Валидация решения заказчика: только явно зафиксированное и относящееся к этому scope/фазе подтверждение, не текст «ПМ считает согласованным».
6. Описать стабильные коды причины (`MISSING_INPUT`, `INVALID_GATE`, `HUMAN_APPROVAL_REQUIRED`, `WRONG_ROLE`, `ZONE_CONFLICT`, `STALE_EVIDENCE`, `AMBIGUOUS_STATE`, `STALE_SNAPSHOT`, `EXTERNAL_ENFORCEMENT_UNKNOWN`) и человекочитаемые детали с путями к evidence.
7. Зафиксировать приоритет источников: решения заказчика и спецификации как нормативные правила; Git/файлы/реестр/CI как наблюдаемые факты; сообщения агентов лишь как навигация к evidence. При конфликте фактов блокировать и объяснять.
8. Определить матрицу ответственности: runtime может запретить запуск/приёмку, CI может запретить PR, branch protection защищает main; локальный CLI сам по себе не доказывает настройки GitHub.

## Совместимость

`flow_check.py` остаётся детерминированным валидатором фактического состояния, без вызова LLM и запуска агентов. `pm_bounds_check.py` не превращать в единую state machine. Дублируемые проверки унифицировать адаптерами либо вынести общие чистые функции после тестов старого поведения. Согласовать с `contracts/artifact_contract.md`, `agents/README.md`, `AGENTS.md`, `README.md` и правилами CI.

## Приёмка

- OpenSpec `validate --all --strict` проходит.
- Сценарии содержат положительные и отрицательные примеры каждого Flow и human gate.
- Есть таблица «действие → роль → входы → evidence → gates → результат» и версия формата решения.
- Никакой новый этап не стартует только на основании текста ответа агента.
