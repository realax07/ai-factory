# ТЗ 03. `flow_transition.py`: проверка действий

**Flow:** 4. **Зависимость:** 02. **Результат:** чистая функция `check_action(snapshot, action)` и CLI `check/next`.

## Решение

`Decision` включает `allowed: bool`, `status: ALLOW|DENY|UNKNOWN`, `action`, `scope`, `actor_role`, `snapshot_digest`, `requirements_checked`, `blocking_reasons`, `required_gates`, `evidence_refs`, `next_candidates`. `UNKNOWN` не разрешает исполнение. `next` может вернуть несколько независимых допустимых действий, но не запускает их.

## Правила

1. Проверять входные артефакты, роль, task dependencies, independent reviewer, статус QA, human gate и допустимый Flow перед разрешением. Параллельная dev-задача допускается только при `[P]`, выполненных зависимостях и отдельной проверке зон.
2. Flow 1: утверждённые требования → change/SDD → architecture review → dev task/review/merge → QA по контрактам → archive → release gate. Не сводить QA к одной булевой переменной.
3. Flow 2: BUG-NNN и существующая спецификация; при изменении ожидаемого поведения либо API/схемы действуют правила эскалации и дельты из актуального контракта.
4. Flow 3: аварийная стабилизация и отдельная последующая цепочка bug-fix/PR; emergency-действие фиксирует причину и не выдаёт полный цикл за завершённый. Деплой и откат требуют существующих полномочий/подтверждений.
5. Flow 4: обслуживание не должно обходить PR/review и отдельное решение на изменение правил фабрики.
6. Flow 5: только условия экспресс-режима из BACKLOG/README; ретроспективные requirements, spec delta и кейсы становятся обязательными до закрытия цикла.
7. Этапные ворота `AGENTS.md`: новый change, релиз/фаза релиза, новый релиз из backlog, работы вне утверждённого плана возвращают `HUMAN_APPROVAL_REQUIRED`. Разрешение ограничено указанной фазой; после её закрытия не переносится автоматически.
8. Действие `accept_review/merge` запрещено, если approve относится к другой задаче, SHA или устаревшему diff. До внедрения строгой provenance из ТЗ 05 такой переход должен иметь явный `UNKNOWN` либо отдельный консервативный compatibility gate, описанный в 01.
9. Никаких переходов на основании `agent_result.success=true`, даты review как единственного proof или наличия файла без содержательной валидации.

## Интерфейс CLI

`flowctl check --repo PATH --project ID --flow N --change ID --task ID --action ACTION --role ROLE [--json]`; `flowctl next ...`. Exit: 0 только для `ALLOW`, 1 для `DENY`, 2 для `UNKNOWN`/ошибки входа (коды можно согласовать с текущими CLI; не путать gate failure с запуском агента). Вывод содержит конкретный недостающий факт и источник правила.

## Приёмка

- Табличные тесты для каждого Flow: разрешённый путь, пропущенный этап, неподходящая роль, отсутствие решения заказчика, устаревшее evidence.
- Две независимые задачи могут одновременно быть `ready`; зависимая ждёт merge предшественницы.
- Для любого запрета возвращается стабильный код и путь к правилу/evidence, а не только `False`.
