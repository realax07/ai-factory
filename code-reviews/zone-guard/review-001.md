## Замечания

### major

1. **scripts/package_runner.py:2044-2046 (+ factory_bootstrap.py:151-167, role-packs/*/settings.example.json:9) — копия в `~/.pi/agent/extensions/` продолжает действовать на стадиях раннера.** Документация пака (`skills/pm-factory/pi/role-packs/regress-runner/README.md:91`): «Пользовательские расширения из `~/.pi/agent/extensions/` грузятся всегда». Bootstrap кладет туда копию, `settings.example.json` всех паков дополнительно прописывает её в `extensions`. Значит `pi … -e <репо>/zone-guard.ts` на стадии раннера грузит **оба** guard'а, и блок любого из них — блок. Сценарий отказа (ровно тот, что PLAN описывает «после мержа, VPS»): на машине лежит старая копия → (а) devops-стадия получает отказ на `docker compose up` от старого guard'а — решение «Всем, кроме devops» на раннере не исполняется; (б) старый guard на любом отказе пишет `test-model/regress/zone-guard.log` в worktree → у не-regress ролей дифф вне зоны → STOP на finish; (в) `zone_guard_sha256` в отчете утверждает, что действовал guard репо, хотя фактически действовал ещё и другой файл — аудит вводит в заблуждение. Это расходится с решением «Прямо из репо … копия в ~/.pi нужна только для ручных запусков» и с приемкой ТЗ J64.10 («STOP, если guard … не совпал по хэшу»). Рекомендация: либо запускать pi с отключенным автообнаружением расширений (если pi поддерживает флаг вида `--no-extensions` при сохранении явных `-e` — сверить с докой pi), либо раннеру сверять sha копии `fp.pi_agent_dir()/extensions/zone-guard.ts` (и `extensions` из `settings.json`) с эталоном: расхождение — STOP с кодом (или как минимум оба sha в отчете). Тест: копия с иным содержимым в `PI_AGENT_DIR` → STOP/запись в отчете.
