# Домен: severity-классификация (FR-1)

- **Change:** add-incident-protocol
- **Источники:** requirements.md FR-1 + spec.md «Requirement: Severity-классификация инцидентов Флоу 3» (сценарии: S1 — немедленный откат; S2 — приоритетный хотфикс-PR; S3 — перевод в Флоу 2)

## Классы эквивалентности

| Класс | Вход | Кейс |
|---|---|---|
| S1 (прод недоступен/потеря данных) | валидный | TC-SEV-001 |
| S2 (деградация части функций) | валидный | TC-SEV-002 |
| S3 (некритично/косметика) | валидный | TC-SEV-003 |
| S4+ (вне матрицы) | невалидный | TC-SEV-004 |

Границы между классами: матрица — дискретный allowlist (S1/S2/S3), числовых границ нет; край класса — «следующий уровень S4» → TC-SEV-004. Регистр/дефис префикса — границы парсинга маркера, отнесены к домену маркера (см. delegation-marker.md, TC-DEC-003).

Негативные классы: TC-SEV-004 (невалидный уровень severity=S4 → ожидаемая ошибка MISSING_INPUT/DENY).

Состояния: повторная классификация инцидента, классификация после начала реакции — N/A (в спеке не определены; ретроактивная перемаркировка — Won't-граница пакета, ОВ-1).

Комбинации: N/A (один вход — класс severity; таблица решений «severity × наличие файла» отработана в домене post-mortem-gate, TC-PMG-001…006).

## TC-SEV-001 — S1: немедленный откат первым действием

- **Источник:** FR-1 + Scenario «S1 — немедленный откат» (Must)
- **Тип:** позитив

**Данные:** инцидент «прод недоступен» (все запросы 5xx), маркер делегации `incident_ref=S1-prod-down`, старт реакции T=10:00:00.

**Шаги:**
1. Классифицировать инцидент до начала реакции: прод недоступен → S1.
2. Начать initial response.
3. Зафиксировать таймлайн действий с timestamps.

**Ожидаемый результат:** первая запись таймлайна post-mortem (test-model/incidents/2026-10-15-S1-prod-down.md, секция «## Таймлайн») — откат по RUNBOOK (deploy_rollback) с timestamp < времени начала разбора причин; разбор причин начинается только после записи о стабилизации. Проверяемо: в таймлайне timestamp rollback < timestamp стабилизации < timestamp начала раздела root cause.

## TC-SEV-002 — S2: хотфикс-PR вместо отката

- **Источник:** FR-1 + Scenario «S2 — приоритетный хотфикс-PR» (Must)
- **Тип:** позитив

**Данные:** инцидент «деградация корзины» (часть запросов корзины 500, прод доступен), маркер `incident_ref=S2-cart-500`.

**Шаги:**
1. Классифицировать: прод доступен, функции работают неверно → S2.
2. Начать initial response.

**Ожидаемый результат:** первым устраняющим действием создается хотфикс-PR в приоритетном порядке (ветка hotfix/*, PR-цикл review + pr_validate), а НЕ deploy_rollback; в таймлайне post-mortem нет записи rollback как первого действия. Проверяемо: первая устраняющая запись таймлайна — «создан PR <номер>», не «выполнен rollback».

## TC-SEV-003 — S3: перевод в Флоу 2, протокол не применяется

- **Источник:** FR-1 + Scenario «S3 — перевод в Флоу 2» (Must)
- **Тип:** позитив

**Данные:** дефект «опечатка в футере», маркер `incident_ref=S3-footer-typos`, каталог test-model/incidents/ не содержит файла этого инцидента.

**Шаги:**
1. Классифицировать: некритично → S3.
2. Зарегистрировать задачу.
3. Запросить архивацию Флоу 3-задачи (flow_transition, check_archive_flow3) без post-mortem.

**Ожидаемый результат:** задача исполняется по обычному Флоу 2; ворота post-mortem нарушения не возвращают (Finding по post-mortem отсутствует — для S3 протокол не применяется); архивация не блокируется post-mortem-воротами.

## TC-SEV-004 — S4: уровень вне матрицы невалиден

- **Источник:** FR-1 + FR-4 (allowlist S1/S2/S3) + Scenario «Инцидент без severity в маркере» (негативный класс: невалидный уровень) (Must)
- **Тип:** негатив

**Данные:** маркер `incident_ref=S4-data-loss` — уровень S4 в матрице FR-1 не существует.

**Шаги:**
1. Передать маркер в flow_transition (Флоу 3), запросить переход архивации.

**Ожидаемый результат:** инцидент трактуется как неклассифицированный; Finding MISSING_INPUT («неклассифицирован: incident_ref без severity-префикса S1-/S2-/S3-»), статус DENY, exit-код CLI 1; архивация не проходит.
