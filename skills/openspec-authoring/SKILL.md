# Авторинг OpenSpec и SDD

Как превратить `requirements.md` в формальную спеку и change-пакет OpenSpec (Fission-AI) плюс SDD. Спека — контракт наблюдаемого поведения, не план реализации.

## Когда применять

- Есть валидный `requirements.md` и нужно создать `openspec/` артефакты
- Изменение существующего поведения системы (brownfield)
- Написание или обновление `sdd.md`

Не применять для: сбора требований, тест-кейсов, кода.

## Процедура

1. **Проверь вход** по контракту 1 (`contracts/artifact_contract.md`). Дефекты — возврат БА, не «доделывание».
2. **Разбей систему на домены.** Группировка по функциональным областям (для wiki: `pages`, `editor`, `search`, `api`). Домен = один файл `specs/<domain>/spec.md`. Домены размером с 1–3 человека-недели; крупнее — дроби.
3. **Пиши Requirements из ТЗ.** Один Requirement — одно требование ТЗ, с ссылкой `FR-N`/`NFR-N`. Модальность по RFC 2119: MUST для MoSCoW-Must, SHOULD для Should, MAY для Could. Прямое соответствие — иначе теряется смысл приоритизации.
4. **К каждому Requirement — сценарии.** Формат GIVEN/WHEN/THEN, покрывай happy path и негатив. Сценарий проверяем, если по нему можно написать автотест. Сценарий, тестирующий внутреннее устройство (имена классов, SQL) — ошибка.
5. **Собери change-пакет** `openspec/changes/<change-id>/`: `proposal.md` (intent, scope in/out, approach), `specs/` (дельты ADDED/MODIFIED/REMOVED), `design.md` (техрешения), `tasks.md` (чеклист). Change-id: `<глагол>-<объект>` латиницей (`add-page-crud`).
6. **Задачи в tasks.md** — атомарные (одна сессия агента), с иерархической нумерацией 1.1, 1.2. Задача «реализовать поиск» — не задача; «создать endpoint GET /api/search с фильтром по подстроке» — задача.
7. **Напиши sdd.md**: стек, компоненты, контракты API (метод, путь, схема запроса/ответа, коды ошибок), модель данных, матрица трассировки FR-N → Requirement.
8. **Прогони валидатор**: `openspec validate --all --strict`. Красная валидация = пакет не существует для конвейера.
9. **После реализации — архивация в master-spec** (контракт 7): change-пакет — предложение; пока дельты не слиты в `openspec/specs/`, master-spec («as is») не соответствует реальности. Триггер: все tasks `[x]` + зеленый QA + разрешение ПМ. Механика: `openspec archive <change-id>`, валидация strict, пакет → `changes/archive/<дата>-<id>/`. Архив без слияния ловит `flow_check.py` (exit 1). Правка master-spec напрямую мимо change запрещена — теряется аудит «почему изменилось».

## Куда что кладется

- Поведение, видимое пользователю и соседним системам → `spec.md`
- Внутренние решения (фреймворки, схемы БД, паттерны) → `design.md`
- Шаги работы → `tasks.md`
- Тест: если реализация может измениться без изменения внешнего поведения — этому не место в spec.

## Ошибки

- Requirement без источника в ТЗ — «улучшение» спеки мимо Заказчика. Новая идея → proposal как предложение, не в спеку.
- Полная перезапись спеки при точечном изменении — используй дельты, иначе ревьюер не видит изменений.
- tasks.md с задачами-этапами вместо задач-результатов.
