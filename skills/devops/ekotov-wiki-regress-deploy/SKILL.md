# ekotov-wiki: регресс и релизный деплой

Прод — DOCKER COMPOSE (`PROJECT=ekotov-wiki-par`, nginx 10443, теги
`p15-wiki-N`-стиля). /opt/systemd-схема — легаси: процессы оттуда (uvicorn
127.0.0.1:8377, владелец `wiki`) не прод и без sudo не убиваются.

## Регресс: детерминированный контур + flowctl regress (J51.2)

- Канонический контур: nginx:18443 → app:8080 + search:8378 + images:8379
  (+ video:8380 + weather:8381), свежая БД + seed + миграции wiki/gallery/video/r4,
  `EKOTOV_WIKI_BASE_URL=http://127.0.0.1:18443` и DB/AVATARS/IMAGES/VIDEOS
  на /tmp-каталогах стенда. Без env — fixture-ERROR пачками. Env задавать
  ДО запуска flowctl/pytest ЦЕЛИКОМ: без `EKOTOV_WIKI_IMAGES_DIR` в env
  pytest TC-GAL-107 (объемная проверка) краснеет — сервис пишет в том
  стенда, а тест читает дефолт /tmp/qa21-gallery/images. Повторный полный
  прогон — только после reset стенда (свежая БД на сессию, иначе
  count-ассерты поиска ловят хвосты прошлого прогона).
- `python3 scripts/flowctl.py regress --change <id>` — маппит дифф → домены
  (frontend→tests/web, backend→tests/api, остальное→tests/), дедупит домены
  (общий tests/ поглощает частичные — иначе коллизия conftest на коллекции),
  пишет артефакт `test-model/regress/<change>/regress-<N>.md`; `--final` —
  regress-final.md (ворота merge, J51.3).
- `--final` БЕЗ явного таймаута имеет дефолт 120s — на полном наборе это
  фиктивный «PASS по таймауту». Всегда явно `--timeout 1800`.
- Голый `from conftest import` в tests/api ломает полную коллекцию
  (sys.modules['conftest'] затирается tests/web/conftest) — импорты через
  пакет/фикстуры.
- regress_runner: изолированный worktree (`git worktree add ... --detach`),
  зона записи только test-model/regress/, FAIL → изолированный перепрогон 2×
  (баг vs флак), артефакт коммитится [chore] в ветку. Свежесть артефакта:
  commit — предок HEAD, а из «измененных файлов» ИСКЛЮЧЕНЫ пути-метаданные
  code-reviews/**, test-model/regress/**, test-model/reviews/** (артефакт
  всегда новее удостоверяемого кода, мета-коммиты не влияют на тесты —
  иначе вечно STALE); в CI нечитаемый worktree-путь = WARNING, flow.yml
  job'у pr_validate — `fetch-depth: 0`.
- НЕ исключены test-model/approved/** и test-model/impact/**: перенос
  кейсов в approved/ и impact-проекция H5 делай ДО regress-final, не
  после (иначе REGRESS_FINAL_STALE на финальном PR и полный перегон).
- Мета-файлы ревью правь ТОЛЬКО на релизной ветке: `git checkout <ветка>`
  ПЕРЕД редактированием — длинные цепочки команд с финальным
  `reset --hard origin/main` стирают правки, сделанные на main-чекaуте.
- Зеркалируя фабричный скрипт в проект, тяни его импорт-замкнутость целиком:
  flowctl.py ← session_check.py ← pr_validate.py ← flow_transition.py /
  gate_runner.py / role_zone_policy.py (+ shell: session_worktree.sh,
  flow_mode/flow_state/flow_check); одиночный файл = AttributeError на
  первом прогоне. После копии сверять md5 всех файлов с фабрикой.
- Зеркала/установщики (install_regress_skeleton, factory_init) ставят
  СКЕЛЕТЫ: пустые regress-domains.json/baseline.json/manifest и README без
  тестов. В докладе Заказчику различай «каркас поставлен» и «эшелоны
  работают» — наполнение контентом отдельная волна; доклад «зеркало ✅» при
  пустых каркасах Заказчик читает как «эшелоны готовы» и справедливо
  спрашивает «а где тесты?».
- Диспетчируя code_reviewer, сразу задай формат review-файла: строка
  «## Вердикт: approve|return», «Reviewer-Delegation: deleg_<id>» ВПЛОТНУЮ
  к метке, имя review-<NNN>-<task>.md или review-mapping.json с задачами —
  иначе J10 не покроет задачи и круг повторится.
- Известный фон (не дифф, не чинить в волне): test_flowctl-дрейф см. MAP,
  teardown-флейк textarea, хвост test_p15_wiki_editor льет tmp*.png (лечится
  FilePayload-именем + teardown-фикстурой).
- Reset-скрипт стенда глушит ВСЕ сервисы контура: паттерн только по порту
  app оставляет search/images/video на старой БД+SECRET_KEY → массовые 401
  (токены нового app не проходят на соседних сервисах). SECRET_KEY — один
  env на весь контур; перед прогоном pgrep по каждому порту контура.
- Полный regress-final — пакетно перед плановым деплоем (J54): на каждую
  микро-правку — regress своего куска; freeze tooling (зеркала фабрики не
  коммитить после артефакта).
- Канонический стенд канонизирован в репо (P16): `scripts/qa_stand_up.sh`
  (reset|up|health|stop; guard занятых портов) + `deploy/qa-stand-nginx.conf`
  (@-шаблон, рендерит скрипт; nginx -t проверяется). STAND_DIR/порты/FFMPEG_DIR
  параметризуются — второй контур поднимается рядом с занятым 18443 без правок.
  /tmp-скрипты — больше не источник истины.
- Эшелоны (контент в проекте): доменная карта regress-domains.json (5
  кейс-доменов: wiki/gallery/video/auth-search/tasks-board), smoke-сьют
  tests/smoke_cross/ (7 read-only requests-тестов, ~3s), manifest,
  baseline.json (пустой = флейков нет; ведение — README smoke_cross).
  `flowctl regress --tier smoke` гоняет манифест; `regress --change` режет
  набор по карте. Исполняемые rules в карте требуют каталогов
  tests/<домен>/ — до их появления движение по срезам через паттерны, а
  rules держать пустыми (смешанный дифф иначе гоняет api+web одним
  вызовом → collection errors от голых conftest-импортов).
- xdist (гайд docs/guides/xdist-regression-echelons.md): tests/api —
  `-n 4` безопасен ТОЛЬКО на доменных срезах без fastline/fast2 (они
  держат глобальную fast-line стенда → взаимные 409; полный tests/api —
  сериально или reset после); tests/web — только сериально
  (детерминированные коллизии заголовков сущностей между воркерами +
  cleanup-фикстуры трекают только успешные id + общая БД/seed);
  regress-final — всегда сериально. Web-сьют под xdist — бэклог-идея
  (worker_id-суффиксы + префиксный cleanup + --dist loadfile), не
  реализовано.

## Релиз (контейнеры)

0. Сборка релизного PR — ПОРЯДОК (каждый пункт оплачен лишним перегоном):
   промежуточный PR с change-маркером НЕ открывать — маркер включает полные
   релизные ворота и PR гарантированно красный (кейсы/ревью/регресс еще
   не собраны); ветку держи, все артефакты (кейсы→approved, ревью кейсов,
   impact-проекция H5, QA-отчет) вливай ДО regress-final; regress-артефакт —
   ПОСЛЕДНИЙ коммит ветки, после него ни одного касания (STALE ловит любое
   изменение любого файла диффа, включая ops-фиксы и impact-проекции).
1. regress-final PASS на HEAD ветки (см. выше) + `openspec validate --strict`
   + flow_check OK. Комплект артефактов release-PR с change-маркером:
   test-model/approved/<change>/ (кейсы после утверждения Заказчиком),
   test-model/reviews/<change>/ (ревью кейсов, вердикт «одобрить» —
   отдельная роль ДО release-PR), test-model/impact/<change>.md
   (проекция J58-карты — старое правило H5 требует её при
   MODIFIED/REMOVED дельтах, содержанием = openspec impact.md),
   regress-final СВЕЖЕЕ последнего касания любого из этих файлов.
2. **static_v** (backend/app/pages.py) — бамп ОДНИМ коммитом оркестратора при
   merge-волне (не devops, не забытый): иначе кеш-маркер не совпадет со
   статикой.
3. Деплой: `sg docker RELEASE_TAG=<тег> MIGRATE_MODULE=app.migrate_wiki
   PROJECT=ekotov-wiki-par SRC_DIR=/home/openclaw/ekotov-wiki
   BACKUP_DIR=/tmp/<тег>-backups bash deploy/deploy.sh` — сначала DRY_RUN=1.
4. BACKUP_DIR свежий named volume создается root-owned — chown 10001:10001 +
   chmod 0777 через alpine-контейнер (прецедент images-data).
5. Проверки: exit 0 + сводка; health 200; 5–7 контейнеров healthy НА ТЕГАХ
   нового релиза; `v=<тег>` в живом HTML; sha256 ключевой статики = локальному;
   страницы/версии в БД до/после идентичны; 502 в логах nginx = 0.
6. Откат — ОПАСЕН, и статика — тоже: deploy.sh безусловно пересобирает
   образы из SRC_DIR —
   откат «старым тегом» из актуального HEAD = новый код под старым тегом
   (ложный откат). Только отдельный клон на историческом коммите деплоя
   (искать в живом логе того деплоя); подлинные образы сохранить под
   `*-orig-*` до отката. Проверка честности: static_v и sha256 статики =
   старому релизу. static_v бампай на КАЖДУЮ волну со статикой (волна 7
   без бампа = девопс справедливо остановил деплой до выкатки).
7. Пост-релиз: factory_init --force-синк промптов/скриптов в проект (снимает
   WARNING рассинхрона), архивация пакета (см. openspec-правила ниже).
   Проектный .github/workflows/flow.yml factory_init НЕ перезаписывает
   (в т.ч. --force: kept + WARNING) — сверку required-checks/триггеров с
   фабричным эталоном делает ПМ руками.

## openspec-архивация (хвосты)

- tasks.md все `[x]` → `openspec archive <id> --yes` → new capability получает
  настоящий Purpose; MODIFIED-дельты чужих активных пакетов — вернуть дословно
  из master-spec (MODIFIED заменяет блок целиком); после каждого archive —
  validate --all --strict. Несколько пакетов: сначала тот, чьи ADDED создают
  Requirements, на которые ссылается MODIFIED следующего.
- flow_check I3: маршруты, покрытые только заархивированными пакетами,
  добавляются строкой трассировки в sdd.md.
- `openspec validate --strict` — ТОЛЬКО schema-lint структуры, не
  семантические ворота: НЕ ловит ADDED-требование, уже существующее в
  master-spec (тихий дубль при архивации), Why<50/пустой What Changes,
  сценарий без WHEN/THEN-структуры, дубли сценариев, tasks без чекбоксов;
  ловит отсутствие SHALL-в-теле, пустые сценарии, отсутствие дельт (exit 1
  на ERROR честный). Семантику держат flow_check (I3/I4, J10),
  coverage_matrix и ревьюеры — «validate green» не докладывать как признак
  качества спеки.
- ffmpeg-пин (services/video/Dockerfile): primary johnvansickle с ретраями,
  fallback — ТОЛЬКО датированный иммутабельный autobuild-релиз BtbN (тег вида
  autobuild-YYYY-MM-DD-HH-MM — ассеты НЕ перекатываются). Rolling-ассет «latest»
  НЕ использовать: дрейфовал трижды за сутки, каждый раз CI краснел на sha
  mismatch ПОСЛЕ «downloaded from fallback» (фактический sha — из лога сборки).
  Смена пина = сознательная смена релиза: скачать файл, снять sha256, обновить
  URL+sha256 в Dockerfile парой.
- flow_check rule 6 (TC-трассировка тестов): маркер вида `TC-<домен>-\d{3}`
  — РОВНО 3 цифры (двузначный не матчится), ВНУТРИ docstring теста
  (маркер перед `"""` ломает файл в SyntaxError: ведущий ноль парсится
  как int). Вставляй индексной вставкой после открывающих кавычек +
  ast.parse проверка; продолжай нумерацию кейсов домена.
- PR-циклы: `gh pr edit` НЕ перезапускает CI (правь title/body через
  `gh api ... -X PATCH` + пустой коммит для ретриггера); `cmd | tail -1`
  маскирует exit code — в цепочках с `&&` редирект без пайпа, иначе
  сломанный коммит уходит в push с ложным «pushed».
- Баг-репорты проекта: имя строго `BUG-NNN-<slug>.md` (NNN — следующий
  свободный; lowercase-сегменты невалидны) + раздел «Статус» — иначе
  FLOW-ERROR.

## Релиз с НОВЫМ сервисом (прецедент video-1)

- nginx-сниппет нового сервиса — чек-лист arch-ревью по прод-паттерну видео (все три пункта — типовые RETURN-находки): (1) auth_request ТОЛЬКО на локациях, где nginx сам отдает контент; API-локации аутентифицирует сессионный middleware сервиса (401 JSON) — auth_request на обеих = двойная проверка одной сессии; (2) proxy_pass через переменную + resolver 127.0.0.11 — статическое имя резолвится один раз на старте: nginx не стартует без контейнера и держит мертвый IP после пересоздания; (3) proxy_intercept_errors off для API-локаций с управляемыми 503 — иначе честная JSON-ошибка сервиса подменяется общей деградацией nginx. Страницу сервиса отдавай рендером ЯДРА (Jinja-шелл из base.html: static_v-бамп, активный пункт сайдбара, auth-редирект бесплатно), не nginx-статикой — статический HTML вне static_v-бампа и дублирует сайдбар.
- Деплой-скрипт не знает новых сервисов: их миграции применять ОТДЕЛЬНО
  после штатной (`app.migrate_video` — таблицы нового сервиса), smoke-матрица
  deploy.sh новые ресурсы не проверяет — чек-лист руками.
- Named volume нового сервиса ПРЕДСОЗДАТЬ до первого up (иначе root-owned),
  chown 10001:10001 + chmod 0777; каталог под ro-маунт ЧУЖОГО тома
  (mkdir /data/videos в wiki-data через app-контейнер) — до пересоздания
  nginx: ro-маунт не даст mkdir, и точка входа лежит до ручного фикса
  (проверено: ~3 мин простоя :10443). То же правило для target'а тома В
  compose: маунтпоинт НЕ под чужим ro-маунтом (кэш сервиса не в /data/*,
  а на верхнем уровне: /cache) — иначе «make mountpoint: read-only file
  system», контейнер не стартует вовсе (поймано e2e, не локально —
  раскладка маунтов стенда и CI различается, проверяй compose-сценарием CI).
- deploy.sh: добавление сервиса в SERVICES/матрицу НЕ поднимает его в
  шаге up — сервис поднимается волной 2 (`up -d search images backup weather`
  с ПОЛНЫМ набором *_IMAGE env); независимо от этого сверяй теги ВСЕХ
  контейнеров после up — depends_on пересоздавал app на дефолтных
  :local-тегах даже в рамках гейтованного деплоя. Гейт `_matrix_compose_config`
  (до up): `docker compose config` — каждый сервис матрицы обязан
  резолвиться в релизный тег, :local/:latest = fail; негативный кейс
  (убрать WEATHER_IMAGE из env → :local → гейт ловит) — часть проверки.
- Контракт 5: approved-кейсы без test-model/reviews/<change>/review-001.md
  с вердиктом «одобрить» не проходят pr_validate — ревью кейсов отдельной
  ролью ДО release-PR (прогон QA 25/25 его не заменяет); вставляй шаг в
  волну QA, не жди красного CI на интеграционном PR.
- Имена полей ВНЕШНЕГО API проверять живым запросом ДО записи в спеку:
  наивное имя (wind_direction_10m_max) дало 400 от Open-Meteo на каждом
  запросе (реальное — _dominant); спека с выдуманным полем = 100% отказ
  фичи в проде при зеленых моках.
- Повторный deploy.sh пересобирает образы с новыми ID (недетерминизм билда)
  → смоук «образ ≠ тег» краснеет: после любого пересбора — compose up -d
  --force-recreate со ПОЛНЫМ набором *_IMAGE env + ручная сверка тегов всех
  контейнеров.
- Откат релиза с новым сервисом: старые nginx-образы не знают его локаций;
  новый сервис ИСКЛЮЧИТЬ из up-набора (compose stop <svc>), его таблицы
  аддитивны — откату не мешают.
- video — ВНЕ матрицы SERVICES deploy.sh: собирается/поднимается вручную
  (build из services/video + force-recreate с VIDEO_IMAGE); frontend-образ
  несет его статику, поэтому багфикс-деплой статики видео-образ не трогает
  (video остается на прежнем теге — это ОК).
- deploy.sh отвергает worktree как SRC_DIR (проверка `[ -d .git]` — у
  worktree файла нет): деплой из worktree требует чекаута head в основной
  клон; либо фикси проверку (git rev-parse), либо чекаут — фиксируй в
  отчете девопса, молчаливая подмена SRC_DIR = деплой не того кода.

## Деплой-факты

- openspec CLI глобально в PATH, node через nvm; прод-том галереи/аватары
  чистить нельзя (данные пользователей); миграции идемпотентны
  (app.migrate_wiki), но перед деплоем — sha256-отпечатки строк данных
  до/после.
- Старый пункт бэклога перед исполнением ПРОВЕРЯЙ на актуальность
  (замер/сверка кода), не исполняй по записи: записи протухают — фича
  ушла другим релизом (адаптив: Заказчик подтверждает «работает»),
  проблема не воспроизводится (dockerd CPU: замер 0–7%), пакет заархивирован
  (process-review не нужен). Закрытие с вердиктом-фактом — легитимный исход;
  молчаливое исполнение протухшей записи — нет.
