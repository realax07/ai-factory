# Оценка внешнего ТЗ для ai-factory

Всегда-на-каждый-раз правила (порядок, решения, форма выхода):

1. **Исходник не редактировать.** Внешний материал класть отдельной папкой
   `docs/<имя-источника>/` в ai-factory, коммит с пометкой «внешний исходник»
   (коммит-путь понятнее отката перемешанного файла).

2. **Разбор = сопоставление, не пересказ.** По каждому пункту ТЗ:
   дублирует существующий слой / закрывает дыру (сверять с реестром дыр в
   бэклоге) / новое. Существующий исполняемый слой читать по коду, не по памяти
   (wc -l, grep def, режимы CLI).

3. **Слабые места ТЗ называть явно** — внешнее ТЗ не норматив само по себе;
   где оно молчит (например, кто вызывает проверку в enforcement-режиме), там
   дыра проектирования, не «само решится».

4. **Форма выхода — пофазовая оценка:** реализуемость × эффект × трудозатраты,
   срезами (какая доля пользы за какую долю труда), с рекомендацией стартового
   срезa. Решение о скоупе — только Заказчик.

5. **Старт работ: ветка от main по явному «погнали», в main не вливать до
   явного решения и отладки; ветка основная на время работ** ( standing order
   Заказчика для крупных внедрений).

6. **Первый шаг после «погнали» — change-пакет** (proposal + спека strict-valid
   + requirements с преамбулой и ссылкой на решение Заказчика + tasks с
   трассировкой + design + sdd), затем диспатчи сабагентов с разведенными
   зонами записи. Самоссылочные ошибки flow_check на активном пакете —
   помечать в tasks.md, не чинить ворота.

## Комплект багрепортов (Флоу 2, внешний аудит кода)

Когда Заказчик приносит не ТЗ, а набор багрепортов с репро-рецептами:

1. **Верифицировать чтением кода до принятия.** Репро-скрипт из комплекта
   может не дойти (приложен только markdown) — не считать это блокером:
   открыть каждое названное место в коде и подтвердить/опровергнуть дефект
   самому. Статус «воспроизведён локально» в чужом отчете не заменяет
   собственной проверки; неподтвержденный пункт — явно пометить.
2. **Имена репортов подгонять под контракт CI ДО создания файлов.**
   Проверить всех потребителей имени: flow_check (правило имен),
   pr_validate (glob `BUG-NNN-*.md` — суффикс после NNN разрешен, комплекс
   в середине `BUG-A-B-NNN` — glob не найдет), раздел «Статус» обязателен
   в теле репорта, маркер `[BUG-NNN]` — в title/body PR. Имя вида
   `BUG-<комплекс>-NNN.md` проходит flow_check, но ломает pr_validate —
   безопасная форма: `BUG-NNN-<slug>.md`.
3. **Локальный прогон pr_validate до пуша**: `python3 scripts/pr_validate.py . --id "[BUG-001] x"` — дешевый цикл вместо CI-круга на маркер.
4. **Цикл ревью: code_reviewer с адверсариальным фокусом на security-фиксах**
   (обходы через `../`, само-декларации `kind=docs`, naive-время в
   expires). «Верификатор» может отработать раньше фикса и проверить
   устаревшую голову ветки — его расхождение с отчетом фикса решает личный
   прогон ПМ по критериям приемки (полный pytest, обе flow_check), не спор
   отчетов.
5. **После мержа**: diff-проверить и переустановить измененный плагин в
   `~/.hermes/plugins/`, зеркалировать измененные skills/ в проект,
   обновить MAP (закрытые баги — отдельным блоком).

Питфоллы:
- Не класть пункты внешнего ТЗ в бэклог как задачи без сопоставления —
  дубли исполняемого слоя обнаружатся на ревью и съедят цикл.
- Не начинать доработку правил под ТЗ до решения Заказчика о скоупе —
  срезы обсуждаются ДО старта, не после.
- Нейминг артефактов выбирать после просмотра контрактов потребителей,
  не до — переименование постфактум тянет пересинхронизацию ссылок в
  тестах, PLAN и README.
