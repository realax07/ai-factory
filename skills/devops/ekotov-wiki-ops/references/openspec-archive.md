# Архивация OpenSpec change-пакетов: рецепт и классы хвостов

Проверено на сквозной архивации трех релизных пакетов (Р4 → Р5 → Р6). Полный цикл релиза — SKILL.md; здесь — механика архивации и то, что ломается.

## Порядок

1. tasks.md пакета: все `[x]`. «Бумажные» задачи (фактически выполнены, галочка не поставлена) закрывать с inline-комментарием `<!-- факт: … -->`: каким коммитом/прогоном фактически закрыто, как разошлось с формулировкой (пример: релизный бамп из задачи уехал в составе более позднего чужого релиза — цепочкой фактических бампов). Пустая галочка без факта = скрытое расхождение план/факт.
2. Ворота ДО archive: `openspec validate --all --strict` + `python3 /opt/ekotov-wiki/scripts/flow_check.py <repo>`.
3. `openspec archive <id> --yes` — дельты сливаются в `openspec/specs/`, пакет уезжает в `changes/archive/<дата>-<id>/`.
4. После КАЖДОГО archive: `validate --all --strict` заново. Слияние меняет master-spec и может сломать валидность ДРУГИХ активных пакетов — красное после слияния чинится в их дельтах, не в master-spec.
5. Коммит архивации (удаления старого пакета + изменения спек + sdd) — отдельным коммитом с перечнем слитого.

## Порядок нескольких хвостовых пакетов

Архивировать сначала пакет, чьи ADDED-дельты создают Requirements, на которые ссылаются MODIFIED-дельты следующего (пример: MODIFIED «Загрузка аватара» в Р5 валиден только после слияния ADDED «Загрузка аватара» из Р4). Обратный порядок = archive refuse / validate fail на несуществующий заголовок.

## Классы хвостов после archive

| Хвост | Механизм | Лечение |
|---|---|---|
| Новая capability с Purpose «TBD — created by archiving…» | archive пишет заглушку Purpose для новой capability | Написать настоящий Purpose прямо в master-spec: дельтовый `## Purpose` читается только при СОЗДАНИИ capability, он не может заменить уже существующий |
| Активный пакет: `MODIFIED "X" omits scenario(s)` | MODIFIED заменяет Requirement ЦЕЛИКОМ; в master-spec появились сценарии, которых в его дельте нет (слиты более поздним пакетом) | Вернуть пропущенные сценарии в дельту ДОСЛОВНО из master-spec. Формат парсить регэкспом по факту: свежеслитые сценарии могут быть БЕЗ пустой строки после `#### Scenario:` — шаблон «заголовок\n\nGIVEN» не сматчится |
| flow_check I3 «маршрут не упомянут» | После архивации всех пакетов corpus покрытия сужается до sdd.md + чеклистов; маршруты, покрытые только заархивированным пакетом, выпадают из проверки | Добавить строку трассировки маршрута в sdd.md (таблица FR-покрытия) |
| Активный пакет: `MODIFIED "X" — header not found` (INFO) | Дельта модифицирует Requirement, которого в master-spec еще нет (сидит в незархивированной ADDED-дельте другого пакета) | Зависимость: сначала архивировать пакет-владелец ADDED. INFO до порги, refuse — при archive |
| archived-пакет: «'X' не слит в master-spec» после ручного слияния | MODIFIED-заголовок в дельте — ДОСЛОВНЫЙ идентификатор прежней редакции; заголовок в master после слияния переименован под новую редакцию — парсер контракта 7 не находит дельтовый заголовок | Заголовок в master-spec держать ДОСЛОВНЫМ (идентификатор дельты), новую редакцию отражать только телом/scenario'ями; не переименовывать заголовок при слиянии MODIFIED |
| Новая capability из дельты не имеет master-spec (архивация руками, без openspec archive) | Контракт 7 сверяет каждый Requirement дельты с master; при ручной архивации master-spec надо создать самому | Скопировать ADDED-тело дельты в `openspec/specs/<cap>/spec.md` (шаблон: `# <cap> Specification` + Purpose из дельты + `## Requirements`); MODIFIED-дельты влить в соответствующие существующие master-файлы |
| I3 «маршрут не упомянут» на только что заархивированном пакете | Корpus покрытия = sdd.md + master-specs + активные дельты; маршрут, упомянутый в дельте лишь перефразом («SQL LIKE через API») без литерального пути, выпадает | Вписать литеральный путь маршрута (и актуальные факты — например регистронезависимость) в соответствующий Requirement master-spec |
| PLAN-заглушка старого пакета остается в корне после архивации | Заглушка J41 лежала как PLAN-<id>.md в корне; archive двигает только каталог пакета | git mv PLAN-<id>.md в каталог архива пакета (станет PLAN.md) вместе с архивирующим коммитом |

## Извлечение сценариев «вернуть дословно»

Регэкспом по master-spec: блок `#### Scenario: <имя>\n` + последующие строки `- **GIVEN**/- **WHEN**/- **THEN**`, вставка после последнего сценария MODIFIED-блока дельты. Python-однострочник в сессии достаточен; скрипт не заводить — операция разовая на пакет. После правки: `openspec validate <id> --type change --strict` по конкретному пакету.
