# Аудит стилей UI против дизайна (computed-style audit)

Техника ловит дефекты вида «элемент не оформлен», которые пропускают функциональные
тесты: сьюты проверяют поведение и DOM, а не визуальное соответствие дизайну.

## Быстрая проверка «элемент покрыт стилями»

0. **Новые кнопки добавляй в существующие группы селекторов, не дублируя правила.** При введении кнопки того же класса (первичная/вторичная) расширяй готовые selector-группы (`#task-form-cancel, #task-delete-button, …`) — покрыв сразу base/hover/focus-visible; отдельный дубликат правила расползается при следующей смене токенов. И помни: ID-селектор покрывает один элемент — следующий такой же элемент должен попасть в группу явно, сам он не «подхватит» стиль.

1. **Проверка класса в стилях.** Взять классы элемента из разметки и найти каждый
   в стилях (search_files, target=content, path=`frontend/static/css/`, паттерн
   `\.btn\b` и т.д.).
   Класс, которого нет ни в одном CSS-файле (пример: `btn btn-primary` без правил
   `.btn`/`.btn-primary`) — элемент гарантированно дефолтный.
2. **Computed styles в браузере.** Открыть страницу (стенд или прод) и для каждого
   интерактивного элемента (button, a[role=button], input, select, textarea)
   прочитать `getComputedStyle`. Признаки отсутствия CSS-правила:
   - кнопка: `background: rgb(239,239,239)`, `border-radius: 0px`, `font: Arial`
     (UA-дефолты Chrome);
   - правило «не с тем телом»: значение токена не из палитры дизайна (для V3
     «Бумага» акцент — `rgb(168,67,44)`, текст — `rgb(61,54,48)`).
3. **Состояния.** Проверить не только покой, но `:hover` (эмуляция через CDP/Playwright
   `hover()`), `:focus-visible` (Tab-фокус), `[disabled]` — правила состояний
   часто забывают при добавлении нового элемента.

## Сверка с дизайном (релизы с UI-дельтой)

Источник истины — `design/` (мокапы) и токены `frontend/static/css/app.css`
(`--color-*`, `--radius-*`, `--font-*`, `--space-*`). Для каждой формы/виджета
в дельте: радиусы, цвета, типографика и отступы берутся из переменных, не
хардкодом; подписи/состояния — по мокапу. Критерий приемки форм — согласованность
с токенами и мокапом, а не «выглядит прилично».

При добавлении элемента того же класса, что уже оформлен (первичная/вторичная
кнопка), расширяй существующую selector-группу и покрывай сразу base/hover/
focus-visible — дубликат правила расползается при смене токенов; ID-селектор
покрывает ровно один элемент, «такой же следующий» сам стиль не подхватит
(проверка класса из разметки по правилу 1 выше — часть приема любой UI-задачи).

## Автоматизируемый минимум

Кандидат в скрипт-ворота (принцип «проверяем скриптами»): прогон по DOM, сбор
`getComputedStyle` всех `button, input, select, textarea, a[role=button]`, флаг
элементов с UA-дефолтным фоном/радиусом. Детерминированно, дешевле агентного аудита.

## Верстка-съезды блоков (класс дефектов, невидимых фунциональным сьютам)

Перенос/переделка секций формы (комментарии из окна деталей в форму, новые ряды)
ломает раскладку: селектор-группы и стили остаются рассчитанными на старую
вёрстку. Ловится только геометрией: в playwright-тесте для блока проверить
boundingBox-инварианты (input и кнопка в одном ряду — y-центры совпадают в допуске;
ширина поля не 0/не вылезает за контейнер; соседние блоки не перекрываются),
не скриншоты. Тест-файл верстки кладется в tests/web рядом с тестами формы —
один съезд = один ассерт навсегда.

## DV-сверка раскладки: проверяй ПОЗИЦИИ элементов, а не только сетку

Формальная DV-сверка (классы/токены/gridTemplateColumns) имеет слепую зону на
топологию макета: лишний элемент внутри grid-контейнера (например h1 в первой
ячейке) сдвигает авто-placement — контент падает в колонку соседа (280px дерева)
при «правильной» строке сетки. Симптом на живой приемке: «контент сжат как под
мобилу», инпут вылезает за плитку. Правило: тест раскладки ассертит boundingBox
каждого основного блока против ожидаемой колонки (дерево — левая колонка,
контент — правая, ширины), не только строку grid-template-columns; DV-чек
раскладки — живой пробой на стенде с замерами, не сверка классов по спискам.

## Живая проба раскладки на проде: сессия и метрики

- Аутентификация для пробы против прода: пароль Заказчика не запрашивать — создать сессию прямо в прод-БД через `docker compose -p ekotov-wiki-par -f deploy/compose.yaml exec -T app python -c "…INSERT INTO sessions (token, user_id, created_at, expires_at) VALUES (…)…"` (схема sessions: token/user_id/created_at/expires_at, UTC-ISO; протухла — UPDATE expires_at), затем токен — кукой в playwright-контекст (`ctx.add_cookies`, domain хоста прода). Служебный probe-юзер (если заводится) и его сессия — в список на удаление сразу после приема. Проверка «страница открылась, а не редирект на /login» — до снятия метрик: рандомная сессия/кука молча дают 302 и probe снимает метрики login-страницы (все селекторы None — симптом именно этого).
- Метрики пробы: boundingBox основных блоков + `scrollWidth > clientWidth` на контейнерах-кандидатах (дерево, тулбар, колонки) — детектор переполнения без скриншотов; та же проба повторяется после деплоя как верификация (числа «до/после», не «должно работать»).
- Скрипт пробы живет в /tmp и в main не коммитится — воспроизводится по этому рецепту за минуты.

## Flex-переполнение узкой колонки (класс дефекта живой приемки)

flex-элемент НЕ сжимается ниже ширины контента без `min-width: 0` — длинный заголовок выталкивает соседей и выезжает за контейнер при зеленых тестах (ассерты не меряют геометрию). Фикс-набор для узкой колонки: сжимаемому текстовому элементу — `min-width:0 + overflow:hidden + text-overflow:ellipsis + white-space:nowrap`; служебной подписи справа — `flex-shrink: 0` (сжимается контент, не подпись); страховка — `overflow-x: hidden` на контейнер; обрезанному заголовку — `title`-атрибут с полным текстом (подсказка). Диагноз одной пробой: scrollWidth > clientWidth указывает контейнер и величину вылета.

## Отступление от утвержденного мокапа — decision-record ДО фикса

Если возврат с приемки ведет к варианту, которого нет в мокапе (дерево слева,
когда мокап показывает дерево в потоке; ширина контента больше мокапной) — сначала
decision-record в `decisions/` (дословный выбор Заказчика, фиксируемое отклонение,
критерий приемки, последующие уточнения — дополнять в тот же файл), затем dev-фикс,
обновление affected web-тестов раскладки, бамп static_v, DV-ре-чек коротким кругом,
повторный деплой. Решение «оставить как в мокапе» — тоже decision-record (отказ
зафиксирован).
