# Проведение сессий через flowctl-ворота (ekotov-wiki / ai-factory)

## Правило плана релиза (J41)

Релиз стартует с PLAN-файла, пишет ПМ до диспатча СА; СА лишь детализирует в tasks.md, план не переписывает. Легальные пути: PLAN-ИДЕНТИФИКАТОР.md в корне репо (ИДЕНТИФИКАТОР — имя change-пакета) ИЛИ PLAN.md внутри каталога пакета openspec/changes/ИДЕНТИФИКАТОР/. Состав: цель; строка «Флоу: N» (1–5) с обоснованием; этапы/волны с ролями; развилки Заказчика; план прогонов по наборам; критерий закрытия. Два контура: старт-ворота flowctl prepare (create_change/dev_task — проверки PLAN_RELEASE_MISSING/PLAN_FLOW_UNDECLARED в фабричном flow_transition) и мерж-аудит flow_check (активный change без плана или без «Флоу: N» — нарушение, смержить нельзя). Дисциплина обхода та же, что для bypass-делегаций (J39): ПМ — единственная дыра, правки ворот без решения Заказчика запрещены. Включение мерж-аудита краснит CI на легаси-пакетах без планов (ожидаемые нарушения J41) — путь закрытия (owner-merge или помеченные заглушки + архивация) решать Заказчику ДО влития; у ПМ-токена admin нет — required check API не обходит.

## When to Use

Использовать при ЛЮБОМ prepare/run/finish через scripts/flowctl.py в
ekotov-wiki или ai-factory: Флоу 1 (create_change, approve_requirements,
design_task, dev_task, code_review), Флоу 2 (bug_fix), релизные/ops-этапы.
Каждое правило здесь — сэкономленная итерация боевых ворот.

Процесс целиком — ai-factory/docs/README-flow-control.md; зоны ролей —
agents/README.md репо.

## Подготовка сессии (prepare)

1. ВСЕГДА сначала `--dry-run`: все DENY видны за один прогон. Не проводи боевые попытки — каждая боевая создает reservation/registry-мусор и жрет итерации.
2. `--project wiki` (НЕ ekotov-wiki-par) — scope в decision-record сверяется дословно; несовпадение = DENY «разрешение не переносится».
3. `--approval-ref` — decision_id файла decisions/<YYYY-MM-DD>-<slug>.md. Файл решения обязан: action ТОЧНО равен действию этапа (approve_requirements ≠ start_flow1 ≠ create_change), поле `commit` заполнено, scope.project = --project.
4. `--path`: каталог с `**` после change-id не матчится (glob '*' не переходит через '/'); передавай конкретные файлы (proposal.md, requirements.md, research.md, design.md, tasks.md) плюс литеральное `openspec/changes/<id>/specs/**` — литеральное совпадение с политикой принимается. Зона pm — только PLAN.md/BACKLOG.md/README.md.
5. Не используй `--create-worktree`: session_worktree.sh лежит в ai-factory, в ekotov-wiki его нет. Работай веткой в основном репо.
6. Зомби-hold чужой зоны (running, а работа давно влита): admin-close правкой active_sessions.json (lifecycle history + status=completed с evidence) — только с фактом влита/принята; иначе escalate, не удалять.

## Маркеры PR (pr_validate)

- Валидные: [BUG-NNN]/[change-id]/[chore]/[docs]/[ops]. Иного ([design] и пр.) валидатор не знает. `[pipeline]` — маркер фабричной истории, wiki-валидатор его НЕ знает: привычный фабричный префикс в тайтле wiki-PR дает «маркер ID не найден» и красный flow; процессные правки в wiki нести под [chore].
- J26-ворота deploy-диффа (детерминированные, оба уровня): коммит ПМ-сессии с deploy/** или RUNBOOK.md без [ops]-маркера краснится pm_bounds_check; PR с deploy-диффом не-[ops]-типа краснится CI (check_deploy_gate, env PR_CHANGED_DEPLOY). Любая правка деплой-инфраструктуры — только [ops]-PR (девопс-делегация + приемка Заказчика).
- change-маркер — ТОЛЬКО финальному PR пакета: он триггерит полный QA-хвост (impact/checklists/approved/reviews), которого на промежуточной стадии нет. Поэтапный dev-PR и точечные правки (дозаполнение review-файла, review-mapping.json, чекбоксы) — маркер `[chore]`/`[docs]`.
- Дополнительно (когда change-маркер все же нужен на непосильном QA-хвосте): `Reviewer-Delegation` в review-файле должна указывать на делегацию со state='completed' в async_delegations — оборванная делегация получает state='error' и валит чек (даже реальный ревьюер с dropped-делегацией выглядит как SELF_REVIEW). Обход для артефактного PR: [chore]-маркер, он QA-хвост не тянет.
- J11-role-сверка (уже в pr_validate): делегация из Reviewer-Delegation обязана иметь РОЛЬ code_reviewer в active_sessions — ревью-файл, записанный ПМ/dev/QA-делегацией (в т.ч. восстановленный ПМ по транскрипту), больше не засчитывается валидатором, даже при completed. Легитимный путь записи вердикта при оборванной ревью-делегации — передиспатч ревью-сабагента, а не самозапись ПМ; исключения с документированной историей — только [chore]-маркер.
- pm_bounds_check дополнил: прямой коммит ПМ-сессии в code-reviews/ — отдельное нарушение (вердикт пишет ревьюер из делегации; влитие review-файла — PR'ом ветки роли).
- Ретриггер с новым титулом: `gh run rerun` берет СТАРЫЙ event-payload (титул на момент триггера) — правка титула после запуска чеков на реран не подействует; свежее событие = пустой коммит в ветку.
- `gh pr edit` падает (GraphQL Projects-classic). Смена титула без пересоздания PR: `gh api -X PATCH repos/<owner>/<repo>/pulls/<N> -f title='...'`; ретриггер чеков после смены титула — пустой коммит в ветку (`gh run rerun` берет старый event-payload).

## Реестр делегаций: вытеснение старых записей ломает pr_validate

async_delegations хранит ограниченное число записей (~50) — Reviewer-Delegation
в review-файлах старых этапов пакета может выпасть из реестра к моменту
финального PR (pr_validate: «не найдена в реестре — ревью не засчитано»).
Восстановление БЕЗ подделки provenance: манифест делегации живет в
~/.hermes/cache/delegation/live/<id>/manifest.json (goals, статусы, таймстампы)
— вставить запись в async_delegations (state=completed, task_json из манифеста,
result_json с полем restored+source_manifest, origin-поля из образцовой строки
реестра). Полные dispatch-данные утерянных делегаций извлекаются из сообщений
старой сессии (messages LIKE '%deleg_<id>%'). При диспатче ревью/этапных
делегаций марафона — сразу вписывать Reviewer-Delegation в review-файл (сабагент
свой id не знает) и проверять наличие записи в реестре до финального PR.

Имя review-файла с нечисловым slug'ом (review-004-wave3.md) матчит J10 как
задачу «3» из slug'а — реальные задачи 3.1–3.4 остаются «без ревью». Именовать
review-файлы по задачам: review-004-3.1-3.2-3.3-3.4.md (парсер вытаскивает все
числовые id из task-части). Аналогично не называть файлы словом этапа/волны.

## Красный flow/pr_validate: диагностика и типовые причины

- Сначала воспроизводи локально, без CI-рантрайлов: `python3 scripts/flow_check.py .` (в корне репо на ветке PR) и `GITHUB_HEAD_REF=<ветка> python3 scripts/pr_validate.py . --id '<текст title>'` — оба чека воспроизводятся за секунды, лог CI не нужен.
- flow_check (rule 6) валит автотесты: `time.sleep(` запрещен спекой qa-pipeline, и в тексте файла должна быть TC-ссылка вида `TC-xxx-NNN`. Девы-сабагенты регулярно пишут оба нарушения; фикс ПМ в pipeline-PR: TC-ref в docstring (брать существующий id домена — для галерейных кейсов TC-GAL-*), а sleep, легитимный по смыслу (различимые created_at), заменять на `time.monotonic()` busy-wait — запрещен буквальный паттерн, не само ожидание. TC-ref должен матчить паттерн валидатора (`TC-<domen>-\d{3}`) — короткие id типа `TC-P14-2` rule 6 не проходят.
- flow_check сканирует ВСЕ дерево tests/ ветки PR, а не только дифф: красный на файл, который твой PR не трогал — это процесс-долг ранее влитого кода, вскрывшийся на твоем PR. Чинить process-фиксом в этом же PR (TC-ref/monotonic отдельным [chore]-коммитом), не RETURN деву и не ретриггерить.
- `gh run view --log-failed` бывает пустым при упавшем шаге; точные строки валидатора брать через `gh api repos/<owner>/<repo>/actions/jobs/<job_id>/logs` (job_id из `gh run view <id> --json jobs`).
- Review-файл обязан нести мета-строку `Reviewer-Delegation: deleg_XXXX` (машинный парсер REVIEWER_META_RE; id — реальная платформенная делегация ревьюера из async_delegations, state=completed): без нее approve-вердикт НЕ засчитывается и flow/pr_validate краснеют, даже при валидном «## Вердикт: **APPROVE**». Перед влитом ревью — `grep -i 'Reviewer-Delegation' <review-файл>`.
- VERDICT_LINE_RE матчит ТОЛЬКО `## Вердикт...` без нумерации секции: заголовок `## 7. Вердикт` молча не парсится (parse_verdict → None) и J10 рапортует «закрытая задача без approve», хотя вердикт в файле есть. После спасения/записи review-файла проверяй парсером: `flow_check` локально или `grep -E '^#{1,4} Вердикт' <файл>` — строка обязана начинаться с «Вердикт» сразу после решеток.
- Починка отсутствующей меты — одна строка в review-файле + `[chore]`-PR; после влита ребейзни открытую ветку на main (`git rebase main` + `push --force-with-lease`), чтобы flow_check на ней позеленел.
- Дубли id (два разных инцидента J17/J19) в MAP: файлы получают суффикс -2 (backlog/<ID>-2-<slug>.md); заголовок файла = реальный item, не id.
- Правки титула PR: `gh pr edit` падает (GraphQL Projects-classic) — только `gh api -X PATCH repos/<owner>/<repo>/pulls/<N> -f title="..."`; после смены титула пустой коммит в ветку (gh run rerun берет старый event-payload).
- Каждый PR обязан нести маркер в ТИТУЛЕ (не только body): [BUG-NNN]/[change-id]/[chore]/[docs]/[ops] — pr_validate читает title+body, но title забывают чаще всего.
- Локальный main при divergent: `git config pull.rebase false; git pull; git config --unset pull.rebase` — одноразово, настройку не оставлять.

## Красный e2e: Docker Hub rate limit раннеров (инфра, не дифф)

- e2e job падает на старте compose-стенда с 429 на pull из Docker Hub (netdata и базовые образы) — это IP-пул GitHub-раннеров исчерпал анонимную квоту: краснеет ЛЮБОЙ e2e в этот момент, дифф ни при чем. Проверять grep'ом job-лога (`gh api .../actions/jobs/<id>/logs | grep -i 'toomany\|rate limit'`), не ретрай-циклом.
- Лимит откатывается ~час; рераны в коротком цикле бесполезны. Ставить один отложенный реран (фон 30–40 мин); «давай еще разок» Заказчика — одиночный реран после паузы, не серия.
- Постоянная заглушка netdata уже в flow.yml (NETDATA_IMAGE строится локально из services/frontend/Dockerfile со stub-conf, healthcheck отвечает 200): не откатывать — прод compose.yaml не тронут, реальный netdata остается дефолтом. Правило Заказчика: netdata — не наш сервис, в нем не коммитим; UI-тесты проверяют ЛИНК /netdata/, не дашборд.
- Docker-образ, собранный ранее в том же job, для FROM не виден без pull-policy (buildkit лезет в реестр) — для локальной пересборки под новым именем использовать `docker tag` локального образа, не `FROM <локальный-образ>` в Dockerfile.

## Восстановление потерянной ветки (PR закрыт/остался без мержа, ветка удалена)

- Коммит несмерженной ветки живет в reflog даже после `git branch -D` и `git push origin --delete`: `git reflog | grep '<ключевое-слово-сообщения>'` → sha; либо `git fsck --dangling | grep commit`. Восстановление: checkout main → `git branch -f <ветка> <sha>` → `git push --force-with-lease origin <ветка>` → новый PR; содержимое идентично.
- `git branch -f` на ветку, занимаемую текущим worktree, падает ('used by worktree') — сначала `git checkout main`, потом force-update.
- `gh pr merge` на закрытом-не-влитом PR невозможен ('not mergeable') — это не конфликт; пересоздавать PR той же веткой.
- Профилактика: не удалять ветку, пока PR не влит; зачистка веток — только по `--merged origin/main` (см. «Гигиена веток»), не по названию.
- Ветка с merge-коммитами (от привычки `git pull` без rebase на divergent main) не ребейзится на origin/main — rebase падает на чужих merge-узлах. Спасение: пересоздать ветку от origin/main (`git branch -f <ветка> origin/main` из main-checkout) и `git cherry-pick <sha>` рабочего коммита; содержимое идентично, история чистая. Профилактика: рабочий контент держать ОДНИМ коммитом на ветке — тогда перенос тривиален.

## Закрытие сессии (finish)

- finish design/dev-сессии требует pm_bounds_check с ЯВНЫМ `--pm-mode sessions --pm-registry <active_sessions.json>` — без режима gate дает ERROR и блокирует.
- Если finish уже ушел в blocked по этой конфигурационной ошибке — повторный finish игнорирует флаги; спасает `--pm-resume` (только для blocked по gate ERROR без дефектов по существу) → verdict returned; затем ПМ закрывает lifecycle вручную (finished → completed с evidence).
- Проверку pr_validate финального PR: `--pr-id`; гейты --gate-scope не подменять (политический набор вычисляется).

## Жизненный цикл задачи внутри пакета

- Чекбокс задачи НЕ ставить в `[x]` до review-вердикта: flow_check считает закрытые dev-задачи без approve-вердикта ошибкой и краснит CI PR-а. Порядок: PR открыт с `[ ]` → review → review-файл влит отдельным pipeline-PR ([change-id]-маркер) → чекбокс `[x]` координационным PR → мерж основного PR.
- QA-хвост (impact/checklists/approved/reviews) существует только к финальному PR пакета; поэтапные dev-PR с change-маркером падают на нем. REQUIRED CHECKS включены в обоих репо (wiki ruleset: flow+e2e; ai-factory: test-flow-control+flow) — эта краснота теперь БЛОКИРУЕТ merge, «докладывать как ожидаемый статус» больше не работает для мержа: поэтапные dev-PR нести под [chore]-маркером, change-маркер только финальному PR пакета.
- tasks.md-задача с роль-маркером: маркер-слот ОДИН и сразу после ID, MoSCoW — вторым: `[x] 5.2 [ops] [M]`. Порядок `[M] [ops]` regex closed_dev_tasks не матчит — задача числится dev и J10 дает ложный FAIL на main (после required checks красный main блокирует merge — чинить маркерным [chore]-PR, не откатывать чекбокс).
- Параллельные задачи требуют [P]-маркер в tasks.md и непересекающиеся зоны; без этого admit_session не пропустит — при пересекающихся зонах (общий css/**) работай последовательно.
- Параллельные сабагенты в одном клоне репо делят ОДИН HEAD и один индекс: каждый агент обязан сидеть на своей feature-ветке и НЕ переключать общий checkout (переключение другим агентом ломает идущие прогоны и уносит чужие staged-файлы). Чужие ветки читать только через `git show origin/<ветка>:<файл>`; собственные playwright-прогоны — во временном worktree (`git worktree add /tmp/<имя> <sha>`), стенд поднимать оттуда. Пиши эти три правила прямо в ТЗ каждому параллельному деву.
- Легкая альтернатива при СТРОГО непересекающихся зонах и одной волне: агенты работают прямо в общем worktree на main, не переключая checkout и не коммитя; ПМ по завершении отчетов собирает ветку этапа и коммитит. Зоны из ТЗ при этом режиме обязательны — при малейшем пересечении файлов возврат к режиму отдельных веток. Перед сборкой сверить `git status`: файлы каждого агента должны соответствовать его зоне.
- Перед сдачей сверяй `git show --stat` своего коммита: staged чужие файлы прилипают к коммиту из общего индекса и «вычистить постфактум» нельзя — ветку пересобирают с нуля. Если идентичный контент все же попал в две ветки, назначь порядок мержа в теле обоих PR (общие файлы схлопываются у второго) — иначе ложный conflict.
- После мержа задачи гаси зомби-hold ее сессии в реестре (running → completed с evidence влита) — иначе следующий prepare на ту же зону получит ZONE_CONFLICT.
- Общий чекаут — место постоянных инцидентов при параллельной волне: один агент переключает HEAD и ломает прогоны другого, WIP улетает в dangling. ПМ-протокол: WIP каждого агента закоммитить в его ветку сразу по завершении отчета (не оставлять незакоммиченным в общем дереве); перед ребейзом/переключением веток спрятать чужой WIP в stash с именем-владельцем и вернуть на его ветку; дубль-WIP поверх уже закоммиченного сверять `git diff <коммит> -- <файлы>` (пусто = дубль, удалять) — не оставлять второй копию в дереве.
- Dev-коммит, тест которого валит flow_check (rule 6), чинит ПМ в pipeline-ветке последующим коммитом, а не возвратом деву: это правка процесса (TC-ref/sleep), а не диффа — фиксировать это в commit-message.

## Архитектурный контур

Триггер обязательности arch-review (services/контрактные границы backend/deploy/контрактообразующие дельты), процедура явного skip для UI-only и известная дыра движка (sdd.md молчаливый проход) — references/arch-review-policy.md. Правило введено решением 2026-10-08-arch-review-policy; ПМ проверяет триггер на prepare каждого пакета.

## Среда ревью/дев-сабагентов (стенд, env, дисциплина прогонов)

Стенд для playwright-проверок: uvicorn app.main (env DB_PATH на tmp + SECRET_KEY;
схему поднять init_db + seed owner bcrypt-хешем, getpass-интерактив обходить
прямым вызовом seed) + http.server на frontend/static; роль nginx в браузере
играет route-паттерн: /static/** перехват → http.server со срезанным префиксом
/static — без этого CSS не грузится и все стилевые ассерты ложатся. ТОТ ЖЕ
паритет обязателен в тест-прокси над сервисами (images-класс): прокси, шлющий
/static/* на static_url БЕЗ отрезания префикса, дает 404 на всю статику —
«редактор/страница не открывается» выглядит как продуктовый баг, а это стенд
(docroot http.server = frontend/static, внутри docroot префикс /static уже
отсутствует). DB_PATH-константы в тест-модулях читать из env рантайма
(os.environ.get в теле фикстуры), не на импорте модуля — conftest выставляет
env только при подъеме стенда, после импорта. Playwright ≥1.63: тест,
заканчивающийся сразу после навигации (redirect/save), оставляет in-flight
/static-запросы — teardown Browser.close утилизирует fetch-response под
работающим route-handler'ом и валит зеленый тест ERROR'ом «Route.fulfill:
Fetch response has been disposed»; фикс — page.wait_for_load_state("networkidle")
в конце таких тестов. Python
сабагента наследует чужой PYTHONPATH — стенд/пробы запускать с env -u
PYTHONPATH. Нативный скролл (scroll-snap, свайп-колонки) тестировать ТОЛЬКО
через CDP `Input.dispatchTouchEvent` — синтетические JS TouchEvent нативный
скролл не двигают, ассерт ложно красный. Перед подъемом nginx-стенда по
протоколу tests/README проверять занятость :18443 — при чужом (даже с мертвыми
бэкендами) поднимать свой контур на соседних портах, не воевать за порт. Каждый playwright-прогон — одна команда ≤30 сек синхронно; фоновые
процессы — только с process_manage wait; стенды гасить в конце обязательно
(осиротевшие uvicorn/http.server — прямой источник stall и портовых конфликтов).
После cherry-pick/переноса коммитов между ветками сверять, куда лег коммит:
review-файл в PR дев-задачи входить не должен. Ревьюеру мобильных модалок:
безусловный scrollIntoView на focusin ломает дропдауны/поповеры, якорные к полю
(скролл перезапускает фокус-цепочку и список мгновенно закрывается — ловится
только А/Б-пробой на обоих состояниях); корректный паттерн — скроллить только
при реальном выходе поля за вьюпорт (getBoundingClientRect-проверка), и
вариант «через setTimeout(0)» НЕ чинит. Смежные web-тесты при подозрении
на 401/падение /api/suggestions или /api/auth: сначала проверить Secure-куку
(на http-стенде `c.secure=False` перед запросом) — это инфраструктурный фейл,
не продуктовый; браузерные дропдауны при этом могут падать реально (пустой
listbox) — перепроверять на стенде с поднятым search-сервисом. Ленивые/опциональные
фикстуры стенда (тесты «без живого приложения») — НЕ вводить (решение Заказчика):
падение сборки без стенда — полезный сигнал E6 «подними стенд», размывание его
дает «тесты зеленые, но половина реально не проверялась» — симуляция вместо
реальной проверки. Фикстура-коллекция артефактов (созданное через UI в тесте)
обязана иметь РАБОЧИЙ teardown-путь: атрибут, в который тест «регистрирует»
созданное, teardown должен читать и чистить — мертвый атрибут (тест пишет,
teardown не читает) дает порядко-зависимые фейлы на session-БД, ловится только
инвертированным порядком прогонов — новый сьют гонять в двух порядках.

tests/api не поднимают свой стенд: conftest ждет ЖИВОЕ приложение на :8080
(EKOTOV_WIKI_BASE_URL). Канонический прогон по tests/README: (1) `python -m
app.db` (схема ядра) → (2) seed → (3) миграции пакетов → (4) uvicorn :8080 →
(5) pytest с env EKOTOV_WIKI_BASE_URL + EKOTOV_WIKI_DB_PATH. Seed через
`app.seed_users.main()` интерактивен (getpass) и вешает безголовый вызов —
сеять прямым вызовом `seed_user(login, desc, password)`. Фейлы ядра на
самодельной /tmp-БД — НЕ регресс диффа: тесты ядра исторически гоняются
QA-сабагентами на своих полных стендах, в CI только e2e. Доказательство
pre-existing — контрольный прогон того же набора на чистом main в том же
окружении (git stash → pytest → git stash pop): у диффа фейлов должно быть
не больше, чем у чистого main.

## Спасение оборванного сабагента (iteration-cap / interrupt без коммита)

Работа сабагента, упершего в лимит итераций, обычно цела в рабочем дереве и в
dangling stash-коммитах. Порядок спасения: (1) `git status` на всех ветках —
незакоммиченные файлы на чужой ветке; (2) `git fsck --dangling | grep commit` +
`git log -1 --format=%s <sha>` — потерянные stash'ы находятся по сообщению
«WIP on <ветка>»; (3) `git stash apply <sha>` → отсечь чужое (`git checkout --
<чужие файлы>`) → перенести на свою ветку (перебейзить на свежий main) →
коммит ПМ. Сверить дифф со статистикой отчета сабагента — файлы должны
совпасть. Не перезапускать задачу, пока WIP не найден. Дубли WIP поверх уже
закоммиченного содержимого сверять `git diff <коммит> -- <файлы>` (пусто =
дубль, рабочий экземпляр удалить). После падения сабагента гаси его стенды
(`ps aux | grep -E 'uvicorn|http.server|nginx'` + kill по pid — стендовые
процессы переживают делегацию и дают port-conflict следующему прогону).

Если iteration-cap кончился ПОСЛЕ завершения проверок, но ДО записи
вердикт-файла — задачу НЕ перезапускать: ПМ пишет review-файл дословно по итогам
из живого транскрипта (delegation/live/<id>/task-0.log), с пометкой в шапке «отчет
восстановлен ПМ», свежим correlation и Reviewer-Delegation этой делегации.
Дисциплина марафона «доведи до конца»: ограничь верификационные циклы —
визуальный баг, не воспроизводимый в playwright-эмуляции (живой композитинг
Safari/iOS отличается), фиксится по описанию и подтверждается Заказчиком на
живом устройстве после выката, а не 8+ А/Б-пробами на стенде.

Техника А/Б-ревью фикса: два detached-worktree из /tmp — база (до фикса) и
голова фикса; одинаковые playwright-пробники на обоих, свежая БД на каждый.
Дает счетчик «X/10 до → Y/10 после» вместо голословного «исправлено»; виновника
регресса изолировать отключением подозрительного механизма (listener/hook) на
дельте.

Флейк-вердикт: тест, падающий в связке но зеленый изолированно, гонять МНОГОКРАТНО
(5+) на диффе И на родителе — вердикт «флейк/не регресс» только при одинаковой
частоте на обоих. Root cause гонки искать в тест-механике: два раздельных
evaluate-чтения DOM (attribute + dataset) с async перерисовкой между ними —
элемент отрывается до второго чтения; фикс — атомарное чтение одним evaluate,
и это фикс тест-хелпера (отдельный багфикс), не диффа задачи.

## Итерационный бюджет сабагентов: профилактика iteration-cap

Дев/ревьюер, уперший в max_iterations, теряет финальный артефакт (коммит или
вердикт-файл) — вся работа висит в рабочем дереве. Профилактика при диспатче:
(1) задачу [L] резать на ≤[M] (реализация отдельно, тесты отдельно) — один
сабагент не съедает объем; (2) в ТЗ явно: «вердикт/отчет — ПЕРВЫЙ артефакт,
пиши по мере прохождения секций, не одним куском в конце» — тогда cap оставляет
готовый отчет, а не потерю; (3) «фикс-пробы приоритетнее regression-пачки»;
(4) гигиену диффа (git show, sha256) — без прогонов.

Механические траты бюджета, которые выноси из ТЗ сабагента в подготовку ПМ:
ручные playwright-отладочные скрипты (пишутся итерациями), поштучные прогоны
тестов в цикле, grep aria-snapshot — это отладка, а не результат. Тяжелый хвост
механики — в qa_runner/delegate с передачей уже установленных фактов артефактом,
оркестратор прогон-фиксирует только цифры.

## Аудиты конвейера (J20/J8-класс): делегат + скрипты, не контекст ПМ

Аудит по историческим данным (транскрипты делегаций, review-файлы, баг-карточки,
async_delegations) — делегировать leaf-сабагенту с явными правилами в ТЗ:
вся работа скриптами в /tmp/<имя>/, данные НЕ читать в контекст, отчет в
/tmp/<имя>/report.md, факты из данных (пометки N/A где метрик нет — не оценки),
стенды не поднимать, прод не трогать. Источники: async_delegations (state,

active_sessions.json. Отчет после приемки — влит в docs/ репо обычным PR
([docs]-маркер), сырые json-выжимки в репо не тащить. Прецедент: J20+J8 одним
делегатом (129 ревью, 325 делегаций за один прогон ~23 мин).

## Волна кода после «approve после фиксов»: ревью-фикс-верификация на одном сабагенте

Вердикт «approve после фиксов» (F-1..F-n с координатами) проводить БЕЗ возврата авторам: один фикс-сабагент получает полный список находок с координатами и правилом «только пункты N..M, спорный пункт не трогать», плюс обязательные прогоны (включая инвертированный порядок — ловец порядко-зависимых фикстур). Затем ОРИГИНАЛЬНЫЙ ревьюер верифицирует фиксы по своему же вердикту (независимая проверка, не по отчету фикса) и ставит итоговый approve; параллельно можно диспатчить design_validator (DV-сверка DOM/классов/состояний/раскладок против мокапов через aria-snapshot стенда) — эти два сабагента независимы. Review-файл ревьюер дополняет секцией «Верификация фиксов», не создает новый. Волну диффа не дробить по ревьюерам — один ревьюер на весь дифф волны.

Вотчдог ловит только bypass делегаций; правки ПМ руками в РОЛЕВЫЕ зоны (deploy/**, code-reviews/verdict, test-model артефакты, QA-контур) машина не видит вовсе, а дисциплина ПМ протекает (рецидивирующий класс: R1.3 — QA проскочен; add-wiki — ПМ сам правил deploy/deploy.sh и собирался гонять боевой деплой, хотя это зона devops-роли и накатка — Заказчика). - БА-делегации передавать решения Заказчика ДОСЛОВНО как решения (не вопросы): «РЕШЕНИЯ ЗАКАЗЧКА (уже приняты, фиксировать как решения)» + факты продукта с указанием проверить по репо (спека, паттерн миграций, токены), не выдумывать. В goal делегации НЕ использовать фигурные скобки `{...}` — в т.ч. в URL-паттернах вида /wiki/ID: delegate_task отвергает goal как «нераскрытый шаблон-маркер». Переписывать словами (GET /wiki/ID) до диспатча. Сюда же — маркерные шаблоны в остальном тексте goal: `{id}`, `{page_id}` и подобные конструкции валидатор считает нераскрытыми плейсхолдерами.

Backend-задачи пакета, не зависящие от мокапов (миграция, API, роуты-каркас), диспатчить ПАРАЛЛЕЛЬНО дизайн-этапу — зоны из ТЗ не пересекаются (design/** против backend/app/**).

## Финальный PR пакета: грабли J10/контрактов (2026-10-09, P14)

- QA-задача волны 5 в tasks.md: маркер-слот ОДИН и сразу после ID — `[x] 5.1 [design] [M]` (не `[M] [design]` — regex closed_dev_tasks не матчит).
- parse_verdict берет ТОЛЬКО заголовок `## Вердикт: ...` (нумерованный `## 7. Вердикт` не матчится), в нем — одобрить/approve.
- pr_validate валидирует КАЖДЫЙ review-*.md (не последний по задаче): regex Reviewer-Delegation берет ПЕРВОЕ совпадение — в файле с историей прогонов завершившая (completed) делегация стоит ПЕРВОЙ строкой, обрывы ниже.
- design_validator-вердикт обязан содержать «ОДОБРИТЬ»/approve (контракт 5); contract 5 ищет это слово в test-model/reviews/<change>/review-*.md — вердикт-файл без него валит approved-кейсы пакета.
- Чеклист: каждая CHK-строка несет FR-N/NNR-N/Requirement; раздел «Дефекты спеки» обязателен (пустой — с записью «не найдены»).
- QA-сьют: time.sleep запрещен даже в seed-хелперах (busy-wait на monotonic); в docstring теста обязателен TC-xxx-NNN (3 цифры).
- dnd_helpers-гонка (async refreshBoard между двумя evaluate) — flaky ~35% в связке, root cause подтвержден; фикс (атомарный evaluate) — багфикс.
- БАГ-016 (flaky bug014 computed_styles): evaluate без предварительного expect — элемент отсутствует в момент снятия; фикс — expect(...).to_be_visible() перед evaluate (паттерн автожиданий, не sleep).
- TC-UIP-110: тест написан под до-фикс семантику продукта (ожидание недостижимо после фикса) — это «тест vs фикс», не продуктовый дефект; вердикт — переписать ассерт, не откатывать фикс.
- Известный продуктовый нюанс: sticky/mobile-header без z-index — элементы с transform (hover/active-карточки) рисуются поверх шапки при скролле (z auto < transform stacking context в порядке DOM). Фикс: базовый z-index шапке (10 — выше контента, ниже drawer-стека и лайтбокса, который позже в DOM). Эмуляция playwright может НЕ воспроизвести визуальный баг (живой композитинг Safari/iOS отличается) — фиксить по описанию Заказчика, не требуя стенда-репро.

## Статус-доклады Заказчику (по запросу «дай статус»)

Статус собирать из источников, не из памяти: (1) git log origin/main — последние
влиты; (2) gh pr list --state open + checks по каждому; (3) tasks.md пакета —
чекбоксы; (4) активные делегации — async_delegations state + хвост живого
транскрипта delegation/live/<id>/task-0.log (последняя активность = доказательство
жизни); (5) реестр active_sessions — статус-счетчики и незакрытые сессии; (6)
сироты-стенды (uvicorn/http.server — количество, гасить при зачистке). Формат:
таблица задач (статус + цикл ревью), блок «в работе» с delegation_id, блок
«хвосты» (minor'ы, pre-existing, flaky — все снесенные в волну 5), блок «риски»
(пустой — тоже писать). Цифры — из свежих команд (см. «Верификация перед докладом»).

## Гигиена веток после релизов (правило Заказчика, 2026-10-08)

После влита релизного/задачного PR — чистить смерженные ветки в ОБОИХ репо
(ekotov-wiki И ai-factory): `git branch -r --merged origin/main` → `git push
origin --delete <ветка>` для всех, кроме main и несмерженных активных.
Делать пакетно одним скриптом с явным списком, НЕ glob'ом; несмерженные ветки
активного пакета (feature/docs/pipeline текущей волны) не трогать до влита.
Локальные копии смерженных — тоже (git branch -d). Проверка после: `git
branch -r` без мусора.

## Архив промежуточных артефактов (порядок в репо)

Закрытые артефакты — в archive/ обоих репо (README внутри — манифест-индекс).
Прежде чем двигать путь — проверить, не сканирует ли его конвейер: flow_check
читает только openspec/changes/* активных (НЕ archive/), code-reviews/<id>/ по
активным change и корневой requirements.md как ТЗ текущего change (реликт
закрытого пакета в корне = ложная опора; у активных пакетов requirements.md
лежит внутри пакета — корневой можно архивировать). Живые документы
(process-context, guarantees, ci-gates, README-flow-control) НЕ архивировать,
даже если лежат рядом с мусором: перед переносом docs/* сверять каждую ссылку
в README/AGENTS и править пути тем же PR. Двигать только git mv/commit,
проверка после — flow_check + pr_validate локально.

## Pre-existing красные тесты: правило скоупа

Красный смежный тест — pre-existing тогда и только тогда, когда воспроизведен
на чистом main в том же окружении (отдельный worktree): сам факт красноты не
доказательство — среда сабагента (общая /tmp-БД, чужие хвосты) дает
интермитент. Pre-existing фиксируется в отчете дева/ревьюера как вне скоупа
задачи и сносится ПМ в BACKLOG кандидатом в багфикс-флоу — не тащится в
вердикт и не чинится в зоне чужой задачи.

## Восстановление статуса конвейера (после обрыва сессии)

Свернутый рецепт — references/status-restore.md: реестр + git + gh + flowctl_state за один проход, без додумывания оборванных вводных.
Два систематических хвоста после волн с обрывами: (1) zомби-holds в
active_sessions.json (running при влитой работе) — гасить пакетно в конце волны;
(2) неконечные статусы flowctl_state (running/prepared/returned у давно
закрытых задач) — на зоны не влияют (зоны свободны после completed-записей
реестра), чистить разом при закрытии пакета, не в разгар волны.

## Бэклог фабрики: сверка и закрытие item'ов

Перед закрытием item'а по памяти — проверять факт по коду (как J33/J34/J35/J37):
grep по скриптам/промптам на каждое «остаточное действие» из item'а. Сделано,
но не отмечено — закрывать с фактом в теле (что именно найдено, где).
Инциденты платформенного уровня (роутинг сессий, rollover, iteration-cap) —
закрывать как «принятый риск платформы»: Заказчик обновляет Hermes регулярно;
условие переоткрытия — рецидив с новым фактом, не теория. Решения класса
«профили сабагентов» сначала сводить к легкой версии в существующих ролях
(рекомендации к декомпозиции в выходных контрактах SA/impact: типы работ,
швы нарезки, план прогонов по наборам), перестройку политик — только при
доказанной пользе легкой.

## Верификация перед докладом

Цифры доклада (SHA, PR, чеки, кол-во тестов) брать из свежего вывода команд, не из отчета сабагента: сабагентский отчет — self-report; перед «влито/зеленые» — gh pr view + gh pr checks самому. Полный протокол — sp-verification-before-completion.
