# Смена агентов и исполнителей

В фабрике у каждой стадии три независимые настройки: **роль** (что делать и в
какой зоне: промпт и `agents/roles.json`), **модель** (`provider`/`model`) и
**исполнитель** (чем запускать: модуль `scripts/executors/<имя>.py`). Над ними
**оркестратор**, обычно ПМ на Hermes. Менять можно любую настройку по
отдельности. Ворота (prepare, резервация зоны, сверка диффа, гейты,
provenance) делает раннер вокруг исполнителя, поэтому подмена исполнителя их
не отключает. Подмена в обход раннера отключает.

Справочник: `docs/guides/pipeline-manifest.md` (правило `run:`),
`scripts/executors/__init__.py` (интерфейс), гайд внешнего оркестратора
`docs/guides/external-orchestrator.md`.

## Когда применять

- Роль плохо справляется на своей модели: дать ей другую модель.
- Одну стадию нужно отдать другому агенту, например сложное ревью отдать
  Claude Code или Codex, а остальной пакет оставить на pi.
- Нужен исполнитель, которого еще нет в `scripts/executors/`.
- Сессию ПМ ведет не Hermes, а Claude Code или Codex.

## Не применять

- **Весь флоу на Claude Code или Codex.** Решение Заказчика 2026-11-15:
  «Полный флоу для клода и кодекса это дорого». Подменяй точечно: одну
  стадию или оркестратор. Остальные стадии оставь на pi.
- Чтобы обойти отказ ворот. DENY по зоне, гейту или ревью не лечится сменой
  исполнителя: исправь причину.

## Исполнители сейчас

| Исполнитель | Что делает | Защита записи во время работы |
|---|---|---|
| `pi` | боевой: Pi роль-пак, ключ в `~/.pi/agent/models.json` | zone-guard (`skills/pm-factory/pi/zone-guard.ts`): запись вне зоны, `git push`, docker-мутации |
| `hermes` | стоп-точка ПМ: раннер ждет `delegate_task` | flow-enforcer Hermes на `delegate_task` |
| `stub` | команда из `AF_EXECUTOR_STUB_CMD`, эталонный прогон | нет (только для тестов) |

Claude Code и Codex модулей пока не имеют. Модуль пишется, когда стадию
впервые нужно отдать им (уровень 3).

## Процедура

### Уровень 1. Сменить модель роли

1. Постоянно для роли: поля `provider` и `model` роли в `agents/roles.json`.
   Для одной стадии: ключи `provider:` и `model:` у стадии манифеста.
2. Проверь, что ключ провайдера есть у исполнителя (у pi —
   `~/.pi/agent/models.json`). Раннер секретов не касается.
3. Прогони `python3 scripts/package_runner.py PLAN-<пакет>.md --dry-run`:
   он проверяет манифест, ключи стадии видны в его выводе. Модель из
   `roles.json` раннер разрешает при запуске стадии: не задана — STOP
   `MODEL_UNRESOLVED` до ворот входа, зона не резервируется.

Готово, когда в отчете стадии стоит `executor: <имя> (<провайдер>/<модель>)`
с новой моделью. Для боевых SA, архитектора, DEV и BA правка `roles.json`
— только по решению Заказчика: модель яруса (glm-5.3) зафиксирована им.

### Уровень 2. Отдать стадию другому исполнителю

1. В манифесте замени префикс: `run: pi:code-reviewer` на
   `run: <исполнитель>:code-reviewer`. Роль, `zones`, `inputs`, `task` не
   трогай: зона остается зоной роли.
2. Исполнитель должен быть модулем `scripts/executors/`. Если его нет —
   уровень 3. Неизвестный исполнитель раннер отвергает уже на `--dry-run`
   с перечнем разрешенных.
3. Запиши причину подмены строкой в журнал делегаций PLAN.md.
4. Запусти раннер. После стадии раннер сам сверит дифф с зоной, прогонит
   гейты и поставит provenance (`executor: <имя> (<провайдер>/<модель>)`).

Готово, когда стадия `done` и в отчете стадии видно имя исполнителя.

Ограничение п.17 AGENTS.md: боевые SA, архитектор, DEV и BA идут на
`pi:<роль>`. Сам п.17 допускает другое только при недоступном Pi или срочном
хотфиксе, с обоснованием в журнале делегаций PLAN.md. Постоянно отдать их
стадии другому исполнителю — это смена правила: эскалируй ПМ, решает
Заказчик, решение передается артефактом (п.5, п.18). Ревьюеров, QA-роли и
вспомогательные стадии можно подменять по решению ПМ с записью в журнале.

### Уровень 3. Подключить новый исполнитель

Один файл `scripts/executors/<имя>.py` с объектом `EXECUTOR`. Раннер,
flowctl, gate_runner и session_check не правятся. Образцы — `stub.py`
(минимум) и `pi.py` (guard и provenance).

1. `preflight()`: проверь бинарь и обязательные файлы, верни provenance
   (версию, sha256 конфига). Не готов — `ExecutorUnavailable`, стадия
   остановится до ворот входа.
2. `command(launch)`: argv и env неинтерактивного запуска. Бриф —
   `launch.brief`, модель — `launch.model`, рабочий каталог — `launch.workdir`.
   - Claude Code: `claude -p <бриф> --model <модель>`. В режиме `-p`
     некому подтверждать запросы, поэтому нужен `--permission-mode
     acceptEdits` и явный `--allowedTools`. Push запрети через
     `--disallowedTools "Bash(git push*)"`: это дополнительная мера, а не
     guard, команда в обертке ее обойдет. Списки `--allowedTools` и
     `--disallowedTools` принимают несколько значений, поэтому бриф ставь
     сразу после `-p`, иначе список поглотит его. Чужие настройки отключают
     `--setting-sources project` и `--strict-mcp-config`. Сверь с
     `claude --help`.
   - Codex: `codex exec -m <модель> --sandbox workspace-write <бриф>`.
     Сверь с `codex exec --help` установленной версии.
   - Режимы без проверок запрещены (yolo, п.4): `--permission-mode
     bypassPermissions`, `--dangerously-skip-permissions` и
     `--allow-dangerously-skip-permissions` у Claude Code,
     `--yolo` и `--dangerously-bypass-approvals-and-sandbox` у Codex.
3. `list_active()`: `active_by_binary(self.name, "<бинарь>")`, чтобы
   `executor_watchdog` видел ручные запуски этого исполнителя.
4. `prepare_workdir()` по умолчанию кладет роль в `AGENTS.md`, а при
   проектном `AGENTS.md` — рядом в `AGENTS.<имя>.md`. Claude Code читает
   `CLAUDE.md`, а не `AGENTS.md`: переопредели метод или сошлись на файл
   роли в брифе.
5. Тест в `tests/unit/` по образцу `test_j65_executor_adapter.py`
   (подставной бинарь в PATH, настоящие ворота раннера). Пакет — Флоу 4,
   ревью до approve.

Готово, когда `names()` из `scripts/executors/__init__.py` возвращает новый
исполнитель, а тестовая стадия `run: <имя>:dev` проходит ворота раннера.

### Уровень 4. Сменить оркестратора

ПМ на Hermes можно заменить сессией Claude Code или Codex: раннер и
`flowctl` — обычные скрипты. Порядок сессии, что теряется и как это
компенсировать — `docs/guides/external-orchestrator.md`. Главное:

- оркестратор запускает стадии только раннером или `flowctl prepare → run →
  finish`. Свои сабагенты Claude Code или Codex для ролей не годятся;
- ревью делай стадией раннера: раннер ставит `Reviewer-Delegation` и
  provenance. Во Флоу 1 и Флоу 2 `pr_validate` засчитывает approve только с
  доказательством независимости: `Reviewer-Delegation` (стадия раннера или
  завершенная делегация Hermes) или provenance-sidecar
  `gate_runner record-review`. У ревью сабагентом оркестратора нет ни того,
  ни другого. Ограничения проверки — в разделе «Ошибки»;
- работа в main — только PR, ревью обязательно (п.21).

## Что сохраняется и что теряется при подмене

| Защита | Через раннер (любой исполнитель) | В обход раннера |
|---|---|---|
| Резервация зоны, `ZONE_CONFLICT` | есть | нет |
| Сверка диффа с зоной после стадии | есть | нет |
| Гейты и коммит стадии | есть | нет |
| Provenance и `Reviewer-Delegation` | есть | нет: во Флоу 1 и 2 ревью не засчитано |
| Запрет записи во время работы | только у `pi` (zone-guard); у других — их песочница | нет |
| Запрет `git push` | zone-guard у `pi`; у других — запрет в `command()` и ruleset main | только ruleset main |
| Вотчдог обхода (если крон включен) | для исполнителей с модулем | не видит агента без модуля |

## Ошибки

- **Подмена в обход раннера.** Исполнителя запустили руками в worktree, без
  резервации. Ни сверки диффа, ни provenance нет. Если крон вотчдога
  включен, `executor_watchdog` поднимет BYPASS `proc:<исполнитель>:<pid>`,
  без крона обход никто не заметит. Почему важно: ворота висят на
  раннере, а не на исполнителе.
- **Ревью сабагентом самого оркестратора.** Claude Code или Codex позвал свой
  Task-сабагент «ревьюером». У такого ревью нет `Reviewer-Delegation` и
  provenance, во Флоу 1 и 2 `pr_validate` его не засчитает. Делай ревью
  стадией раннера (`run: <исп>:code-reviewer`). Пределы проверки: Флоу 3–5
  (`[chore]`, `[docs]`, `[ops]`) ревью в `pr_validate` не проверяют; в CI
  реестров нет, и `Reviewer-Delegation` там только помечается `SKIPPED`
  — проверит pre_merge ПМ (`gate_runner --pr-id`; без PR-контекста шаг pr_validate — SKIPPED), где без реестра ревью не засчитывается
  (J65.6). Sidecar внешнего агента (`<агент>:<id>`) проверяется по полям, но
  реестра id внешних агентов нет: в CI — SKIPPED, вне CI — отказ;
  независимость подтверждает Заказчик при merge.
- **Чужие настройки исполнителя.** pi сам грузил расширения из `~/.pi`, и
  старая копия guard'а действовала рядом с эталоном (J64.10). Claude Code и
  Codex так же читают `~/.claude`, `~/.codex`, `CLAUDE.md`. В `command()`
  отключай пользовательские настройки или фиксируй их в provenance.
- **`MODEL_UNRESOLVED`.** Модель не задана ни в `roles.json`, ни в стадии.
  Дефолтов в коде нет намеренно: модель роли — решение, а не случайность.
- **Затертый `AGENTS.md` проекта (BUG-026).** Свой `prepare_workdir()` не
  должен перезаписывать проектный файл: роль кладется рядом.
- **Обрезанный `ps`.** На Linux длинная командная строка режется, и имя
  бинаря теряется. `processes()` уже вызывает `ps -ww`; свой поиск процессов
  не пиши.
- **Самовольный push.** Сабагенты пушат сами (урок пилота pi). У
  исполнителя без zone-guard запрет push должен стоять в его собственной
  песочнице или списке запретов.
