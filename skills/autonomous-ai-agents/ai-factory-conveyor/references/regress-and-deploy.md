# Regress-final, деплой и гигиена веток — уроки видео-эры

## Эшелонированный регресс (J54, решение Заказчика)
- Полный regress-final — НЕ на каждый change: change = smoke + доменный regress своего куска; полный прогон — пакетно перед плановым деплоем.
- xdist (`pytest -n auto`) для доменных и финальных прогонов; session-фикстуры не делятся между воркерами, serial-fallback флагом; pytest-xdist должен быть в тест-venv проекта.
- Freeze tooling: зеркало фабрики/tooling-изменения ЗАПРЕЩЕНЫ после последнего regress перед merge — иначе перегон (трижды поймано: зеркало pr_validate после артефакта = STALE).

## Свежесть regress-final (J51.3, BUG-022/023/024)
- Сам артефакт и test-model/regress/** исключены из сверки свежести — артефакт всегда новее удостоверяемого кода.
- Мета-файлы (code-reviews/**, test-model/reviews/**) тоже исключены — они не влияют на поведение тестов.
- CI-клон shallow: проверка предка через merge-base невозможна — flow job использует checkout fetch-depth: 0; строки worktree из артефакта в CI нечитаемы → WARNING, инвариант несет commit-сверка.

## Живой regress_runner: контур
- reset-скрипт стенда обязан глушить ВСЕ сервисы контура (паттерн только по :8080 оставлял search/images/video на старой БД+SECRET_KEY → массовые 401 на «чужих» токенах).
- SECRET_KEY единый на весь контур; полный env в pytest-процесс (EKOTOV_WIKI_BASE_URL, AVATARS_DIR, IMAGES_DIR, VIDEOS_DIR) — без них fixture-ERROR до тестов.
- --final требует явный таймаут ≥1800 (дефолт 120s давал фиктивный PASS по таймауту).

## Схема сборки пакета (J57, решение Заказчика): ветка на роль, интеграция — dev-lead
- Делегация = `flowctl prepare` (ветка из cid в worktree) — безусловно, включая ревьюеров и фикс-раунды; сабагент коммитит ТОЛЬКО в свою ветку.
- Множественные делегации: сборку делает dev-lead — `flowctl integrate <repo>` (ветки пакета из реестра, REFUSE при активных сессиях, integration/<cid>), конфликты — семантика dev-lead'а; сборный прогон до PR.
- ПМ: git-операций в чужих ветках/чужом дереве НЕТ; свои правки — своя ветка → PR; из git — только merge и диспетчеризация деплоя. push_gate (PM_PUSH_POLICY) DENY-ит ПМ-push в продуктовое репо без маркера [integrate]/[pipeline] в HEAD или смерженного HEAD — механика, не дисциплина; enforcer лежит в ~/.hermes (переустанавливать после изменений плагина в фабрике).
- При активной делегации ПМ не делает checkout/reset --hard в ОСНОВНОМ дереве репо — только через отдельный worktree: reset общего дерева сносит незапушенную работу агента (два сноса за одну сессию, восстановление — reflog агента).
- Деплой выполняет девопс-сабагент; ПМ готовит релиз (static_v, матрица deploy.sh, RUNBOOK) и ПРИНИМАЕТ результат (контейнеры healthy, смоук, данные нетронуты).

## Деплой (J26 + прецеденты)
- static_v бампает ОРКЕСТРАТОР до диспетчеризации devops, отдельным [chore]-PR, при КАЖДОМ изменении статики; внутри релиза после первого бампа — бамп до нового значения (video-1 → video-1.1), не «деплой без бампа».
- Новый сервис: named volume предсоздать с chown 10001:10001 + chmod 0777 ДО старта; точки монтирования ro-маунтов должны существовать в томе-источнике (иначе nginx не поднимется). Том НЕ монтировать в под-путь ro-маунта: «make mountpoint: read-only file system» на старте контейнера — маунтпоинт выносить на верхний уровень (/cache, не /data/cache при ro на /data). Ро-чтение sqlite с ro-маунта — паттерн search: mode=ro с fallback immutable=1 (обычный connect дает «unable to open database file» → 500).
- deploy.sh: новый сервис добавлять во ВСЕ четыре точки (SERVICES, <SVC>_IMAGE, dockerfile_for, image_for) — матрица не выводит сервис сама; и раздел RUNBOOK (порты, тома, миграции/их отсутствие, отказные сценарии).
- QA-фаза нового пакета: qa_author (кейсы 1:1 к сценариям спеки) → утверждение кейсов Заказчиком (test-model/approved/<id>/ + APPROVAL.md — контракт 6) → qa-прогон по кейсам; approved-кейсы открывают change-маркер в PR. Для UI-фич design_validator гонять ПАРАЛЛЕЛЬНО code_reviewer (сверка живой страницы с мокапом — отдельно от кода).
- Deploy.sh пересборка образов недетерминирована (новые image ID при том же теге) — после боевого прогона сверять Image-теги контейнеров и пересоздавать с полным набором *_IMAGE env.

## Git-дисциплина ПМ (повторялось трижды)
- Перед ЛЮБЫМ commit/правкой: `git branch --show-current` — целевая ветка чекаутнута; правки в основном чекауте при active-ветке уезжают в main и теряются при reset.
- Потерянный коммит: `git reflog <branch>` → sha → cherry-pick на целевую ветку. Конфликт при cherry-pick = на ветке уже есть та же правка — разрешить объединением, не дублировать.
- `pkill -f <pattern>` убивает собственную команду, если паттерн совпадает с ее аргументами — использовать брекет-трюк `patte[r]n` или kill по PID.

## Словарь и домены проекта
- `docs/glossary.md` (J53, свободная форма) есть в каждом проекте: перед делегацией сверяйся с ним и объясняй термины сабагентам своими словами — не пересказывай контракты из головы; новое рабочее название (сервис/том/таблица/статус) — одна строка в глоссарий.
- Домены regress = домены тест-кейсов (правило Заказчика): проектная карта `test-model/regress-domains.json` префикс→домен; активная карта отключает свертку кейс-доменов в общий tests/ (сверка с парсером flow_check при изменении формата).

## Контракты — в промпты ролей, не в голову ПМ
- Дев: репорт BUG-NNN — часть коммита багфикса; ветка/worktree из ALLOW.
- code_reviewer: точный машиночитаемый формат review-файла («## Вердикт: approve» + «Reviewer-Delegation: deleg_<id>» вплотную, id рядом с меткой) — иначе J10 не покрывает задачи.
- regress_runner: freeze tooling; зона только test-model/regress/.
- Приемка: Заказчик принимает ФИНАЛ (не каждую волну) — не останавливаться на поэтапных приемках без его запроса.
