# Subagent Delegation Discipline (Conveyor)

## Parallel-first is the default proposal (customer order)

When planning a phase or wave, PARTITION it into independent contours (disjoint write zones, or work in different repos) and PROPOSE the parallel plan in the status report BEFORE dispatching — "tasks A and B are independent, I am launching both; reviews run sequentially after returns". Do not wait for the customer to say «параллель»: proposing the split proactively is the standing expectation. The constraint set is unchanged: zone cross-check against the registry before spawn, orchestrator creates worktrees before sessions start, sequential execution remains mandatory for dependent and same-zone tasks.

## Stopping everything on customer «Стой» (verified behavior)

- An out-of-band customer «Стой» means FULL stop of orchestration actions: no new dispatches, no gate retries, no fixes «до конца итерации». First action after the stop: inventory what is still running (pgrep for spawned processes, delegate_task action=list), kill any process spawned by an in-flight command, and report exactly what completed before the stop and what was NOT started. In-flight background commands the gateway moved to background complete on their own — their results are notifications, not license to continue.
- При попытке «завалить ворота» нужным решением (decision-record) НЕ подгонять файл решения под сообщения об ошибках ворот вслепую: каждое сообщение flowctl называет точное ожидаемое поле (action, phase, scope) — прочитать сообщение целиком и исправить именно названное поле, один микро-PR на исправление, а не серию проб. Серию из трех подряд форматных микро-PR считать сигналом: сначала прочитать валидатор в исходниках, потом править.

## External copilot agents (Codex and similar)

An external agent attached to the repo (Codex as copilot) is an EXTERNAL delegation, not a Hermes subagent: its outputs are pointers to files, not proof; commits only via PR and standard gates; in provenance-sidecar it figures as author_delegation `codex:<id>` (otherwise reviewer independence computes wrong); write zones — from the role's policy, session_check reservation required; customer decisions are never passed to it verbally. Rationale lives in the factory AGENTS.md section «Внешние агенты-copilot».

## Branch practice (customer order)

- Large factory-evolution work (external ТЗ rollout, new executable layer) goes in a dedicated branch off main: «в main не вливать, пока явно не скажу и все не отладим» — the branch is THE working branch until the customer explicitly says otherwise. Report status by facts (git log, pytest, gates), never by subagent reports.

## Role isolation

- One pipeline role = one subagent delegation. Never merge author + reviewer (or executor + acceptor) roles into a single subagent session — a context that wrote an artifact cannot independently review it, and a long multi-role chain overflows the context and degrades (phrase loops, garbage output). Hand off between roles ONLY through committed artifacts, never through shared conversation.
- Exception: for small packages (<5 checklist items) MAY merge the two analysis-only roles (impact + checklist) into one delegation; author/reviewer/automation stay separate always.
- Each role's delegation goal must state: role prompt path (read it first), worktree path, branch, session id, WRITE ZONE (paths allowed to change), inputs as artifact paths, DoD, and 'push NO'. The write zone must not overlap any concurrently running delegation's zone.
- Boundary-check rule: the subagent's first action is verifying worktree path + branch + SESSION.md marker match the task brief. The worktree creator script drops SESSION.md (session id, branch, repo) into the worktree root.

## Cycle-return pattern (review → fix → re-review)

- Verdict 'return' spawns: a NEW author-session (fresh context) that edits only the returned artifacts per the review findings, then a NEW reviewer-session (fresh context) that re-reviews only the returned items. The reviewer — never the author — moves approved artifacts into the approved/ location.
- Review history is append-only: iteration files are never edited, a new iteration file is created. Acceptance is verified by counting files on disk (approved N, returned M), not by trusting the report.
- Findings that fall outside the artifacts under review (checklist errors, spec contradictions) are passed to the orchestrator in the report, never fixed by the reviewer in the same session.

## Delegation validator quirks

- Every task in a delegate call requires 'goal'. Unexpanded template markers (e.g. <change-id>) in goal cause a validator error — substitute real values before dispatch.
- Long multi-step briefs: put absolute worktree path on its own line; shared working-tree assumptions between parallel sessions have caused directory swaps before.

## Degradation pings

- While delegations run, ping live transcripts every 5–10 minutes: log growth + meaningful tool calls = healthy; phrase loops / repeated identical calls = stop and restart the role from a clean session. Artifacts from a degraded session must not be reused.
- Diagnosing WHY a delegation died or whether the main session was killed: grep `~/.hermes/logs/gateway.log` and `agent.log` around the incident timestamp — `STOP for session` + `Interrupt requested (hard): explicit stop requested` = a `/stop` command arrived in chat; `Async delegation … targets permanently-gone session … dropping delivery` = results orphaned by session death. This distinguishes customer-initiated stops from crashes before reporting anything to the customer.

## Second executor (Codex CLI)

- Codex CLI can serve as an additional dev executor (user's paid subscription; login via `codex login` on the server, agent only invokes the CLI). Use it to offload token-heavy debug/playwright loops; orchestrator keeps review/acceptance. In gateway sessions sandboxing may be unavailable — if so run with full-access sandbox only with compensating controls: clean `git status` before start, narrow task brief, diff review after.

## Dedicated runner role for test sweeps (J17)

- Running full regression suites AND triaging their failures is its own subagent role (qa_runner), explicitly requested by the user: do not burn the orchestrator's (or dev-lead's) context on stand setup, env isolation, repeat runs, and root-causing failures. The orchestrator/dev-lead accepts numbers and verdicts from the runner's report; a personal run is only for spot verification.
- Runner scope: execute suites per tests/README (stand, port, env, seed), attribute each failure to product vs test vs environment using isolated reruns (never guess), file bug candidates in test-model/bugs/ format. The runner does NOT fix product or test code — it hands artifacts to dev/qa_automation.
- Brief the runner with the known-failure list so it skips re-triaging documented failures, and require per-suite numbers plus a root cause per failure in the report.

## Review-brief discipline (G6/J10 verdict routing)

- Always state the verdict file's exact directory in the reviewer brief, per routing: product code → `code-reviews/<change-id>/`; tests/cases/architecture → `test-model/reviews/<change-id>/`. Without it a reviewer invents a location — `test-model/reviews/`, repo root, or `/tmp` — while the J10 gate reads only the routed directory; an honest approve stays invisible and costs a second legalization session. After a static-only review, copy the verdict file from wherever the reviewer left it into the routed directory yourself before committing.
- Verdict format: a heading line `## Вердикт: approve` — bold text without `#` is invisible to the gate's parser; the word «return» must NOT appear anywhere in the verdict line (the regex scans the whole line — an original-RETURN mention inside the parenthetical turns approve into return); file name must match the gate regex (`review-<NNN>-<slug>.md`), not `review-<task-ID>-slug.md`.
- Verify a dev's «готово» claim BEFORE dispatching the reviewer: the subagent may report success while the work is still uncommitted (or committed on a different branch than stated) — check `git log --oneline -1` and `git status` in the worktree yourself, and commit the WIP yourself (J21) if the session died short of it. A reviewer dispatched against an uncommitted tree reviews nothing.
- After RETURN→fix, re-review only the fix diff; brief the second reviewer with the original review file path as the primary source and require per-item closure status.
- When a subagent dies at the iteration cap BEFORE committing, salvage the WIP yourself instead of re-dispatching: commit the staged/unstaged delta onto the session's branch (verify `git branch --show-current` first — the shared checkout may be parked on a sibling's branch), rebase onto fresh main, and open the PR yourself. Verify the salvage by diff-stat (only the claimed zone files) and byte-compare any duplicated WIP against the commit — a stale uncommitted copy that duplicates committed content must be dropped, not committed twice. A reviewer that hit the cap before WRITING the verdict file is salvaged differently: the checks are done, so write the verdict file yourself from the live transcript with a provenance note naming the delegation — never re-run a finished review to produce a file.
- A subagent hitting the iteration cap mid-fix leaves its TEST STAND as background processes (uvicorn×N + nginx). Kill them at acceptance (`ps aux | grep -E 'uvicorn|http.server|nginx'`) before spawning anything else — orphans hold ports and the next stand binds beside them or fails.
- Parallel subagents sharing ONE checkout corrupt each other even with disjoint write zones: switching HEAD kills another agent's staged work and redirects its commits. Mitigations in the brief: each playwright run = one synchronous ≤30–60s command; background pythons only with process_manage wait; `env -u PYTHONPATH` (harness leaks py3.14 site-packages into project venvs); stands killed in finally; when review-only, read other branches via `git show origin/<branch>:<file>` or a /tmp worktree — never switch the shared checkout. Instruct the verdict file to be written INCREMENTALLY as checks complete (header/Provenance first, append per section) — iteration caps have repeatedly eaten finished-but-unwritten verdicts.
- After parallel agents finish in a shared worktree, run the FINAL full-suite verification SERIALLY: a suite executing while a sibling does git operations (checkout/commit/branch switch) fails with transient `ModuleNotFoundError`/half-swapped files that exactly mimic a merge regression. An individually-green rerun on the settled tree is the discriminator, not a diagnosis session.
- Reviewer-Delegation placeholders: a subagent cannot know its platform delegation id — review files it writes carry `Reviewer-Delegation: deleg_<id>` placeholders. At acceptance the orchestrator MUST replace the placeholder with the real delegation id (the batch that dispatched the reviewer) and commit — pr_validate's SELF_REVIEW check fails the PR otherwise. Subagents also must NOT self-declare review skips (`[skips-review]` in a commit message) or re-review their own gate failures: review routing is the orchestrator's call; when a subagent does either, re-review the diff personally (it may be small) and put the discipline lesson in MAP.
- Subagents push to remote DESPITE a «push NO» brief line, and may overwrite a branch tip with an intermediate broken state (a 23-of-29-scenario spec pushed over the finished 29). Before merging a fan-out child's PR, compare the remote tip against YOUR verified local commit (`git fetch` + `git log origin/<branch>`) and `push --force-with-lease` the verified state when they diverge, with a PR comment naming what was overwritten and why. Then read the CI verdict off the NEW run — `gh pr checks` may still display a stale run for the old tip.

## Wave rhythm (customer order)

- In a long release, pause after each wave (task group): report what closed (commits, test counts) and what is next; start the next wave only on an explicit go-ahead. Phase gates apply between waves, not just between phases.
- In every status update state explicitly whether you are waiting on subagents or on the customer — the customer cannot always tell who is paused.

## Test-stand env hygiene (ekotov-wiki pytest)

- stale env from a parallel session (EKOTOV_WIKI_BASE_URL/DB_PATH/AVATARS_DIR pointing at a dead stand) produces connection-refused or silent wrong-stand runs — clear with `env -u` before any pytest, and give each parallel session its own scratch port + tmp dirs.
- Avatar tests additionally need AVATARS_DIR (or EKOTOV_WIKI_AVATARS_DIR for the suite) pointed at a tmp dir — without it uploads 500 writing to the production path /var/lib.
- API stand: fresh DB + `python -m app.db` + seed owner/wife via piped stdin + `python -m app.migrate_r4` (bare seed does not set R4 roles), then uvicorn on a scratch port; stop it after the run.
- Seed без tty: pty-вариант падает `termios error` на getpass — севить inline: `DB_PATH=… SECRET_KEY=… python -c "from app.seed_users import seed_user; seed_user('owner','owner','QaOwner_Pass_1!'); seed_user('wife','wife','QaWife_Pass_2!')"` из каталога `backend` (пакет `app` резолвится из CWD); env задавать В ТОЙ ЖЕ команде — терминальные вызовы не наследуют экспорты друг друга.
- Стенд поднимать фоном (`background=true`), НЕ через `&` в foreground-команде — харнес такие команды блокирует; готовность проверять отдельным curl к `/api/health` в следующем вызове.
- Web-сьют поднимает свой стенд сам — гонять с `env -u EKOTOV_WIKI_BASE_URL` (иначе фикстура требует внешний стенд и падает за 60 с молчанием); api-сьют — против своего стенда на 8080 с явными `EKOTOV_WIKI_BASE_URL` + `EKOTOV_WIKI_DB_PATH` (без второй DB-тесты молча SKIP и «зеленый» прогон неполон).

## Session death vs async delegations (recovery discipline)

- Async delegations belong to the gateway session that spawned them: a `/stop` in the customer chat (or any hard interrupt of the main session) kills the session AND all its in-flight async delegations mid-run; a gateway restart orphans their results and delivery is terminally dropped. Assume every async delegation can die at any moment:
  - Do not start long (>10 min) background delegations right before an unattended wait; babysit them to completion or split into shorter delegations whose results are committed before the next risky wait.
  - Brief subagents to commit early and incrementally — work left uncommitted in the worktree at interrupt time is lost work (a ~50-minute qa session was killed with all its edits uncommitted).
- Main-session context rollover kills in-flight async delegations the same way a /stop does: when the main session hits the context ceiling (session_reset/session_switch), every orphaned child's delivery is terminally dropped. Gateway log signature: `stale self-heal artifact` followed by `targets permanently-gone session … dropping delivery`. Avoid spawning background children at a compaction point — after a big context drop, END THE TURN with a short customer reply first, then spawn.
- A batch dispatched exactly ON a session-rotation boundary misroutes onto the chat's own session key instead of an isolated subagent session: the brief text lands as the first user message of the NEW telegram session and NO `source='subagent'` row is created at all — the main chat session itself plays the subagent role. This, not an actual switch, is what a «провалился в сабагента» complaint means in that case. Verify in state.db: the delegation's `dispatched_at` coincides with a new session's start AND its goal text is that session's first user message AND no subagent-source child exists for the delegation = misroute. There is nothing to «exit» — the chat key never changed; confirm that to the customer and continue the role work in the normal cycle. Prevention is the same as for compaction points: answer the customer's message and end the turn first, spawn after.
- When the customer reports repeatedly «проваливаюсь в сессии сабагентов», distinguish a rollover cadence from user stops with `sqlite3 ~/.hermes/state.db "SELECT end_reason, COUNT(*) FROM sessions WHERE session_key=… GROUP BY end_reason"` (`session_reset`/`session_switch` = context-ceiling rollovers) plus the gateway.log signatures above. A rollover cadence means the trigger is main-session size + long-lived background children — the fix is shorter delegations and the static-only split, not asking the customer to stop interrupting.
- A dropped delivery is not a lost result: both the full report and the original brief survive in `~/.hermes/state.db`, table `async_delegations` (`result_json`, `task_json`, keyed by delegation_id). Extract them BEFORE restarting the role — the report may already contain a usable verdict, and reusing task_json guarantees the restart matches the original brief instead of a paraphrase. Proactive discovery, not just after a known death: when reconstructing «что стало с сабагентом», check `delivery_state` per delegation — `state='completed'` with `delivery_state='dropped'` means the work finished AND reported but the chat never received it; recovery path: latest `sessions WHERE source='subagent'` → its delegation row → json-unescape `result_json` before reading.
- Customer remedy for «верните меня в main-сессию из Telegram»: a Telegram DM is hard-bound to its session_key, and subagent sessions (`source='subagent'`) carry no chat origin, so the gateway's IDOR guard refuses `/resume` into them (fail-closed) — nobody can actually «застрять в сабагенте», and the ask always means «switch my main session». The working return path is a stable session NAME, not new tooling: `~/.hermes/hermes-agent/venv/bin/hermes sessions rename <session-id> main`, after which the customer types `/resume main` in Telegram from any session and lands back with full history. Titles are unique — if an auto-title ever retakes the anchor name, re-run the rename; keep one short name (`main`) reserved for the anchor session instead of relying on auto-generated descriptive titles.
- A recovered report speaks as of its `completed_at`, not as of now: before relaying its verdict (СТОП, красный регресс, «коммит не сделан») to the customer, reconcile it against the CURRENT repo state — `git log` in the affected repo for commits after `completed_at` plus a fact-check of what the report says is missing (commit present? service restarted?). Later commits routinely supersede a stale СТОП; presenting the stale verdict as current produces a false alarm the customer then has to talk down.
- After any `/stop`, gateway restart, or suspected session death, do NOT trust `delegate_task action=list` alone or the sessions registry — reconstruct state from facts, in this order: (1) `delegate_task action=list` (live children; empty = none alive, whatever any file says); (2) `~/.hermes/cache/delegation/live/deleg_*/manifest.json` (per-task status/exit_reason: completed vs interrupted) + the tail of each `task-N.log` (what it actually did last); (3) `git status`/`git log` in every worktree (committed vs uncommitted work) — check staged changes explicitly (`git diff --cached --stat`) and `git stash list`; interrupted sessions leave diffs staged-but-uncommitted and duplicate WIP stashes, both invisible to a plain `git log`; (4) `~/.hermes/logs/gateway.log` (STOP / session_reset / inbound-message timeline). Then rewrite the registry from those facts with per-entry notes.
- The tail of a dead delegation's `task-N.log` ends with a `final | end status=... exit_reason=...` line: `max_iterations (iteration budget exhausted)` means the subagent ran out of iteration budget mid-task (not a crash) — its report summary says honestly what is NOT done; treat all uncommitted output as WIP. Garbage symbols or wrong-language fragments in the summary are a degradation marker — do not reuse that session's artifacts.

## New-project onboarding (factory_init)

- Recipe: clone the empty repo → `python3 ~/ai-factory/scripts/factory_init.py --target <path> --name "<Name>" --skip-plugin` (the flow-enforcer plugin lives on the machine once, per-machine — never per-project) → drop the customer's ТЗ/docs into the root → one init commit → push → CI must be GREEN on the empty project.
- A fresh empty project needs three things factory_init now supplies (added after a 3rd-project init went red): `openspec/config.yaml` (root marker — without it `openspec validate` errors «No OpenSpec root found»), `tests/test_smoke.py` with TC-BOOTSTRAP-001 in the docstring, and `test-model/regression/_bootstrap/smoke.md` (as-is base satisfying flow_check контракт 6: tests without approved cases require a regression base).
- The machine's GitHub account has per-repo permissions: a NEW repo under the customer's account gives the runner account READ only — the first push is rejected until the customer adds it as a collaborator (Write). Detect with `gh repo view <repo> --json viewerPermission` before diagnosing anything else.

## Customer-message interpretation before machine changes

- When the customer references something that does NOT exist in the environment («just фабрики» meaning the J-backlog, not a justfile), confirm the interpretation BEFORE installing new tooling or creating files for it. Installing software on the user's machine from a guessed reading produces cleanup work and a «я не знаю что это» correction; one clarifying question is cheaper than an uninstall.

## Доделывание брошенного контура (смерть сабагента с готовыми артефактами)

- «Доделай» после смерти сабагента НЕ означает перезапуск роли: сначала инспекция брошенных артефактов — если содержательные артефакты готовы (impact/чеклист/кейсы/тесты лежат в дереве незакоммиченными), доработка сводится к верификации + одному коммиту по ТЗ контура, и её делает оркестратор сам как механическое завершение (это не ролевая работа — роли уже отработали). Артефакты всё равно верифицируй прогоном: брошенный контур мог не дойти до прогона тестов — первый же прогон часто вскрывает и стенд-проблемы, и флейки, которые автор не видел.
- Отладочный мусор брошенной сессии (probe-тесты вида test_zz_*) коммиту не подлежит — удаляй до коммита.
- Registry/стенды/ветки чистить ПОСЛЕ merge: сначала доделать и влить работу, потом сносить worktree, ветку, запись active_sessions.json и фоновые uvicorn — обратный порядок теряет единственную копию незакоммиченной работы.

## Iteration budget discipline (large tasks)

- A dev delegation dies at the iteration-budget ceiling after ~80 minutes regardless of progress: a task sized [L] spawned as ONE subagent will exhaust the budget before the final test run and commit. Split [L] tasks BEFORE spawning: implementation and its test suite are separate delegations of ≤[M] each.
- This applies to bugfix delegations too: a Флоу-2 bugfix with a mandatory full-suite regression is implementation + regression as separate delegations — the implementation session dies at the ceiling having committed the fix but not run the full suite, and the regression is qa_runner work anyway.
- When the customer interrupts mid-acceptance with «ты увлекся, сабагентов давай», STOP the personal work immediately: commit the WIP (J21 rule, one commit with the full fix+tests so nothing is lost), hand the remainder (full suite run + triage) to a qa_runner delegation with the known-failures list, and route the next steps through review. Do not defend the personal work by finishing it — the handoff itself is the correction being requested.
- A continuation delegation ("finish the predecessor's uncommitted work") costs a full budget — re-verifying someone else's code plus re-debugging eats the iterations. WIP-commits make continuation cheap; without them, budget for two full sessions, not one.
- Reinforce in every dev brief: commit early and incrementally, and when the iteration budget feels ~70% spent, commit WIP with a marker and report the remainder — never die with a staged diff.
- Keep LLM subagents out of mechanical work: the orchestrator (or qa_runner) runs test sweeps itself and hands the reviewer the numbers as trusted inputs, with an explicit "do NOT run tests or servers" clause in the brief. A static-only reviewer finishes in minutes; a reviewer that raises its own test stand lives ~40 minutes, crosses session rollovers, and its verdict is dropped with the session it was pinned to.
- Pass run results as a scratch FILE (e.g. `/tmp/<scope>/PROGRESS.md`: suite commands with env, numbers, skips, flake isolations), never as prose in the brief — the file is an artifact the reviewer cites and the acceptance checklist re-verifies. The split is by "does this step need reasoning", not by task: any step that is command→log→number (suite runs, stand bring-up, env debugging) stays with the orchestrator even when it sits inside a delegated task.
- Size every delegation to a single concern so the brief fits in ~10 minutes of agent work; decompose "review + run everything + write the verdict file + commit" into steps done by different actors (orchestrator runs, subagent judges, orchestrator formats/commits).
- Verify every reported finding at least by spot-check before acceptance — pull the named file:line and re-read it. Reviewers' findings have checked out 1:1 when verified, but the verification itself is the acceptance gate: accept the report on the checklist «verify with facts, not trust», not on the reviewer's authority.
- When the customer questions an orchestration design decision, answer by restating the underlying principle with its boundary, not by reverting: e.g. the delegation-criterion is «isolated context for REASONING», and mechanical command→log→number steps never needed isolation — the same criterion, cut finer. Overturning a working pattern to match a misread principle loses both.
- Fix a finding in a MERGED task by routing it through the current task's review as a cross-zone finding: give the reviewer the verified fact and ask for a severity ruling (return-of-the-merged-task vs backlog item). Do not let the current dev subagent patch another task's zone — zone isolation outranks convenience, and the ruling (not the fix) is what keeps the audit trail consistent.
- Cross-zone findings in a MERGED task close by a PM-made micro-hotfix ONLY when mechanical (selector/text/one-liner): style the fix on an existing V3 pattern in the same file, run the affected suite yourself, and send the commit to the same reviewer for a micro-review before merge. Content-level defects still go back to the owning role.
- When an acceptance gate fails on a previously «green» artifact, fix the ARTIFACT to satisfy the gate (preserving content), not the gate: e.g. a MODIFIED-delta header carrying a parenthetical note breaks the delta parser — move the note to an HTML comment before the header and complete the scenario set. Loosening the gate to pass a broken artifact hides the defect from the archive merge.
- When orchestrator-made spec/gate fixes ride along with an accepted task, commit them as a separate PM commit with its own message (what was broken, why the gate could not pass before) — never fold them into the dev's or reviewer's commit, the blame boundary must stay per-role.
- Size every delegation to a single concern so the brief fits in ~10 minutes of agent work; decompose "review + run everything + write the verdict file + commit" into steps done by different actors (orchestrator runs, subagent judges, orchestrator formats/commits).
- Parallel dev sessions with disjoint write zones still share the integration surface: after merging both branches, run the FULL combined suite (api + web) on the merged tree BEFORE dispatching reviews. Zone-disjoint diffs do not guarantee contract agreement — one task's frontend consumed a response field the other's backend never emitted, and each dev's in-process TestClient smoke passed because neither exercised the merge. Budget a triage pass: tests a dev subagent writes are never executed by its author (running is the orchestrator's job), so their first real run routinely surfaces 1–3 failures — static green (py_compile, node --check) is not test green.
- Between FULL suite runs ALWAYS rebuild the stand from scratch (fresh DB → schema → seed → migrate): avatar/file-upload tests leave state (avatar files, avatar_url set, tasks in board) that other domains' fixtures assert against («avatar_url is None»), and a dirty stand produces 30+ cross-domain failures that look exactly like a merge regression — a fresh-stand rerun is the discriminator, not diff bisection. First reaction to a mass-fail in a suite you just ran green: rebuild the stand, rerun, only then diagnose.
- Parallel delegations under one dispatch fan-out (one delegate call, several tasks) may be dispatched with SEPARATE backends but share one completion unit: results re-enter as a single batch message when the last finishes. When children finish at very different times, the long tail delays every sibling's report — for a fast [S] task that must not wait on an [L], dispatch it as its own delegate call.
- Parallel children with DISJOINT write zones dispatch cleanly as one fan-out when each goal lists its zone as an explicit path list plus a «do NOT touch <sibling zone> — parallel task there» clause and a «push NO» line; verified live: two children committed to the same branch interleaved with zero conflicts. Still verify each child's commit yourself at acceptance (git log + pytest), never trust the report.
- Dispatch fan-outs EARLY in the orchestrator's turn, not at its end: batch results are delivered only after the current turn ends, so a late dispatch wastes wall-clock while the orchestrator still holds the turn. End the turn with a one-line customer status immediately after dispatching.
- The active-sessions registry (`~/.hermes/state/active_sessions.json`) is hand-maintained and drifts on every abnormal session end: it keeps stale `running` entries (phantom sessions) while interrupted work stays unrecorded. Treat a registry entry as a claim, never as evidence; a `running` status is not proof a delegation is alive, and an empty live-children list is proof it is not. On any customer report of «хрень с сессиями», reconcile the registry against the facts above before answering.
- Run acceptance gates (openspec validate --all --strict, flow_check) on the merged tree locally BEFORE pushing — a role's commit message claiming a green gate may not reproduce (a delta header carrying a parenthetical note, a MODIFIED block missing master scenarios). The push itself is not the deadline, but a red gate discovered after push still costs a legalization commit; discovering it before costs nothing.

## Registry hygiene for flowctl sessions (pm bounds)

- The flowctl session registry and active_sessions.json mirror each other; after closing a task (merge + checkbox) set its session entry to `completed` with per-item evidence (delegations, PRs, SHAs) IN THE SAME PASS as the merge — a stale `running` entry blocks the next zone reservation (ZONE_CONFLICT) for the role that follows.
- A dropped (session-death) delegation used as Reviewer-Delegation in a verdict file fails pr_validate's SELF_REVIEW/state check (`state='error'` ≠ `completed`). Route the verdict file through a `[chore]` pipeline-PR instead of the change-marker PR — the change-marker also drags the full QA tail (impact/checklists/approved) that intermediate review artifacts cannot satisfy.
- Edit a PR title via `gh api -X PATCH repos/.../pulls/N -f title=...` and retrigger with a FRESH event (empty commit push), not `gh run rerun --failed` — rerun consumes the OLD event payload (old title/marker) and repeats the same failure.
- Merge-order dependency: when two PRs contain byte-identical copies of the same files (worktree collision fallout), merge them in a declared order and rebase the second onto main before merge — the duplicate delta collapses to zero and the merge is clean; declare the order in the first PR body so the gate and the customer see the plan.

## Stage-cost measurements (J23)

- When the customer questions whether a pipeline stage earns its context (e.g. qa_checklist), archive the stage's delegation transcripts OUTSIDE the repo (e.g. `~/hermes-qa-measurements/<topic>/`) BEFORE running the next instance of that stage — live logs live in `~/.hermes/state/session-archive/<deleg_id>/task-0.log` and are the measurement source. Include a README stating what to measure: tokens/duration per session (size + duration + tool-call count from the log), defects the stage caught before the NEXT stage consumed them (cross-check the next stage's review files), and the cost of the scripted alternative that would replace it.
- Identify sessions for the archive by goal prefix in the first 500 bytes of task-0.log (role name + package id); a merged-stage run (e.g. impact+checklist in one delegation) must report the split of effort between the phases, or the measurement cannot separate them later.

## Deploy/production work goes through devops (J26)

- ALL changes to deploy.sh, RUNBOOK.md, nginx/systemd configs, backup/rollback/smoke procedures, and deploy-stage order go through the devops subagent (agents/devops_agent.md) — never made by the orchestrator. The former G7 refusal of a DevOps role is fully rescinded for deploy work; the role's context is expanded: it owns the deploy tree of every project, keeps a registry of «outside rsync root» items (root-edited prod files gated by script checks), and joins release planning BEFORE code freeze to list deploy steps for new functionality (R4 pattern: migrate_r4 step, nginx /avatars/ location).
- Orchestrator's part: state the release delta and affected external components, then accept on facts (bash -n, DRY_RUN run, zone-only diff). A deploy gap found by the orchestrator (e.g. a missing nginx check letting a release ship 404s) is still devops work — hand it over with the reproduced dry-run failure as the artifact instead of patching deploy.sh personally.
- Any deploy incident (prod deploy fails on a schema/migration/order bug) is debugged by a dev/qa subagent given the local-rehearsal recipe (copy of the OLD prod schema through: schema → migration → repeat schema), not by the orchestrator iterating locally.
- New-feature packages that change UI go the FULL flow with an explicit design pass (customer order, J25): requirements (BA, customer words verbatim) → SA change package (deciding open questions like front-crop vs server-side crop, zoom limits, touch/keyboard a11y, client-must-not-be-trusted server revalidation) → ui_designer mockup in design/ as a package artifact (J25 live-mockup) → dev → design_validator against the mockup → code_reviewer → QA. Express/skip-the-design shortcuts for visible-UI features are what produced unpainted buttons reaching main in R4.
- When a BA artifact arrives with numbered open questions for the SA (ОВ-СА-N), do NOT answer them in the SA brief — instruct the SA to DECIDE each with justification in design.md and report the decisions back; the orchestrator surfaces decisions to the customer only when they are UX-visible (crop interaction model), otherwise the pipeline self-serves.
