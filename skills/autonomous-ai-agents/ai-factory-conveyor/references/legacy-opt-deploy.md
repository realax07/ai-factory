# Легаси-деплой: /opt + systemd (до контейнерной схемы)

Грузить при работе со старой /opt-схемой ekotov-wiki (systemd-юниты,
rsync-каталоги). Актуальная схема — docker compose, см. skill
ekotov-wiki-regress-deploy.

- Развертывание на машину с sudo-паролем (без passwordless): ПМ готовит идемпотентный bash-скрипт (guard `if [ ! -f ... ]` на .env/сертификат/seed — повторный запуск продолжает со сломанного шага, не дублирует) и выполняет его Заказчик; диагноз падения — патч скрипта и повторный запуск целиком, не ручные команды. Собирать приложение отдельным venv внутри /opt-копии, БД — вне репозитория, секреты через .env с правами 640, приложение — под непривилегированным системным юзером.
- Модули управления приложением (`python -m app.db`, seed_users) требуют ВСЕ обязательные env на импорте (config fail-fast на первый отсутствующий): запускать через `set -a; source .env` целиком, а не точечным `DB_PATH=... python -m ...` — иначе RuntimeError на SECRET_KEY посреди деплоя (проверено: миграция падает при заданном DB_PATH).
- Деплой-скрипт не должен предполагать, что прод-каталог — git-репозиторий: каталоги, развернутые копированием/rsync, `.git` не имеют и `git pull` падает с «not a git repository». Факт проверять командой до выбора механики (`git -C <dir> rev-parse --git-dir`); при отсутствии — rsync из локального клона (exclude .git/.env/.venv/__pycache__) + ОБЯЗАТЕЛЬНЫЙ `chown -R <служебный-юзер>` после: rsync -a под root сохраняет владельца источника и root-owned файлы ломают сервис. Скелет с пре-флайтом и смоуком — templates/deploy-release.sh этого скилла.
- Скрипт деплоя пишется под запуск Заказчиком ИЗ-ПОД ROOT, тогда как агент работает под своей учеткой: всё, что трогает код/БД/venv/бэкапы, выполняется через `sudo -u <служебный-юзер>`, иначе права перемешиваются; диагностика падения — патч скрипта и повторный ПОЛНЫЙ прогон (шаги идемпотентны по построению), не ручные команды из чата. Пре-флайт скрипта — проверки до любой мутации: целевой коммит клона, наличие утилит (rsync/sqlite3/curl), служебный юзер, venv, БД; шаг 1 всегда — бэкап БД через `sqlite3 <db> ".backup <file>"` (WAL-безопасен, сервис останавливать не нужно).
- Пост-рестарт смоук деплой-скрипта — минимум четыре проверки через реальный URL деплоя: health, HTML-страница, один JS-файл, один CSS-файл. Отдача статики — цепочка «приложение + внешний веб-сервер», обвал которой невидим для API- и DOM-сьютов (см. слепой контура ниже); `curl -o /dev/null -w '%{http_code}'` по каждому из четырех путей, любой не-200 = fail скрипта с командой отката.
