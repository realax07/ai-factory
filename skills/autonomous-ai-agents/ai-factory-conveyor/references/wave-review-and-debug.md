# Волновые ревью и отладка волновых фейлов (Р4/волны 5); J23-замеры QA; J25 дизайн-макет

## Живой дизайн-макет J25 (Р5, применено)

- UI-фича = макет в design/ ДО dev (ui_designer, самодостаточный html с токенами 1:1 из app.css, демо-JS переключения состояний), затем design_validator — сверка РЕАЛИЗОВАННОГО кода с макетом (4.2), затем code_reviewer. Приемка макета — ПМ (состав по design.md + сверка токенов скриптом), валидатор на макет не вызывается.
- Действие design_task требует в фабрике реализации в flow_transition (STAGE_TABLE + check_design_task); при рассинхроне фабрики с проектом пакет с [design]-задачей блокируется воротами — синхронизировать ядро фабрики от проектного репо (см. flow-control.md «flowctl: рабочая последовательность»), не вести дизайнера в обход ворот.
- Мокапы заказчику в Telegram — скриншотами (playwright headless, el.screenshot() по секциям/модалке), не путями к HTML; перед отправкой просматривать скриншоты самому (vision) — рендер может отличаться от замысла.
- Решения Заказчика по мокапам (вариант сетки, «ок» модалке) фиксировать decision-файлом в decisions/ + [x] в задаче тем же коммитом; выбор вида «сетка = masonry» вписывать в текст задачи dev в tasks.md, чтобы dev не перечитывал историю чата.
- Мелкий UX-дефект, найденный при верификации (смещение текста кнопки при active из-за обнуленного паддинга + жирного шрифта), — воспроизводить ЗАМЕРОМ координат (playwright boundingBox до/во время/после), а не «на глаз»: фикс без замера не доказан, замер ловит и вторую причину (не бордер, а padding+font-weight).
- Миноры валидатора макета вшивать в макет сразу (drag-reset демо-JS, disabled кнопок на границах диапазона, базовый кегль body, пометки-заглушки для отложенных NFR у фокусируемых элементов) — dev получает чистый эталон; собственные цвета/тени макета вне токенов = major.
- Скрипт сверки токенов макета сравнивать по ЗНАЧЕНИЯМ hex, а не по именам переменных, и собирать эталон со ВСЕХ css-файлов проекта (примитивы могут жить в одном файле с префиксом `--p-*`, семантические — в другом): сверка «имя переменной из app.css :root» дает ложные «вне токенов» на legitimately-used значения, а пропуск второго файла — ложный green. Итог приемки формулировать фактами (использовано N, вне токенов — перечень), не «сверено».
- Поздний артефакт для уже работающего dev-сабагента (макет, готовый пока сессия крутится) доставлять steer'ом живой сессии (delegate_task action=steer: путь к эталону + «стили сверяй с ним») — не перезапускать сессию и не оставлять dev «стилизовать по токенам на глаз».
- Замер «излишнего» этапа QA (J23): объединенная сессия impact→чеклист с отчетом о разделении усилий в процентах + транскрипты всех сессий этапа в каталог ВНЕ репо (~/hermes-qa-measurements/<класс>/ + README-план замера); решение об упразднении — по цифрам.

## Волновая схема и J10: ревьюер ДО merge, не после

- Волновой ревьюер обязателен ДО merge. Ревью, написанное оркестратором пост-фактум после влития — самопроверка исполнителя, а не независимая голова; дефекты при этом доехали до main и были пойманы только прогонами оркестратора (реальные случаи: 500 на создании задач из-за IndexError на позиционном кортеже; пустые tags во всей выдаче поиска). Восстановление при нарушении: независимое пост-merge ревью + честная фиксация нарушения в review-файле (append-only), не тихое затирание.
- Параллельные волны дробить ДО параметра «параллельно»: сабагенты захлебываются на больших задачах (max_iterations ~250 api_calls, ~80–100 мин) — волна [L] одним сабагентом умирает на финальном прогоне/коммите. Правило дробления: один сьют/один прогон/один фикс-цикл = одна делегация (кейсы — по доменам, обновление тестов — по одному сьюту, прогоны — отдельные сессии со своими стендами). Фоновые процессы сабагента (uvicorn, http.server) умирают с сессией — прогонам нужны собственные стенды в своей делегации.
- PR волн, ожидающие QA-контур, висят открытыми с FAIL pr_validate (change-маркер требует impact/чеклист/кейсы/ревью) — это НОРМА порядка Флоу 1, не дефект: dev-PR мержится только после QA-волны; не чинить CI ретиками и сменой маркеров на живом dev-PR.
- Параллельные dev-волны в ОДНОМ worktree: последний коммитивший побеждает в checkout — чужой коммит легко попадает на чужую ветку, а sync/маркерный коммит оркестратора легко растет из чужой ветки и при merge затягивает её в main до QA (тройной прецедент). Правила: каждая волна в СВОЕМ worktree (session_worktree.sh); перед PR проверять `git log main..HEAD --name-only` — чужие файлы = ветка растла не из main, ребейз; оркестраторские коммиты (маркеры [P], sync) делать ТОЛЬКО с checkout main и проверкой `git branch --show-current` после commit.
- Dev-сессия уперлась в лимит итераций ПОСЛЕ завершения правок, но ДО коммита: работу коммитит оркестратор в ветку сессии (изменения валидны, в зоне), гейты гоняет сам (node --check/py_compile/pytest по списку из отчета) — не перезапускать сессию ради одной команды commit; отчет сабагента в этом случае содержит полный список файлов и результаты самопроверок.
- Фоновые стенды сабагента (uvicorn с tmp-БД) умирают вместе с сессией — при необходимости повторить прогон поднимать стенд заново в своей сессии, не рассчитывать на чужой процесс.
- Волновой ревьювер работает с волновым диффом (base..last), ищет то, что прогонами не ловится: контракты/edge-cases/race-риски. Его находки — в дополнение к review-файлу волны; RETURN = hotfix-коммиты forward, история не переписывается.
- Прогон-фиксация чисел и приемка — оркестратору; циклическая отладка (бисекция, playwright-логи, гипотезы с прогонами) — dev-сабагенту. Факты передавать АРТЕФАКТОМ (item бэклога: корни, бисекция, подозреваемые, известные flakes с директивой «одиночное падение фиксируй, не чини»), не пересказом в goal. Экономия ~часов работы главной сессии при том же результате.
- Сабагент уперся в max_iterations — остаток работы (полный регресс + коммит) уходит ОТДЕЛЬНОМУ сабагенту (qa_runner) минимальной задачей, не в руки оркестратора: «добить сам» — тот же расход главной сессии, за который Заказчик останавливает. WIP-коммит для сохранения работы допустим (J21), дальнейшая доработка руками — нет. Рационализация «объём мелкий, добью сам» — тот же запрет: правки тестов затягивают оркестратора в циклы прогонов и ответов на падения. Правильный ход одним дыханием: WIP-коммит → спавн qa_runner (полный прогон + разбор красных: flake vs детерминированный, вердикт GREEN/RETURN) → code_reviewer на дифф → только потом любые действия оркестратора по RETURN-пунктам (они обычно мелкие: бамп версий, докстринги). Между WIP-коммитом и спавном у оркестратора НЕТ собственных правок кода/тестов — иначе снова «ты увлекся, сабагентов давай». Превентивно: в ТЗ любой dev-задачи [L] вшивать правило J21 сразу («при ~70% бюджета — WIP-коммит с маркером + отчет остатка»), не надеясь, что сабагент догадается сам на исчерпании. Правило в ТЗ само по себе не срабатывает: сабагент проскакивает WIP-момент и упирается в лимит ДО фазы коммита (повтор на M-задаче, вся работа осталась uncommitted) — long-running dev-сессии у границы бюджета (~85+ мин) напоминать стиром «коммить сейчас», а финальный коммит писать в ТЗ явным пунктом DoD и проверять его наличие при приемке ожидающих сессий.

## Оформление review-файлов под ворота flow_check (ловится только пост-фактум прогоном ворот)

- Имя review-файла обязано матчить регэксп ворот: `review-<NNN>-<task-slug>.md` или `review-<task-slug>-<NNN>.md` — имя вида `review-<task-ID>-slug.md` без ведущего NNN воротами НЕ парсится: файлы «есть», а ворота красные «задача без ревью». Приемку оформленных review-файлов делать прогоном flow_check, не ls.
- Вердикт — заголовочная строка `## Вердикт: approve` (жирный пункт списка `- **Вердикт:**` заголовком не является и не парсится). В строке вердикта НЕ упоминать слово «return» ни в каком виде — регэксп вердикта ищет его по всей строке, и упоминание первичного RETURN в скобках превращает approve в return; историю первичного возврата — отдельным абзацем ПОД заголовком.
- Между `#` и словом «Вердикт» не должно быть НИЧЕГО: регэксп `#{1,4}\s*Вердикт` не матчит нумерованную секцию (`## 7. Вердикт: approve` невидим для ворот — файл «есть», а задача числится «без ревью»). Писать заголовок без префиксов; после восстановления/правки review-файла парсинг вердикта сверять прогоном flow_check, не глазом.
- Восстанавливая вердикт ревьюера, упершего в iteration-cap до записи файла, оркестратор пишет файл сам: пометка в шапке «отчет восстановлен из транскрипта» + Reviewer-Delegation прерванной делегации. Учитывать: SELF_REVIEW-парсер pr_validate требует state=completed у делегации — dropped-делегация (state=error) валит чек, и такой файл нести отдельным [chore]-PR (change-маркер краснеть будет и на обязательном QA-хвосте финального PR).
- Merge+push волны и удаление веток/worktree — РАЗНЫМИ вызовами терминала: команда «merge + push + branch -D» проходит ворота подтверждения целиком, и при молчании пользователя блокируется вся (включая безобидный merge). Неразрушительные шаги — пачкой, деструктивные — отдельным явным вызовом после подтверждения.

## Технические ловушки волны (проверено на конвейере)

- Добавление JOIN к SELECT сдвигает позиционные индексы row[N] во всех потребителях запроса: колонка tags (row[10]) после LEFT JOIN users стала логином creator → tags=[] во всей выдаче поиска при зеленых статус-тестах. Правила: (а) выборки с JOIN — по явным квалифицированным колонкам/алиасам, не по позиции; (б) при изменении состава ответа API обновлять content-уровень ассертов (элементы tags в каждой строке), не только статусы — кандидат в чеклист QA-импакта: «изменяет ли дельта состав ответов — какие тесты проверяют содержимое?».
- Frontend select, наполняемый асинхронным списком (GET /api/users), гейтит поле payload флагом «список загружен»: иначе задержка/сбой загрузки превращает пустой select в null, и сохранение молча ОЧИЩАЕТ исполнителя задачи (PATCH null легален для сервера). Серверная семантика model_fields_set (поле не в payload — не тронуто) позволяет просто не включать поле; плюс токен поколения против stale-ответов при переоткрытии формы на другой записи; onerror флаг «загружено» НЕ поднимает.
- Тест на каноническую сериализацию (normalized_query и подобные round-trip) проверяет ВХОЖДЕНИЕ условий, не их порядок: flat-структура фильтра канонизирует порядок предикатов при сериализации; закрепление порядка ввода в тесте дает ложный RETURN.
- Стенд API-сьюта ekotov-wiki: после seed ОБЯЗАТЕЛЬНО `python -m app.migrate_r4` (требует SECRET_KEY) — без миграции бэкфилл ролей не применен (role wife=NULL) и падает профильный тест; приложение читает AVATARS_DIR, тесты — EKOTOV_WIKI_AVATARS_DIR: задавать ОБА. Без миграции пачка failed+errors выглядит как регресс диффа, а является средой. tests/api СТАНД НЕ ПОДНИМАЕТ сам (в отличие от web-сьюта): uvicorn поднимать руками по tests/README фоном до прогона — лес «connection refused» на всех фикстурах = нет стенда, не регресс. Между ПОЛНЫМИ прогонами стенд пересоздавать (свежая БД + пустой avatars-каталог + seed + migrate): avatar-тесты оставляют файлы и avatar_url в БД, профильные тесты ассертят «avatar_url is None» и падают на остатках прошлого прогона — грязь состояния выглядит как дефект диффа.
- Легитимная смена поведения по спеке, ломающая существующий тест, кодирующий СТАРУЮ семантику — резолв через Заказчика, затем ревизия тест-кейса ПОД спеку (дельту не трогать): пиксельные/структурные ассерты старого поведения (center-crop, порядок полей) снимаются, суть инварианта (геометрия, формат, контракт кодов) сохраняется; решение Заказчика фиксировать в docstring теста. Dev-сабагенту в ТЗ вшивать: «действующие тесты не менять; если легитимное по ТЗ изменение ломает существующий тест — СТОП-факт: proposed-файлы вне репо + перечень, коммит не делать» — такой возврат с готовыми артефактами стоит минуты, а самовольная правка теста под код — потерю контракта.
- Сущности, созданные через UI-форму, регистрировать в cleanup-фикстуре так же, как API-созданные: незарегистрированная переживает teardown и раздувает выдачу фильтрованного поиска следующего теста («ожидал 1, получил 2»), мигает в зависимости от порядка файлов. Содержимое nested-результатов поиска (tags в строках) api-сьютом не проверяется — добавлять content-ассерты.
- Бисекция по коммитам может обманывать: дефект внесен тем же диапазоном, что и падающие тесты, но в соседнем модуле, который тесты этого файла не проверяют (tags ломал search.py, а падали тесты формы). Бисекцию дополнять вопросом «какой еще потребитель этого модуля/данных затронут?» и content-smoke'ом API напрямую (создать с тегами → проверить выдачу).
- Join-проекции в search-модулях дублируют тег-загрузчики (_load_search_tags как копия tasks._load_tags) — при правке тег-логики искать копии grep'ом по backend, иначе копия дрейфует. Мертвые импорты из tasks.py в search.py — маркер такой копии.
- Race/сбой загрузки асинхронного справочника в форме не должен менять payload: гейт «список загружен» (assignedLoaded-флаг) решает — поле не включается, серверная model_fields_set семантика оставляет значение нетронутым; onError флаг не поднимает; токен поколения отсекает stale-ответы при переоткрытии формы на другой записи. Прогонами не ловится (test auto-retry expect скрывает гонку) — ловится ревьюером на вопрос «что отправится, если ответ не пришел?».
- Виджет-дропдаун, живущий НАД формой (комбобокс тегов), закрывать во ВСЕХ путях закрытия формы (submit / «Отмена» / крестик), а перерисовку открытого списка при late-ответе сети выполнять только при document.activeElement === input: иначе поздний ответ пересоздает option-узлы под курсором → «option intercepts pointer events» над кнопкой сабмита (флейк, в изоляции не воспроизводится), а после закрытия формы список остается видимым в скрытом overlay и «повисает» при переоткрытии. Регресс-тест: открыть форму → фокус в поле (список открыт) → закрыть форму без клика по странице → переоткрыть → список скрыт, клик по сабмиту не перехвачен. Модульное состояние виджета (lastAnnounced и т.п.) сбрасывать в том же close-пути — иначе aria-live не озвучит переоткрытую форму.
- Playwright-эмуляция ОТСУТСТВУЮЩИХ браузерных API (fallback-тесты): `delete window.X` в init-скрипте не работает для own-свойств window — в addInitScript использовать `Reflect.deleteProperty(window,'X')` + `Object.defineProperty(window,'X',{value:undefined})` в IIFE. Тач: контекст has_touch=True + синтетический dispatch PointerEvent/TouchEvent через evaluate (полный gesture-пайплайн playwright не умеет — preventDefault на реальном устройстве тестом не покрывается, фиксировать как границу). Reduced-motion — CDP `Emulation.setEmulatedMedia` с ассертом computed transition/animation-duration = 0s.
- Синтетические TouchEvent НЕ двигают нативный scroll-контейнер (snap/swipe-тесты): реально листающий жест эмулировать через CDP `Input.dispatchTouchEvent` — результат дев-смоука с синтетикой «зеленый» не доказывает скролл; прогон с CDP-тачем обязателен для touch-фич, где ассерт зависит от фактической прокрутки.
- Порог touch-жеста верифицировать ГРАНИЦЕЙ (49px не листает, 50px листает), а не «большой свайп листает»: ассерт только на большой свайп пропускает неверно взятый порог целиком.
- Автовоспроизведение тапа Playwright может проскроллить элемент к центру до клика (scroll into view) и сдвинуть scroll-позицию, на которую ассертит тест: если тест меряет scrollY вокруг клика — кликать через JS-evaluate, не через locator.click(), либо замерять позицию до автоскролла.
- Безусловный scrollIntoView при focusin роняет попап-виджеты, живущие рядом с полем (комбобокс-дропдаун мгновенно закрывается): фокус-скролл делать только при реальном выходе поля за вьюпорт (getBoundingClientRect против innerHeight). Диагностику «дропдаун открывается и сразу закрывается» начинать с А/Б (дельта vs база) + отключения подозрительных слушателей по одному: инфраструктурная версия (401 куки/стенд) опровергается контрольной пробой API на том же стенде.
- Флекс-порядок детей шапки мерять числом (titleCenter vs headerCenter), не «на глаз по скриншоту»: смещение от перестановки соседей (бургер+gap) детерминировано равно ширине соседа+gap (−48px при бургере 44+gap 4) — мокап-арбитр задает ПОРЯДОК детей, и «титул по центру» достигается только им, text-align:center внутри собственной flex-коробки центрует не относительно шапки.
- Гео/версточные ассерты регресс-теста сверять с ИСТОРИЧЕСКИМ видом компонента до принятия теста: dev на лимите итераций пишет ассерты под предполагаемый идеал («кнопка справа от textarea»), которого в продукте никогда не существовало — ложный фейл маскирует реальный симптом (сжатие ширины секции). Инварианты брать из фактического рендера (bbox формы/секции, выравнивание левых краев), а не из гипотезы; лишний строгий ассерт заменять на исторически верный, не ослаблять до прохода.
- Тестовые данные, созданные через UI-форму, должны регистрироваться в cleanup-фикстуре — иначе миграция изоляции одного теста в другой проявляется как «ожидал 1, получил 2» только при полном прогоне (порядок файлов). Диагностика: гонять подозреваемый файл изолированно И в составе сьюта.

- Мокап-арбитр задает и flex-ПОРЯДОК детей, не только стили: расхождение порядка (титул до бургера вместо после) — RETURN-находка уровня major, даже при «совпадающих стилях» — text-align:center внутри собственной flex-коробки центрует не относительно шапки, смещение детерминировано равно ширине соседа+gap. Верифицировать замером центров (titleCenter vs headerCenter), А/Б против базы.
- Прерванный design_validator/QA-финал (iteration-cap до записи вердикта) дособирать из артефактов, не перезапуском: промежуточный отчет (в /tmp по мере секций), приготовленные скрипты проверок, осиротевший nginx-конфиг стенда — всё переиспользуемо; недостающие пробы добить одним прогоном скрипта на реанимированном стенде (поднимать фоном по одному сервису, health-проверка каждого, гасить после) и записать вердикт-файл с пометкой о финализации ПМ.

## QA-контур после волны: гэп-driven кейсы и замер этапа (J23)

- Кейсы писать ТОЛЬКО по гэпам чеклиста (CHK «НЕ покрыт — кандидат»): покрытые CHK не переизобретать, в goal автору передавать существующие числа сьютов (api 176p, web 112p) как границу «не дублируй». Гэпы считать по колонке покрытия, которую impact-шаг подставляет без повторного чтения кода.
- Когда этап подозревается в излишести (чеклист = пересказ дельт), не спорить по ощущениям: (1) запускать ОБЪЕДИНЕННУЮ сессию «impact → чеклист» с обязательным отчетом о разделении усилий (проценты времени на шаг — напр. impact ~35% / checklist ~65%); (2) складывать транскрипты всех сессий этапа в каталог ВНЕ репозиториев (~/hermes-qa-measurements/<класс-сессий>/ + README с планом замера) — репа хранит артефакты, архив хранит сырые логи для анализа расхода. Решение об упразднении этапа — только по этим цифрам и слову Заказчика.
- Гэпы чеклиста — не абстракция: формулировать их как «что прогонами НЕ ловится» (содержимое полей выдачи, средовые ОГР, расинхрон дублирующихся полей, гварды hotfix) — такие пункты становятся либо manual-процедурами (прод/деплой), либо целевыми автотестами (route-перехват, объект-сравнение выдачи), а не общими «проверить поиск».
- Ревьюер кейсов с правом minor-правок на месте экономит полный цикл возврата автору: содержательные изменения — return, механические (синтаксис грамматики в шаге кейса, невоспроизводимый в сьюте шаг → примечание, уточнение контракта поля) — правит сам и помечает в отчете. Приемка — по его же отчету.
- Ревьюер кейсов обязан ПРОГОНЯТЬ шаги кейса против грамматики/фактической системы, а не только читать текст: кейс с `tag = "..."` в advanced-шаге падал бы 400 до объект-сравнения (грамматика допускает только `tag IN (...)`) — это находит прогон шага, не чтение.
- Design_validator (E13) — сверка РЕАЛИЗОВАННОГО UI с макетом ПОСЛЕ dev (computed styles на стенде), не ревью макета: приемка макета до dev — ПМ (состав по design.md + программная сверка токенов с app.css). ТЗ с формулировкой «ревью макета — design_validator» — ошибка постановки; сверять ТЗ с ролью из agents/README до спавна. Миноры валидатора макета (drag-reset демо, disabled на границах диапазона, базовый кегль, пометки-заглушки) вшивать в макет сразу — dev получает чистый эталон. В оси сверки ЗАКЛАДЫВАТЬ нативные form-контролы (file input, select, checkbox): браузерный вид «Choose File» рядом с токенизированной кнопкой — повторяющийся DEF-004-класс, невидимый behavioral-тестам; паттерн — скрытый input (1×1, opacity:0) + стилизованная кнопка/label, change-механика не трогается, клавиатурный доступ сохраняется. Виджет, перехватывающий флоу формы (кроп = новое «Применить»), делает старый submit-CTA бесполезным — НЕ удалять его из разметки: скрывать при активном модуле (hidden после init), а в fallback-режиме (нет canvas/JS) кнопка остается единственным путем загрузки — иначе ломается NFR-откат. Диагноз «вплотную/не применяется стиль» начинать с проверки, что класс формы/элемента вообще присутствует в разметке: рефакторинг разметки оставляет CSS-селекторы мертвым кодом, и стили молча не исполняются.
- Находки design_validator на реализованном UI — Флоу 2 dev-сабагенту (тот же worktree/зона), не правки оркестратора: major — с тестом-регрессом (bbox/opacity скрытого input, expect_file_chooser на клик кнопки); наблюдения валидатора вне его зоны (чужой модуль, средовые) — в бэклог продукта, не в фикс.

## Деплой волны: этап 6.2/6.3 и выкатка (уроки Р4)

- Формат CHK «тот же /» (ссылка на источник предыдущей строки) валит rule 6 flow_check (строка без FR/NFR в тексте): при генерации чеклиста РАЗВОРАЧИВАТЬ «тот же» в полный источник в каждой строке, до коммита — пост-фикс «раскрыть ссылки» не меняет смысл CHK, но правка 70+ строк после факта дороже, чем сразу полная колонка.
- Регэксп rule 6 считает источником ТОЛЬКО `FR-\d+|NFR-\d+|Requirement` — голые «ОГР-21», «СЦ-14», «ОВ-СА-2» источником не считаются, и строка валит ворота: источник CHK писать канонически «Requirement: <имя> (FR-…, NFR-…)», остальные маркеры — при нем в скобках. Чеклист проверять прогоном flow_check ДО коммита, не пост-фактум.
- В отзыве ревьюера вердикт-строку `## Вердикт: approve` не засорять упоминаниями первичного возврата даже словом «вернул» — негативный регэкс ищет подстроку по всей строке; историю возврата — отдельным абзацем под заголовком (см. subagent-delegation.md «Review-brief discipline»).
- 6.2 (полный регресс) на flaky-популяции: единичные error/failed, не воспроизводимые изолированно и в контрольном прогоне, фиксировать как известные flakes в отчете ЧИСЛАМИ (два зеленых подряд после красного = зеленый валиден), не перегонять бесконечно.
- 6.3 (бамп static_v) — одиночная однострочная правка одним коммитом; после него main — целевой коммит деплоя (EXPECTED_COMMIT).
- Миграционная сверка «после» не равенство дефолту, а валидность по справочнику (см. раздел «Релизный деплой» ниже); негативный чек «значение вне справочника валит миграцию» сохранять в репетиции обязательно — защита от мусора не ослабляется вместе с ослаблением позитивного чека.
- Мелкие UX-правки Заказчика в час релиза («убрать лейбл X») — минорный хотфикс отдельным dev-сабагентом на отдельном worktree (Флоу 5): изолированная правка + обновление затронутых тестов + точечный прогон соседних тест-файлов той же зоны. При снятии видимого label не ронять доступность: aria-label/aria-labelledby на поле обязательны — behavioral-тесты за этим не следят, за этим следит ТЗ.
- Прод-инцидент «no such column» на шаге схемы (см. SKILL.md ekotov-wiki-ops правило 11): упавший деплой ДО рестарта безопасен — прод продолжает работать на старом коде, бэкап уже снят; фиксировать это в докладе Заказчику явно, чтобы не бросил прод полуживым.
- Отладку деплой-инцидента НЕ тянуть в оркестратор: локальная репетиция (копия старой схемы → схема → миграция → повторная схема) — механическая работа dev/qa-сабагенту; оркестратор — формулировка репетиции и приемка. Правило J24 распространяется на деплой-инциденты.
- Корень «упал шаг схемы» бывает НЕ в дельте задачи, а в порядке шагов деплоя: SCHEMA_SQL может содержать объекты по НОВЫМ колонкам (индексы creator/assigned), которые на существующей прод-БД создает только миграция, идущая ПОСЛЕ схемы. Репетиция на копии СО СТАРОЙ схемой — обязательный шаг приемки любого пакета, трогающего схему (см. SKILL.md ekotov-wiki-ops правило 11, init_db делит SCHEMA_SQL на базу и Р4-хвост).
- Баг-репорт Заказчика с прода — верифицировать репродукцией на локальном стенде ДО делегации фикса, и фикс-сессии давать: точный симптом, стенд-команды с env, известные flakes с директивой «одиночное падение — перезапусти изолированно, не чини». Без репродукции сабагент чинит гипотезу, а не дефект.
- Багфикс-цикл по прод-репорту (проверено, окупилось): репродукция у dev-сабагента → WIP-коммит при обрыве → qa_runner (полный прогон + классификация красных, GREEN/RETURN) → code_reviewer на дифф (его зона: зацепленные смежные тесты, забытый static_v-бамп, историческая корректность ассертов) → RETURN-пункты оркестратора мелкой пачкой → контрольный полный прогон → merge/push. Ревьюер на багфиксе — не ритуал: единственный major цикла был именно его находкой (статика без бампа кешируется прод-браузерами на срок expires; фикс «не доедет» неделями). Контрольный прогон после RETURN-правок обязателен даже при «однострочных» правках: бамп версии или класс-селектор меняет резолвинг локаторов в смежных тестах.

## Релизный деплой: порядок схемы/миграции и J26 (Р4 финал)

- SCHEMA_SQL, содержащий объекты по НОВЫМ колонкам (индексы creator/assigned), на существующей прод-БД падает «no such column» на шаге схемы ДО миграции 4b — фикс: init_db делит схему (базовая часть vs хвост по новым колонкам, флаг «колонки уже есть»), миграция создает колонки и свои индексы сама. Репетиция обязательна на копии СО СТАРОЙ схемой (см. ekotov-wiki-ops правило 11); тесты на свежих БД этот путь не исполняют никогда.
- После падения шага схемы прод безопасен (старый код, бэкап снят) — фиксировать это Заказчику явно и чинить hotfix-коммитом forward, не инструкциями править файлы руками.
- Миграционная сверка «после» НЕ должна требовать равенство дефолту: бэкфилл ролей ставит дефолт только при role IS NULL, а легитимная смена роли пользователем через UI делает сверку «роль = дефолт» детерминированным FAIL на проде. Сверка проверяет ВАЛИДНОСТЬ по справочнику (дефолт ИЛИ допустимые значения; NULL там, где бэкфилл обязан был заполнить); негативный чек (значение вне справочника валит миграцию) сохранять. Репетиция — на копии с данными ПОСЛЕ легитимных пользовательских изменений, не только seed-дефолтов.
- J26: любые изменения deploy.sh / RUNBOOK / nginx / systemd / процедур бэкапа-отката-смоука — через devops-сабагента (E9), не ПМ; ПМ — формулировка и приемка (bash -n, DRY_RUN на реальном проде, дифф зоны). Гейт проверок внешних компонентов (5b/6: location /<новый путь>/ в прод-nginx до смоука с полной инструкцией при отсутствии) — деплой-скрипт обязан падать до «успеха», иначе релиз выкатывается с 404-ами молча.
- Миграционная сверка «после» НЕ должна требовать равенство дефолту: бэкфилл ролей ставит дефолт только при role IS NULL, а легитимная смена роли пользователем через UI (PUT /api/profile) делает сверку «роль = дефолт» детерминированным FAIL на проде — деплой встает, хотя данные валидны (прецедент: owner сам выбрал «Product engineer» через настройки). Сверка миграции проверяет ВАЛИДНОСТЬ значений по справочнику (дефолт ИЛИ допустимые значения; NULL там, где бэкфилл обязан был заполнить), не равенство дефолту. Репетиция миграции — на копии с данными ПОСЛЕ легитимных пользовательских изменений, не только на дефолтных seed-данных: значения, измененные UI, бэкфилл-сверка иначе считает дефектом. Негативный чек сохранять: значение вне справочника обязано валить миграцию по-прежнему.
- Продуктовые идеи Заказчика (контейнеры, сервисы, инфраструктурные переустройства) — в PRODUCT_BACKLOG.md РЕПОЗИТОРИЯ ПРОЕКТА (ekotov-wiki), не в фабричный BACKLOG.md: фабричный бэклог — только тюнинг конвейера/процесса. Перед записью идеи проверять назначение файла (фабрика vs продукт) — промах ловится Заказчиком («не туда») и тратит цикл на откат.
- Внешние ТЗ/материалы от Заказчика (архивы документов, backlog-паки) класть ОТДЕЛЬНОЙ папкой в репо (`docs/<имя-источника>/`, файлы не редактировать, пометка «внешний исходник»), не вливать в BACKLOG.md — бэклог остается картой пунктов, исходники остаются исходниками; коммит с путем понятнее отката перемешанного файла.
- Полный web-сьют из worktree требует `PYTHONPATH=<worktree>`: без него ModuleNotFoundError на tests-пакете выглядит как поломанный сбор, хотя это среда прогона, не дифф.
- Кеш-маркер data-URI не ставится хвостом `?v=1` — это непарсимый URL (Chromium ломает XML-парсинг, naturalWidth=0): маркер версии зашивать комментарием ВНУТРЬ data-URI SVG (`<!--cache:v=N-->`) — изменение маркера меняет сам URI и сбрасывает кеш. Фикс favicon/инлайн-SVG проверять живым рендером (naturalWidth>0), не фактом правки.
- Footer сайдбара («Настройки»/«Выйти») в flex-лейауте без фиксации к viewport уезжает за нижний край на ДЛИННЫХ страницах (сетка галереи растягивает документ, justify-content:space-between раскладывает по полной высоте документа), на коротких не проявляется — «баг только на одной странице» с такой геометрией начинать диагностику с проверки высоты документа vs viewport. Фикс: body.app-shell height:100vh; .sidebar height:100vh + position:sticky + top:0 + overflow-y:auto; .content height:100vh + overflow-y:auto. Проверять на стенде с длинным контентом: footer в viewport И скролл контента колесом работает (обе половины фикса).
