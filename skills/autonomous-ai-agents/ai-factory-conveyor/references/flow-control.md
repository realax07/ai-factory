# Flow Control layer: разрешающий детерминированный слой поверх ретроспективных ворот

## Статус и вводные (пересмотренный план Заказчика)

- Слои 1–5 + hardening P0.1–P0.6 СМЕРЖЕНЫ в main через PR (ruleset на main требует PR, прямые пуши отклонены); режим **enforcing включен** (`flow_mode.py set enforcing --by customer`): DENY/UNKNOWN блокируют действие в штатном маршруте flowctl.
- **Статус-доклад всегда содержит этапы ворот со статусами** — блок `prepare | reserve | zone-check/gates | provenance` со значениями PASS/DENY/UNKNOWN/SKIPPED и кодами причин (правило 9 AGENTS.md). Скрывать/сглаживать запрещено.
- Ruleset main: PR-only + non-fast-forward + **required checks `test-flow-control`** (название job синхронизировано с ruleset; переименование job без правки ruleset = PR навсегда BLOCKED) + bypass never. Прямой push и локальный merge отклонены: мерж — только ветка + PR + `gh pr merge`.
- Установка: `factory_bootstrap.py` — новая машина (окружение, state, вотчдог-крон, приемочные тесты, дефолт shadow); `factory_init.py` кладет в проект базу И ядро Flow Control (7 скриптов + контракт + скилл factory-flow + decisions/releases) — фабрика = часть проекта.
- Жесткое правило тест-модели: кейсы as-is группируются **по доменам/сервисам** (`regression/<domain>/`), не по релизам; 1 кейс = 1 файл (inline-TC из общих файлов R1–R3 переносятся целиком в legacy/ как документ, не раскладывать); контроль миграции — все TC из автотестов должны находиться в новой структуре (скрипт-сверка), промежуточные (чеклисты/ревью/impact закрытых пакетов) → archive/workflow/.
- Вводные схемы: один VPS, одна ОС-учетка для Hermes и сабагентов, один GitHub-токен без admin у всех. Это известное допущение: enforcing = дисциплина и воспроизводимость штатного маршрута, НЕ песочница. Цель этапа — «local_ready=ALLOW + external_enforcement=UNKNOWN явно», а не скрытое превращение UNKNOWN в ALLOW.
- Branch protection настроен как **Ruleset** (не legacy protection): проверять через `GET /repos/{repo}/rules/branches/{branch}` (ruleset enforcement=active + rules содержит type=pull_request + bypass never), старый `/branches/{branch}/protection` дает 404 при токене без admin даже на защищенной ветке. Живая проверка замка — probe-push в main (ожидаем отказ GH013).
- Ворота-обходы закрыты: обязательные gates вычисляются из политики (flowctl required_gates_for), `--gates` только добавляет, `--diagnostic` дает diagnostic_only без accepted; зоны ролей — из ROLE_ZONE_POLICY (дословно из таблицы зон agents/README), CLI только сужает, policy_version в резервации, diff сверяется с суженной зоной.
- Остаток доработки (бэклог): P0.4 журнал решений Заказчика (approval_ref = decision_id с scope/action/SHA/expiration, не произвольная строка), таблица «GitHub-enforced vs машинная vs договоренность» в docs/ci-gates.md, CI-job с pytest на PR.

## Компоненты (main)

- `scripts/flow_state.py inspect --repo PATH --project ID --flow N --change ID [--task ID] [--json] [--registry PATH]` — read-only снимок FlowSnapshot (факты с source/fingerprint/confidence, snapshot_digest; missing/invalid/unknown/ready различаются; битый реестр = unknown, НЕ «сессий нет»; symlink за пределы repo не следует; повторный вызов на неизменном вводе = эквивалентный JSON).
- `scripts/flow_transition.py check|next ... --action ACTION --role ROLE [--approval-ref] [--parallel] [--json]` — чистая check_action(snapshot, action) → Decision: allowed/status ALLOW|DENY|UNKNOWN, blocking_reasons (стабильные коды: MISSING_INPUT, INVALID_GATE, HUMAN_APPROVAL_REQUIRED, WRONG_ROLE, ZONE_CONFLICT, STALE_EVIDENCE, AMBIGUOUS_STATE, STALE_SNAPSHOT, EXTERNAL_ENFORCEMENT_UNKNOWN), required_gates, evidence_refs, next_candidates. Exit 0 ALLOW / 1 DENY / 2 UNKNOWN|ошибка.
- `scripts/session_check.py reserve|check|reconcile|status [--json] [--registry PATH]` — атомарная резервация зон записи (лок-каталог + tmp+os.replace; идемпотентность по delegation_id: тот же payload OK, иной = DUPLICATE_PAYLOAD; пересечение зон = ZONE_CONFLICT; glob-семантика `src/**`=вложенность, `src/*`=один уровень; мертвый лок с pid детектируется и снимается), post-check границы (changed paths base..HEAD + незакоммиченные + `git log --name-only --no-renames` против зоны; symlink наружу = отказ), reconcile без молчаливых удалений; реестр schema v2 с миграцией v1 (бэкап обязателен на ВСЕХ путях записи, не только reserve).
- `scripts/gate_runner.py run|status|record-review|diff-digest [--json]` — единый запуск ворот как subprocess (cwd=repo, timeout): GateReport с input_head/digest (HEAD + sha скриптов-ворот → STALE после нового коммита, повтор обязателен), статус PASS|FAIL|ERROR|SKIPPED; ERROR на timeout/missing/parse, SKIPPED только по явному правилу (pr_validate без PR-контекста, pm_bounds_check без явного режима — не «доказательство проверки»); audit JSONL append-only с correlation_id, без секретов и полного stdout, лог не единственное доказательство.
- Provenance review: sidecar JSON рядом с review-.md (schema_version, project, change, task_ids, author/reviewer delegation, reviewed SHA/diff_digest, verdict); accept_review/merge при согласованном sidecar → ALLOW (strict), легаси без sidecar → не незаконны задним числом, но без авто-merge (UNKNOWN/legacy evidence).
- Решения Заказчика по shadow-сверке Р6: 3.1-А (approved-кейсы ИМЕННО своего change → qa_automation без них DENY/MISSING_INPUT; QA-роли практики qa_case_author/qa_impact_analyst в графах), 3.2-Б (release строго после archive — практика Р6 признана нарушением), 3.3-А (архивация = sa, контракт 7).
- **P0.1: merge/release достижимы до ALLOW при полном комплекте фактов** (решения Заказчика А/Б/В1): факт `change.archived` (в archive/ + слитые дельты + openspec validate ok; CLI недоступен = unknown с причиной, не молчаливый PASS), факт branch protection (Rulesets API, TTL ≤24ч, привязка repo/branch/HEAD), релизное решение файлом `releases/<id>.md` (change-id + слово согласия + SHA). Формулировка — «решение зафиксировано», не «личность подтверждена».
- Режим SHADOW: решения не блокируют; расхождения машина/ПМ — данные для решения о enforcement. Норматив: `openspec/changes/*/specs/deterministic-flow/spec.md` + `contracts/flow_control_contract.md`.
- Семантика: UNKNOWN не разрешает исполнение; DENY сильнее UNKNOWN-пометок (жесткое нарушение не маскируется непроверяемостью); недостающий исполняемый критерий текстового правила = честный UNKNOWN, не додуманное DENY/ALLOW.

## Уроки shadow-внедрения (сверка машина/ПМ на реальной истории)

- Сверку делать на КОПИИ репо (git checkout <sha> в detached, git-история сохраняется при cp -a), живой репозиторий не трогать; после прогона сверять его `git status`.
- Сценарий сверки готовить ДО прогона: точки = реальные решения из git-истории, для каждой — action/role/flow, ожидаемый вердикт, факт. Результат — таблица «decision / факт / совпало / классификация».
- Ложное разрешение (машина ALLOW при фактическом нарушении порядка) — самый опасный класс: чинить первым (обычно проверка смотрит глобально по каталогам, а не по scope change-пакета).
- Ложный запрет может вскрывать расхождение ГРАФА с ПРАКТИКОЙ (машина запретила релиз-до-архивации и роль, которая реально делает архивацию) — не править механически: сначала решение Заказчика, что нормативно, граф или практика.
- Правила, существующие только текстом (AGENTS.md), машина дает честным UNKNOWN — целевое поведение, не дефект; не «дорабатывать до полного покрытия».
- Пост-фактум snapshot слеп на самом коммите перемещения артефакта (пакет уже в archive/) — контроль такой точки возможен только шагом раньше; фиксировать как ограничение, не баг.

## Запуск конвейера: срез 2/3 в действии (проверено живыми прогонами)

> Рабочая последовательность команд flowctl (prepare/run/finish, --pm-mode, --pm-resume, ловушки зон и маркеров PR) — в разделе «flowctl: рабочая последовательность» ниже.

- Проверка сабагент-отчетов фактом: ручной reserve второй делегации на пересекающуюся зону → ZONE_CONFLICT с указанием держателя; qa_automation на change без своих approved-кейсов → DENY/MISSING_INPUT; gate_runner pre_merge на репо с самоссылочными ошибками → честный FAIL, а не зеленый. Это критерий приемки поставок слоя, не декларация.
- GateRunner при прогоне на активном change-пакете дает FAIL по самоссылочным воротам (J10 по его же задачам) — это правда, а не дефект runner: отчет Заказчику маркировать «self-referential, снимается архивацией».
- Миграция реестра: клон старого v1-формата для тестов, бэкап на каждом пути записи; тест конкурентного reserve двух процессов (ровно один WIN) — обязательный негатив поставки reservation-класса.
- npm-глобал openspec в среде Hermes отсутствует по умолчанию: адаптеру — параметр `--openspec-cmd`, в тестах fake-executable с управляемым exit code (из ТЗ 05); реально ставить через npx @fission-ai/openspec при прогоне ворот вручную.

## Ворота (flow_check) — дополнения

- requirements.md и sdd.md активного change искать и в корне репо, И внутри `openspec/changes/<id>/` — мульти-change репозиторий ломает только-корневую проверку; расширение ворот проверять негативом и на обоих реальных репо (обратная совместимость).
- Самоссылочные ошибки ворот на активном change-пакете (J10 по его собственным задачам, контракт 6 по его же тестам) — нормальны до архивации; помечать self-referential в tasks.md с указанием, что снимается архивацией, не чинить код ворот.

## Запуск конвейера через flowctl (рабочая последовательность, проверено P12)

- Полная последовательность на действие: `prepare` (выдает ALLOW и goal-файл) → `run --correlation-id` (отмечает старт, status=running) → внешний delegate_task → `finish --correlation-id --report <файл> --pm-mode <mode> --pm-commits <sha>`. --report — путь к СУЩЕСТВУЮЩЕМУ файлу отчета (указатель на измененные артефакты); finish без существующего отчета = blocked.
- Обязательные аргументы prepare: `--owner-pm pm-main` и зоны `--path` — ТОЛЬКО glob-паттерны из политики роли (`role_zone_policy.allowed_zones_for('rolename')` посмотреть заранее и передавать подмножество); запрос пути вне политики = ZONE_OUTSIDE_POLICY, отклонение до резервации.
- finish: `--pm-mode` обязателен (без него pm_bounds_check = ERROR «режим не задан» — конфигурационная ошибка запускающего); для dev-задач `--pm-mode commits --pm-commits <sha коммита агента>`.
- `--report` — только АБСОЛЮТНЫЙ путь к файлу отчета: относительный резолвится от CWD процесса flowctl (каталог фабрики, а не репозиторий проекта), файл «не найден» и сессия уходит в blocked при фактически существующем отчете; лечение — повтор finish с абсолютным путем + `--pm-resume` (если дефекты только gate ERROR/SKIPPED).
- **--pm-resume**: первый finish с конфигурационной ошибкой (забытый --pm-mode) переводит сессию в blocked НЕОБРАТИМО — повторный finish с тем же correlation-id отклоняется («вердикт уже вынесен»). Лечение: повтор finish с `--pm-resume` — принимается ТОЛЬКО когда все дефекты записи gate ERROR/SKIPPED (конфигурация запускающего); FAIL/zone-дефекты по существу resume не проходит (проверено тестами).
- OUT_OF_ZONE при finish смотрит ВСЕ пути base_sha..HEAD + незакоммиченные — при параллельных волнах в ОБЩЕМ worktree чужие правки соседней сессии красят зону текущей: приемку делать на чистом дереве (все чужие волны закоммичены в свои ветки) либо в изолированном worktree сессии.
- «design_task не входит в граф Флоу 1» в фабрике при рассинхроне с проектом: копия фабрики отстает от проектной — синхронизировать `scripts/flow_transition.py` (+`flow_check.py`) из проектного репо (там action появляется первым), прогнать `pytest tests/test_flow_transition.py tests/test_flowctl.py`, и затем тот же фикс коммитом в проект (правка могла наработаться только в фабрике — эталон определяется направлением изменения).
- Приемка коммита параллельной волны: мерж может произойти через ЧУЖОЙ PR (sync-ветка одного агента, растущая из ветки другого, при merge затягивает чужой коммит в main) — перед merge сверять `git log base..HEAD --name-only` своей ветки: чужие файлы в диапазоне = ветка растла не из main, ребейзить на main до PR.
- PR-маркер `[change-id]` честен только когда diff содержит ЗАКРЫТЫЕ dev-задачи: PR создания change-пакета (задача 0.1) под этим маркером дает FAIL по QA-контракту (impact/чеклист/кейсы/ревью еще не существуют — они появятся позже) — PR создания пакета маркировать `[docs]`/`[chore]`; переименование title после пуша не перегенерирует event — пустой коммит для ретрига CI.
- ZONE_CONFLICT при prepare может держать Finished-сессия с широкой зоной (например `backend/**` от старого пакета): завершенность не освобождает зону — `flowctl reconcile --delegation-id <id>` переводит в stale (ничего не удаляет молча) и зону отпускает; после reconcile повторить prepare с новым correlation-id (DUPLICATE_PAYLOAD на старом).

## flowctl: рабочая последовательность (проверено на живом пакете)

- Полный цикл на действие: `prepare` (выдает ALLOW и goal-файл) → `run --correlation-id` (отметка старта, status=running) → внешний delegate_task → `finish --correlation-id --report <файл> --pm-mode commits --pm-commits <sha>`. Файл отчета должен СУЩЕСТВОВАТЬ до finish — finish без него = blocked.
- prepare требует `--owner-pm` и зоны `--path`: передавать ТОЛЬКО glob-паттерны из политики роли (`allowed_zones_for('rolename')` посмотреть заранее, CLI может только СУЗИТЬ); запрос пути вне политики = ZONE_OUTSIDE_POLICY до резервации. Зоны из справки CLI (`--zones`) не существует — флаг называется `--path` (повторяемый).
- decision-record в `decisions/<id>.md` должен точно матчить запрошенное действие: `action` из графа Флоу (не «package_start» — точное имя вида `create_change`), `phase` = фаза действия (create_change = 1, не 0); расхождение любого поля = HUMAN_APPROVAL_REQUIRED/DENY «разрешение чужого действия/фазы не переносится».
- Имена действий — ТОЛЬКО из графа Флоу (accept_review, approve_requirements, architecture_review, archive_change, code_review, create_change, dev_task, design_task, merge_task, qa_*); выдумывать «sa_start»/«create_package» бесполезно — MISSING_INPUT.
- finish: `--pm-mode commits --pm-commits <sha>` для dev-задач — без pm_mode pm_bounds_check = ERROR «режим не задан» и сессия уходит в blocked НЕОБРАТИМО; лечение — повтор finish с `--pm-resume` (принимается только если ВСЕ дефекты записи — gate ERROR/SKIPPED, т.е. конфигурация запускающего, не дефекты агента; FAIL/zone не обходятся). Повторный finish без resume отклоняется идемпотентно («вердикт уже вынесен»).
- OUT_OF_ZONE при finish считает ВСЕ пути base_sha..HEAD + незакоммиченные: при параллельных волнах в общем worktree чужие правки красят зону текущей сессии — приемку делать на чистом дереве (чужие волны закоммичены в свои ветки) или в изолированном worktree.
- ZONE_CONFLICT при prepare от FINISHED-сессии со широкой зоной: завершенность не освобождает зону — `flowctl reconcile --delegation-id <id>` переводит в stale и отпускает; после reconcile prepare с НОВЫМ correlation-id (старый = DUPLICATE_PAYLOAD).
- «Действие не входит в граф» в фабрике при рассинхроне с проектом: копия фабрики отстала — синхронизировать `flow_transition.py` (+`flow_check.py`) из проектного репо (action появляется в проекте первым), прогнать `pytest tests/test_flow_transition.py tests/test_flowctl.py`, затем зеркальный коммит если правка была только в одной стороне.
- Приемка коммита параллельной волны: мерж может пройти через ЧУЖОЙ PR (sync-ветка одного агента, растущая из ветки другого, затягивает чужой коммит в main) — перед PR сверять `git log base..HEAD --name-only`: чужие файлы = ветка растла не из main, ребейзить.
- PR-маркер `[change-id]` честен только при закрытых dev-задачах в диффе: PR создания пакета (0.1) под ним FAIL по QA-контракту (impact/чеклист/кейсы/ревью еще не существуют) — маркировать `[docs]`/`[chore]`; переименование title не перегенерирует CI-event — пустой коммит для ретрига.

## Ревью-цикл исполняемого слоя

- Сабагент, упершийся в лимит итераций: правки остаются в рабочем дереве (незакоммичены), остаток работы — довести по его же отчету (список оставшихся фиксов точен), НЕ переписывать заново.
- Закрытые задачи пакета с ревью-файлами без task-id в имени (review-001…007.md) закрывать картой покрытия `code-reviews/<change>/review-mapping.json` ("файл" → ["task-id",...]) — парсер flow_check принимает карту как второй источник; НЕ переименовывать исторические ревью (append-only) и не переносить пакет между репозиториями.
- Скиллы роли — в репо фабрики (`skills/<name>/SKILL.md`), не в личной памяти: через ветку + PR (ruleset). Общий скелет флоу — один скилл (skills/factory-flow), роль-специфика — короткие секции в agents/*.md промптах; не дублировать скелет в каждом промпте.
- Ревьюер подтверждает major-находки живыми пробами (реальный CLI-вызов на fixture), не только чтением диффа — проба находит то, что чтение пропускает ([P]-флаг, недостижимая ветка кода, rename-эскейп).
- Классы дефектов, которые ловит только live-проба на границах: rename-эскейп (файл создан вне зоны, переименован внутрь — виден только через `git log --no-renames` + porcelain со старым путем), мертвый лок после crash (нужен pid в локе + проверка живости), паттерн-против-паттерн пересечение зон (рекурсивная посегментная сверка, иначе `**/test/**` vs `src/**` = ложно-отрицательное), глобальные-vs-по-scope проверки (approved-кейсы старых пакетов маскируют отсутствие кейсов текущего).
- Re-review после RETURN — append-only review-NNN+1, рецепты закрытия из предыдущего review; minor вне зоны dev-фикса (контракт) оценивать отдельно: блокируют ACCEPT или переносятся docs-долгом.
- Дублирование парсеров между скриптами слоя — координационное решение ПМ (общая чистая функция), не самовольная унификация автором одного скрипта.
- Побочный эффект фикса может быть ожидаемым поведением по ТЗ (починка пересечения паттернов сделала честным ZONE_CONFLICT то, что раньше молча ALLOW) — ревьюер оценивает по ТЗ, не автоматический RETURN.
