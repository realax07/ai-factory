# Делегации: лимиты, параллельные волны, общий worktree

Уроки многих циклов конвейера; применять при планировании фаз с несколькими
сабагентами (dev-волны, QA-автоматизация, прогоны).

## Лимит итераций: норма ~250 tool-вызовов

- Сабагент, упирающийся в лимит (TRUNCATED), почти всегда сделал работу и
  застрял на верификации/коммите. Порядок спасения: прочитать «Незакрытое» в
  отчете → прогнать гейты самому → закоммитить самому. Не перезапускать с нуля.
- **Дроби длинные фазы на мелкие делегации — один сьют / один прогон /
  один фикс-цикл на делегацию.** Волна «вся автоматизация разом» гарантированно
  обрезается; фаза, уложенная в ~50–120 вызовов, доходит до отчета целиком.
- Разбивку делать по доменам/сьютам, каждой части — свой префикс файлов
  (TC-<домен>-*) и явный список CHK/ ассертов из чеклиста.
- Прогоны тестов — отдельными делегациями со своим стендом: фоновые процессы
  сабагента умирают вместе с ним; «поднял uvicorn в прошлом шаге» к приему
  тестов не живет.

## Параллельные волны и общий worktree

- Общий worktree у параллельных волн = checkout-race: волна переключает ветку
  под ногами другой между edit и commit. Правила:
  - каждой делегации предписывать КОММИТИТЬ СРАЗУ по завершении (не «в конце
    отчета»), точечными путями (`git add <свои файлы>`);
  - зоны записи в flowctl разводить до файлов (префиксы), не до каталогов с
    пересечениями;
  - при rescue: незакоммиченные правки спасать `git diff <base> -- <paths> >
    patch` ДО любого reset — reset по unborn-ветке убивает работу;
  - ветку восстанавливать `git branch -f <name> <commit>`; потерянные коммиты
    искать в `git reflog` и `git fsck --lost-found`;
  - синхронизационные/хотфикс-ветки ветвить ТОЛЬКО от main — ветка от
    незалитой фичи протаскивает ее в main мимо QA-гейта.
- Альтернатива, когда волн >2 и правки большие: `git worktree add` на волну —
  дороже на настройку, но снимает весь класс race.

## Приемка при известном шуме зоны

- Когда волна A закончилась, а в общем дереве лежат правки волны B, flowctl
  finish волны A даст OUT_OF_ZONE по чужим файлам. Вердикт returned по этой
  причине не бракует работу: сверить дифф коммита с заявленной зоной (коммит-
  уровень, не уровень дерева) и принять решением ПМ с фиксацией в lifecycle.
- Дефекты формата артефакта (разделители таблиц, отсутствующий служебный
  раздел) чинит ПМ сам и приемлет — это формат, не содержание; отправлять
  агента на второй круг из-за `||` вместо `|` — трата итераций.
- Параллельных автоматизаторов в одной директории кейсов разводить ПРЕФИКСАМИ
  имен файлов (`TC-<домен>-*`), а не каталогами; `git add` давать точечным
  списком своих файлов — `git add <dir>` захватывает чужие untracked-файлы
  коллег, и вычищать их приходится отдельным коммитом.
- После TRUNCATED-сессии проверять состав дерева ПОЛНОСТЬЮ: в общем checkout
  к правкам автоматизатора прилипают чужие продуктовые файлы (дельта
  параллельной волны) — `git add` только по списку своей зоны, чужие правки
  возвращать в дерево, фикс сохранять.
- Регэксп-валидаторы артефактов (идентификаторы кейсов, имена ревью-файлов)
  сверять с номенклатурой ДО старта авторов: `TC-<домен>-NN` с двузначным
  номером не матчится `\d{3}`-паттерну flow_check («нет кейсов TC-*-NNN») —
  зафиксировать формат до генерации дешевле, чем переименовывать файлы с
  перекрестными ссылками после.
- Node-симуляции логики фронта (копии функций «1:1» внутри скрипта) —
  валидный приемочный гейт, но режимы до/после фикса держать ЯВНЫМ флагом
  (`--fixed`): скрипт с зашитой старой логикой после фикса продукта продолжает
  рапортовать «утечка есть», и фикс принимают за нерабочий.
