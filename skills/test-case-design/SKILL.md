# Проектирование тест-кейсов

Как из спеки получить полный трассируемый набор проверок и тест-кейсов. Основа: техники test design (эквивалентное разбиение, граничные значения, негативные классы).

## Когда применять

- Есть change-пакет OpenSpec, нужен чеклист проверок
- Есть чеклист, нужны тест-кейсы в `test-model/new/`
- Оценка полноты существующего набора кейсов

Не применять для: написания автотестов (это автоматизация), ревью (это роль ревьюера).

## Процедура

1. **Инвентаризация.** Выпиши все Requirements и Scenario из спеки change-пакета. Каждый Scenario — кандидат в пункт чеклиста.
2. **Техники дополнения.** Для каждого требования с входными данными:
   - граничные значения: пустая строка, 1 символ, максимум+1, максимум;
   - негативные классы: невалидный тип, отсутствующее поле, чужой ресурс (403), повторное действие;
   - состояние: действие на несуществующем объекте, повторная операция, операция после удаления.
   Типовые баги живут на границах, не в середине классов — поэтому п.2 обязателен, а не «по желанию».
3. **Составь чеклист.** Строки: `CHK-N | источник (Requirement + FR-N) | проверка | тип (поз/нег/гран/НФТ) | приоритет`. Приоритет наследуй от MoSCoW источника — не переизобретай.
4. **Проверь покрытие.** Каждый Requirement ≥ 1 пункта; каждый Scenario ≥ 1 пункта; у каждого пункта есть источник. Непокрытый Must — блокер набора.
5. **Разверни в тест-кейсы.** Каждый пункт → кейс `TC-<domain>-NNN`: предусловия, атомарные шаги, ожидаемый результат, конкретные тестовые данные. «Валидный пользователь» — не данные; `user: test_user_1 / Corr3ct_Pass!` — данные.
6. **Положи в `test-model/new/<change-id>/`** — по файлу на домен. Путь имеет процессный смысл: только там их увидит ревьюер.

## Ожидаемый результат

Проверяемый без знания кода: HTTP-код, тело ответа, элемент UI, состояние БД. «Работает корректно» — не ожидаемый результат, а отказ от проверки.

## Ошибки

- Кейс объединяет два пункта чеклиста — падение одного делает результат второго нечитаемым.
- Тестовые данные описаны, а не приведены — кейс невоспроизводим.
- Негативный кейс без ожидаемой ошибки — проверка превращается в «не упало, и ладно».
- Пункт без источника — трассировка разорвана, при изменении спеки кейс останется незамеченным.
