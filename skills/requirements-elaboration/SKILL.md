# Выработка требований

Как превратить разговор с Заказчиком в проверяемый документ требований. База: IEEE 830/29148, MoSCoW.

## Когда применять

- Проект или крупная фича не имеют `requirements.md`
- Требования есть, но содержат оценки без критериев («быстро», «удобно»)
- Заказчик просит «сформулировать ТЗ»

Не применять для: архитектуры и стека (это системный анализ), тест-кейсов (это QA).

## Процедура

1. **Собери интент.** Один вопрос: какую проблему решает система и для кого. Не уходи в функции, пока не зафиксирована ценность — функции без ценности порождают лишнюю разработку.
2. **Перечисли функции.** Формулировки со стороны пользователя: «пользователь может X». Глагол действия + объект + результат. Проверяй каждую: если нельзя назвать пользователя, который это заметит — это не функция, а реализация.
3. **Пронумеруй.** `FR-N` для функциональных, `NFR-N` для нефункциональных. Идентификаторы нужны трассировке: без них требование невозможно проверить на покрытие в спеке и тестах.
4. **Проверь каждое требование на качество.** Атомарное (одно «должно» на требование), однозначное (два читателя поймут одинаково), проверяемое (можно написать тест). Оценочные слова заменяй числами или объективными условиями: «быстро» → «ответ API < 500 мс при 100 RPS».
5. **Приоритизируй MoSCoW.** Must — без этого релиз бессмыслен; Should — важно, но есть обход; Could — приятно. Расставляй вместе с Заказчиком: приоритет, назначенный без него, будет оспорен на приемке.
6. **Собери НФТ.** Производительность, безопасность, доступность, совместимость. Каждое — с измеримым порогом. НФТ без числа непроверяемо и потому бесполезно.
7. **Зафиксируй ограничения и открытые вопросы.** Недоговоренности — в раздел «Открытые вопросы» с пометкой, кто решает. Скрытая недоговоренность всплывет на приемке в худшей форме.
8. **Покажи черновик Заказчику** малыми итерациями после каждого раунда. Правка требований в начале стоит минуты, на приемке — недели.

## Формат результата

Структура `requirements.md`: Общее описание → Аудитория → FR → NFR → Приоритеты → Ограничения → Открытые вопросы. Полные шаблоны и условия контракта: `contracts/artifact_contract.md`.

## Пример

**Плохо:** «Система должна быстро искать по страницам».
**Хорошо:** «FR-3: Пользователь получает результаты поиска по подстроке заголовка за < 500 мс на corpus до 10 000 страниц».

## Ошибки

- Требование-фича «на вырост» без Must-приоритета — мусор в скоупе.
- Решения реализации в ТЗ («React», «PostgreSQL») — забирают у системного анализа свободу выбора.
- Требования от лица системы («система должна хранить») вместо пользователя — проверять нечем.
