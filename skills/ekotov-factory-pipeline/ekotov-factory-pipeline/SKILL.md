## Финальный регресс — сабагент, не ПМ. regress_runner/qa_runner с узким брифом (ветка/коммит/затронутые сьюты — контекст релиза не нужен): прогон, различение бага от флака изолированным перепрогоном, FAIL → возврат dev'у. ПМ принимает артефакт (вердикт + provenance: commit hash, хвост лога), не запускает прогон сам. Порядок: ВСЕ фиксы — включая инфра/ops (ffmpeg-пин, APPROVAL-перенос, impact-проекция H5) — приземляй ДО финального прогона; любой коммит после артефакта, касающийся файлов диффа PR = REGRESS_FINAL_STALE → честный перегон (меняй порядок работ, а не спорь с воротами). Инфра-фиксы (ffmpeg-пин, H5-проекция) — ТОЖЕ до прогона: они файлы диффа, ворота их не исключают.

## Инфраструктура делегаций: worktree-гигиена ПМ. Не rm -rf каталоги /tmp, являющиеся дефолтным cwd делегированных агентов — их терминалы молча падают (exit 126, cd в несуществующий путь), раунд перезапускается целиком; сначала mkdir-заглушка, удаляй только после закрытия всех делегаций. ПМ-операции в репо с активной делегацией — через отдельный worktree: checkout/reset --hard в общем дереве сносил незапушенную работу dev дважды за сессию.

Механика реализована (J51, обе репо): `flowctl regress --change <C> --final` на worktree ветки пишет артефакт `test-model/regress/<C>/regress-final.md`, pr_validate на change-PR требует его (verdict PASS, commit == PR-head, свежесть); нумерованные `regress-<N>.md` финальными не считаются. Маппер дедуплицирует домены (tests/api+tests/web + общий tests → один pytest tests) — до дедупа дубль ронял коллекцию (механика — references/ci-pr-pitfalls.md). **Зеркало скрипта = его импорт-замкнутость**: sync flowctl.py без session_check (change_id_problem) — AttributeError на первом прогоне. Глубина (эшелоны 0–4, tier smoke, baseline, xdist, freeze, harness, release) — references/regress-tiers.md.

**Политика регресса (J54):** на change — smoke + доменный regress своего куска (карта test-model/regress-domains.json, контент у проекта); regress-final полный — пакетно перед плановым деплоем. xdist — pytest -n auto (serial-маркеры для стендов). Baseline не красит ворота (--final игнорирует); мета-файлы (code-reviews/**, test-model/regress/**, test-model/reviews/**) не инвалидируют свежесть; freeze tooling — не трогать scripts/.github после regress-final. и pr_validate (check_regress_final) = AttributeError на первом же прогоне — тяни зависимые файлы тем же коммитом и прогоняй flow_check проекта до пуша. В CI (shallow-клон, локальные worktree-пути нечитаемы) ворота regress-final требуют спец-режима — контракт в references/ci-pr-pitfalls.md, раздел «Ворота regress-final в CI» (BUG-022). Ворота regress-final вскрывают и гигиену main: pre-existing фейлы (дрейф test_flowctl, strict-heading empty-state) блокируют merge релиза — гигиену main правь той же веткой до перегонов, не спорь с воротами.

## Git-маршрут: ветка → PR → merge

Прямые push в main запрещены ruleset'ом (bypass never), оба репо; локальный merge + push = то же нарушение.

- Коммить в рабочую ветку, пуш, `gh pr create`, мерж `gh pr merge <n> --merge` только после зеленых чеков.
- Если PR BLOCKED из-за красного required check — сначала чинить источник красноты в отдельном PR (например, гигиена flow_check), потом мержить. Ретриггер пустым коммитом легитимен только когда код не менялся, а краснота — устаревший чек после метадата-фикса (title/body) или инфра-флака: один пустой коммит; снова красный — реальная проблема, докладывать. Падающий тест ретриггером не «пересматривают». Title/body чеки не перезапускают; `gh pr edit` падает с GraphQL-ошибкой (Projects classic) — через `gh api …/pulls/<N> -X PATCH`.
- **Маркер трассировки ([chore]/[change-id]/[BUG-NNN]) закладывай в title или body ПРИ СОЗДАНИИ PR** — pr_validate парсит title+body одним текстом; маркер, добавленный постфактум, требует перезапуска checks, а правка title checks не перезапускает. Маркер — ЛИТЕРАЛЬНЫЙ токен из списка, служебное содержимое внутрь скобок не заворачивай: `[change-id:<hex>]` с двоеточием не матчится MARKER_RE (в классе символов только `[a-z0-9-]`) и дает FAIL «маркер ID не найден»; change-id пакета передается СВОЕЙ скобкой — `[<change-id>]` (например `[add-ui-polish-r8]`), он же служит идентификатором check_change. Локально прогони `python3 scripts/pr_validate.py . --id "<title+body>"` до пуша.
- **CI читает title/body из снапшота события на момент старта рана (GITHUB_EVENT_PATH), не живой PR**: правка title ПОСЛЕ старта рана раном не видится — повторный красный прогон при «уже правильном» title означает, что ран стартовал до правки. Порядок: правь title (`gh api -X PATCH`) → ОДИН пустой коммит-ретриггер → новый ран видит новый title. Рабочий ретриггер после правки маркера — ОДИН пустой коммит в head-ветку (`git commit --allow-empty -m "[chore] ретриггер flow"` + push); им же дополняй правило «после двух неудачных ретриггеров — стоп».
- **`gh pr edit --title` на этом gh-билде молча падает** (rc=1 на deprecated GraphQL Projects, title НЕ меняется при видимом отсутствии ошибки в основном выводе). Правка title/PR-полей: `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -f title="..."` — REST, применяется сразу; после правки сверяй title через `gh pr view --json title`.
- **не удалять head-ветку открытого PR**: PR переходит в CLOSED без возможности reopen — содержимое приходится пересоздавать новым PR.
- **Правка title постфактум не перезапускает checks и для [chore]-кейса**: если PR уже создан с change-id маркером, а пакет заархивирован (CHANGE-ARCHIVED) — переименовывай через `gh api -X PATCH … -f title="[chore] …"` И РЕТРИГГЕРИ checks пустым коммитом; после этого сверяй rollup (`gh pr view --json statusCheckRollup`) с фактическими check-runs нового SHA — GH может показывать стейл-FAILURE от старого SHA (см. раздел CI-аудита). Локально прогоный pr_validate до пуша — дешевле, чем водить Заказчика по красным прогонам. Поля PR (`statusCheckRollup`, state, title) разбирай `gh pr view <n> --json …` + `json.loads` в python — jq-инлайн с одинарными кавычками внутри `bash -c` не парсится, цикл ожидания чеков сгорает впустую.
- Откат собственного ошибочного локального merge в main: `git reset --hard origin/main`, затем штатный merge PR'ов через `gh pr merge` — и признать ошибку Заказчику в чате.
- **Чистка superseded-веток с уникальными коммитами — через архив-тег**: `git tag -f archive/<branch> origin/<branch> && git push -f origin archive/<branch>` ТОЛЬКО ПОТОМ `git push origin --delete <branch>` — история остается восстановимой навсегда, а ветки не копятся. Слитые без уникальных коммитов — сразу удаляй (число веток в этих репо нарастает по 10+ за релиз, если не чистить в тот же день).
- **Пункт бэклога перед реализацией — ревизия на актуальность**: пункт может протухнуть (фича уже вышла в другом пакете, проблема не воспроизводится, преемник закрыл) — директива Заказчика: сначала проверка целесообразности каждого, потом «давай». Проверка фактом (git log по теме, замер, ls), вердикты «закрыто-неактуально / реализовано / актуален» в бэклог — не реализовывать протухший пункт по инерции.
- **Пуш в ветку УЖЕ смерженного PR теряется молча** (PR закрыт, merge резолвился): перед follow-up-коммитом проверяй `gh pr view <n> --json state`; опоздавший коммит переноси cherry-pick'ом на новую ветку от origin/main и веди отдельным PR. Sync-коммит ядра (зеркала скриптов) после переноса сверяй фактом в origin/main (`git show origin/main:<file> | grep <маркер>`) — sync, легший не на ту ветку, оставляет в main старую версию скрипта и красный CI на чужом PR. То же до ветвления: sync, закоммиченный на служебной ветке, в main НЕ попадает — каждая новая ветка от main получает устаревшее ядро и краснеет на воротах; перед созданием очередной ветки убедись, что недавние sync-коммиты дошли до origin/main (`git log origin/main -- <file>`), найдя несинхрон — cherry-pick sync-коммита в свою ветку первым, а не дублируй правку.
- **Сабагент может закоммитить отчет/фикс прямо в ЛОКАЛЬНЫЙ main** (правило «только через PR» в ТЗ игнорируется; push ruleset отвергнет — коммит висит непушенным на локальном main, а origin/main отстает). В ТЗ каждой делегации явно предписывай: «коммитить только в свою ветку, main не трогать» — общей дисциплины нет. Если коммит уже лег: не переписывай и не реbase'ь — забери его в PR-маршрут веткой от этого же SHA (`git branch pipeline/<slug> <sha>` + push + PR + merge), дереву, авторству и вердикту ревью это не вредит.
- **Номера задач в title/body PR = задания для J10-парсера**, но требование только по ЗАКРЫТЫМ DEV-задачам (правки pr-validate-dev-only + 0518e06): `§N.N`, «шаг N.N» и диапазоны после «шаги» вырезаются до матчинга; [ops]/[docs]-задачи и незакрытые исключаются — парсер сверяется с `closed_dev_tasks` tasks.md. Для dev-задач требование честное — покрыть review-файлом до пула; контекстные ссылки словами остаются хорошим тоном.
- **J10-ревью по задачам: имя файла `review-001-<task>.md`** — `approved_review_tasks` матчит только `review-NNN-<task>.md` / `review-<task>-NNN.md`; голый `review-001.md` задачи не покрывает. Проверка покрытия: `python3 -c "import sys; sys.path.insert(0,'scripts'); from flow_check import approved_review_tasks; from pathlib import Path; print(sorted(approved_review_tasks(Path('.'), '<change-id>')))"` — сверяй с задачами диффа до пула.
- **Типы задач в tasks.md: [ops]/[docs]/[design] исключают из J10** (решения Заказчика: 2026-10-03 ai-factory 0518e06; [design] 2026-10-05 ekotov-wiki): боевые/деплой-задачи (`[ops]`) — артефакт = протокол приемки Заказчика (дата, что проверено, дословное «ок») в `code-reviews/<change-id>/acceptance-protocol-*.md`; доковые (`[docs]`) — верификация фактов с ссылкой на источник; дизайн-задачи (`[design]`) — мокапы ui_designer в `design/`, приемка = утверждение мокапа Заказчиком (review-файл не нужен). Регэксп матчит маркер после `[S]`/`[P]`: `- [x] 2.3 [S] [ops] ...`. Без маркера закрытая задача требует review — включая QA-задачи вне раздела 6.x. Дизайн-фаза ОПЦИОНАЛЬНА: в пакетах без UI-дельты задач `[design]` просто не пишут — ворота их не требуют; наличие/отсутствие решает СА при проработке.
- **design_task — отдельное действие Флоу 1 (решение Заказчика 2026-10-05-design-task-flow1)**: Stage `design_task` (роль `ui_designer`, зона `design/**`) в STAGE_TABLE рядом с dev_task, check_design_task = те же предшественники (requirements approved + arch review + задача существует) без параллель-блока. НЕ диспатчь ui_designer как dev_task (WRONG_ROLE) и как голый delegate_task — через delegate_gate как остальные роли; идиом для design_task в ТЗ ревьюеру не нужен, ревью визуала — design_validator (зона test-model/reviews/*/review-*-design.md). Реализация в обоих репо (эволюция ядра — в эталон фабрики через его PR-процесс).
- **SELF_REVIEW запрещен (ai-factory 0518e06)**: review-файл пишется только независимым code_reviewer на чужой дифф. ПМ/диспетчер не создает review-файлы никогда — даже на работу своих сабагентов, даже под красным CI (код нарушения SELF_REVIEW в контракте). Красный CI из-за непокрытых задач = диспатч независимого ревьюера или протокол приемки, не самописный approve. Прецедент: self-review 005–007 на add-containerization удалены, заменены протоколом приемки.

### Отладка красного CI: иди по логу джобы, не гадай

Логи конкретной джобы: `gh api repos/<owner>/<repo>/actions/jobs/<job_id>/logs` (прямой REST — работает даже когда `gh run view --log-failed` отвечает «run in progress, logs unavailable»). Схема разбора: (1) какой step упал — `gh run view <id>`; (2) текст ошибки из лога джобы; (3) фикс — коммит с причиной из лога в сообщении; (4) ретриггер одним пустым коммитом. Для e2e/compose-сьюта добавляй step «дамп логов контейнеров при падении» (`if: failure()`) заранее — без него каждая итерация отладки теряет прогон: контейнеры teardown'ятся до чтения логов.

Глубже по openspec-дельтам и archive-механике: `references/openspec.md` — читай его ПЕРЕД любым редактированием spec.md, даже точечным ПМ-при архивации: строгий валидатор валит правила, которые там уже записаны (требования >500 символов — сплит с ПЕРЕРАСПРЕДЕЛЕНИЕМ существующих сценариев, никакие новые не создавать: покрытие-тесты ассертят точное число; каждый requirement ≥1 Scenario + MUST; новая capability — шапки `## Purpose` + `## Requirements`); патологии CI этих репо (openspec@latest strict-регрессия, gh pr edit GraphQL, no-checks, Docker Hub rate-limit на pull'ах образов) — `references/ci-red-diagnosis.md`.

Выкатка матричного прода (deploy.sh/тома/uid/compose-ручные операции): `references/prod-deploy-matrix.md` — читать перед передачей Заказчику команд боевого деплоя.
Релизный протокол web-регресса ekotov-wiki (env-протокол, чистая БД, симптом→причина): `references/web-regress-protocol.md`.

## Правила flow_control в проектах

`factory_init.py` устанавливает в проект полный набор: ядро (flow_state, flow_transition, session_check, gate_runner, flowctl, flow_mode, role_zone_policy), контракт `flow_control_contract.md`, скилл `factory-flow`, каталоги `decisions/` и `releases/`.

- **factory_init не ретроактивен**: новые устанавливаемые артефакты (agents/*.md промпты, AGENTS.md, delegate_gate/watchdog) появляются в проекте только при повторном запуске/ручной синхронизации — старые проекты (инициализированные до появления слоя) живут без них, и это незаметно, пока не спросишь «а где промпты?». После расширения списка установки фабрики синхронизируй существующие проекты (cp + закоммитить). Проверяй установку `ls scripts/`, а не по памяти: заявленная установка без фактического файла всплывает denial'ом на первом боевом prepare.
- **Архивация change-пакета осиротила I3-покрытие маршрутов** (покрытие жило в дельтах заархивированного пакета): каноничный flow_check держит корневое покрытие (sdd.md + openspec/specs/**) ВСЕГДА, дельты активных пакетов добавляются сверху — при синхронизации ядра убедись, что проектная копия несет этот фикс, иначе после каждой архивации flow_check краснеет на всех немодифицированных маршрутах.
- **openspec archive валидирует MODIFIED как полную замену**: MODIFIED-дельта, опустившая сценарии, которые есть в текущей спеке, валит `validate --strict` («omits scenario(s)») — скопируй пропущенные сценарии в MODIFIED-блок дословно, потом archive. После архивации у новой master-спеки TBD-Purpose при strict считается фейлом — напиши настоящий Purpose.
- **Финальный PR после archive: маркер change-id валится CHANGE-ARCHIVED** — pr_validate требует [chore]-маркер в title для пост-релизного PR по заархивированному пакету. Последовательность: переименуй title через `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -f title="[chore] …"` (gh pr edit молча падает — см. выше), затем ретриггер checks одним пустым коммитом (правка title сама checks не перезапускает). Прогоняй pr_validate-исход локально до пуша, чтобы не водить Заказчика по красным прогонам.
- **AGENTS.md и agents/README.md — защищенные пути конвейера**: их изменение в проектном репо pm_bounds ловит без `[pipeline]`-маркера (первый живой прогон: установка agents-слоя была поймана и легализована amend'ом с маркером). Правки конвейера в проекте — коммит с `[pipeline]`.
- Режим: `flow_mode.py show|set shadow|enforcing`. Enforcing блокирует DENY/UNKNOWN на маршруте flowctl.
- required checks синхронизированы с именем job в flow.yml: если job переименован (например flow → test-flow-control), ruleset с чеком старого имени делает ВСЕ PR навсегда BLOCKED — имя job менять синхронно с required checks (и наоборот).
- Локальный PASS ≠ защита main: внешний факт — только через Rulesets API `GET /repos/{repo}/rules/branches/{branch}` (legacy `/branches/{branch}/protection` дает 404 для rulesets, даже при работающей защите). Токену машины достаточно права write.
- Решения Заказчика фиксировать записью в `decisions/<дата>-<slug>.md` (decision-record/1: scope, action, SHA, source-цитата), approval_ref = decision_id. Формулировка — «решение зафиксировано», не «личность подтверждена».

## Сквозной цикл flowctl (проверено живым прогоном, Флоу 4 enforcing)

Командная цепочка от решения до accepted. Все вызовы — из корня проекта; `--registry` и `--state` ОДИНАКОВЫЕ во всех вызовах цикла.

```bash
# 0. Решение Заказчика — файл releases/<дата>-<slug>.md (decision-record/1), коммит.
# 1. prepare: роль/зона из политики, approval_ref = decision_id
python3 scripts/flowctl.py prepare --repo . --project <proj> --flow 4 --change chore \
  --task <N> --action chore_task --role dev --path "<зона>/**" \
  --approval-ref <decision_id> --owner-pm pm-main
# 2. run: --state ТОТ ЖЕ файл, куда писал prepare (дефолт ~/.hermes/state/flowctl_state.json);
#    другой путь → MISSING_INPUT «нет записи prepare» хоть запись и существует.
python3 scripts/flowctl.py run --correlation-id <id> --registry <registry> --state ~/.hermes/state/flowctl_state.json
# 3. finish: report обязателен, gates обязательные из политики; --pr-id если PR есть,
#    иначе pr_validate = SKIPPED и overall ≠ PASS (returned, не accepted — честно).
python3 scripts/flowctl.py finish --correlation-id <id> --report /tmp/report.md \
  --state ~/.hermes/state/flowctl_state.json --registry <registry> \
  --gate-scope pre_merge --pm-mode commits --pm-commits . [--pr-id <N>]
# 4. merge через PR (gh pr merge), не прямым push.
```

Подводные камни цикла:

- **--pm-mode обязателен на finish**: без явного `--pm-mode commits --pm-commits <sha>` обязательный pm_bounds_check дает ERROR «режим не задан… конфигурационная ошибка запускающего» и вердикт blocked — это не поломка гейта, а пропуск флага; перезапусти finish с флагами.
- **flowctl/gate импортируют role_zone_policy из каталога СВОЕГО скрипта (фабрика), не из проекта**: зона, расширенная только в проектной копии политики (например `deploy/**` для dev), проходит понимание в чате, но дает ZONE_POLICY_MISMATCH на finish — при готовящемся расширении зоны первым делом синхронизируй фабричную копию (ее PR-процессом), потом диспатчи.
- **flow_check требует аргумент репо**: `python3 scripts/flow_check.py .` — голый вызов без пути печатает usage и выходит с exit 2; не путай с реальным FAIL.
- **change-id для Флоу 4 — ровно `chore`** (regex `^chore$`, не `chore-<slug>`); для Флоу 1 — kebab-case. Неверный ID → AMBIGUOUS_STATE до всего остального.
- **correlation-id определяет имя ветки worktree: деривация берет первые 8 символов** — два id с общим префиксом (`<slug>-A`, `<slug>-B`) получают ОДНУ ветку, второй prepare деградирует в общее дерево (WARN WORKTREE_UNAVAILABLE) или падает на занятой ветке. Бери id, различимые в первых 8 символах; исправление деривации (полный id или хэш-суффикс) — отдельная доработка flowctl.
- **--owner-pm обязателен** для reserve, иначе MISSING_INPUT после уже пройденного ALLOW — потерянный цикл.
- **run не принимает произвольный --state**: prepare пишет в дефолтный путь, run обязан читать оттуда же. Подсунул /tmp — «нет записи prepare» при живой записи.
- **Живая проверка блокировок (прогоны-отказы безопасны):** ZONE_OUTSIDE_POLICY (чужой --path), DENY WRONG_ROLE (чужая роль), MISSING_INPUT (run без prepare) — каждый отказ не создает side effects; используй как smoke-тест enforcing после изменений политики. Отказ prepare печатает полный decision-record: строка `record: {…}` (JSON с blocking_reasons/details) или `reservation: {…}` (при ZONE_CONFLICT) — парси ее для точной причины, `note:` в шапке сокращен; exit code 0 при DENY не означает ALLOW. `--dry-run` prepare НЕ резервирует зону: ALLOW от dry-run ≠ пройдет реальный start (ZONE_CONFLICT от чужого резерва ловится только им) — dry-run годится для проверки approval_ref/роли, не зоны.

## J10: исторические ревью без task-id в имени

Имена `review-001.md` (без номера задачи) flow_check не матчит — задача числится «без ревью», хотя ревью было. Task-часть имени парсится как ЧИСЛОВЫЕ идентификаторы: словесная часть (`review-004-wave3.md` → «3») покрывает не ту задачу — называй wave-ревью перечислением (`review-004-3.1-3.2-3.3-3.4.md`) и сверяй покрытие списком до коммита. Фикс без переименования истории: `code-reviews/<change-id>/review-mapping.json` — `{"review-002.md": ["0.1","0.2",…], …}`; flow_check читает его НАТИВНО (второй источник привязки, приоритет у имен файлов), и мета Reviewer-Delegation обязательна и для mapping-файлов. Вноси mapping ЗАРАНЕЕ для объединяющих ревью, даже с task-id в имени: `review-001-1.2.md`, покрывающий 1.2/1.3/1.4, матчит task-first регэкспом только ПЕРВУЮ задачу (1.2) — 1.3/1.4 остаются «без ревью», пока их нет в mapping. До коммита mapping прогони `python3 scripts/flow_check.py .` — он зеленеет сразу, ревью-файл править не нужно.

## J10: ревьюер-сабагент не знает свой delegation id — ПМ вписывает мету сам

Review-файл от сабагента приходит БЕЗ `Reviewer-Delegation:` — сабагент не видит свой платформенный id. Сразу после завершения ревью вписывай `Reviewer-Delegation: deleg_<id>` (id из реестра делегаций этого ревью) в шапку файла ПМ-проходом, до flow_check/чекбоксов.

## J10: QA-раннеры вне 6.x — чекбоксы держать открытыми до финального этапа

`closed_dev_tasks` исключает только раздел 6.x и маркеры `[ops]/[docs]/[design]`. QA-наборы вне 6.x (этапы с артефактом REPORT, а не review-файл) при закрытии `[x]` дают FAIL «закрытые dev-задачи без review» — не борись с воротами и не пиши self-review: держи чекбоксы открытыми до финального этапа/протокола приемки и закрывай единым коммитом после него. Контур артефактов (чеклист/кейсы/impact) — `references/qa-artifact-gate.md`.

## J10: формат approve-файла: мета + заголовок секции Вердикт

`approved_review_tasks` засчитывает approve только при ДВУХ вещах в файле:

- строка `Reviewer-Delegation: deleg_<id>` (REVIEWER_META_RE толерантен к markdown-жирности в любом порядке: `**Reviewer-Delegation:** deleg_...` и `**Reviewer-Delegation: deleg_...**` матчатся паттерном `Reviewer-Delegation[^A-Za-z0-9]{0,6}(deleg[-_][A-Za-z0-9]+)`). Файл без меты = задачи «без ревью». Ревьюер-сабагент не знает свой id — вписывай сам из `async_delegations` (реестр = истина; `deleg_UNKNOWN` заглушки не проходит).
- вердикт на строке, начинающейся с заголовка `#{1,4} Вердикт:` (VERDICT_LINE_RE матчит только заголовочные строки; жирный `**Вердикт: approve.**` без `##` парсер молча не видит — parse_verdict возвращает None, flow_check краснеет «задача без ревью» при живом approve и мете). Слово вердикта — ЛАТИНИЦЕЙ `approve`/`return`: VERDICT_APPROVE_RE знает `approve|approved|одобрен\w*|одобрить`, VERDICT_RETURN_RE — только `return|доработк\w*`; «ВЕРНУТЬ»/«ВОЗВРАТИТЬ» по-русски не матчится НИ return, НИ approve. parse_verdict берет ПЕРВЫЙ заголовок Вердикт, распознанный как approve или return: нераспознанный заголовок молча ПРОПУСКАЕТСЯ, а не обнуляет ревью — файл с секционными вердиктами (ревью волны: вердикт на каждый PR) парсится по СЛЕДУЮЩЕЙ секции, т.е. файл с главной секцией return превращается в approve. Отсюда: (1) ТЗ ревьюеру предписывай ровно ОДИН машинный заголовок `## Вердикт: одобрить` или `## Вердикт: return` — находки перечисляй телом секции, не заголовками. НЕ рекомендуй `## Вердикт: APPROVE` заглавными: pr_validate (контракт 5) знает только слово «одобрить» и не знает латиницы — файл с APPROVE проходит flow_check, но валит финальный PR красным чеком. Промежуточные раунды машинным вердиктом НЕ оформляй — пиши «## Итог раунда N: return (устранено)»: устаревший заголовок «Вердикт:» с return, стоящий выше финального approve, засчитывается вместо него; (2) перед коммитом review-файла сверяй `parse_verdict` с фактическим решением ревьюера; (3) устаревший вердикт не закрывает задачу — после фикс-диффа по return-находке диспатчь независимое ре-ревью коротким кругом (ТЗ требует мутационную проверку фикса: снять фикс — тест краснеет, вернуть — зеленеет), а mapping и чекбоксы закрывай только по финальному approve. Покрытие нескольких задач объединяющим wave-ревью — через `review-mapping.json` (раздел выше): имя без task-id матчится как «задача-строка» и реальных задач не покрывает. Содержание вердикта правкой заголовка не меняется — после правки сверяй `python3 scripts/flow_check.py .` до коммита. Подозрение на «approve есть, а машина его не видит» проверяй за один прогон: `from flow_check import parse_verdict; parse_verdict(open(<файл>).read())` — None значит regex/формат, не логика покрытия.

Self-review файлы (003/004-класс) — в `archive/` подкаталог пакета, не удалять (история), они не считаются.

## Делегации через машину: delegate_gate.py, не прямой delegate_task

Каждая делегация задачи change-пакета — через `python3 scripts/delegate_gate.py` (start → диспатч сабагента → finish), не через голый delegate_task. **Инцидент 2026-10-04 (решение Заказчика, decision `2026-10-04-microservices-full-dev-tasks`)**: 8 делегаций ЭТАПА B add-microservices-full ушли мимо ворот — вотчдог крона */5 ловит это и шлет BYPASS-напоминание в Telegram main-сессии; для dev_task пакета approval_ref = `2026-10-04-microservices-full-dev-tasks`, роль ровно `dev` (не devops — WRONG_ROLE, даже если задача в tasks.md помечена «Devops»), зоны — фактические файлы задачи в пределах зон роли. Машина (enforcing) ловит DENY/ZONE_CONFLICT/SELF_REVIEW на входе; прямой диспатч = обход ворот независимо от качества результата — фиксируется в статус-докладе как нарушение.

Это правило действует и когда ТЗ задачи не упоминает ворота: «работа по ТЗ» не легализует обход — платформенный вотчдог (крон */5) сверяет `async_delegations` с flowctl-prepare и регистрирует КАЖДУЮ голую делегацию как BYPASS-инцидент, и Заказчик видит их счетчиком, а не объяснениями. Прежде чем диспатчить, убедись, что для approve_ref существует maшиночитаемое решение (decisions-файл с ```decision-record-блоком); если нет — запроси его у Заказчика ДО делегации, не после. Инцидент задним числом не «догоняют» гейтом — фиксируют как нарушение и дальше работают через ворота.

**«Служебных» диспатчей вне ворот не существует**: ревьюеры и QA-агенты идут через delegate_gate так же, как dev — реестр видит диспатч независимо от роли, и после настройки каналов доставки каждый новый обход доставляется Заказчику как свежий BYPASS (сигнал должен быть редким и настоящим, доверие к каналу сгорает быстрее, чем от самих обходов). Типовая ошибка — считать ревью или фикс-цикл «срочным служебным вызовом» и диспатчить его голым delegate_task, пока dev-цикл уже идет через ворота: именно в момент спешки обход и происходит. Если действия (`code_review`) нет в покрытии текущего decision — запроси дополнение decision-record ДО диспатча.

- **start**: `delegate_gate.py start --project wiki --flow N --change <id> --task <N> --action <action> --role <role> --path "<зона>/**" --approval-ref <decision_id>` → печатает `GATE: ALLOW — correlation_id=<id>`; этот id кладется в ТЗ сабагента. Сразу после ALLOW отметь старт: `python3 scripts/flowctl.py run --correlation-id <id> --registry <registry> --state ~/.hermes/state/flowctl_state.json`, затем диспатч; без run сессия остается `reserved` и не видна анти-BYPASS-сверке. Повторный run на уже-started записи отвечает `started: False` при status=running — это НЕ ошибка и не повод перезапускать цикл. DENY (prepared: False, ZONE_CONFLICT, MISSING_INPUT) = делегация НЕ создается; чини причину (reconcile stale-резерва, decision-record), а не обходи.
- **--action должен быть из графа флоу** (не придуманное слово): «implement» дает UNKNOWN со списком допустимых; старт пакета SA = `create_change`, dev-задача = `dev_task`, дизайн-задача = `design_task` (ui_designer), дизайн-валидация = `design_validation` (design_validator), Флоу 4 = `chore_task`. Машина резервирует ПАРЫ действие+роль: подстановка чужого действия под роль = DENY WRONG_ROLE. Если у зонной роли нет СВОЕГО действия в графе — это пробел ядра: эскалируй Заказчику развилку (расширить ядро [pipeline]-коммитом в оба репо vs идти в составе другой задачи) с DENY-фактами всех подстановок, не подбирай обход.
- **Зона ревью-делегации — review-файл, не дифф**: политика роли `code_reviewer` покрывает только `code-reviews/*/review-*.md`; запрос `--path "frontend/**"` на действие code_review дает ZONE_OUTSIDE_POLICY (ревьюер не пишет в продуктовый код, дифф он читает read-only). Запрашивай путь целевого review-файла. Политика роли может фиксировать ФОРМАТ ИМЕНИ файла (у design_validator — литеральный шаблон `review-NNN-design.md`): re-ревью файлу давай каноничное имя по шаблону (`review-005-design.md`), а не содержательное (`review-005-design-fix.md` — вне шаблона = DENY ZONE_OUTSIDE_POLICY и потерянный цикл); различай циклы в заголовке и теле отчета, не в имени файла.
- **Разрешенные действие и роль для задачи определяй машиной, не меткой в tasks.md**: `python3 scripts/flow_transition.py next --repo . --project <proj> --flow 1 --change <id>` печатает кандидатов вида `dev_task (dev) task=N.N` — это sanctioned-пара. Флоу 1 не имеет ops-действия: инфраструктурные задачи (образы/compose/deploy), помеченные в tasks.md как «Devops», проходят как `dev_task` с ролью `dev` — prepare с `--role devops` дает DENY WRONG_ROLE. Зона у роли dev — продуктовые каталоги политики (services/**, tests/** и т.д.); пути deploy/** или отдельного файла вне ее требуют [pipeline]-расширения политики, не подбора роли. Расширение зоны — развилка для Заказчика: опиши DENY-факты (оба варианта: роль без действия, действие без зоны) и предложи варианты, зафиксируй его выбор в [pipeline]-коммите с дословной цитатой (policy + таблица agents/README синхронно).
- **--path сверяется с политикой роли как glob**: если в политике путь-файл (`scripts/export_openapi*.py`), запрос каталога (`scripts`) не сузит — ZONE_OUTSIDE_POLICY; запрашивай точным путем. Гранулярность звезд тоже из политики: `dir/*` (уровень каталога) ≠ `dir/**` (рекурсивно) — запрос `test-model/bugs/**` при политике `test-model/bugs/*` = DENY ZONE_OUTSIDE_POLICY и потерянный цикл. При DENY читай `zone_violations`/`note:` в ответе prepare и копируй паттерн ДОСЛОВНО из `scripts/role_zone_policy.py`, не угадывай синтаксис. **Флаг зоны — только повторяемый `--path` (флага `--zones` нет), и паттерны бери из политики САМИМ ИХ ВИДОМ**: литеральный путь пакета (`openspec/changes/<id>/**`) при политике из пер-файловых глобов (`openspec/changes/*/tasks.md`, `…/specs/**`) дает ZONE_OUTSIDE_POLICY — CLI может только СУЗИТЬ политику, поэтому передавай сами паттерны политики (список: `python3 -c "import sys; sys.path.insert(0,'scripts'); from role_zone_policy import allowed_zones_for; print(*allowed_zones_for('sa'), sep='\n')"`), каждый отдельным `--path`. Политика роли хранится в проекте (`scripts/role_zone_policy.py`): шаблон фабрики (`src/**`) не соответствует реальной структуре проекта (backend/**, frontend/**, contracts/**) — расширение политики это `[pipeline]`-коммит (защищенный путь agents/README + policy), синхронно правь таблицу в agents/README.md. Расширение Заказчик может требовать В ОБЕИХ репах (дословно: «обе репы учти») — тогда эталон фабрики получает ту же аддитивную правку своим PR-процессом, а не копированием мимо него. Зонные роли вне кода уже в политике: ui_designer = design/**, design_validator = test-model/reviews/*/review-*-design.md — действия для них ищи в STAGE_TABLE flow_transition (design_task и design_validation), не изобретай dev_task с чужой ролью (WRONG_ROLE) и не подставляй действие другой роли: машина резервирует пары действие+роль (code_review→code_reviewer, qa_automation→qa_automation). Если у зоны роли действия в графе НЕТ — это пробел ядра: эскалируй Заказчику развилку (расширить ядро [pipeline]-коммитом в оба репо vs идти в составе другой задачи) с DENY-фактами всех подстановок, не подбирай обход.
- **DUPLICATE_PAYLOAD на повторном prepare** с тем же correlation_id (после DENY другого вида или оборванного цикла) — не бага: возьми новый correlation_id с суффиксом (`p12-dev-21-retry`), payload не меняй.
- **Сессия в статусе `finished` ТОЖЕ держит зону и валит новый prepare по ZONE_CONFLICT**: `flowctl reconcile --delegation-id <id>` переводит finished → stale, после чего prepare проходит — прогони reconcile, прежде чем планировать админ-клоуз руками. Зоны конфликтующих задач при параллельных волнах разводи ЗАРАНЕЕ в ТЗ: файл, заявленный в границах двух задач (task-form.js у fastline-волны и combobox-волны), отдай одной — пересечение паттернов = ZONE_CONFLICT на втором prepare.
- **approval_ref проходит машину только при машиночитаемом блоке в decisions-файле**: fenced ` ```decision-record ` JSON (schema decision-record/1), `scope` — словарь `{"project", "change_id", "phase"}`, где `project` — скаляр machine-имени проекта (`wiki`), НЕ полный путь (полный путь = DENY HUMAN_APPROVAL_REQUIRED «относится к другому scope» — фикс схемы, [pipeline]-коммит decisions-файла, суть решения не меняется), строка-описание вместо словаря = DENY «не словарь»; `phase` в scope = НОМЕР ФЛОУ действия (create_change/dev_task Флоу 1 → `"phase": 1`; phase=0 на Флоу 1 = DENY «относится к другому scope» — читай details, правь фазу, суть решения не меняется); `decision_id` совпадает с scope. **Машина ищет запись по ИМЕНИ ФАЙЛА** — `decisions/<decision_id>.md`: два решения в одном файле под разными decision_id не читаются (второй id дает «записи нет в журнале решений») — каждое самостоятельное решение (в т.ч. отдельный change_id того же запуска) держи в отдельном файле. По `action` машина проверяет валидность решения пакета, а не строгое равенство строк — живой прогон: decision-record dev-задач пакета (action=dev_task) проходил и для его code_review-диспатчей; но рассчитывать на кросс-действие нельзя — при DENY по action дополняй decision-record отдельным блоком, не подбирай обход. Обычный человекочитаемый markdown машина не читает; отказ prepare печатает полный decision-record в строке `record:` — парси ее, `note:` в шапке сокращен; каждый DENY честный, чинить поля, а не искать обход.
- **ZONE_CONFLICT от зомби в реестре сессий**: сессия в `active_sessions.json` в статусе needs_attention держит свою зону и блокирует новый prepare; `flowctl reconcile --delegation-id` ищет только async_delegations и для реестр-зомби возвращает пусто. Рабочий путь: убедиться, что делегация фактические завершена, закрыть админски (status/lifecycle → completed в реестре) с журнальной записью перехода в lifecycle.history — не удалять запись и не ослаблять mode.
- **Зомби живут в ДВУХ хранилищах** — закрывать СИНХРОННО: реестр `active_sessions.json` и `flowctl_state.json` (runs). Синк из state в реестр происходит при следующем gate-старте: если закрыть только реестр, тот же prepare перезапишет его обратно `running` из state — двойная работа. После админ-клоза проверяй ОБА файла на не-completed статусы этой делегации. В записи реестра закрывай ОБА поля: верхнеуровневый `status` И `lifecycle.state` (с append в `lifecycle.history`) — записал только lifecycle.state, `status` остается `running` и держит зону; после записи перечитай файл и убедись, что закрытые id больше не в списке не-completed.
- **НЕудачный gate-start оставляет осиротевшую running-запись под ТВОИМ deleg-id — повторный start с ДРУГИМ составом --path ловит ZONE_CONFLICT с самим собой**: prepare с DENY по решению печатает «reservation не создавались», но попытка старта (особенно до готового decisions-файла) может оставить `running`-запись в реестре с частичной зоной; твой ретрай с полной зоной тогда падает ZONE_CONFLICT. Диагноз и лечение: перед ретраем старта выведи не-completed записи реестра (`python3 -c "... for s in d['sessions'] if s['status'] != 'completed'"` по active_sessions.json) — свою свежую запись закрывай админски синхронно в ОБЕИХ хранилищах (см. выше), затем повторяй start; работу ты не вел, запись чисто административная.
- **Вотчдог принимает gated-статусы только `running/returned/finished/completed`** — статус `needs_attention` из flowctl_state для gated-делегации = ложный BYPASS (deleg есть в gated_map, но flowctl-статус вне списка). После админ-клоза/финиша прогони watchdog руками ДВАЖДЫ (1-й может чинить, 2-й обязан exit 0) и очисти `pm_instruction.txt`, если он остался от прогона с устаревшим списком — иначе relay доставит Заказчику неактуальную инструкцию.
- **Схема flowctl_state.json: `runs` — словарь keyed по correlation_id, не список** — админ-клоуз скриптом пиши `d['runs'][<correlation_id>]`; итерация списком (`for run in d.get('runs', [])`) дает строки-ключи и AttributeError посреди правки (половина хранилищ уже поправлена — перепроверяй оба файла после скрипта клоза).
- **Bypass-делегация оставляет утечку, которая блокирует СЛЕДУЮЩУЮ легальную делегацию**: если gate-сессия была запущена (run) и брошена без finish, она висит `running` и резервирует зону; новый prepare на пересекающийся паттерн (например `services` vs `services/search/**`) дает ZONE_CONFLICT с деталью «паттерн пересекается». Это вторая цена обхода ворот, помимо BYPASS-инцидента. Перед prepare проверяй `flowctl status`/active_sessions на running-сессии в зоне; осиротевшую закрывай админски (lifecycle → completed + запись в history) только убедившись, что работа фактически завершена (git/тесты), иначе сессия честно держит зону от параллельного писателя.
- **finish**: `delegate_gate.py finish --correlation-id <id> --report <path> --flow N` — без PASS-вердикта сессия висит running в `flowctl status` (видимый долг). Сессия-сирота (делегация была, prepare-записи нет) = нарушение, видимое в status. `--report` — ПУТЬ к существующему файлу (не текст); файла нет на момент finish → вердикт blocked «агентский отчет не найден» — цикл перезапускается тем же finish'ем с готовым файлом; файл вне зоны делегации дает дефект OUT_OF_ZONE в вердикте — отчет должен писать сам сабагент в своей зоне, а ПМ ссылаться на него; сабагент отчитался только текстом ответа — ПМ фиксирует его факты в файл-отчет до finish (это протокол приемки, не SELF_REVIEW: review-файлы ПМ не пишет никогда). finish с FAIL-дефектами сессию НЕ закрывает (она остается running, зона держится) — закрывающий шаг цикла всегда админ-клоуз обоих хранилищ.
- **ПМ-коммит приемки — ПОСЛЕ gate finish, не во время живой сессии**: pm_bounds_check на finish видит все коммиты в диффе сессии; ops-коммит приемки ПМ на той же ветке, пока сессия дева/QA еще running, валит pm_bounds в FAIL и портит вердикт finish'а. Порядок приемки задачи: сабагент коммитит → gate finish → админ-клоуз зоны → ПМ-коммит ([x] в tasks.md + релизный журнал). [x] при этом все равно ставится только после коммита approve-файла (см. ниже).
- **Зоны резервируются и после закрытия задачи**: делегация в статусе `finished`/`needs_attention` продолжает держать свою зону — новый prepare на ту же зону дает ZONE_CONFLICT, а `flowctl reconcile` по такой записи возвращает пусто (ищет только в async_delegations). Закрывай реестровую запись админски (status/lifecycle → completed в `active_sessions.json` с журнальной записью в lifecycle.history), убедившись, что задача фактически завершена и принята. Автоосвобождение зон на finished — открытой вопрос J37.
- **GATED_MAP: платформенный id gate-делегации не совпадает с flowctl-id** — gate start генерирует свой delegation-id ДО диспатча, платформенный появляется только в ответе delegate_task; без маппинга вотчдог считает легитимную делегацию обходом и репортит ложный STALE каждые 5 минут. Вписывай пару platform_id → flowctl-delegation_id (формат `deleg-<hex>`, НЕ correlation_id) в словарь `"map"` ВНУТРИ `~/.hermes/state/delegate_gate_gated_map.json` В ТОМ ЖЕ ХОДЕ, что и диспатч. Значение копируй из ПОЛЯ `delegation_id` записи flowctl (`runs[<correlation_id>]['delegation_id']`), не из ключа-корреляции: оба начинаются с `deleg-` и визуально неразличимы — correlation в значении дает тихий нематч и ложный BYPASS Заказчику; при таком репорте первым делом сравни `d['map'][<platform_id>]` с полем `delegation_id` run'а, не с ключом. — записи в корень JSON вотчдог НЕ видит (живой инцидент 2026-10-05: две корректно gated-делегации дали три ложных BYPASS/STALE-доставки Заказчику кроном */5, пока формат не исправлен); после записи проверяй чтением назад `id in d["map"]`, не фактом записи файла — вотчдог тикает */5, и map, записанный после завершения делегации или в чужой уровень JSON, дает ложный STALE/BYPASS, который уходит Заказчику и релеем ПМ (реальный ложный отчет при отсрочке маппинга). После записи делегация эквивалентна gated для вотчдога. Проверка лечения: два ручных прогона watchdog подряд (1-й чистит дельту, 2-й обязан exit 0) + удаление устаревшего `pm_instruction.txt`, иначе релей */2 разнесет старую инструкцию.
- **В зону резерва (--path на start) включай и путь отчет-файла**, не только код: OUT_OF_ZONE на finish ловит ЛЮБЫЕ изменившиеся пути сессии — отчет сабагента вне reserve валит вердикт. Заодно вычищай untracked-артефакты верификации (стендовые бэкапы, tmp-дампы, файлы, созданные контейнерным uid) до finish — они тоже «измененные пути».
- **Zone-check считает ВСЕ измененные пути base..HEAD + незакоммиченные, включая ЧУЖИХ акторов**: свой [pipeline]-артефакт (релизный журнал), незакоммиченный на момент start, или коммит, сдвинувший HEAD после старта сессии, попадает в дифф сессии и дает OUT_OF_ZONE на finish. Порядок: собственные коммиты ПМ — ДО gate start; HEAD во время живой сессии не двигать. Туда же попадают правки ПМ ВНУТРИ зарезервированной зоны во время живой сессии (review-mapping.json, мета-патч review-файла) — незакоммиченные пути в диффе сессии дают OUT_OF_ZONE на finish: мета/mapping правь ПОСЛЕ finish + админ-клоуза; если правка ушла в живую — фиксируй дефект как ошибку порядка ПМ в релизном журнале, ревью не перезапускай. OUT_OF_ZONE из-за чужих путей НЕ обесценивает ревью: flow_check засчитывает approve по review-файлу + мете Reviewer-Delegation, а вердикт `returned` у code_review-сессии — норма (pr_validate SKIPPED без PR-контекста); не перезапускай ревью-делегацию из-за returned, закрытие сессии с дефектом — приемлемый конец цикла.
Вход в роль пачки задач через ворота: start → run → диспатч. Проверь оба статуса: `prepared: True` в gate-старте и `running` в flowctl status после run — без run сессия остается `reserved`, не видна анти-BYPASS-сверке и получает ложный STALE от вотчдога.

- **Типовая последовательность ошибок при двух параллельных gate-стартах**: (1) первый start до решения Заказчика оставил `running`-запись — второй start на ту же зону ловит ZONE_CONFLICT с самим собой (см. выше про осиротевшую запись). (2) Готовишь ворота для второй делегации ДО того, как первая сессия реально закрыта и ее зона освобождена админ-клоузом в реестре — ZONE_CONFLICT от легитимной сессии. Порядок: gate start → run → диспатч → (по завершении) finish → админ-клоуз зоны → gate start следующей. Зона `deploy/**` блокирует две делегации одновременно — подтверждено вотчдогом и списком active_sessions.
- **Отчет-файл для finish: пишет САБАГЕНТ в своей зоне до своего финиша** — если отчет пишет ПМ после закрытия сессии, файл оказывается вне зоны делегации (OUT_OF_ZONE в вердикте) и главный артефакт цикла не привязан к автору. В ТЗ сабагента закладывай пунктом: «финальный отчет — файл в своей зоне, путь включи в финальное сообщение». Зона резерва на start должна покрывать путь отчета: задавай --path так, чтобы и код, и отчет-файл были внутри (иначе верный отчет валит finish по OUT_OF_ZONE).
- **Пакетный диспатч (несколько сабагентов одним delegate_task) = ОДИН платформенный id на несколько flowctl-сессий**: gated_map мапит batch-id на ПЕРВУЮ flowctl-делегацию (формат значения deleg-<hex>); второй flowctl-статус не покрывается map — не сетуйся на него в анти-BYPASS-логике. Коммитты параллельных сессий в общем base..HEAD дают друг другу OUT_OF_ZONE на finish — известная норма для параллельных зон, работы верифицируются независимо, сессии закрываются админски с журнальной записью.
- **pr_validate на доревью-стадиях честно SKIPPED/FAIL** (нет PR-контекста: локальный finish без --pr-id дает SKIPPED, с --pr-id — FAIL «маркер ID не найден», т.к. title/body читаются из PR, которого локально нет) → overall ≠ PASS, вердикт returned — норма для смерженного PR с зеленым CI: реальный арбитраж gates — CI на PR (там title/body и merge-дерево). Не перезапускай цикл из-за returned у code_review/qa-сессии, чей PR в CI зелен. Промежуточные задачи Флоу 1 закрывает flow_check (штатный FAIL «задачи без code-review» до ревью — цикл, не дефект).
- **В CI pr_validate гоняется на КАЖДОМ PR пакета и читает дерево merge-рефа (PR-ветка поверх main)** — QA-артефакты (impact/чеклист/approved-кейсы/test-model reviews), живущие только на отдельной QA-ветке, для dev-PR невидимы, и ВСЕ dev-PR пакета краснеют «артефакты отсутствуют», хотя локально у каждой волны все зеленое. Решение — интеграционный [chore]-PR: cherry-pick коммитов QA-ветки на актуальный main (`git checkout -b pipeline/<slug> <main-sha> && git cherry-pick <base>..<qa-branch>` — не мерж всей ветки с ее базой), локальный прогон `pr_validate` + `flow_check` до пуша, merge, затем ретриггер висящих red-dev-PR пустыми коммитами (изменения main чеки PR сами не перезапускают). Решение Заказчика «ждать полного цикла» валидно только пока dev-PR не мержатся — по умолчанию артефакты должны попасть в main раньше dev-мержей.
- **Финальный PR change-пакета: собери артефакты pr_validate ДО создания PR** (первый прогон PR без них = красный check, ретриггеры не спасают):
  - `test-model/impact/<change>.md` — обязателен при ЛЮБОЙ MODIFIED/REMOVED-дельте (H5): характер дельты, вердикты keep/revalidate/retire по факту прогонов;
  - `test-model/checklists/<change>.md` — каждая CHK-строка несет источник `FR-N|NFR-N|Requirement` (обобщенное слово «Requirement:» в колонке Источник проходит), плюс раздел «Дефекты спеки» (даже пустой с фиксацией «не обнаружено»);
  - `test-model/approved/<change>/` — кейсы (1 файл = 1 TC-, с CHK-трассировкой) и `test-model/reviews/<change>/review-*.md` со словом «одобрить» в тексте (формат эталона: `## Вердикт: **ОДОБРИТЬ**` + мета Reviewer-Delegation);
  - все code-reviews файлы закрытых dev-задач — с валидной метой Reviewer-Delegation; имена без task-id (или объединяющие несколько задач) — через `review-mapping.json`.
  Локальный прогон набора ДО пуша: `python3 scripts/pr_validate.py . --id <change-id> --type change` + `python3 scripts/flow_check.py .`; после пуша — лог джобы `pr_validate`. Нюансы парсеров: источник CHK-строки — регэксп `FR-\d+|NFR-\d+|Requirement` по всей строке (голое «Scenario:» в колонке Источник НЕ проходит — добавь FR/NFR-ссылку); TC-трассировка теста матчится по `change_id` ИЛИ `TC-<ПЕРВЫЙ-ТОКЕН>-NNN` (для `add-<slug>` префикс `TC-ADD-…`) — клади его в docstring нового теста; QA-гейт `qa_review` требует кейсы в `test-model/new/` — пусто = INVALID_GATE. Чинить красный PR постфактум дороже, чем собрать артефакты заранее.
- **QA-фазу задачи начинай с qa_checklist, не с qa_review**: `qa_review` с ролью dev дает DENY WRONG_ROLE + INVALID_GATE («нет кейсов в test-model/new/ — ревьюить нечего») — это машина, требующая цепочки контрактов 3–6. - **SELF_REVIEW механически**: author_delegation_id ≠ reviewer_delegation_id — review-файл на свою/подопечную работу обертка не легализует (ai-factory 0518e06, код SELF_REVIEW).
- **ТЗ ревьюеру: никогда не задавай литеральный delegation-id** (ярлык вида deleg-arch-rev-001 из текста ТЗ ревьюер честно впишет в мету, но реестр его не засчитает — pr_validate FAIL «не найдена в реестре»). В ТЗ передавай фактический платформенный id делегации (возвращается диспатчем: delegation_id из ответа delegate_task) и формулируй: «в мета-строку Reviewer-Delegation впиши свой платформенный id: <id>».
- **Два похожих id — не перепутай**: gate start печатает flowctl-id `deleg-<hex>` (его место — gated_map и flowctl-сессия), платформенный `deleg_<hex8>` появляется только в ответе delegate_task, и только он есть в `async_delegations`. Мета review-файла сверяется с реестром — flowctl-id в мете проходит REVIEWER_META_RE (регэксп ест оба разделителя), но валит pr_validate «не найдена в реестре» на финальном PR. Лечение отказа «не найдена в реестре»: возьми платформенный id из реестра — `sqlite3 ~/.hermes/state.db "SELECT delegation_id, state FROM async_delegations WHERE delegation_id LIKE '%<hex>%'"` — и поправь мета-строку точечным патчем; не переписывай review и не гоняй ревьюера заново, вердикт остается его. БД реестра — `~/.hermes/state.db`; файл `~/.hermes/state/state.db` — пустая заглушка с тем же именем, запросы в него дают «no such table». Заодно: отказавший gate start тоже печатает delegation_id попытки — бери любой id из вывода только при `prepared: True`, иначе замапишь/передашь пустышку.
- **Мержить PR с красным required check НЕВОЗМОЖНО только если check реально required**: правила ветки без required status checks пропускают merge с красным flow — после каждого такого инцидента проверяй Rulesets API и предлагай Заказчику список чеков для required (см. J37).
- **Готовность гейта ≠ доступность скрипта**: pm_bounds_check.py ставится только в ai-factory, в проектах его нет → gate_runner честно ERROR/blocked (J34 в BACKLOG фабрики) — не путать с обходом; чинить установкой (E15), не ослаблением гейта.
- flowctl пишет `prepared: True/False` YAML-строкой (не JSON) — при парсинге вывода лови оба формата; exit code flowctl может быть 0 при reservation denied — читай машиночитаемый факт, не только exit code.

Инцидент-урок (SELF_REVIEW-обход под красным CI): ПМ создал self-review 005–007 вместо диспатча независимого ревьюера — формально ворота закрыты, фактически самоаттестация. Правильно: при непокрытых задачах диспатчить независимого ревьюера или оформлять [ops]-протокол приемки; признавать обход Заказчику честно и чинить механизм (так появились SELF_REVIEW-код, Reviewer-Delegation мета и delegate_watchdog), а не отчитываться результатом.

## Три слоя гарантии и delegate_watchdog (детектор обхода)

Машина флоу гарантируется тремя независимыми слоями; ни один не опирается на дисциплину агента:

1. **Движок** — flowctl DENY на входе (зоны, approval_ref, роли) блокирует неправильное до старта делегации.
2. **Вотчдог** (`scripts/delegate_watchdog.py`, крон */5 в фабрике) — сверяет платформенный реестр `async_delegations` (state.db, пишется при КАЖДОМ delegate_task независимо от воли агента) с prepare-записями flowctl. Делегация мимо машины → BYPASS-инцидент в `~/.hermes/state/delegate_bypass_incidents.json` + exit 1; забытый finish → STALE. Baseline-файл `delegate_gate_baseline.json` хранит дату внедрения — делегации до нее история, не инцидент.
3. **Правило** — видимый обход = нарушение независимо от результата работы (SELF_REVIEW/OPS_TASK_AS_DEV в контракте).

Меняя поведение/доставку вотчдога (текст BYPASS-напоминания, target доставки), правь ОБЕ копии: установочную `~/.hermes/scripts/delegate_watchdog.py` (ее читает крон) и эталон в репо фабрики, затем зеркаль в проекты ([pipeline]-коммит) — правка только установочной теряется при следующей синхронизации. То же правило при СОЗДАНИИ нового крон-скрипта: эталон в фабрике без установочной копии = крон падает «Script not found» на первом срабатывании (кроны ищут скрипты только в ~/.hermes/scripts) — копируй в установку В МОМЕНТ создания, а не к первому запуску, и после первого боевого срабатывания проверь `last_status` job'а в jobs.json, не полагаясь на ручной прогон. Направление синхронизации определяй по содержанию, не по месту: живая установочная копия бывает НОВЕЕ эталона фабрики (горячие фиксы идут в установку в момент инцидента) — перед коммитом `diff` их, не «копируй фабрику в установку» по умолчанию. Целевой канал доставки крона — поле `deliver` в jobs.json (cronjob_manage update), не скрипт; после правки прогони скрипт руками и проверь last_status в списке jobs.

Трехканальный дизайн отчета (норма): канал ЗАКАЗЧИКА — сухой машинный stdout (`BYPASS DETECTED: новых N …` + JSON, только дельта по ack-файлу), без обращений к ПМ; канал ПМ-0 — файл `~/.hermes/state/pm_instruction.txt`, который доставляет крон `pm-instruction-relay` (*/2, `pm_instruction_monitor.py` как change-detector + no_agent=False): monitor молчит при неизменном файле, при новом будит агента, и его финальное сообщение доставляется в DM ПМ как ХОД СЕССИИ. Смысл канала-0: ПМ не читает output-логи крона в момент решения — инструкция, записанная «в stdout», обнаруживается постфактум при разборе логов, т.е. не работает; доставляться инструкция должна тем же каналом, что сообщения Заказчика. Канал ПМ-1 (stdout самого watchdog-крона) — дублирующий. Обращение к ПМ и машинный отчет НЕ смешивать в одном сообщении: Заказчик не должен читать нареканий в адрес ПМ.

Релей-крон с агентом (no_agent=False): финальный ответ агента доставляется Заказчику ВСЕГДА, кроме ровно `[SILENT]` — не задавай в промпте заглушек вида «при пустоте верни NOOP»: заглушка уходит Заказчику как обычное сообщение. Промпт релея: контент в файле → вернуть дословно и удалить файл (удаление = машинное подтверждение доставки, вотчдог может писать новую инструкцию не затирая недоставленную); пусто/нет файла → ровно `[SILENT]`.

Канал доставки ≠ средство прерывания: сообщение между ходами ПМ видит до следующего шага, но физически выполняющийся tool-call не прерывает — закладывайся реагировать на границе хода. Дедуп monitor-канала — по хэшу содержимого файла (self-dedup в monitor-скрипте): без него агент гоняется каждый тик. Полный цикл правки каналов: правь ОБЕ копии скриптов (установочная `~/.hermes/scripts/` + эталон фабрики), зеркаль в проекты `[pipeline]`-коммитом, затем E2E-проверку подстановкой (убери id из ack → watchdog записал инструкцию → monitor выдал ровно 1 раз → повтор 0 байт → ack восстановлен → тишина).

Анти-рекурсия канала ПМ ОБЯЗАТЕЛЬНА: инструкция ПМ триггерит его действия → новые делегации → новые инциденты → новые инструкции = бесконечные прерывания. Тройная защита в скрипте: (1) дедуп по fingerprint состава инцидентов — неизменившийся состав не печатается; (2) cooldown (мин 15 мин) после каждой доставки даже при изменившемся составе; (3) жесткий потолок доставок в час — сверх него канал ПМ молчит с пометкой suppressed, машинный канал и файл инцидентов продолжают работать. Каждую защиту проверяй повторными прогонами скрипта руками (run2 без повторной печати; подавленный budget), не по коду.

Канал Заказчика — только НОВЫЕ инциденты (ack-слой): no_agent-крон с ненулевым exit доставляет stdout КАЖДЫЙ прогон — вотчдог, репортящий одни и те же принятые обходы, спамит Заказчика каждые 5 минут. Признанные инциденты (решением или явным ack) уводи в ACK-файл (ids + decision_ref); stdout пуст при отсутствии новых → крон молчит (это его штатное поведение), полная история остается в файле инцидентов. **Ack вписывай СРАЗУ после признания Заказчиком** — вотчдог тикает */5, и каждый тик с не-ack-нутым id доставляет Заказчику повтор «спама»; бухгалтерия (decision-файл, ветки, flowctl) не должна откладывать ack-строку. После ack прогони watchdog руками ДВАЖДЫ (2-й обязан exit 0). Один из первых шагов при восстановлении статуса сессии — ручной прогон watchdog: накопленный за простой ack-долг (волны фактически приняты в git, ack-строки не вписаны) всплывет до боевых действий; исторические волны ack'ай ОДНИМ батчем с decision-basis в ACK-файле, не по одному id за прогон. Проверяй дельту подстановкой: id вне ack → ровно один отчет с дельтой («новых N, принято ранее M»), не вся копилка. Служебные platform-запуски (cronjob_manage run тестового огня крона, ручные no_agent-файры) тоже попадают в `async_delegations` и триггерят ложный BYPASS — ack'ай сразу с retro_note «cron-run, ворота конвейера к кронам неприменимы», не оформляй задним числом decision-record.

Инструкции агенту — не гарантия; гарантией является «нельзя + заметят + не засчитают» (README фабрики, секция Гарантии). При работе в проектах: delegate_gate/delegate_watchdog ставятся factory_init (COPY_FILES) и bootstrap (кроны */2 + */5); pm_bounds_check — известный пробел (J34). hermes update движок не трогает: конвейер живет в git-репо фабрики и проектов, не в установке Hermes — при расхождении копий ядра синхронизируй из эталона фабрики (см. ниже).

**Прямая доставка кронов в чат Заказчика отключена: в чате только суточный дайджест (23:00 UTC, no_agent-скрипт).** Глуша крон-канал, проверяй НЕ только `deliver`, но и `failure_deliver` КАЖДОЙ job'ы в `~/.hermes/cron/jobs.json`: failure-only канал на busy-скрипте доставляет Заказчику КАЖДЫЙ неудавшийся прогон — вотчдог с легитимным инцидентом превращается в спам каждые 5 минут. При заглушенном watchdog-кроне сверку делегаций гоняй руками (два прогона подряд, второй exit 0) на каждом закрытии зоны — машинный слой не отключается вместе с каналом доставки. После паузы/правки job'а проверяй факт по jobs.json (`enabled`, `last_status`, `last_error`), не по ответу инструмента; новый крон-скрипт проверяй ручным fire (`cronjob_manage run`) до первого боевого тика.

## Режим работы ПМ: непрерывное доведение до релиза

Терминология: ПМ-сабагент не запущен — роль ПМ выполняет main-сессия (решение Заказчика); вся терминология «ПМ-коммиты», «ПМ-зоны» относится к main-сессии, не путать в докладах.

Этапные ворота и паузы волн ОТМЕНЕНЫ директивой Заказчика: задачи конвейера доделывать непрерывно, не останавливаясь между фазами/задачами на запрос «погнали». Пауза допустима ТОЛЬКО в трех случаях: (1) развилка, требующая решения Заказчика (по спеке — прод-выкатки, помеченные «с явным участием Заказчика»); (2) отсутствие вводной, которую может дать только он; (3) релиз готов — итоговый доклад. Перед любым докладом «жду команды» проверь, не попадаешь ли в один из этих трех случаев, — иначе работа стоит зря.

**Пауза на развилке обязана заканчиваться сообщением с вопросом, не молчанием**: легальная пауза — это ход, завершающийся явным «жду решения, ОВ-N: <вопрос>» (вопросы Заказчику — нумерованным списком ОВ-N); конвейер, остановленный перед развилкой без доставленного вопроса, Заказчик читает как «опять застрял» — для него тишина неотличима от зависания. Если ход оборвался после достижения развилки, но до доставки вопроса — первым же сообщением по следующему поводу доставь развилку нумерованным ОВ-N, не жди третьего запроса статуса. Проверка перед паузой: могу я назвать номер ОВ-N, который прямо сейчас ждет Заказчика; нет — пауза нелегальна, доделывай.

**Действия, а не объявления** — «запускаю/делегирую» говори только ПОСЛЕ фактического вызова delegate_task (сначала диспатч, потом статус), иначе пауза после объявления выглядит как молчание и подрывает доверие: Заказчик читает «запущено» как «работает сейчас».

**Неоднозначное слово в запросе — уточняй ДО действия**: омоним («just»-бинарник vs «j-бэклог фабрики», имя инструмента vs содержание задачи) не разворачивай в установку/запуск по первой интерпретации — один уточняющий вопрос дешевле удаления неверно установленного инструмента и объяснений. Реверс-сигнал («стой», «удали», «выключи») исполняется немедленно и без контраргументов. **В Telegram каждый текст = отдельное сообщение Заказчику**: не слать нарративные интермедии перед каждым tool-батчем («верифицирую», «проверяю факты», «запускаю...») — инструментальные шаги невидимы и не требуют трансляции; текст — только по факту и по существу (вердикт, результат верификации, развилка, итоговый статус). Один существенный доклад вместо пяти промежуточных строк. Исполняющая роль (dev) коммитит в свою ветку САМА по завершении задачи — не останавливайся вопросом «коммитить?»: commit в рабочую ветку входит в определение «задача выполнена» (зона записи та же, что у кода). Если ход оборвался между объявлением и действием — первым же сообщением доложи фактическое состояние, не жди вопроса.

Если сабагент уже в полете (async-делегация), молчание родителя — НЕ повод заканчивать ход без диспатча: результат придет между ходами. Нормальный ритм после диспатча: однострочный статус и конец хода — не ждать и не поллить транскрипты. Прерывать асинхронную задачу «чтобы переспросить» нельзя: это теряет результат в dropped.

**Не дроби одну задачу/фикс-цикл на несколько сабагентов, «раз так тяжело»**: зоны эксклюзивны (второй prepare на пересечение = ZONE_CONFLICT, а резка зоны мельче = [pipeline]-расширение политики — развилка Заказчика ради одного цикла не окупается); стенд один (параллельные прогоны воюют за порты/БД и дискредитируют результаты друг друга); массовые падения сьюта обычно имеют ОДНУ системную причину — деление размазывает разбор по изолированным контекстам и ломает трассировку «1 задача = 1 отчет + 1 ревью». Точка деления — ПОСЛЕ отчета: независимые product-дефекты в разных зонах пускай параллельными фикс-циклами Флоу 2, каждый в своей зоне.

**Параллельные делегации на РАЗНЫЕ ветки одного репо — только через git worktrees**: две ветки не могут быть checkout в одном дереве одновременно — диспатч двух сабагентов в общее дерево заставляет их переключать ветки под друг другом (потеря файлов, урок E5). Процедура: `bash ~/ai-factory/scripts/session_worktree.sh create <repo> <session-id> <branch>` (скрипт живет в ФАБРИКЕ, не в scripts/ проекта — не ищи его там); ветка, уже checkout в основном дереве, worktree не создаст — сначала переведи основное дерево на нейтральную ветку (main), потом создавай worktrees; steer'ом сообщи каждому сабагенту его worktree-путь (без steer он пойдет в путь из ТЗ). Зоны делегаций при этом все равно готовь через delegate_gate ДО диспатча: ZONE_CONFLICT по `deploy/**` ловится на старте, не в дереве.

**Обрыв хода между gate start/run и диспатчем — додиспатчивай в СУЩЕСТВУЮЩУЮ сессию**: flowctl-сессия уже `running` и держит зону; новый prepare на нее же даст ZONE_CONFLICT с самим собой. Проверь статус (`flowctl status` / реестр), возьми correlation_id живой записи и диспатчь в нее; повторный start плодит параллельные резервы, которые потом закрывать как зомби. Признак ситуации: в реестре делегаций последняя — чужая, а в active_sessions висит твоя `running`-запись без платформенной пары в async_delegations.

**Обрыв делегации на репликации/длинном прогоне — докатывай ход ПМом, не перезапускай**: патчи сабагента уже в рабочем дереве (проверь git diff до любых действий); допиши верификацию сам (py_compile/bash -n/лимитированная реплика), закоммить АВТОРСТВОМ цикла с пометкой в коммит-сообщении, кто патчил и кто верифицировал, отчет пиши в зоне задачи. Репликацию циклов с бесконечным while пиши с ЖЕСТКИМ лимитом итераций/sleep-вызовов (мок sleep, бросающий исключение по счетчику) — безлимитный мок зацикливает прогон и сжигает ход.

**Лимит-обрыв (max_iterations) — тот же протокол доката, с обязательной проверкой дерева**: оборванный по лимиту сабагент возвращает честный статус «работа НЕ завершена» + хэндофф-список (сделано/не сделано/эскалации) — и этот список тоже самоотчет: сначала git status/diff и лог прогона (дерево бывает ЧИСТЫМ даже после сотен tool-вызовов — тогда единственный путь повтор, докатывать нечего). Верифицированные факты из отчета переиспользуй (стенд живой, изолированные прогоны, логи в /tmp), финализирующие шаги (правки, коммит, отчет-файл) передавай завершающей делегацией В ТУ ЖЕ flowctl-сессию (зона удержана, gated_map впиши тем же ходом). Два лимит-обрыва подряд на одном цикле — сигнал перекомпоновать ТЗ: оставь сабагенту исполнение правок, а чистку данных, финальный прогон и коммит докатывай ПМом — лимит съедается на диагностике средовых причин, не на правках. После лимит-обрыва/dropped-делегации проверь осиротевшие фоновые процессы сабагента (uvicorn/nginx стендов: `pgrep -af 'uvicorn|nginx'`) — сводка batch-complete числит их «TERMINATED», но реально они переживают смерть родителя и держат порты следующего прогона; гаси по PID до нового стенда.

**Преждевременное снятие `[x]` чекбокса — не чинить перезаписью**: gate start по закрытой задаче честно DENY INVALID_GATE («история не переписывается») — это правильный ответ машины, а не поломка: откатить чекбокс в рабочем дереве (это не переписывание истории коммитов), диспатчить ревью, закрывать задачу после approve-файла. flow_check между ревью волнами честно красный («задача без review») — это ожидаемый промежуточный сигнал, не блокер.

**Сообщение «операция на подтверждении» = ход заморожен, не брошен**: permission-gate отклонил команду с «The user has NOT consented... do NOT retry» — следующий ход исполнить ту же команду только по явному «продолжай» от Заказчика (тишина ≠ согласие), не переформулировкой обхода. Команды с heredoc/python-блоками часто требуют ручного подтверждения — дроби большие батчи на мелкие шаги, чтобы заморозка не ела ход целиком. Одноименные admin-правки стейт-файлов конвейера (админ-клоуз реестра/flowctl_state, gated_map) — пере-маршрутизируй в управляемую Python-сессию execute_code (тот же доступ, но чтение правки уже резолвятся без permission-freeze): НЕ пере-набирай ту же shell-форму и не оставляй ход с незакрытой зоной — блокировка формы ≠ запрет операции.

**Релизный журнал (директива Заказчика): во время релиза веди append-only лог передач** — `docs/releases/<дата>-R<N>-release-log.md` в проекте. Формат строки: `[время UTC] КТО → КОМУ: ЧТО (артефакт/вердикт)`; один файл на релиз, дописывай каждую передачу (Заказчик→ПМ, ПМ→сабагент, сабагент→ПМ, вердикты гейтов и ревью) сразу после факта, не по памяти в конце. В конце релиза показать журнал Заказчику целиком. Детали не дублировать: ссылки на gate-reports и review-файлы.

Прерывание сессии шлюзом (сталл → session_reset, «обнулился контекст») НЕ отменяет ни одной задачи: перед диспатчем новых сабагентов восстанови состояние по фактам — недоставленные результаты делегаций лежат в `async_delegations.result_json` (delivery_state='dropped'), ход прерванного сабагента — в live-транскрипте `~/.hermes/cache/delegation/live/<deleg_id>/task-N.log`; уже закоммиченное и прогонное не переделывай (проверь git, не слова). Правило «1 задача = 1 dev-сабагент + ОТДЕЛЬНЫЙ ревьюер» действует и на догоняющих диспатчах: у закрытой задачи без ревью сначала ревью отдельным агентом, потом следующие задачи поверх этого кода.

**Статус после обрыва/«дай статус» восстанавливай ИНВЕНТАРИЗАЦИЕЙ артефактов, не по памяти сессии** — транскрипт оборван, а конвейер оставляет достаточно фактов для точной картины. Порядок (заного воспроизводимый): (1) git обоих репо: `git log --all --oneline --since=<дата старта цикла>` + текущая ветка/статус — свежие коммиты показывают, какая задача реально закрылась, включая коммиты сабагентов, чьи результаты не дошли; (2) `~/.hermes/state/active_sessions.json` — не-completed записи (running/reserved/stale): кто формально в полете и держит зону; (3) чекбоксы `openspec/changes/<id>/tasks.md` — официальный прогресс (расхождение «коммит есть, чекбокса нет» = приемка ПМ не доведена — и это твой следующий шаг, не признак потерянной работы); активные пакеты живут на ветках/worktrees при чистом main-чекaуте — чекбоксы, REPORT-файлы и release-log читай С ВЕТКИ пакета (`git show <branch>:openspec/changes/<id>/tasks.md`, `git ls-tree -r --name-only <branch>`), а релизный журнал цикла ищи и лентой коммит-сообщений (`git log --all --grep='release-log'`) — файл `docs/releases/…-release-log.md` бывает только на одной из веток или не существует вовсе; (4) REPORT-файлы в затронутых каталогах (design/, test-model/) — артефакты дизайн/QA-фаз; (5) PLAN-R<N>.md — где цикл стоит (развилка). Доклад строится: закрыто → в полете → развилка (номер ОВ-N) → следующий шаг. Типовой итог такой инвентаризации: «зависание» — это штатная пауза на развилке утверждения (мокапы/прод-выкатка), которую надо просто пере-доставить Заказчику вопросом, а не чинить конвейер.

## Эскалация needs-debug: debug-агент (вне flow-графа)

Сабагент, застрявший на непонятном отказе («локально OK / CI FAIL», среда необъяснимо, итерационный бюджет съеден отладкой — прецеденты J31), НЕ крутится дальше и НЕ чинит вслепую: возвращает задачу ПМ с маркером первой строкой отчета `needs-debug: <гипотеза одной фразой>`. ПМ диспатчит debug-агента (agents/debug_agent.md фабрики) параллельно — изолированный диагност, запись в продукт ЗАПРЕЩЕНА (фиксы текстом в отчете, применяет исходный dev), вердикт СРЕДА/КОД/ТЕСТ с доказательством, пополнение docs/project-pitfalls.md.

- Сабагент НЕ вызывает диагноста сам: делегации только от ПМ (J1-контаминация) и прямой вызов = дыра в флоу («просто почини» мимо ревью). Один хоп через ПМ окупается: итерации автора не сгорают на чужом домене.
- Повторная эскалация той же задачи без нового факта — сигнал сменить подход/профиль (J32), не перезапуск диагноста.
- Установлен в фабрике (agents/debug_agent.md); factory_init копирует его в проекты вместе с остальными промптами (см. выше про ретроактивность).

## Верификация отчетов сабагентов (перед докладом Заказчику)

Отчет сабагента — самоотчет, не факт. Перед переносом в статус докладу проверь руками: git HEAD/статус/дифф в репо, живое состояние ресурсов (`docker ps -a`, `volume ls` по проекту стенда), наличие и размер файлов-артефактов (бэкапы), полный лог прогона (exit-код каждой ступени). Ключевое из отчета — подтверждающая команда, не цитата. Отчет, полученный через async-delegation после сбоя шлюза, ищи в `async_delegations.result_json` — delivery_state='dropped' означает только недоставку, не потерю результата. Ищи ОБЕ разновидности: запрос только по `state='completed'` пропускает оборванные ротацией делегации — они получают `state='error'` при том же `delivery_state='dropped'`; фильтруй `state IN ('completed','error')`.

**Расхождение «у сабагента PASSED, у ПМ ERROR» — сначала ищи разницу СРЕДЫ, не дефект отчета.** Типовая причина в этом конвейере: скрытая фикстура/плагин тянет ресурс (стенд, env), который у сабагента был поднят. Диагноз: прочитай фикстуры затронутого каталога (conftest, `--setup-plan` показывает цепочку), проверь stale env (`env | grep EKOTOV`), подними ресурс по tests/README и повтори — только после этого квалифицируй как дефект теста. Доклад Заказчику в этом состоянии — «воспроизведено у ПМ после подъема стенда, отчет подтвержден», не «не проверял».

Ревью-замечания с severity major/major+ закрывать фикс-коммитом немедленно (Флоу 2), предварительно подтвердив дефект СОБСТВЕННЫМ чтением кода: у ревьюера могут быть ложные срабатывания, но у подтвержденного мажора фикс — одной строкой и до любых следующих задач поверх этого кода. Компенсирующая проверка (sandbox/согласие не дали живой прогон) — честно писать в коммит-сообщение «проверка живым прогоном отложена на N». Фикс-коммит отдавай АВТОРУ исходного кода (delegационный круг: ревьюер нашел → автор чинит → тот же ревьюер ре-ревьюит коротким кругом только фикс-дифф), не ревьюеру и не ПМ. Сабагент не объявляет пропуск ревью сам: маркер вида [skips-review] в его коммите — не основание merge; решение «ревьюить/не ревьюить» принимает ПМ (увидел self-skip — прогони ревью все равно и отметь нарушение в ретро/MAP).

## Синхронизация ядра фабрики (эталон ↔ проект)

Когда в проекте правили фабричные скрипты (ворота/flow_check/контракт), проверяй перенос в эталон `~/ai-factory` — проектные правки ядра без upstream-синхронизации превращают каждый следующий `factory_init` в новый рассинхрон. Синхронизация БИДИРЕКЦИОННА: фабричная версия может отставать от проектной (у проекта правки появляются раньше) — перед копированием определи, какая сторона новее по содержанию, а не по дате; эталон — та версия, где логика полнее. В треугольнике «эталон фабрики ↔ живая установка `~/.hermes/scripts/` ↔ проект» сверяй ВСЕ пары: установочный скрипт, отставший от эталона (или наоборот) — тот же рассинхрон, что и проектный. Не все установочные скрипты живут в проектах: session_watchdog и pm_instruction_monitor — только эталон + живая копия (проверяй фактическое содержимое каталога scripts проекта через search_files/target=files, а не по памяти: shell `ls` без явно переданного cwd молча показывает чужой каталог).

Документацию конвейера (README.md, AGENTS.md фабрики) актуализируй В ТОМ ЖЕ PR, что и код: роли/скрипты/каналы, добавленные в код без обновления README и AGENTS.md, — рассинхрон, который следующий агент читает как устаревшую картину. Метод: прогони `git log --oneline -15` фабрики и свер каждую фичу с README (таблица ролей против фактического списка `agents/*_agent.md`, таблица артефактов против фактического списка `scripts/`), устаревшие абзацы (отмененные директивы, завершенные релизы) заменяй, а не дополняй. После генерации markdown-таблиц скриптом/кодом проверяй разделитель и ячейки глазами или grep'ом (`^\|\| ` — дефект двойного пайпа, ломает таблицу молча): сгенерированный синтаксис не проверяется линтером. AGENTS.md — защищенный путь: pm_bounds требует явного подтверждения на каждую правку — при батче правок получай разрешение СПИСКОМ диффов одним вопросом (по одному вопросу на правку — сжигает ходы Заказчика); инструмент блокирует правку защищенного файла без подтверждения — если разрешение дано, а write все равно отражен гвардом, пере-спроси точечно именно эту правку (вопрос «разрешаете именно эту правку?» после показа диффа), не обходи через терминал.

- Метод — дифф по списку, не по памяти: для каждого файла ядра (`flow_state/flow_transition/gate_runner/flowctl/session_check/role_zone_policy/flow_check.py`, `contracts/flow_control_contract.md`) `diff <(git -C <проект> show <ветка>:scripts/<f>) ~/ai-factory/scripts/<f> | wc -l`; ноль = идентично.
- Классификация диффа: аддитивное ослабление ворот (плюс допустимый источник артефактов) — переносить в эталон через ЕГО собственный процесс (ветка → PR, негативная фикстура на новый допуск), оно переиспользуемо будущими проектами; правка, кодирующая структуру конкретного проекта (пути его test-model), — оставаться проектной, эталон не трогать.
- Против спешки: если в эталоне структуры, ради которых сделана правка, еще нет — поведение не меняется, перенос можно отложить пунктом в `ai-factory/BACKLOG.md`, деградации нет.
- Зеркалируй диффом, не файлом: CI/workflow-файлы (flow.yml, pr_validate) у фабрики и проекта расходятся окружением (в проектном workflow — установка зависимостей проекта, у фабрики — свои джобы). Копия эталонного файла целиком теряет проектные шаги и роняет CI постфактум; новое правило переноси в проектную версию точечным блоком тем же кодом, что у эталона, и проверяй прогоном проектного CI.

## Проверка авторства review-файлов: Reviewer-Delegation (SELF_REVIEW-слой)

Git-учетка у всех одна — git author не различает сабагентов; независимость
подтверждается платформенным `delegation_id` (устойчив к пересозданию
main-сессий):

- review-файл ОБЯЗАН нести строку `Reviewer-Delegation: deleg_<id>` — файл без
  нее `approved_review_tasks` не засчитывает (REVIEWER_META_RE tolerant к
  markdown-жирности вокруг: `**Reviewer-Delegation:** deleg_...` матчится
  паттерном `Reviewer-Delegation[^A-Za-z0-9]{0,6}(deleg[-_][A-Za-z0-9]+)`).
- pr_validate дополнительно сверяет deleg с `async_delegations` (существует +
  completed + ≠ dev-делегации задачи из flowctl runs) и делает это ВНЕ
  привязки к pr_tasks — подделка артефакта ловится даже когда задачи не
  упомянуты в тексте PR.
- Ревьюер-сабагент не знает свой delegation_id — вписывай его в файл сам из
  реестра (файл с `deleg_UNKNOWN` не пройдет). Живой прогон на
  add-containerization: fake deleg → FAIL, нет меты → FAIL, подмена на
  dev-делегацию → FAIL (на пакетах, идущих через delegate_gate).
  Дешевле предупреждать: клади в ТЗ ревьюеру ГОТОВУЮ мета-строку целиком
  для копипасты (`- **Reviewer-Delegation: deleg_<id>**`, id — платформенный,
  возвращается диспатчем). Свободная формулировка «впиши свою мету
  Reviewer-Delegation» дает варианты вроде `Review-Delegation:` —
  REVIEWER_META_RE ищет литеральное `Reviewer-Delegation`, опечатка молча
  не матчится, и файл числится «без ревью» до ручного патча меты из
  реестра отдельным коммитом.

## Контейнеризация и deploy.sh: верификация матричного деплоя

Пути внутри образа — от факта в контейнере, не от репозитория; маунты/тома — от фактического mount view: `references/service-extraction.md` (раздел «Пути внутри образа»). Тонкая верификация deploy.sh, деплой-бэкапы, rollback-параллели, [ops]-приемка вручную исполненных задач — ниже.

- DRY_RUN ничего не исполняет — он ПЕЧАТАЕТ команды через `run()` и зелен для любой, даже сломанной команды: мультистрочное продолжение, битый флаг, опечатка в подкоманде им не проверяются вовсе, `bash -n` проверяет только синтаксис файла. Рискованный шаг верифицируй (а) структурным тестом — обертка-функция с теми же аргументами доказывает, что bash парсит конструкцию как ОДНУ команду, и (б) реальным прогоном шага на изолированном стенде; DRY_RUN-прогон — не верификация команды, а проверка плана.
- Комментарий внутри backslash-продолжения команды обрывает команду: bash завершает ее на строке с комментарием, хвост становится новой командой («command not found») — а `fail`-ветка или guard внизу может это замаскировать. Комментарии ставь ТОЛЬКО до или после мультистрочной команды, никогда между строками продолжения; регресс не ловится `bash -n` и DRY_RUN (реальный кейс: blocker найден только независимым ре-ревью, деплой падал бы на каждом запуске).
- Релизный бэкап в каталог, где живет чужой retention-процесс (sidecar): пиши в staging-подкаталог ВНЕ масок retention (та читает только префиксы `*-daily-*` в корне), mv в релизное имя — только свежевынесенных файлов, c guard «moved == ожидаемое число»: guard ловит и «0 файлов» (вынос не сработал), и «2 файлов» (двойной прогон), вместо неявной ставки на сортируемость UTC-штампов. Иначе деплой затирает суточную историю sidecar — страховку между релизами, которую design фиксирует как обязательную.
- Ре-ревью коротким кругом — не формальность: фикс одной находки может внести новый blocker, невидимый статике и DRY_RUN (реальный кейс именно таков). Ре-ревьюить фикс-дифф обязан тот же ревьюер, даже если фикс «механический».

## Параллельные dev-волны в ОДНОМ дереве: ветку сверяй перед КАЖДЫМ коммитом

Делегации без worktrees переключают checkout-ветку общего дерева под себя:
коммит сабагента молча ляжет на чужую ветку (кейс p12-2.1). Протокол
(сверка `git branch --show-current` перед add/commit, восстановление через
`git branch -f` + `reset --hard` чужой ветки на прежний HEAD): см.
`references/parallel-waves.md`.

**Финальный полный регресс ветки — СЕРИАЛЬНО на итоговом HEAD**, после закрытия
всех параллельных делегаций: прогон, стартовавший во время git-операций соседа
над общим деревом, дает транзиентные фейлы (ModuleNotFoundError на
свапающихся файлах) и ложную диагностику; промежуточные прогоны агентов — их
самоотчет. Исполнитель финального прогона — ВЫДЕЛЕННЫЙ САБАГЕНТ, не ПМ
(ПМ не исполнитель): узкий бриф (ветка, коммит, затронутые сьюты), обязан
различить баг от флака (изолированный перепрогон упавших), FAIL → возврат
dev'у на доработку; ПМ принимает артефакт (вердикт + provenance). Роль —
новая regress_runner или переиспользование qa_runner (J17-2); механизация
(worktree в prepare, regress своего куска, regress-final как ворота merge) —
J51 фабрики. Перед merge PR сверяй remote-tip
СОДЕРЖАТЕЛЬНО (счетчики сценариев/тестов, validate), а не по факту пуша:
сабагент может запушить промежуточный сломанный коммит в ветку PR вопреки
«не пушить» — чинится `push --force-with-lease` актуальной версией с
комментарием в PR, что и почему перезаписано.

Мерж перекрывающихся волн — в порядке, предписанном ревьюером wave-ревью,
следующая волна ребейзится на обновленный main. Конфликт ребейза в общем
файле (две волны независимо внесли один код — типовой вердикт «X мержить
первым, из Y дубли выбросить») резолви проверкой «надмножество»: сравни
общие функции обеих версий байт-в-байт (`git show <ref>:<файл>` + difflib
по функциональным блокам); если версия поздней волны содержит общий код
идентично, а отличия — только ее собственные блоки, бери ее версию ЦЕЛИКОМ
(`git show <ветка>:<файл> > <файл>` + `git add`), не склеивай вручную —
ручная склейка и оставляет те дубли, которые ревьюер велел устранить.
После резолюции — `node --check` каждого тронутого JS до `rebase --continue`.

Основное дерево, занятое живой делегацией (сабагент переключил checkout на свою
ветку), ПМ НЕ переключает под себя — checkout роняет его сессию. ПМ-правки
(чекбоксы tasks.md, review-mapping.json, журнал) делай во ВТОРОМ worktree от
origin/main: `git worktree add /tmp/<slug> origin/main && git -C /tmp/<slug>
checkout -b pipeline/<slug>`, правка/коммит/пуш/PR там, после мержа —
`git worktree remove`. Основное дерево проверяй `git branch --show-current`
перед любым действием — текущая ветка принадлежит делегации, не тебе.

## Тесты ekotov-wiki: стенды, прогоны, дисциплина QA — `references/testing-ekotov-wiki.md`

Всегда актуальное: api-сьют требует живой стенд (канонический подъем — `scripts/qa_stand_up.sh` в репо; процедура в tests/README.md, offset-aware ISO в seed), xdist: api `-n 4` — да (кроме fastline-сьютов), web/regress-final — только сериально; длинный сьют — только tracked background, TC-трассировка в docstring при написании теста, числа прогонов — только после фактического прогона, регресс-тест обязан дискриминировать дефект (негативная подмена), полный регресс — честный. Остальное (nginx mime.types, page.request vs requests, чистая БД, закрытие задач и ревью-покрытие) — в reference.



Любой тест в `tests/api/` тянет session-фикстуру `base_url` (плагин pytest-base-url + `_verify_url` выполняют ее для ВСЕХ тестов каталога, даже файловых) и падает ERROR-at-setup без живого приложения — `env -u EKOTOV_WIKI_BASE_URL` не помогает, дефолт `http://127.0.0.1:8080` зашит в conftest. Процедура подъема — tests/README.md, порядок критичен: (1) схема ДО seed (пустая БД без таблиц), (2) `app.seed_users` интерактивен (getpass) — в no-TTY подавай пароли stdin-pipe, (3) uvicorn — терминальным background-режимом (shell `&` блокируется), (4) health `:8080/api/health` == `{"status":"ok"}` перед прогоном, (5) стенд гасить после. Seed сессий пиши offset-aware ISO (`datetime.now(timezone.utc).isoformat()`): ядро ведет aware-метки и сравнивает aware-объекты — наивные `datetime('now')` sqlite дают «can't compare offset-naive and offset-aware» 500 на первом запросе с кукой, и подозрение падает на код сервиса, а виноват seed. В ТЗ на НОВЫЙ тест сразу закладывай TC-трассировку в docstring: `TC-<change>-NNN` (ровно 3 цифры) ВНУТРИ docstring-литерала; маркеры в готовый файл вставляй только скриптом с `ast.parse`-верификацией до пуша (подводные камни — в правиле rule 6 в индексной строке выше).

«Тест зависит только от файлов, но лежит в tests/api/» — кандидат на вынос из каталога: он наследует требование стенда от каталога, а не от собственной логики. Пока лежит — ТЗ сабагенту на прогон включай подъем стенда, иначе отчет «PASSED» не воспроизведется у ПМ.

**Длинный сьют в сабагенте — только tracked background**: foreground-терминальный вызов имеет таймаут (~420с) — web/e2e-сьют на ~8.5 мин он убивает на середине, сабагент теряет прогон и на перезапуске фоном часто ловит ротацию родителя (делегация state='error' + dropped, интригуся interrupted в result_json). В ТЗ на любой сьют длиннее ~6 минут предписывай: запуск terminal background=true, ожидание через process_manage wait, лог в /tmp с полным хвостом. После оборванного цикла проверь git-дерево ДО ре-диспатча: фикс-цикл, убитый на прогоне, может не оставить ни коммитов, ни правок — тогда повтор целиком, «докатывать» нечего; повтор диспатчь в ТУ ЖЕ flowctl-сессию (зона удержана), id — в gated_map тем же ходом.

**Локальный /tmp-стенд nginx для web-сьюта: include mime.types ОБЯЗАТЕЛЕН** — конфиг без него отдает всю статику `text/plain`, ES-модули (strict MIME) браузер отбрасывает, точка входа фронтенда не исполняется → 100% web-сьюта красный до единого реального ассерта; первым делом при массовой красне проверь `curl -sI <static.js> | grep -i content-type`. Туда же lift-чеклист живого стенда: web_server в external-режиме НЕ сеет категории — справочник «Дом/Работа/Личное» сенти руками через API, и `EKOTOV_WIKI_AVATARS_DIR` обязателен (иначе 15 teardown-errors r5/settings/tooltip). Релизный протокол web-регресса (полный стенд :18443, четыре env вместе, чистая БД, таблица «симптом красноты → причина»): `references/web-regress-protocol.md`.

**API-проверки внутри playwright-теста — requests-сессией, не page.request**: `page.request` (APIRequestContext) соблюдает флаг Secure куки СТРОГО и на http-стенде не шлет session-cookie → 401, тогда как страница того же контекста работает (Chromium считает 127.0.0.1 trustworthy). Симптом: UI-ассерты зеленые, а `page.request.get(...).json()["<поле>"]` дает KeyError — это 401-тело, не отсутствие поля. Паттерн конвенции conftest: отдельная requests.Session, login через API, `for c in s.cookies: c.secure = False` — вынеси в хелпер теста и гони ВСЕ сверочные API-запросы через него.

**Проектные копии тестов ядра (test_flowctl) могут массово краснеть на zone-policy проекта** — тесты писались под фабричную политику (`src/**`), проектная (осознанная адаптация: backend/frontend/contracts вместо шаблонной) их валит DENY ZONE_OUTSIDE_POLICY. Перед правкой ядра фиксируй базу: прогони сьют, stash, прогони снова, сравни списки FAILED (diff отсортированных) — правка легитимна, если списки идентичны; расхождение из-за проектной политики — тема синхронизации тестов с политикой, не откат правки.

**Регресс-тест обязан ДИСКРИМИНИРОВАТЬ дефект, а не сопровождать его**: перед сдачей доказуй негативной подменой — верни дефектный вариант кода (убери fallback, верни DELETE+UPDATE, сним encoder) и покажи, что тест краснеет. Тест, зеленый на дефектном коде, проверяет смежное поведение, а не заявленный регресс — независимый ревьюер ловит это spy'ем/подменой и ставит major. То же для «объединить pytest tests/ одной командой»: pytest 8+ жестко валиит `pytest_plugins` в не-корневом conftest (collection error до исполнения) — прогоняй сборку всего дерева до того, как записать в README/отчет «совместный прогон работает».

**Числа прогонов — в коммит-сообщения/PR только ПОСЛЕ фактического прогона**: не пиши «N passed» в коммит до запуска — предварительное число расходится с фактом (реальный кейс: вписал «20 passed», прогон дал 21), а коммит-сообщение неизменяемо. Если предварительная запись ушла: фактические числа фиксируй комментарием к PR с явной пометкой «в коммит-сообщении число заявлено до прогона», историю не переписывай. Расхождение заявленного и фактического на ревью-артефактах — готовый major ревьюера.

**Web-сьют на живой БД: фейлы интерпретируй ТОЛЬКО на чистой базе, квалификацию «продукт vs тест» делай изолированной репликой**: оборванные/повторные прогоны копят хвосты (UI-созданные задачи без cleanup-трекинга → дубли карточек, seed-категории → 409 already exists, зависшие QAT-% записи) — карусель вида 7→3→10→2 упавших при неизменном коде это хвосты, не продукт; перед разбором чисть БД стенда (DELETE задач по префиксу + его tag-связи, QAT-категории; foreign_keys=ON), финальный подтверждающий прогон — на свежей БД, иначе фейлы невоспроизводимы и число в REPORT недостоверно. Квалификация продуктового дефекта: реплицируй API-путь изолированно — TestClient сервиса + temp sqlite (SCHEMA_SQL из backend/app/db.py, живая сессия в sessions, offset-aware ISO) — зеленая реплика закрывает вопрос одной командой; проба сабагента на грязной БД или без сессии показывает «дефект», которого нет. Playwright strict violation «heading resolved to 2 elements» (карточка за модалкой с тем же именем, что заголовок модалки) чини СКОУПОМ локатора на OVERLAY — семантика ассерта сохраняется, голый get_by_role по странице не восстанавливай.

**Скоуп «полный регресс» — честный, не декларативный**: прежде чем исключить сьют из прогона («нужен браузер/docker/стенд»), реально проверь недоступность инструмента одной пробой — ревьюер повторит пробу, и ложное «недоступно» разваливается в request_changes с major «регресс без сьюта — не полный». Непрогнанное фиксируй в отчете как ограничение с компенсацией (какая задача закроет), а не как невидимый пропуск.

Закрытие dev-задачи через gate finish ДО ее ревью дает flow_check FAIL «закрытые dev-задачи без code-review» и overall FAIL — штатное промежуточное состояние Флоу 1 (finish → ревью → следующий шаг), не дефект; не «чинить» снятием [x] и не писать self-review — диспатчить независимого ревьюера.

Зеркальное правило — `[x]` ставится ТОЛЬКО после коммита approve-файла: gate start `code_review` по уже закрытой задаче дает DENY INVALID_GATE («повторный проход этапа не разрешен», история не переписывается) — откат чекбокса честен, но сжигает цикл. Перед КАЖДЫМ ПМ-коммитом приемки прогоняй покрытие списком — `approved_review_tasks(Path('.'), '<change-id>')` — и сверяй с закрываемыми задачами: правило нарушается пачкой (закрыв несколько задач подряд, легко протащить чекбокс задачи, чей review еще в полете — следующий gate start на ней даст DENY, а чекбокс придется откатывать отдельным [pipeline]-коммитом). В длинной фикс-цепочке (ревью request_changes → фикс → ре-ревью → фикс → финальное approve) чекбокс закрывается ОДИН раз — на последнем approve; до того терпеть красный flow_check «задача без ревью» — это штатный сигнал, а не повод упреждать. Задача, УЖЕ лежащая в main без ревью-покрытия (прямой коммит мимо PR — инвентаризация ловит сверкой `git log main` с `approved_review_tasks`), закрывается тем же порядком: компенсирующее независимое ревью ее диффа через ворота (зона — путь review-файла, не диффа), approve в main, потом чекбокс. Микрокаверка: `flow_check.py` требует аргумент репо (`python3 scripts/flow_check.py .`) — голый вызов печатает usage с exit 2.

## Старт нового цикла (мультипакетный план): PLAN-файл, decisions под каждый change_id

При запуске нового цикла из нескольких пакетов (план R7-класса):

1. План фиксируется в `PLAN-R<N>.md` в проекте (пакеты, состав, ограничения, вводные Заказчика дословно) — коммит до старта СА; при уточнении вводных Заказчиком в чате — дополняй PLAN и помечай решенные ОВ, чтобы план оставался единственной точкой истины.
2. **Каждый change_id получает СВОЙ decisions-файл** с decision-record под его scope (машина ищет запись по имени файла и сверяет change_id — общий файл на два пакета валит второй старт HUMAN_APPROVAL_REQUIRED); `phase` в scope = номер флоу действия (create_change/dev_task Флоу 1 → `"phase": 1`).
3. Ветка под пакет: `add-<slug>` от актуального main; СА-старт через delegate_gate (`create_change`, зона openspec/changes/<id>/** + sdd.md).
