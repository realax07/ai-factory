# openspec CLI: дельты, archive, strict-валидация

Глубина для работы с change-пакетами openspec (CLI 1.14.x) в репо под Flow Control. Всегда: `openspec validate --all --strict` green на каждом шаге пакета.

## Что validate НЕ ловит — это schema-lint, не вердикт спеки

`validate --strict` (проверено адверсариальной батареей проб на CLI 1.14.x) гарантирует ТОЛЬКО структуру: дельта-секции, `### Requirement:` с SHALL/MUST в теле (не заголовке и не code-fence — fences маскируются), ≥1 непустой `#### Scenario:`, exit 1 на ERROR-уровне. НЕ ловит (все подтвержены пробами, exit 0):

- **ADDED-requirement, уже существующий в master-спеке** — тихий дубль при архивации; перед merge/архивом сверяй заголовки ADDED с master grep'ом (сам валидатор этого не делает).
- Why < 50 символов (константа CHANGE_WHY_TOO_SHORT есть, но не срабатывает), пустой `## What Changes`.
- Сценарий без WHEN/THEN-структуры (любое непустое тело проходит), дубли имен сценариев, дубли секций ADDED (молча сливаются).
- tasks.md без чекбоксов; требование >500 символов — только WARNING.

Значит: validate green = «формат структурно валиден», НЕ «спека хорошая». Покрытие, дубли, содержательность держат flow_check/coverage/ревьюеры; не цитируй «validate strict green» как признак качества спеки.

## MODIFIED = полная замена блока (главный источник ошибок дельт)

Валидатор рассматривает MODIFIED-requirement как ЗАМЕНУ всего блока в master-спеке. Ошибка «MODIFIED ... omits scenario(s) the current spec still has» = твоя дельта опустила сценарии, которые уже есть в спеке — архив отказывается их молча выкинуть. Фикс: перенести пропущенные сценарии в MODIFIED-блок дословно (порядок: сначала сценарии из текущей спеки, потом новые). Проверка перед коммитом: `openspec show <change> --json --deltas-only` — сверяй список сценариев каждой дельты с текущей спекой.

## Ручное слияние дельт в master (git mv-путь архивации)

Перемещение пакета в `changes/archive/` и слияние дельт в master — ОДИН PR/коммит: flow_check (контракт 7) проверяет слияние сразу на moved-пакете, отложенное слияние = красный CI на PR архивации (порядок: сначала дельты в master-спеку, потом mv — или оба изменения одним коммитом). Если архивируешь пакет вручную (git mv пакета в changes/archive/ + слияние дельт руками, без `openspec archive`): flow_check сверяет каждую «### Requirement:» дельты с master-спекой ПО ЗАГОЛОВКУ — заголовок MODIFIED-requirement в master остается ДОСЛОВНЫМ (тем же, что в дельте и старой спеке), новое содержание переносится в тело. Переименование заголовка в master под новую редакцию = «'<title>' не слит в master-spec» и красные ворота контракта 7. Новый понятный заголовок — не повод ломать машинное сопоставление.

Новые API-маршруты, введенные пакетом, при слиянии впиши в master-спеку ЛИТЕРАЛЬНО (например `GET /api/wiki/search` в тексте requirement) — I3-проверка flow_check ищет путь по тексту корневого покрытия, перефразированный маршрут без точного пути = «маршрут не упомянут ни в дельтах спек» после архивации. Заодно фиксируй в master поведенческие изменения из возвратов приемки (например регистронезависимость поиска), чтобы спека соответствовала проде.

## archive: механика и обязательные шаги

`openspec archive <change-id> --yes` применяет дельты к master-спекам и переносит пакет в `openspec/changes/archive/<дата>-<id>/`. До архива: tasks.md все `[x]`, QA зеленый, дельты валидны. После архива:

- У новой (созданной архивом) master-спеки Purpose — TBD-заглушка; `validate --strict` считает TBD-маркер фейлом. Напиши настоящий Purpose сразу.
- INFO «requirement text is very long (>500 chars)» — не блокирует strict; WARNING (TBD/placeholder) — блокирует.
- Пакет, на чью master-спеку ссылается следующий пакет (MODIFIED-дельты), архивируется ПЕРВЫМ; до этого валидатор дает INFO о ссылке на несуществующую спеку — ожидаемо.

## Строгий валидатор: требования >500 символов и новые capability

Требования длиннее ~500 символов валидатор помечает WARNING, а CI-шаг `Validate specs (strict)` валится на первом WARNING, как только любой PR трогает specs/** — старые WARNING в активном пакете не «состариваются», их надо чинить сплитом. Правила сплита длинного требования:

- Каждый полученный requirement несет ≥1 `#### Scenario:` — сценарии крепятся к ПРЕДЫДУЩЕМУ заголовку, поэтому механический разрез текста оставляет первый кусок без сценария (ERROR «must include at least one scenario»). Разрез делай по границе прозы, переносом ≥1 существующего сценария под каждый новый блок — не создавай новые сценарии: покрытие-тесты реальных пакетов ассертят ТОЧНОЕ число сценариев (например «Сценариев в спеках: 29»), и +1 сценарий валит регресс.
- Каждый блок сохраняет RFC-2119 keyword (MUST/SHALL) — блок без него дает отдельный WARNING, strict его тоже считает.
- Перечисления (списки кодов, определений пяти флоу, матрицы условий) выноси в ОТДЕЛЬНЫЙ requirement («Стабильные коды причин», «Определения флоу 1–5», «Условия подтвержденной защиты») со своим сценарием — короткое core-требование со ссылкой на перечисление проходит, длинное перечисление отдельным блоком тоже.

Создание НОВОЙ capability при архивации пакета: файл `openspec/specs/<capability>/spec.md` обязан нести заголовки `## Purpose` (не TBD) и `## Requirements` — сырой экспорт требований без секционных заголовков валит CI «Spec must have a Requirements section», хотя локальный validate дельты проходил. Шаблон — по соседним спекам (pipeline/spec.md).

## Структура дельты

Файл дельты: `openspec/changes/<id>/specs/<capability>/spec.md`, заголовки `## ADDED/MODIFIED/REMOVED/RENAMED Requirements`; каждый requirement обязан нести хотя бы один `#### Scenario:` с шапкой `- **Когда** … - **то** …`.

## Покрытие маршрутов (I3) и архивация

flow_check сверяет маршруты кода с артефактами: корневое покрытие (sdd.md + openspec/specs/**/spec.md) применяется ВСЕГДА, покрытие дельтами активных пакетов — сверху. Если в проектной копии корневое покрытие включалось только «при отсутствии активных пакетов», архивация пакета обнуляет покрытие немодифицированных маршрутов — синхронизируй фикс из эталона фабрики.
