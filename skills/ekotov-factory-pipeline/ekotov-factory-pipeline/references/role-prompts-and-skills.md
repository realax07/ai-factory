# Ролевые промпты и скиллы: что куда кладется (формула Заказчика, J45)

**Формула**: скилл = инструкции КАК выполнять конкретную задачу (процедура,
команды, критерии); системный промпт роли = мир сабагента (где as-is, какие
контракты, какие скиллы и когда грузить, зоны записи, окружение в рамках его
attention). Best practice, относящаяся КО ВСЕМ ролям — в системные промпты;
к одной задаче — в скилл.

## J45: БА-скиллы (реализовано 2026-10-12)

- `skills/brainstorming/` — первая фаза elicitation (из obra/superpowers,
  адаптация): пересказ понимания одной фразой, вопросы по намерению кластерами,
  ≥2 альтернативы с trade-off, anti-scope. Идет ДО requirements-elaboration.
- `requirements-elaboration`: (а) нумерационный преемник FR/NFR — нумерация
  продолжает master-specs + архивные ТЗ, дубль между пакетами = дефект;
  (б) разбор утверждений Заказчика: «Утверждаю + текст» → директивы, каждая —
  отдельное ограничение/требование с дословной цитатой; (в) жизненный цикл:
  requirements.md в корне = ТЗ активного пакета, при архивации →
  docs/ba/requirements-<change>.md; (г) дубли контракта 1 сняты — скилл
  ссылается на контракт, не повторяет критерии качества.
- `openspec-authoring` — раздел «Декомпозиция tasks.md» (из sp-writing-plans):
  задачи-результаты, самодостаточность, критерии проверки, трассировка, порядок
  по зависимостям.
- verification-блок «Факты до заявления готовности» — во ВСЕ ролевые промпты
  agents/*.md (единый текст после раздела E16). НЕ скилл: относится ко всем.
- При переносе скилла из ~/.hermes/skills/research/ в фабрику: снимать префикс
  sp-, вписывать в таблицу скиллов роли, зеркалить в ekotov-wiki (промпты с
  шапками factory-version).

## J23: QA-контур без чеклиста (реализовано 2026-10-12)

- qa_case_author читает спеку напрямую; трассировка TC → Requirement/Scenario;
  qa_case_reviewer — 6 осей (покрытие сценариев спеки, негатив/границыы, дефекты
  спеки, воспроизводимость, данные, трассировка). Детали —
  `references/qa-artifact-gate.md`.
- STAGE_TABLE/flow_check/pr_validate/flow-enforcer — без qa_checklist;
  qa_checklist_agent → agents/archive/. Исторические чеклисты — append-only
  (checklists/archive/).

## Проверка зеркальности фабрика ↔ проект

Промпты и скиллы после правки в фабрике зеркалятся в ekotov-wiki (cp с
шапками factory-version = sha эталона, как в factory_init). Если проект
держит собственные доработки (J41-аудит планов в flow_check) — при синхронизации
эталонного файла переноси правку ТОЧЕЧНО, не слепой копией файла.

## J47: дизайн-контур (реализовано 2026-10-13)

- `design/tokens.html` — ЕДИНСТВЕННЫЙ источник токенов проекта (снимок прод
  `app.css :root`): дизайнер пишет токены только там, мокапы оттуда, dev
  переносит в app.css оттуда же; рассинхрон app.css ↔ tokens.html = дефект
  (ловит design_validator). До J47 токены жили в шапках мокапов И в app.css —
  два источника, рассинхрон ловился только глазом валидатора.
- `design/README.md` — дизайн-контракт: изменение токенов только через
  change-пакет (app.css — прод-код, зона dev); обязательные состояния
  (default/hover/focus-visible/active/disabled/error), WCAG AA, сетка 8px,
  один акцентный цвет, без внешних библиотек (ОГР-8).
- **`design/archive/` — as-is визуальное состояние**: после приемки пакета
  утвержденные мокапы переезжают в archive/ (append-only); новые итерации
  рисуются ОТ них, не с нуля.
- Иерархия источников design_validator: README-контракт → tokens.html →
  утвержденный мокап → app.css → спека (арбитр поведения).

## Ревью внешних библиотек скиллов (claude-skills и аналоги, J45+)

Стоящая задача: ревьюить внешние репо скиллов (например
alirezarezvani/claude-skills), брать релевантное, дополнять наши скиллы.
Порядок и правила:

1. **Смотри ВЕСЬ каталог скилла, не только SKILL.md**: у зрелых скиллов
   scripts/ (реальные инструменты, сотни строк), references/, templates/,
   hooks/ — ценность часто в них. Оценивай размер/состав (find + wc -l),
   читай Python-тулы, а не только описание.
2. **Безопасность перед адаптацией** (тексты инструкций = поверхность
   prompt-injection, скрипты = поверхность исполнения): grep по скриптам на
   сеть (requests/urllib/socket), exec/eval/__import__/pickle, base64-декод;
   по SKILL.md — curl|sh, base64 -d, /dev/tcp, injection-фразы; куда пишет
   (cwd/args — ок; expanduser/$HOME — помечать). Клонировать и сканить,
   не верить README.
3. **Дистиллируй, не копируй**: универсальные правила вливаются в НАШ скилл
   (brainstorming ← grill-me + confirm-understanding; implementation ←
   zero-hallucination-coder + minimalist; code-review ← pr-review-expert
   чек-листы + adversarial-персоны); чужедоменные шаблоны,
   TestRail/BrowserStack-интеграции и платные интеграции — не брать.
4. **Формула слоев** (см. выше): общая для всех ролей дисциплина (например
   verification-before-completion) — блок в системные промпты, НЕ скилл;
   builtin-скиллы Hermes (claude-design, design-md) копировать в фабрику не
   нужно — доступны всегда, достаточно документации в таблице скиллов роли.
5. **Адаптация фиксирует attribution**: источник и лицензия в шапке скилла
   (адаптация MIT-репо легальна), дистилляция ≠ копирование 808K тулкита —
   скилл-ядро (правила/таксономия/локаторы) без чужих интеграций.

Пример результата: `skills/playwright-pro/` — дистиллят 808K тулкита до ядра
(golden rules, приоритет локаторов, common pitfalls, flaky-таксономия);
проектные грабли (CDP-touch, Secure-кука) остались в промпте qa_automation.

## AGENTS.md — защищенный файл: правка только с согласия Заказчика

AGENTS.md (обеих реп) защищен платформой: правка сабагентом отклоняется всегда;
правка ПМ требует ЯВНОГО согласия Заказчика. Тихий путь не существует: запрос
согласия, оставшийся без ответа, = отказ (молчание ≠ согласие), повторные
попытки тем же инструментом запрещены. Рабочий порядок при необходимости правки:
подготовь точный diff → спроси Заказчика прямым вопросом с содержанием правки →
после явного «да» применяй → коммит через PR с [pipeline]-маркером (pm_bounds).
Субагенту в ТЗ передавай текст для вставки отдельным блоком («приложит ПМ»),
не отправляя его править AGENTS.md — он все равно получит отказ.

## Стоячие контракты роли — в системный промпт, не в текст делегации

Знание, переданное ПМ в пересказе делегации, теряется кусками (пропущенный
репорт, чужой формат мет, коммит мимо ветки) — каждый пропуск это круг CI.
Стоячие контракты роли (одни и те же на каждой задаче) вшиваются в
системный промпт роли при первом нарушении: dev — «репорт BUG-NNN = часть
коммита; ветка/worktree из ALLOW»; code_reviewer — точный машиночитаемый
формат review-файла (Вердикт: approve + Reviewer-Delegation: deleg_<id>
вплотную); regress_runner — freeze tooling после артефакта. В ТЗ делегации —
только переменная часть (что сделать, где артефакт, id меты готовой строкой
для копипасты). ПМ не носитель контрактов.
