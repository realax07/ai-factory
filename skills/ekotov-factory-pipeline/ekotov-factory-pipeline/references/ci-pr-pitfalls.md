# CI/PR-грабли фабрики и проекта (уроки BUG-AF-RECHECK + PO-рефакторинг)

Подключается к SKILL.md (перерос лимит размера — консолидация куратором).

## GitHub CLI

- `gh pr edit` на этих репо падает по GraphQL (Projects classic sunset) —
  title/body править через `gh api repos/<owner>/<repo>/pulls/<N> -X PATCH
  --input <file.json>` (JSON в temp-файле).
- Rerun красного job'а переигрывает СТАРЫЙ event payload (старый title/body).
  Фикс маркера в title требует нового push — rerun не помогает. Правка
  title/body через API ТОЖЕ не перезапускает CI (нет synchronize-события) —
  ретригер: пустой коммит на ветку PR (`git commit --allow-empty`).

## Контракт pr_validate для багфиксов

- В title/body PR обязателен маркер `[BUG-NNN]` (или `[change-id]`/`[chore]`/
  `[docs]`/`[ops]`). Словарь закрыт: `[test]` и `[pipeline]` маркерами НЕ являются
  — `[pipeline]` живет в сообщениях КОММИТОВ (PM_PUSH_POLICY), не в title PR.
- Маркер change-id тянет ПОЛНЫЙ релизный комплект ворот (approved-кейсы,
  review-файл, regress-final). Промежуточные PR (кейсы, QA-отчеты, доки волны)
 change-маркер не несут — их артефакты едут в финальный интеграционный PR пакета
  (иначе CI краснеет на собственном корректном артефакте).
- Репорт обязан матчиться glob'ом `BUG-<NNN>-*.md` и содержать раздел
  «Статус». Комплект из нескольких багов именуй `BUG-<NNN>-<slug>.md`
  (пример: BUG-001-af-recheck.md), не произвольным комплексным именем —
  иначе CI потребует переименования постфактум. Грамматика id: сегменты
  между BUG- и NNN — только A-Z0-9 (BUG-AF-RECHECK-001 валиден,
  BUG-video-001 с lowercase-сегментом — нет; бери следующий свободный
  BUG-NNN проекта). Scope Флоу 2 в маркере делегации — ТА ЖЕ грамматика
  (единая строка в flow_check + enforcer).

## Impact-гейт (J58): карта затронутого обязательна для change-PR

- PR с change-маркером обязан нести impact-карту — `openspec/changes/<id>/impact.md`
  ИЛИ секцию «## Impact» в design.md/proposal.md. Для `[chore]/[docs]/[ops]/[BUG-NNN]`
  карта НЕ требуется (механическая сверка работает всегда — не душить chore).
- Механическая сверка диффа с правилами (`scripts/impact_rules.json`, формат
  when[path-regex, status?]/require[path,label,hint]; новое правило = правка JSON без кода):
  `services/*/openapi*|contracts/` → перегенерированный contracts/openapi.json;
  новый `services/<name>/` → deploy/deploy.sh + deploy/RUNBOOK.md; `frontend/
  static|templates` → bump static_v; новый migrate_*.py → RUNBOOK. Расхождение =
  DENY с id правила и уроком релиза в подсказке (каждое правило — закрытый инцидент:
  openapi/static_v/deploy-матрица).
- exists-guard: require применяется только если целевой артефакт существует в
  HEAD-дереве репо (`git ls-tree HEAD`) — фабрика без contracts/ и services/ не
  DENY-ит собственные PR. Вне-git — guard не применяется, прежний консервативный
  DENY. CI передает дифф через env PR_CHANGED_FILES (строки «STATUS\tpath»),
  fallback — `git diff --name-status main...HEAD`.
- Шаблон карты рождается с пакетом: factory_init ставит
  `openspec/changes/_template/impact.md` (секции: сервисы/контракты/статика/
  deploy+RUNBOOK/миграции/тесты). СА пишет карту, code_reviewer сверяет с диффом
  (расхождение = blocker).
- flow_check rule 6: каждая тестовая функция обязана нести TC-NNN в docstring.
  Вставляя маркеры скриптом — внутрь docstring (`"""TC-..."""`), не перед ним:
  `TC-J57-001: """` парсится как integer с ведущим нулем → SyntaxError на
  collection во ВСЕХ job'ах сразу. Номер — ровно 3 цифры (regex `\d{3}`):
  «TC-X-01» правилом не матчится. У теста без docstring — добавь однострочный
  `"""TC-<домен>-NNN: …"""` (голое тело без docstring тоже нарушение). Прогон
  до пуша: `python3 scripts/flow_check.py <repo>`.
- H5 (до-J58 эра, действует параллельно): при MODIFIED/REMOVED дельтах
  change-PR обязан нести `test-model/impact/<change-id>.md`. J58-карта в
  `openspec/changes/<id>/impact.md` — канон, но H5 про нее не знает: положи
  проекцию-мостик (пара абзацев + ссылка на канон), иначе change-PR DENY-ится
  на финальном PR после всех остальных зеленых ворот.

## Маркер делегации (flow-enforcer pre_tool_call)

- Продуктовые задачи обязаны нести `paths=<файл1,файл2>` — без него честный
  PATHS_MISSING; «docs-only по умолчанию» не работает.
- `kind=docs` легален только для docs_task/chore_task.
- bypass — только по записи в `~/.hermes/state/flow-bypass-decisions.json`
  (repo/scope/action/expires); подстрока в goal без записи ничего не обходит.

## J50: ворота «UI-дельта ⇒ web-тесты»

- PR с дифом в `frontend/**` (или `services/*/frontend/`) при наличии макетов
  (`design/**` в change-пакете или проекте) обязан нести изменения в
  `tests/web/*.py` — иначе `PR_UI_TESTS_MISSING` (FAIL).
- Честный escape: маркер `[no-ui-tests]` в body PR с основанием ≥10 символов
  после маркера до конца строки; без основания = валидируется как отсутствие.
- Детект — env `PR_CHANGED_UI`/`PR_CHANGED_WEBTESTS` из flow.yml (git diff по
  base-ветке). Бэкенд-диф проверку не триггерит. Правило зеркалировать в
  проектный flow.yml ДИФФОМ (точечный блок), не файлом — см. правило зеркала
  в SKILL.md.

## Откат релиза и revert смерженного

- Деплой-скрипты пересобирают образы из SRC_DIR безусловно: откат «старым
  тегом» из актуального HEAD дает НОВЫЙ код под СТАРЫМ тегом и затирает
  подлинные образы. Перед откатом: найди коммит реального предыдущего
  деплоя (живой лог деплоя), сделай отдельный clone на нем и укажи SRC_DIR
  туда; подлинные старые образы сохрани под отличным тегом `*-orig-*` до
  деплоя. Верификация отката: кеш-маркер (static_v) в живом HTML +
  побайтная сверка ключевого статики-файла (sha256) с историческим коммитом.
- Revert фича-мержей — `git revert -m 1 <merge>`, от новых к старым.
  Статусные файлы, которые правят все PR (PRODUCT_BACKLOG), конфликтуют —
  разрешай сохранением ТЕКУЩЕГО состояния (ревертим код, не статусы
  бэклога). Ключевые файлы восстанавливай из первого родителя мержа:
  `git checkout <merge>^ -- <path>`.
- После реверта вычищай хвосты: `git ls-files` по каталогу фичи (осиротевшие
  модули — `git rm`), grep по ключевому слову фичи в коде (швы в общих
  файлах переживают частичный реверт). Полуотревчнутое дерево хуже
  неотревчнутого — перед PR: flow_check + смоук-сьют.
- Коммит синхронизации зеркал делай на той ветке, что несет его в main:
  перед коммитом `git branch --show-current`. Синхронизация, осевшая на
  фича-ветке, в main не попадает — cherry-pick на целевую ветку (устаревшие
  ворота проявятся как FLOW-ERROR в чужом PR).
- Пуш в уже смерженную ветку не попадает в main. Перед допушиванием
  `gh pr view <n> --json state`; опоздавшие коммиты — cherry-pick на свежую
  ветку от origin/main и новый PR. Коммиты-мимо-ветки ищи в reflog
  потерянного head: `git reflog <branch> | head`, sha из отчета дева.
- Корневая привычка: ПРОВЕРЯЙ `git branch --show-current` ДО первого `git
  add` в команде, а не перед commit — add на main с последующим `git push
  origin <branch>` пушит НЕИЗМЕННУЮ ветку молча, и цикл «CI красный — коммита
  нет на ветке» повторяется трижды.

## Восстановление делегации

- Делегация умерла посреди работы (провайдер 429, reset через N часов):
  до перезапуска осмотри `git log`/`git status` ее ветки — частично
  сконвертированные файлы и незакоммиченные патчи остаются в worktree.
  Передай наследнику контекст «сделано/осталось/базлайны», не начинай с нуля.
- Прогон полного web-набора проекта > 600s — background + уведомление;
  foreground timeout cap 600s.
- Базлайны «рефакторинг ничего не сломал» — через `git worktree add /tmp/wt
  main` и прогон того же файла на main; дельта пофайлово, worktree убрать
  после.

## Дайджест-тесты и shallow-клон CI

- CI чекаутит репо shallow: тест, прибитый к `git show <sha>:<path>`, в
  раннере дает exit 128 и красит ДАЖЕ docs-only PR (тесты гоняются на
  любом коммите). Пиши дайджест-тест ветвлением: коммит доступен — полная
  проверка с пином; нет — самосогласованность (пересчитай задокументированный
  алгоритм по ТЕКУЩЕМУ файлу и сравни со значением в коде). Способ вычисления
  дайджеста — комментарием в коде, иначе следующая правка не воспроизведет.
- Тест, кодирующий СОСТОЯНИЕ бэклога («пункт N открыт»), падает на первом же
  docs-PR после закрытия пункта. Предпосылочные ассерты обновляй в том же PR,
  что меняет состояние, — не обходи и не отключай.

## Ворота regress-final в CI (J51.3): shallow и локальные пути

- Артефакт regress-final несет строку `worktree: <путь>` — это ЛОКАЛЬНЫЙ путь
  машины прогона; в CI-раннере он всегда нечитаем. Нечитаемый worktree =
  WARNING (полагайся на проверку предка по коммиту), не STALE — иначе ворота
  ложны на каждом change-PR.
- Проверку предка (commit артефакта ∈ история PR-head) shallow-клон не может
  выполнить: merge-base по неполной истории дает «не является предком» даже
  для честного артефакта. Порядок деградации: локальный git → тихий `git
  fetch --unshallow origin` (РАСШИРЬ refspec до всех веток ДО unshallow —
  суженный refspec после unshallow оставляет origin/main отсутствующим и
  роняет свежестную сверку «измененные файлы не определимы») → GitHub API
  compare (base...commit, behind/identical = предок) → явный
  UNKNOWN_ANCESTRY с человеческим объяснением.
- В flow.yml проекта job'у, гоняющему pr_validate, ставь actions/checkout
  с `fetch-depth: 0` — дешевле, чем лечить симптомы в коде ворот.
- CI чекаутит ТЕСТОВЫЙ merge PR и main: артефактный коммит может быть
  предком ветки PR, но непрямым предком merge-коммита — сверяй по ветке PR.

## Harness-самотесты ворот: датированные коммиты

- Самотесты regress-ворот на синтетическом репо обязаны ставить
  GIT_AUTHOR_DATE/GIT_COMMITTER_DATE шагом ≥60с между эталонными коммитами:
  сверка свежести — целочисленное сравнение секундных таймстампов, коммиты
  одной секунды схлопывают fresh-ось и harness дает ложное «ось покрыта»
  (проверено ревьюером контрольным прогоном с датированными коммитами).
- Верифицируй harness на ПРЕ-фиксных версиях ворот (родители фикс-коммитов):
  harness, зеленый только на уже починенном коде, не доказывает покрытие
  класса. Кейсы нужны попарно: «на пре-фиксе было бы STALE, на фикс — PASS».
- Не заявляй в доках/коммитах «класс дефектов закрыт» до этой верификации —
  ревьюер ловит преждевременное обобщение отдельным замечанием и возвратом.

## Ревью-артефакты: коммит до merge

- Ревью-файл, не закоммиченный ревьюером, — это untracked: он молча
  путешествует за рабочим деревом между чекаутами и умирает вместе с
  worktree. Перед merge проверяй `git show <branch>:code-reviews/<id>/` —
  ВСЕ итерации должны быть в ветке; недостающие вердикты восстанавливай из
  отчетов делегаций с атрибуцией Reviewer-Delegation (коммит помечай как
  восстановление ПМ).
- Диспетчируя code_reviewer, сразу задай машиночитаемый формат в делегации:
  строка-заголовок «## Вердикт: approve|return»; «Reviewer-Delegation:
  deleg_<id>» — id ВПЛОТНУЮ к метке (regex J10 ищет deleg_ в шести
  неписьменных символах после метки — описательный текст между меткой и id
  рвет матч); задачи ревью — в имени файла (review-<NNN>-<task>.md) или в
  review-mapping.json. Иначе approve не покроет задачи и круг повторится
  (бывает и дубль-конфликт при cherry-pick опоздавшего мета-коммита —
  разрешай объединением, deleg_ вплотную обязателен).
- Неполный change-пакет не PR-и: check_change требует proposal+specs+design+
  tasks сразу. Пакет зреет на ветке через несколько агентских волн, PR —
  когда контракт 2 закрыт; иначе CI краснеет на собственном PR пакета.

## Тест-стенды переживают делегации

- После дев/QA-волн проверяй `ps -eo etime,args | grep uvicorn`: стенды
  (порты 8080/837x, scratch-роутеры в /tmp) переживают смерть делегации
  и копятся сутками. Не мусор: процессы прод-контейнеров (0.0.0.0,
  docker-неймспейс), fail2ban, gateway. Осиротевшие тест-файлы после отката
  фичи дают collection error — удаляй вместе с откатом (след в git-истории).
- Гаси стенды по PID, не `pkill -f <паттерн>`: паттерн из пути/имени БД
  стенда встречается в АРГУМЕНТАХ твоей же команды — pkill убивает
  собственный шелл посреди цепочки. Если уже нужен паттерн — бери
  класс с непримыкающим классом символов (`qa41_ap[p].db`), чтобы он не
  совпал сам с собой.

## Ворота regress-final: свежесть vs сам артефакт

- Свежестная сверка «артефакт новее измененных файлов» НЕ должна считать
  измененными сам артефакт и test-model/regress/<change>/** того же change:
  артефакт всегда новее кода, который удостоверяет, — иначе
  REGRESS_FINAL_STALE срабатывает на каждом change-PR навсегда. Чужие файлы,
  тронутые после прогона (flow.yml, тесты), — по-прежнему STALE.
- Маппинг regress-доменов дедупь ДО прогона: набор [tests/api, tests/web,
  tests] рождает коллизию conftest для bare-импортов на КОЛЛЕКЦИИ (exit 2
  до первого теста) — общий домен tests/ поглощает частичные.
- **Freeze tooling**: фабричные фиксы ворот зеркаль в проект ДО regress-final
  — зеркало/мета-коммит после артефакта = файл «тронут после прогона» →
  STALE → полный перегон (три цикла на одном релизе). То же для ЛЮБЫХ
  ops/инфра-коммитов в цикле релиза (ffmpeg-источник в Dockerfile, доки):
  коммит после финального прогона = честный перегон (STALE механический);
  инфра-фиксы вноси до финального прогона, в самом конце — только
  test-model/** артефакты того же change (они из свежести исключены).
  **Тириг (J54)**:
  полный regress-final — пакетно перед плановым деплоем; на каждый change —
  smoke + regress своего куска; xdist (pytest -n auto) с изоляцией
  session-фикстур между воркерами.

## factory_init --force на живом проекте

- --force перезаписывает проектный `.github/workflows/flow.yml` фабричным
  шаблоном: у проекта имя required-check (ruleset) и кастомные job'ы —
  закоммитишь шаблон = все PR навсегда BLOCKED (проверку не сдать). После
  --force первым делом `git checkout -- .github/workflows/flow.yml`.
  (Финальный фикс: factory_init больше НЕ перезаписывает существующий
  проектный workflow даже с --force — копирует только при отсутствии.)
- Синк скриптов (flowctl/session_check/pr_validate + замкнутость импортов)
  требует полного regress-контура — это дев-волна, не раскатка. Безопасное
  подмножество для прямого прогона: docs/glossary.md, agents/*.md (снимает
  FLOW-WARNING протухших промптов), тест-бутстрапы. Осиротевшие незакоммиченные
  копии после сброса — добить отдельным [chore]-PR (пустое дерево — значит
  файлы уже в main).

## Видеохостинг (video-1.1, прод)

- Сервис video — 7-й контейнер :8380 (порты НЕ публикуются), ffmpeg
  статический с SHA256-pin в Dockerfile. Том videos-data: создать и
  chown 10001:10001 ДО старта video; каталог `/data/videos` — создать В ТОМЕ
  wiki-data до пересоздания nginx (ro-маунт без каталога = nginx не
  поднимается, даунтайм точки входа).
- Откат: RELEASE_TAG=video-1 + полный набор *_IMAGE, video ИСКЛЮЧИТЬ из
  up-набора (compose stop video); таблицы video_* аддитивны, откату не мешают.
- Том нельзя монтировать ВНУТРЬ read-only маунта контейнера: docker не может
  создать mountpoint под ro-деревом → OCI runtime error, контейнер не стартует
  (weather: кэш-том на /data/cache при ro-БД на /data). Маунтпоинт выноси на
  верхнеуровневый путь вне ro-маунта (/cache), каталог создавай в образе
  (RUN mkdir + chown uid сервиса) — пустой том наследует владельца из образа.
  Локальный стенд с другой раскладкой маунтов это маскирует — проверяй подъем
  по CI-сценарию на свежих томах (down -v).
- regress-контур — канонический `scripts/qa_stand_up.sh` из репо (reset|up|health|stop, параметризация портов/путей, guard занятых портов; конфиг — deploy/qa-stand-nginx.conf с bind 127.0.0.1); /tmp-заготовки стенда выведены из оборота. xdist: 3.8.0 в venv, api `-n 4` безопасен (кроме fastline/fast2 — глобальная fast-line стенда, взаимные 409 на -n), web — только сериально, regress-final — сериально (гайд в репо: docs/guides/xdist-regression-echelons.md).
- ffmpeg fallback: пинуй ТОЛЬКО датированные иммутабельные autobuild-релизы BtbN
  (тег `autobuild-YYYY-MM-DD-HH-MM`, ассеты не перекатываются); катящийся `latest`
  — запрещен: пин на нем ломался sha-mismatch трижды за сутки (один прожил часы).
  Смена пина = осознанная смена релиза: скачай ассет, сними sha256 вручную,
  обнови URL+SHA256 в Dockerfile парой. Быстрый диагноз «кто виноват»: в логе
  сборки «primary source unavailable, trying fallback» + «sha256 <hex>» ≠ пин —
  дрейф ассета, не сеть.

## Гигиена веток: unmerged-остатки и поглощение main

- Инвентаризация: для каждой `origin/<branch>` — merged в main? + ahead-счетчик + дата последнего коммита. MERGED + ahead:0 — кандидат на удаление без разбора.
- Unmerged-остаток: `git cherry origin/main origin/<b>` — `+ <sha>` = коммит, не поглощенный по содержанию. Прежде чем возить его в PR, проверь, не эволюционировала ли та же фича в main другой веткой (grep ключевого символа в `git show origin/main:<file>`, сравни счетчик вхождений с веткой): счетчик на main БОЛЬШЕ = фича поглощена и развита, ветка — устаревший срез, возить ее контент в PR не нужно.
- Закрытие unmerged-остатка: PR `[chore] archive: <branch>` с доказательством поглощения в body. При конфликте мержа резолюция В ПОЛЬЗУ main для эволюционировавших файлов, затем ПОЛНЫЙ тестовый сюит до мержа: из merge-резолюции утекает устаревшее тело функции незаметно, падающий dependent-тест = утечка резолюции.
- Удаление origin-веток после мержа закрывающего PR: `git push origin --delete <branch>`; локальные — `git branch -D`. Активные ветки открытых change-пакетов НЕ трогать (чистка — после их релизов).
- Ветка с уникальной историей (ahead > 0), чей контент поглощен или объявлен ненужным: перед удалением поставь архив-тег на tip (`git tag archive/<branch> origin/<branch>` + push) — история восстановима навсегда, ветка не висит. Пакетно: слитые ветки удаляй списком (`git branch -r --merged origin/main | grep -v main | sed 's| *origin/||' | xargs -n 20 git push origin --delete`), неслитые — только по одному с разбором ahead-счетчика.

## Ветка на роль; интеграция — dev-lead (J57, возврат к J9)

- Сабагент коммитит ТОЛЬКО в свою ветку (flowctl prepare: ветка из cid в worktree);
  ревьюеры/фиксеры — свои ветки, не ветка dev'а. ПМ НЕ делает checkout/reset/cherry-pick
  в репо с активной делегацией — дважды снесенная незапушенная работа dev'а;
  свои правки — своя ветка через PR; из git — только merge PR.
- Сборка пакета: `flowctl integrate <repo>` (механика: ветки пакета из реестра,
  REFUSE при активных сессиях, integration/<cid>) → сабагент dev-lead (узкий бриф,
  без контекста продукта) собирает и разгребает конфликты → один интеграционный PR.
- Защита: push_gate PM_PUSH_POLICY — ПМ-push в продуктовое репо без маркера
  [integrate]/[pipeline] в HEAD или merged-HEAD = DENY; фабрика исключена всегда
  (docs-заявки легитимны). После изменения enforcer — переустановить в ~/.hermes
  (копия plugins/flow-enforcer/enforcer.py), действует только с новых сессий.
- Складывание артефактов ролей в интеграционную ветку: черри-пик-цепочки
  конфликтуют, когда один файл трогали две роли (dev переписал web-тест,
  QA дописал отчет) — вместо черри-пиков возьми содержимое по файлам из
  ветки-новейшего владельца: `git checkout <source-branch> -- <пути>` одним
  коммитом [integrate]. После — сверка, что версия каждого файла = новейший
  владелец, а не промежуточный срез.

## Зеркало скрипта = его импорт-замкнутость

- Синхронизируя фабричный скрипт в проект одним файлом, проверь его импорты:
  flowctl без session_check (change_id_problem) падает AttributeError на
  первом прогоне, pr_validate без check_regress_final не несет ворот.
  Зеркаль список: сам файл + все функции/модули, на которые он ссылается;
  после зеркала — `python3 -c "import ast; ast.parse(...)"` и прогон целевой
  команды на проекте (flow_check OK), а не только синтаксис.

## BA-роль: когда нужен requirements-артефакт

- Если требования пишет Заказчик сам (дословная заявка в бэклоге + ответы
  на ОВ-вопросы в чате), артефакт requirements.md НЕ создается — дословная
  заявка и есть requirements (первоисточник, ноль искажений пересказом);
  машина BA-артефакта не требует (ворота change-PR: impact/approved/
  reviews/regress). Зафиксируй в change-пакете запись «роль BA выполнена
  Заказчиком» — иначе следующее ревью спросит «а куда дел BA».
- BA включается только когда требования надо СОБИРАТЬ из разрозненных
  источников (несколько заметок, старые обсуждения, устные вводные) —
  прецедент: большой фича-релиз с requirements.md и ОВ-матрицей.
