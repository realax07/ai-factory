# Матрица гейтов в CI: применимость к среде раннера

Перед добавлением гейта в flow.yml проверь, доступна ли ему среда CI — гейт, зависящий от локального состояния, в CI дает ложный FAIL:

- **pm_bounds_check НЕ в CI**: требует реестра сессий `~/.hermes/state/active_sessions.json`, которого на раннере нет; без него консервативная ветка считает ВСЕ коммиты ПМ-скими → FAIL на любой пуш. Гейт локальный (приемка). Без реестра `author_of_record` пуст — гейт не отличит роли.
- **pm_bounds параметризован**: защищенные пути настраиваются env `PM_PROTECTED_EXCLUDE` (csv). Фабричный дефолт защищает `contracts/` (контракты конвейера); продуктовый репо задает дефолт-исключение `PM_PROTECTED_EXCLUDE=contracts/` — там это OpenAPI-контракты продукта, не конвейера. При переносе гейта в новый проект сверяй список.
- **check_auth_timing + codegraph — В CI wiki**: stdlib-only, детерминированные, ломаются только при реальном нарушении (auth-тайминг, потеря I3-покрытия импортов). Живой прогон перед включением обязателен.
- **Контекстные различия копий pm_bounds_check (проект ≠ фабрика)**: PROTECTED_PATHS в фабрике включает `contracts/`, в продуктовом репо этот путь исключен (там это легитимный продукт-артефакт). Расхождение осознанное; при синхронизации ядра pm_bounds_check переносить ПОЛНОСТЬЮ нельзя — сверять PROTECTED_PATHS отдельно.
- **Прогон локального скрипта из execute_code: всегда передавай cwd явно** (`subprocess.run(..., cwd=...)` или shell `cd`): без него `ls scripts/`, `diff` и относительные пути молча выполняются в cwd сессии и показывают ДРУГОЙ репозиторий — «идентично, 0 различий» бывает артефактом сравнения файла самого с собой. Вывод, противоречащий ожиданию, перепроверь абсолютными путями + md5sum. Туда же: передавай `encoding="utf-8", errors="replace"` — вывод git/ls по этим репо содержит кириллицу и не-UTF8 байты, строгий decode падает посреди вывода и роняет шаг.
- **Стейл-statusCheckRollup у PR**: после ретриггера пустым коммитом GH может продолжать показывать FAILURE от старого SHA, хотя API `commits/<sha>/check-runs` на новом SHA — success. Диагноз: сравни `gh pr view --json statusCheckRollup` с `commits/<head_sha>/check-runs`; если расходятся — закрыть заблокированный PR (`gh pr close`) и пересоздать с того же head: свежий PR поднимает свежий rollup.
- **Поля PR разбирай python'ом**: `gh pr view <n> --json statusCheckRollup,state` + `json.loads` — jq-инлайн с одинарными кавычками внутри `bash -c` не парсится, цикл ожидания чеков сгорает впустую.
