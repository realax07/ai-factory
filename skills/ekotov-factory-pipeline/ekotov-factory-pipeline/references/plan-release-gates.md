# План релиза — обязательный артефакт ворот (J41)

Урок P15 (add-wiki прошел без PLAN-файла): план релиза — это кто/что/этапы/воркфлоу, пишет ПМ ДО диспатча СА; СА лишь детализирует в tasks.md и план не переписывает.

## Форма

- Легальные пути: `PLAN-<change-id>.md` в корне репо ИЛИ `PLAN.md` в каталоге пакета.
- Обязательная строка: `Флоу: N` (N 1–5) с обоснованием выбора.
- Состав: цель; этапы/волны с ролями; развилки Заказчика; план прогонов по наборам; критерий закрытия.

## Три контура ворот

1. Старт: `flow_transition` check_create_change и check_dev_task (транзитивно) возвращают `PLAN_RELEASE_MISSING` / `PLAN_FLOW_UNDECLARED` — flowctl prepare не пускает СА/dev.
2. Обход: `delegate_watchdog` метит bypass-делегации `undelivered_bypass` — результат делегации в обход flowctl не считается доставленным (кандидат 2b J39).
3. Мерж: проектный `flow_check` ловит активный change без плана / без воркфлоу в плане.

Остаточный риск: ПМ может править сами скрипты — закрывается только branch protection и ревью Заказчика.

## Старые пакеты без планов

Если план нужен для зелености ворот мержа — только явная аудит-заглушка с пометкой «план восстановлен постфактум, закрывается при архивации пакета» (не выдавать за подлинный план); вымывается при архивации.

## Маркер PR (фабрика)

pr_validate фабрики требует маркер в TITLE PR: [pipeline] не входит в белый список ([BUG-NNN]/[change-id]/[chore]/[docs]/[ops]) — используй [chore] для инфраструктурных ворот. Маркер в body не помогает — проверяется title. Правка title/body после пуша НЕ перезапускает CI — закрыть и переоткрыть PR.

## J42 — CI-ворота на пушах сабагентов (бэклог, не реализовано)

Идея Заказчика «git даст знать, если этапы пропущены, на уровне сабагента» — механика такая: git сам этапы не знает, проверки несет flow_check в CI; required checks привязаны к PR в защищенную ветку, голый пуш произвольной ветки CI не триггерит (в flow.yml триггеры push: main + pull_request). Варианты: A — правило «сабагент завершается PR'ом» (ноль кода: flow_check гоняется на PR автоматически, красный = ошибка ПМ); B — триггер `push: branches: ["pipeline/**"]` в flow.yml. Замечание: пуш сабагентом технически не отличим от пуша ПМ (общий git-креденшал на машине) — правило дисциплинарное; техническое разделение = deploy-ключи/branch protection с ревью.

## Потенциальный контур 4 — платформенный перехват делегаций (обсуждается, не реализовано)

Hermes `pre_tool_call` хук (плагин с `ctx.register_hook` или shell-хук в config.yaml) срабатывает перед КАЖДЫМ вызовом инстру, включая delegate_task, и может вернуть `{"action": "block", "message": ...}` — валидация делегаций через `flowctl prepare` становится неизбежной на платформенном уровне, а не дисциплинарной: ПМ физически не может диспатчить мимо ворот. Обход = отключение хука в конфиге (видимое действие в защищенных файлах). Требование для реализации: жесткие маркеры в goal каждой делегации (роль/repo/change-id), иначе false-blocks. Решение за Заказчиком.

## Дистрибуция контура 4 из фабрики (согласовано Заказчиком)

- Плагин живет в фабрике: `plugins/flow-enforcer/` (plugin.yaml + код хука + тесты). Установка на любой машине — штатный `hermes plugins install realax07/ai-factory --ref <полный коммит>`; пин обязателен — обновление только после проверки совместимости API хуков.
- Плагин ПЕРЕЖИВАЕТ обновления Hermes: плагины в `~/.hermes/plugins/`, агент обновляется в `~/.hermes/hermes-agent/` — каталоги раздельные. Риск только в изменении API хуков новой версией агента.
- Включение — opt-in: `plugins.enabled: [flow-enforcer]` в config.yaml (сознательный акт, фиксируется) — не путать с gateway-хуками (`~/.hermes/hooks/`, trusted-by-placement без opt-in); gateway-хук для энфорсера отклонен, включение защиты должно быть явным.
- factory_init.py при развертывании конвейера в проект ставит/обновляет плагин и правит plugins.enabled.
