# Дизайн-фаза: design_task, ui_designer, design_validator (паттерн Р4/Р5)

Перенесено из SKILL.md при разбиении. Пакеты с UI-дельтой проходят дизайн-фазу ДО dev-задач фронтенда (требование Заказчика: «Дизайн не забудь» / «У нас есть дизайнер» / «Не забудь валидатора дизайна запустить, после реализации»).

## Процедура

1. СА закладывает в tasks.md задачу `[design] ui_designer` (мокапы в `design/`, standalone HTML на токенах V3 «Бумага» из `app.css :root`, БЕЗ внешних библиотек/CDN — ОГР-8). Наличие задачи в пакете ОПЦИОНАЛЬНО: в чисто бэкенд/инфра пакетах `[design]`-задач не пишут, ворота их не требуют.
2. Приготовь decision-record решения об утверждении requirements (или иное, покрывающее задачу) — approval_ref для design_task.
3. prepare через flowctl: `--action design_task --role ui_designer --path "design/**" --task <N>`; затем `flowctl run --correlation-id <id>`, затем delegate_task (adapter=manual). НЕ пускать ui_designer как dev_task (WRONG_ROLE — сигнал использовать design_task, не поломка) и не внеполосно.
4. Артефакты: standalone HTML-мокапы, открываются файлом без сервера; варианты — в ОДНОМ файле секциями с ярлыками «Вариант А/Б/В» (Д-паттерн); REPORT дизайнера — в design/.
5. **Развилка Заказчика — утверждение мокапов**: HTML в Telegram НЕ рендерится — сырые MEDIA-пути на .html приходят файлами, которые Заказчик не откроет. Рендери скриншоты headless-браузером (playwright из venv wiki; полный page.screenshot + по element.screenshot на каждую секцию-вариант, viewport ~1440×1000) и шли PNG как фото в чат, по одному на вариант, с подписью-вопросом. dev НЕ стартует до зафиксированного выбора; выбор фиксируется decision-record + уточнением в tasks.md. Акк на «макеты утверждаю» = разрешение dev-волны — не задавай повторный вопрос.
6. dev внедряет строго по утвержденному мокапу; затем design_validator сверяет фактический вид против мокапа — он ОБЯЗАТЕЛЕН после реализации. **Диспатч через СВОИ ворота**: действие `design_validation` + роль `design_validator` (STAGE_TABLE Флоу 1), зона — путь review-файла `test-model/reviews/<change>/review-NNN-design.md`. До расширения ядра пары действие+роль не существовало и машина DENY все подстановки (code_review→code_reviewer, qa_automation→qa_automation, qa_review→INVALID_GATE «нет кейсов в new/») — поймав такой DENY, сначала синхронизируй ядро (эталон фабрики своим PR-процессом с `[chore]`-маркером, затем cp в проект байт-в-байт), не подбирай чужую роль. В состав qa_automation дизайн-проход не включать: зона tests/** не покрывает test-model/reviews.

## Правила ворот

- J10 к `[design]`-задачам не применяется (артефакт не код, приемка утверждением); дизайн-фаза опциональна по составу пакета.
- `design_task` и `design_validation` обязаны быть в STAGE_TABLE Флоу 1 в ОБОИХ репо (проект + фабрика) — при DENY «действие не входит в граф» свери ядра байт-в-байт; расхождение устраняй синхронизацией (направление — по содержанию, директива двусторонней синхронизации), эталонный PR фабрики требует `[chore]`-маркера в title (`[pipeline]` pr_validate не знает).
- Зона записи ui_designer — `design/**` только (role_zone_policy); отчет дизайнера тоже в design/ (REPORT-файл) — не расширяй зону ради него.
- ТЗ дизайнеру: решения эскалаций Заказчика (один макет vs варианты, какой вариант сетки) передавай прямо в тексте ТЗ — дизайнер работает без контекста чата; стиль — токены V3 «Бумага» из `app.css :root` дословно, standalone (ОГР-8), favicon-эскиз без отдельной развилки (дизайнер решает сам, если Заказчик делегировал).
- Мокапы НЕ коммитит и НЕ пушит дизайнер: их принимает ПМ в PR-цикл задачи [design] (маркер PR для состава design/ + tasks-строки — `[docs]`, не change-id: test-model комплекта нет).
- **PR ранних стадий пакета — тоже `[docs]`, не `[change-id]`**: change-маркер в title включает check_change в pr_validate, требующий ПОЛНЫЙ QA-комплект (impact/чеклист/approved-кейсы/review) — на PR создания пакета, правки tasks.md или design-файлов его еще нет = гарантированный красный flow. Локальная проверка маркера перед пушем: `python3 scripts/pr_validate.py . --id "[docs] <текст>"` — OK до пуша. Распространяется на phase-0 операции: закрытие `[x]` задач утверждения/архивации, decision-файлы, чистку веток.
- **[P]-маркер обязателен в tasks.md ДО prepare с --parallel**: flowctl подтверждает параллель ТОЛЬКО литеральным `[P]` в строке задачи (формат `- [ ] 2.1 [P] [M] Dev: …`, маркер сразу после чекбокса, до размера); `--parallel` без `[P]` = UNKNOWN MISSING_INPUT, потерянный цикл prepare. Волнам, идущим параллельно, ставь `[P]` при написании tasks.md, не постфактум.
- **Мокапы/скриншоты Заказчику — отрендеренные PNG в чат, не пути файлов** (см. шаг 5): «сюда скидывай файлы» = рендерь скриншоты каждой секции (playwright, page/element screenshot) и шли фото по одному с подписью-вопросом; слово Заказчика («вариант В», «красиво», «favicon ок») — дословно в decision-record.
- **Кеш-маркер data:URI favicon — ВНУТРЬ SVG, не хвостом**: суффикс `?v=N` после `</svg>` в data-URI — непарсимый URL (Chromium ломает XML, naturalWidth=0, проверено пробой). Маркер зашивай комментарием в тело SVG (`<!--cache:v=N-->`): бамп N дает новый URI. Отклонение от буквы требования «URL с ?v=» — задокументируй для design_validator.
- **Если после dispatch дизайнера/дев-волны SA-действие DENY «не входит в граф» — сначала сверь ядро фабрики с проектом** (diff flow_transition.py/flow_check.py байт-в-байт): action мог выпасть из фабрики при enforcement-поставке. Синхронизация — PR в фабрику (cp от проектного эталона), тесты обоих сьютов, потом повтор prepare. Не подменяй действие чужим (dev_task за ui_designer = WRONG_ROLE) и не ходи внеполосно.
- **Зона сессии задается до запуска — но живую сессию можно расширить**: правка zones записи в `active_sessions.json` + запись в lifecycle-history решением ПМ (кейс: rename-UI потребовал шаблон gallery.html, не заложенный в зоны prepare). Проверь ДО расширения: зоны параллельных сессий не пересекаются с добавляемой. После расширения finish проходит по новой зоне.
- **finish без существующего файла отчета → blocked, и повторный finish его не снимает**: если REPORT делегации некуда положить в репо по ее зоне записи, запиши резюме приемки ПМ в файл вне репо (`~/.hermes/state/reports/<corr>-dev-report.md`) и передай путь в finish. Снятие blocked — тот же finish + `--pm-resume` (только для gate ERROR/SKIPPED-дефектов; FAIL/ZONE — не обходится).
- **Ре-ревью design-файла — каноничное имя по шаблону политики**: зона роли — литеральный шаблон `review-NNN-design.md`; содержательное имя (`review-005-design-fix.md`) вне шаблона = DENY ZONE_OUTSIDE_POLICY и потерянный цикл. Различай циклы заголовком/телом отчета, не именем файла.

## Мобильная вёрстка новой UI-зоны — часть дизайн-фазы, не фоллоу-ап

Новая зона обязана нести @media-паттерны существующего соседнего компонента
сразу (для канбана: свайп-контейнер + scroll-snap + колонки 82vw + тач-таргеты
≥44px при ≤480px; 481–768px — десктопный ряд). Заказчик проверяет мобильную
версию первым после деплоя — непокрытая новая зона = «всё поехало» + отдельный
фикс-цикл (CSS-правка → regress-final перегон → деплой). Тесты: device-эмуляция
iPhone-класса 390×844, реальные CDP-свайпы. Правка design-дельты под новое
поведение — через СА-амендмент, не правку спеки под код.

## Роль BA (business analyst): когда включать

BA включается ТОЛЬКО когда требования надо собирать из разрозненных кусков
(несколько заметок, старые обсуждения). Когда Заказчик пишет требования
дословно в чате — его заявка + ОВ-ответы в бэклоге = requirements (роль
выполнена Заказчиком лично; зафиксируй это в СА-пакете). Ворота BA-артефакт
не требуют — машина пропустит, но запись в пакете держит семантику чистой.

## Типовые находки design_validation и их фиксы (ПМ, до ре-ревью)

Валидатор меряет getComputedStyle через playwright против значений мокапа; дефект = «интерактивный элемент без единого CSS-правила», «цвет вне палитры (не var(--…))». Часто возвращаемые находки и рабочие фиксы:

- **Задвоенный класс-контейнер** — JS собирает блок функцией, возвращающей контейнер с тем же классом, что и постоянный wrapper в render-функции: вложение = двойной padding + двойной border (контент в 2× отступе от края по мокапу). Фикс: переносить ДЕТЕЙ встроенного контейнера в wrapper, обертку выбрасывать.
- **Постоянный DOM-узел (id из разметки) внутри перерисовываемого контейнера** — сборщик шапки забирает узел по id (getElementById + appendChild) внутрь очищаемого контейнера: `container.textContent = ""` на следующем рендере уничтожает узел, повторный getElementById дает null, сборщик падает — модалка ломается на ПЕРЕОТКРЫТИИ при зеленом первом открытии. Фикс: изъять узел (removeChild) ДО очистки и передать сборщику аргументом; в сборщике — fallback-создание узла при отсутствии (self-healing). Репро фикса — именно цикл «открыть → закрыть → открыть», первого открытия недостаточно.
- **Дубль CSS-правила из старой задачи перебивает новое** — прежнее правило для того же класса стоит ниже в файле и перекрывает мокапные значения (другой gap/margin). Фикс: удалить дубль целиком после grep'а по шаблонам (новое правило должно покрывать все use-сайты), не наращивать специфичность.
- **Два ритма одного компонента** — часть пунктов стилизована инлайном (общий CSS вне зоны задачи), часть правилом. Фикс: распространить правило на общий класс, инлайны убрать; валидатор меряет gap/выравниание по ВСЕМ пунктам списком.
- **СТРУКТУРА РАСКЛАДКИ — сверять с мокапом отдельно, не только классы/токены.** DV, проверяющий классы, токены, состояния и тексты, пропустит структурный сьезд: в реализацию может проникнуть лишний контейнер уровня макета (например, grid-колонка «дерево слева 280px + контент справа» там, где мокап — ОДНА колонка .content с деревом в потоке под тулбаром). Внешне: «все сжато как под мобилу, форма вылезает за плитку» — контент зажат вдвое лишним columns/offset'ом, при этом каждый класс по отдельности соответствует мокапу. В ТЗ design_validator закладывай пункт «структура макета: топология контейнеров и раскладка 1:1 с мокапом (дерево/сайдбары — на своих местах, без лишних grid-колонок)», и делай это в ПМ-приемке до design_validation: html тело реализации против html тела мокапа, сравнение иерархии контейнеров, не только списков классов.
