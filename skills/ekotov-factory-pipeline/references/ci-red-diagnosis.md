# Отладка красного CI: патологии, специфичные для этих репо

Дополнение к SKILL.md «Отладка красного CI: иди по логу джобы, не гадай».

## Известные патологии (диагноз без долгого копания)

- **openspec validate --all --strict валит большинство айтемов, включая нетронутые спеки и
  заархивированные пакеты, все WARNING «Requirement text >500 characters»** — CI ставит
  `@fission-ai/openspec@latest`, апстрим выкатил версию, поднимающую WARNING до fail strict.
  Проверка: локальный CLI известной-good версии на том же коммите — зеленый. Фикс — пин версии
  в flow.yml отдельным [chore]-PR (сначала источник красноты, потом фича); апгрейд CLI —
  осознанная контентная задача (разбиение длинных requirement'ов по всем спекам).
- **pr_validate FAIL «маркер ID не найден»** при явном маркере в тайтле — `gh pr edit` может
  упасть с GraphQL-ошибкой (Projects classic), не изменив тайтл; тайтл править через
  `gh api -X PATCH repos/<owner>/<repo>/pulls/<n> -f title=...`.
- **pr_validate FAIL «артефакты отсутствуют» на ВСЕХ dev-PR пакета сразу, хотя артефакты существуют** — QA-комплект (impact/чеклист/approved-кейсы/review) живет на несмерженной ветке: pr_validate исполняется на checkout'е PR (merge-коммит в main) и видит только то, что УЖЕ в main. Фикс — интеграционный PR `[chore]`: cherry-pick QA-коммитов на актуальный main (конфликты сверить merge-tree до пуша), мерж; затем локальная симуляция на worktree main'а с `GITHUB_HEAD_REF=<ветка PR>` + `check_change(...)` — нулевой missing = dev-PR разблокированы. «Артефакты есть в репо» значит «есть в main», не на ветке.
- **После мержа фикса источника красноты в main открытые PR НЕ перегоняются** — checks остаются FAILURE от старых SHA: ретриггер пустым коммитом в КАЖДУЮ head-ветку (`git commit --allow-empty` + push), затем сверяй rollup. Очередь мержа dev-PR одного пакета — по координационным условиям ревью-файла (кто после кого, какие дубли выбросить при ребейзе); конфликт ребейза резолвись программной сверкой (общие функции байт-в-байт, версия ветки — надмножество), не «на глаз».
- **«no checks reported» на новой ветке** — workflow без `workflow_dispatch`; ретриггер —
  пустой коммит в ветку (push → pull_request-триггер).
- **pip при сборке образов падает сетью** (BrokenPipe/RemoteDisconnected на /simple/<pkg>
  при живых ретраях, весь провал внутри step'а pip install, ни одной строки про код/тесты) —
  сетевой flaky раннера, не содержательный фейл: один ретриггер пустым коммитом (после двух
  — стоп, правило SKILL.md).
- **e2e/compose краснеет на pull'е образов: 429 toomanyrequests от registry.docker.io** — Docker Hub
  rate limit анонимного пула IP раннеров; бьет ТРАНЗИТИВНО по всем PR (тянутся и базовые образы
  нетронутых сервисов), дифф PR ни при чем. Диагноз: упавший step — pull образа, в логе 429/
  toomanyrequests; час назад тот же workflow был зеленым. Тактика: транзитное окно (~1 ч) → один
  реран failed-джобы; системное лечение — авторизация pull'а (DOCKERHUB_TOKEN в секретах, лимит выше
  и IP-пул не общий) или стаб сторонних сервисов (см. следующий пункт).
- **compose НЕ ВИДИТ локально собранных образов — подмена image на готовый локальный тег не работает**:
  compose/buildkit для любого тега, не собранного в ЭТОМ же workflow-шаге, делает pull с docker.io,
  даже если тег лежит в локальном docker (собственный `ekotov-wiki/frontend:...` тоже потянет).
  Стаб стороннего сервиса в e2e: в том же шаге ДО `compose up` собрать стаб (`docker build -t
  <stub>:local -f <путь-Dockerfile> .`) и подставить в compose-переменную дефолтного образа
  (`NETDATA_IMAGE=<stub>:local compose up`); healthcheck стаба привести совместимым (`healthcheck:`
  в Dockerfile стаба или `docker update --health-cmd` на поднятый контейнер). Путь Dockerfile
  сверять по репо, не по памяти (`deploy/Dockerfile.*` может не существовать — фактический
  `services/frontend/Dockerfile`). Кандидаты на стаб — сервисы с дефолт-образом из compose
  (`${VAR:-third-party:tag}`), на которые никто не ссылается: нет depends_on, нет location в
  nginx-конфах, e2e-тесты проверяют только ссылку/линк. По позиции Заказчика сторонний сервис
  (netdata) не модифицируем — заглушка только в e2e-workflow, прод-compose.yaml не трогать.
- **test_flowctl в проекте массово краснеет на ZONE_OUTSIDE_POLICY** — тесты ядра писаны под
  фабричную политику (src/**), проектная — осознанная адаптация (backend/frontend/contracts).
  НЕ регресс правки ядра: фиксируй базу (список FAILED отсортированный), stash, прогон, diff
  списков — правка легитимна при идентичных списках; синхронизация тестов с проектной
  политикой — бэклог фабрики.
- **pr_validate FAIL «маркер ID не найден» ПОСЛЕ успешной правки title через REST** —
  ретриггер-ран читает title из GITHUB_EVENT_PATH, снапшот которого заморожен НА МОМЕНТ
  СТАРТА рана: ран, стартовавший до применения правки, видит старый title даже если PR-тайтл
  уже правильный. Порядок строгий: сначала `gh api -X PATCH … -f title=...` и сверка через
  `gh pr view --json title`, ТОЛЬКО ПОТОМ пустой коммит-ретриггер; после прогона сверяй не
  только rollup, но и headSha рана с head ветки (`gh run view <id> --json headSha`) — FAILURE
  от предшествующего SHA выглядит как краснота актуального кода. Локальная сверка маркера до
  пуша: `python3 scripts/pr_validate.py . --id "<title> <body>"` — матчит только скобочный
  маркер (`[chore]`), голое слово chore в тексте не маркер; change-id маркер на PR без
  QA-комплекта валит check_change — ранним стадиям пакета `[docs]` (см. design-phase.md).
- **Маркер с двоеточием `[change-id:<correlation>]` — НЕ маркер**: MARKER_RE в скобках
  ожидает `BUG-NNN`, `chore`/`docs`/`ops` или kebab-id `[a-z0-9-]+` — двоеточие роняет матч,
  и PR краснеет «маркер ID не найден» при визуально корректном тайтле. В скобках —
  ЛИТЕРАЛЬНОЕ значение: для функциональных PR это id change-пакета (`[add-ui-polish-r8]`,
  `[chore]`), который parse_id резолвит в `openspec/changes/<id>/`; трассировочные
  correlation-id клади в body или commit-сообщение, не в скобки маркера. Локальный прогон
  pr_validate с тем же текстом title+body до создания PR ловит это бесплатно.

## Порядок разбора

1. `gh run view <id>` — какой step.
2. `gh api repos/<owner>/<repo>/actions/jobs/<job_id>/logs` — текст ошибки (grep по `::error`,
   `FAIL`, `✗`, имени скрипта).
3. Воспроизвести локально тем же инструментом ТОЙ ЖЕ ВЕРСИИ (для validate — той же версией CLI;
   расхождение версий локаль/CI — первый подозреваемый при «у меня зеленый»).
4. Фикс источника (не ретриггер) + коммит с причиной в сообщении.

## Чтение большого машинного вывода

- `flowctl status` и реестр сессий печатают сотни КБ на один вызов (полный JSON всех runs) —
  фильтруй по нужным delegation_id/action/status до печати, не вываливай целиком.
- Ожидание checks — конечным циклом с верхним пределом итераций (sleep 20 × N), не открытым:
  бесконечный sleep-цикл роняет сессию ядра по таймауту вместе с накопленным состоянием.
