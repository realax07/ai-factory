# Прод-выкатка матричного стека: грабли живого деплоя

Дополнение к разделам SKILL.md «Прод-деплой deploy.sh» и «Контейнеризация». Каждый пункт —
правило + механизм; проверено на живой выкатке, где деплой остановился четыре раза подряд.

## deploy.sh и новые сервисы пакета

- Повторный deploy.sh после останова ДОКАТЫВАЕТ, а не начинает заново: миграция идемпотентна
  (повтор no-op), бэкап уходит в новый штамп, `up -d` пересоздает только отставшее.
  После сбоя докатывайся тем же deploy.sh — ручной докат compose-командами из чата и порождает
  каскад ошибок проектов/тегов (см. ниже).
- Матрица SERVICES, `dockerfile_for`/`image_for` и проверка образов (шаг 6.8) захардкожены на
  4 сервиса. Новый сервис пакета соберется и поднимется, но релизная проверка образов его не
  увидит (FAIL «ожидался тег»: контейнер держит image-ID старого билда, тег переклеен повторным
  build, compose при неизменном конфиге контейнер не пересоздал). Добавляя сервис, правь
  dockerfile_for + image_for + смоук тем же PR; долгосрочно — читать матрицу из compose (J38).
- Шаг `up` должен поднимать ВСЕ сервисы матрицы (волна 2: `search images backup weather` с
  полным env): сервис матрицы, не попавший ни в один up-шаг, при деплое поднимается девопсом
  вручную, а `depends_on` пересоздает app на дефолтном `:local` (двойной инцидент одного
  деплоя). Защита — гейт `_matrix_compose_config` ДО up: `docker compose config` обязан
  резолвить каждый сервис матрицы в релизный тег; `:local`/`:latest` = fail (P19).
  Правка deploy/** в PR — маркер `[ops]` (J26), не `[chore]`.

## Томы и non-root uid (главный класс прод-сбоев)

- Свежий named volume создается root:root; сервис под uid 10001 при старте/upload делает
  makedirs/write → PermissionDenied → 500 с пустым телом → JS `response.json()` кидает →
  общий catch «Не удалось загрузить файл». Фикс до/сразу после первого up:
  `docker run --rm -v <proj>_<vol>:/data alpine chown -R 10001:10001 /data`.
  Диагностика: общий catch в UI (не текст HTTP-ошибки) = пустое/не-JSON тело ответа —
  проверь права тома и тело ответа curl'ом, не API-логику.
- Nested ro-маунты на чистом родительском томе валит СТАРТ контейнера: `wiki-data:/data:ro`
  + `images-data:/data/images:ro` — runc создает mountpoint mkdirat'ом внутри уже
  смонтированного ro-тома → «read-only file system». Фикс: пре-создать путь в родительском
  томе: `docker run --rm -v <proj>_<vol>:/data alpine mkdir -p /data/images`.
  Стендом не ловится, если его тома уже насмотрены — репетируй на свежем имени тома.
- ОТДЕЛЬНЫЙ том НЕ смонтировать под ro-родителем вообще (даже с пустым mountpoint):
  `wiki-data:/data:ro` + `weather-cache:/data/cache` — mountpoint-creation падает на
  ro-родителе так же, как nested (кейс: weather не стартует в CI). Разные тома —
  на верхнеуровневые пути одного уровня (`/cache`), а не внутрь чужого ro-маунта;
  маунтпоинт создать в Dockerfile (`RUN mkdir -p /cache && chown 10001:10001`) —
  пустой том наследует владельца образа. Признак в логе: «create mountpoint …:
  read-only file system» на старте контейнера, не на обращении.

## Ручные compose-операции против прода (когда без них никак)

- docker compose НЕ читает env-переменные deploy.sh: `PROJECT=ekotov-wiki-par` игнорируется.
  Имя проекта = `-p` (или top-level `name:` из yaml). Без `-p` — второй параллельный стек
  под дефолтным именем: «port is already allocated» на nginx, мусорные контейнеры и тома.
- Без `*_IMAGE` в окружении поднимаются `:local`-дефолты из yaml — прод МОЛЧА откатывается
  на старые образы. ps покажет «норм», а отдаваемая статика — прошлого релиза. Верифицируй
  прод после ЛЮБОГО пересоздания: `ps --format '{{.Service}} {{.Image}}'` = релизные теги
  И `v=<static_v>` + маркер новой фичи в отдаваемом CSS (`curl -sk .../static/css/app.css | grep <маркер>`).
- `--env-file` ЗАМЕНЯЕТ дефолтный deploy/.env (SECRET_KEY пропадает → interpolation error).
  Объединяй: `cat deploy/.env <release-env> > full.env` и подключай full.env.
- Порядок диагностики «не работает в браузере» после выкатки: (1) отдаваемая статика = репо?
  (`curl -sk <url>/static/css/app.css | diff - frontend/static/css/app.css`), (2) все ли
  контейнеры на релизных тегах, (3) X-Service-заголовки новых локаций, (4) права томов.
  Смешанный стек (новый app + старый nginx, раздающий статику) выглядит как «дизайн сломан»:
  новая разметка рендерится со старым CSS — иконки гигантские, стилей фичи нет.

## Бэкап-контур deploy.sh: хост-uid против контейнерного uid (все операции записи в BACKUP_DIR)

- BACKUP_DIR принадлежит 10001 (chown в шаге 1/8), а deploy.sh выполняется от юзера хоста
  (в группе docker, без sudo). ЛЮБАЯ хостовая запись/переименование в BACKUP_DIR падает
  Permission denied — tar-распаковка (chown/chmod/utime на extracted-записях и на корне '.'),
  mv staging→BACKUP_DIR (rename требует w на ОБА каталога), `cat > файл` (открытие на запись).
  Пиши в BACKUP_DIR только через docker root-хелпер:
  `docker run --rm -i --user 0 -v "${BACKUP_DIR}:/bkp" alpine sh -c 'cat > /bkp/<имя>'` /
  `... sh -s -- args <<'EOF'` (heredoc: busybox `sh -c '…' _ args` СЪЕДАЕТ первый файловый
  аргумент как $0 — передавай аргументы через `-s --`). Ловится только живым прогоном:
  bash -n и DRY_RUN синтаксис/план не проверяют.
- tar-распаковка потока из контейнера: `--strip-components=1` срезает корневой член './' —
  без него tar делает chmod/utime на сам каталог назначения даже с
  --no-same-owner/--no-same-permissions/--touch (подсказка GNU tar: strip-components
  'implies --same-owner'). Два прогона на флагах без strip — тот же FAIL.
- Read-only SQLite из backup-sidecar: `mode=ro` открывает БД только если рядом можно
  создать -wal/-shm; на ro-томе без возможности записи рядом — 'unable to open database file'
  даже при читаемом main-файле (plain open OK, а sqlite падает). Fallback:
  `mode=ro&immutable=1` — читает ТОЛЬКО main-файл (игнорирует WAL-хвост: бэкап может
  отставать на незалитые записи). Для релизного бэкапа безопасно (миграция/checkpoint
  до старта backup); для суточного sidecar — известный риск, эскалировать решение по
  маунту (снять :ro) Заказчику. Проверка варианта отказа — реплика на живом контейнере
 (docker cp probe-скрипта + exec python): fallback-варианты перебирай по одному
 (plain/mode=ro/nolock/immutable), не угадывай по документации sqlite — наличие
 отказа зависит от sqlite-билда в образе. После перевода sidecar на immutable-read
 проверь healthcheck (docker compose ps) и первый суточный тик в логах (WARNING об
 immutable — ожидаемое поведение, не авария), иначе деплой-стоп «backup не стал
 healthy» приходит уже после миграции.
- Тот же класс на UI-данном проде: grid-раскладка с авто-placement роняет контент
  в чужую колонку, если первый элемент контейнера (h1) не получил явный grid-column —
  `gridTemplateColumns` проверяется, а ПОЗИЦИИ элементов нет. Проверяй раскладку
  ассертами на позицию/колонку каждого ребенка контейнера, не на строку шаблона
  колонок; фикс — явный grid-column на ВСЕХ прямых детях grid-контейнера.
- Вынос бэкапа в staging и mv релизных имен — только через docker root-хелпер
  (tar-распаковка с --strip-components=1 --touch --no-same-owner
  --no-same-permissions; busybox `sh -c '…' _ args` съедает первый аргумент как $0 —
  аргументы через `sh -s --`). Хостовые mv/cat> в BACKUP_DIR падают Permission denied
  (владелец 10001).

 ## Планирование пакета: QA-контур не выпускается из плана

- При нарезке Флоу 1 СА обязан закладывать QA-контур задачами (impact → чеклист → кейсы →
  ревью кейсов → автотесты, эталон add-responsive-mobile), а ПМ перед стартом QA-этапа
  проверять их наличие. Иначе pr_validate поймает пробел (контракты 4/6) только на
  финальном PR, кейсы будут написаны задним числом от кода, и «проверка требований»
  подменяется «оформлением сделанного». Независимый аудит покрытия «сценарий дельты →
  кейс → автотест» — до прод-выкатки (прецедент: 40 сценариев, 5 GAP, из них 2 Must —
  закрыты до деплоя).
- ПМ не делает руками роль: правки deploy/**, QA-артефакты, ревью — через сабагента
  соответствующей роли и его флоу. «Быстрее сделать самому» = bypass флоу и потеря
  независимого ревью (фикс deploy.sh, проверенный только его автором — ровно то, что
  независимый ревьюер ловит как blocker). Исключение — только механическое сохранение
  уже полученного артефакта, потеря которого дороже нарушения (например docker-mv
  свежеснятого pre-бэкапа из staging в BACKUP_DIR, когда скриптовый шаг еще не дописан);
  фиксируется в докладе как нарушение, не как норма.
- Прод-накатка — исполняет Заказчик (граница роли devops в agents/devops_agent.md:
  «живой прод — только чтение, реальные накатки выполняет Заказчик»), даже если у
  агента технически есть docker-группа. Исключение — только явное решение Заказчика
  о расширении границы; по умолчанию ПМ готовит команду RUNBOOK и отдает Заказчику.
- Каждый живой отказ деплоя фиксируй в REPORT до повторного прогона (фаза, шаг,
  точная команда, ошибка): повтор пересоздает бэкап/состояние, а ревьюер сверяется
  с отчетом, не с историей shell.
- Playbooks флоу для нарезки/ведения пакетов (обязательный QA-контур по флоу, возвраты
  с этапов) — в отдельном skill `flow-playbooks` (SKILL.md + references/flows/flow-1..5).

## Прод-параллель/переключение вручную: root-скрипты и топология от факта

Дополнение к разделу SKILL.md (дистиллят правил root-скриптов переключения трафика).

- Права на docker у агента — только явное отдельное решение Заказчика (приоритет —
  целостность хоста, не прода); до решения прод-операции оформляются ОДНИМ скриптом в
  репо (фазы как подкоманды: pre/full/switch/status/rollback), который Заказчик запускает
  от root; `set -euo pipefail`, останов на первой ошибке. Точка старта — явное «погали»,
  не предложение «давай я получу права».
- Топологию прода и пути сверяй С ФАКТОМ хоста, не со старым документом: systemd-юнит
  может быть inactive легитимно (прод давно контейнерный; критерий здоровья — HTTP-проба
  порта, не статус юнита), клон — не там, где указан в SRC_DIR старого документа
  (`rev-parse --git-dir` проверяет; каталог без .git — копия файлов). Одновременный
  active-юнит + контейнерный прод на одном порту = два стека на одной БД — честный FAIL.
- Смоук-критерии бери из эталонного смоука репо (код 200/401/422 ОТ СЕРВИСА + служебный
  заголовок), не изобретай строже: требование 200 без сессии валится об честный 401
  контракта. Ложный FAIL скрипта = потерянное доверие; ушедший Заказчику ложный FAIL
  первым сообщением квалифицируй как дефект скрипта, не продукта.
- WAL-БД не бэкапь с `:ro` маунтом: VACUUM INTO требует создать wal-index рядом с БД.
  Маунт rw (wal-файлы в томе — норма), снапшот — VACUUM INTO на ВТОРОЙ маунт; целевой
  каталог — под chown контейнерного uid ДО первого прогона (образ USER 10001 не запишет
  в каталог чужого uid); в slim-образах нет sqlite3 CLI — проверки через python -c.
- Откат = stop без rm: старый стек останавливай (`compose stop`) — откат тогда
  `compose start` за секунды; предупреждай в выводе: записи нового стека после
  переключения при откате в старый том не попадают.
- Скрипт = артефакт репо: [ops]-коммит и push ДО передачи Заказчику (скрипт, живущий
  только в локальной ветке, у Заказчика = «No such file or directory»); команды — с
  абсолютным путем и SRC_DIR (Заказчик запускает из любого каталога).
- Старый rollback-скрипт параллели ОПАСЕН после переключения: его `down -v` сносит уже
  продовой том — гашение второй среды документируй через `compose stop <svc>`, сверяй
  протоколы приемки/RUNBOOK (старая рекомендация переживает смену топологии); риск чини
  правкой протокола в том же цикле.
- [ops]-задачи, исполненные Заказчиком вручную, закрываются протоколом приемки
  (code-reviews/<change>/acceptance-protocol-<task>.md), не review-файлом. Документационный
  хвост [docs]-задачи может быть зона-ограничен: что проходит по политике — делегируй,
  остальное — ПМ-проход с честной фиксацией DENY-ов, не подбором роли.
