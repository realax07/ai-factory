# Выделение сервиса и инфраструктурные задачи (роутеры, БД, docker, nginx)

Глубина для задач класса «выделение сервиса / миграция / деплой-инфраструктура» Флоу 1. SKILL.md держит только указатель.

## Роутеры переносятся КАК ЕСТЬ, контракт первичен

- Роутеры — точная копия поведения, сверка по замороженному контракту (`contracts/openapi-search.json`): пути и схемы ответов сверяй до коммита. Контракт заморожен ЭТАПОМ ранее именно для этого. Сверку делай программно (открытая схема сервиса против замороженного JSON: paths + операторы + responses байт-в-байт), не глазами.
- Если роутеры тянут общие зависимости ядра — минимальные локальные копии в `services/<имя>/app/`, каждая с комментарием-трассировкой на источник («копия из backend/app/X.py@<sha> — при изменении обновлять синхронно»). Без трассировки рассинхрон копий невидим. Верно и в обратную сторону: копия с deviation от ядра (ro-профиль, SELECT-only) обязана нести в шапке файла и отклонение, и его причину — иначе следующий синк «вернет» ядерное поведение.
- Отрезка маршрутов от монолита — ОТДЕЛЬНАЯ задача (активация контрактного гейта), не в том же коммите: монолит продолжает работать, пока сервис не проверен.
- Юнит-тесты сервиса — через starlette TestClient по временной sqlite-фикстуре, БЕЗ живого стенда и uvicorn: иначе тест наследует требование стенда каталога (см. SKILL.md «api-сьют») и теряет воспроизводимость.
- ТЗ на новый тест: TC-трассировка в docstring (TC-openapi-NNN+ продолжением нумерации), протокол needs-debug, стенд гасить. Формулировки эти в ТЗ, не в памяти сабагента.
- Smoke-верификация инфраструктурной задачи вскрывает дефекты кода продукта из ПРЕДЫДУЩЕЙ задачи той же цепочки — режимы (ro-маунт), которых нет в TestClient-тестах, воспроизводятся только смоуком. Дефект чинит исходный автор (его зона), не инфраструктурный сабагент; регресс-тесты — в тесты сервиса с продолжением TC-нумерации, контракт не меняется.
- **Dockerfile нового сервиса — паритет существующего образа семейства**: python:3.12-slim, USER 10001, WORKDIR /srv, healthcheck urllib (curl в slim нет) с теми же интервалами, что в compose, EXPOSE без публикации, CMD uvicorn 1 воркер. Deps-пины образа — ДОСЛОВНО из backend/requirements.txt с комментарием «синхронно requirements, обновлять вместе» — расхождение пинов ревьюер ловит как blocker.

## Read-only профиль данных: свой протокол открытия БД

- Механика поломки копии ядра: `PRAGMA journal_mode=WAL` при connect — ЗАПИСЬ в заголовок БД, на ro-маунте — «attempt to write a readonly database»; когда app в простое закрыл все соединения, sqlite удаляет `-wal`/`-shm`, и read-only читатель не может их пересоздать — 500 в случайные моменты простоя, не сразу.
- Рабочая схема: `sqlite3.connect("file:<quoted-path>?mode=ro", uri=True)` + сразу probe-SELECT (`SELECT count(*) FROM sqlite_master`) — sqlite откладывает открытие wal-index до первого запроса, без пробы fallback не срабатывает в момент connect; при OperationalError — fallback `immutable=1` (снапшот main-db). `immutable=1` при живом `-wal` НЕ использовать: игнорирует wal, читатель перестает видеть свежие записи писателя. URI-флаг `readonly_shm=1` НЕ альтернатива fallback'у: без живого `-shm` не открывается так же, как голый mode=ro. `foreign_keys=ON` — connection-level PRAGMA, сохраняется.
- Копия сессионного middleware для read-only сервиса — SELECT-only: DELETE истекшей сессии и скользящий TTL (UPDATE) ядра на ro-маунте дают 500. Отклонение от ядра — комментарием-трассировкой в шапке файла.

## Docker-ограничения сессии и матрица верификации миграции

- **Нет docker-доступа у сессии — эскалация Заказчику одним сообщением с командами**: subagent-сессия не читает /var/run/docker.sock (openclaw вне группы docker), sudo требует пароль — ретраи бесполезны. Команды с АБСОЛЮТНЫМ путем к worktree (его shell стартует в /root), проси вернуть конкретные числа (`docker stats --no-stream`); цифры — в REPORT как замер, эскалация закрывается, потом чекбокс.
- One-shot миграция БД без тестов в скоупе (QA-артефакты писать нельзя) верифицируется матрицей: (1) двойной прогон на tmp-БД (свежая — все таблицы, повтор — честный no-op; БД без базовой схемы — exit 1); (2) негативная матрица автосверки — мутант на инвариант (лишняя колонка, убранный CHECK/UNIQUE, составной PK к одной колонке, FK без ON DELETE, индекс на чужой колонке, дропнутая таблица — каждый exit 1 с именованным FAIL; «сверка есть» ≠ «сверка ловит»); (3) инварианты поведения живыми вставками; (4) паритет схемы с фикстурой — по `PRAGMA table_info` + `sqlite_master`, не регэкспом по DDL-тексту (рассыпается на комментариях и CHECK-скобках); (5) `docker compose config` обоих файлов + структурная матрица инвариантов design по resolved-YAML (healthcheck-команда в YAML — список: `" ".join(...)` перед поиском подстроки); (6) RAM-замер — через эскалацию Заказчику (см. выше).

## Пути внутри образа и тома — от факта, не от репозитория

- `Path(__file__).resolve().parents[N]` в контейнере дает НЕ тот корень, что на хосте; search path ошибки смотри в логе контейнера — там напечатан фактический путь.
- **Не монтируй том в путь внутри ЧУЖОГО read-only маунта**: если /data контейнера занят ro-маунтом, docker не может создать маунтпоинт /data/cache внутри него — контейнер не стартует («make mountpoint: read-only file system»), и локальный стенд это НЕ покажет, если раскладка маунтов отличается от CI/прода. Выноси том собственного состояния на верхнеуровневый путь (/cache, не /data/*) и прогоняй подъем стенда ТОЧНО по боевому compose-файлу на свежих томах (down -v) до пуша.
- Один named volume, смонтированный в разные сервисы на РАЗНЫЕ глубины, делает содержимое видимым по разным путям — конфиги сверяй с фактическим mount view внутри контейнера.
- Скрипты с getpass не работают в no-TTY (CI, фон): пароли через stdin-pipe или программный API. Схему БД инициализируй ДО seed — пустой том стенда без таблиц.
- Ключи/серты из CI могут быть 600 — non-root uid (nginx-unprivileged 101) не прочитает: `chmod 644` тестовым артефактам стенда. Файл, созданный контейнером в маунте, принадлежит контейнерному uid — чисти тем же контейнерным путем (`--user 0`).
- Несколько сервисов на одной tmpfs: маунт НЕ шарится — второй сервис увидит пустую БД. Named volume проекта + изоляция именем (`compose -p`), очистка `down -v` — задокументируй в шапке стендового compose. Свежий named volume для USER <uid> — root:root: первый `up` требует `chown <uid>` через одноразовый контейнер `--user 0` (прод-том не трогает, но прод-параллель на новом томе споткнется — шаг инициализации тома закладывай в ТЗ).

## nginx-маршрутизация сервисного семейства во фронт-контейнере

- Матчи семейства — пара «`= точный` + `^~ префикс-слэш`» на каждое: голый префикс съедает соседние пути (`/api/x` ловит `/api/x/users`); `^~` отключает regex-проверки — семейство не перебивается будущими regex-локациями.
- proxy_pass через переменную + `resolver 127.0.0.11 valid=<N>s` (docker DNS): nginx стартует без контейнера сервиса и не кеширует умерший IP. Цена valid: после рестарта сервиса nginx до истечения TTL дает 503 — ожидаемое поведение, не дефект.
- 503-деградация остановленного сервиса: `proxy_next_upstream error timeout` + `proxy_intercept_errors` + `error_page 502 503 504 = @named` с JSON-телом и `Retry-After`. На single-upstream proxy_next_upstream не переносит запрос, но флаг гоняет его в error_page — управляемый 503 за ~1мс. Живая проверка: stop search → семейство дает управляемый 503, restart → восстановление ≤0.5с без stale-DNS, плюс смоук ЗАПИСИ в app при упавшем сервисе (изоляция).
- **add_header не наследуется в локацию, где есть хоть один свой add_header** — подключив include с `X-Service`, ты ОТМЕНИЛ все server-level security-заголовки: security-набор повторяй в каждом сервисном include и в error_page-локации. Проверяй итоговые заголовки curl'ом через фронт, не по конфигу.
- Маршрутизация ≠ отрезка: монолит продолжает отвечать на те же пути до отдельной задачи переключения (обе ветки параллельно), xfail-гейт «ядро без маршрутов» снимается только задачей отрезки.
