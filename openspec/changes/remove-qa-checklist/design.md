# remove-qa-checklist — design

**Флоу: 1**

## Матрица Заказчика (согласована 2026-10-12)

- qa_checklist упраздняется; qa_case_author читает спеку напрямую.
- Трассировка TC → Requirement/Scenario (вместо TC → CHK → Req).
- Негатив/границы и дефекты спеки — оси qa_case_reviewer.
- Существующие чеклисты — append-only история (не удалять, не требовать).

## Решения

1. **STAGE_TABLE (flow_transition.py):** Stage `qa_checklist` удален; `qa_cases`
   сохраняет роли qa_author/qa_case_author (решение 3.1/S5), вход — факт
   спеки/дельт (`change.spec_deltas` / `specs.present`) вместо факта чеклиста.
2. **flow_check.py:** валидация чеклистов (контракт 3) удалена; «кейсы без
   чеклиста» удалено; вместо CHK-трассировки — машиночитаемая сверка кейса с
   заголовками `### Requirement:`/`#### Scenario:` master-spec и дельт активных
   пакетов. I3-покрытие маршрутов читает checklists/ рекурсивно (история, вкл.
   archive/, не осиротает).
3. **pr_validate.py:** чеклист удален из обязательного набора change-PR.
4. **Формат трассировки кейса:** строка `Requirement: <заголовок>` и/или
   `Scenario: <заголовок>` в полях кейса (заголовок дословно из спеки) —
   детерминированно проверяется без LLM.
5. **Проект (ekotov-wiki):** тонкий клиент — копируются flow_check.py и промпты
   (qa_case_author, qa_case_reviewer, README-реестр) с sha-шапками; исторические
   чеклисты переносятся в `test-model/checklists/archive/` (не удаляются).

## Риски

- Старые кейсы в `new/` без трассировки к спеке станут красными flow_check —
  это целевое поведение (правило усиливается), миграции ретро-кейсов не требуется
  (активных `new/` в фабрике и проекте нет).
- Тексты контрактов нумеруют контракты 3–6 без переименования: контракт 3
  перепрофилирован («спека как источник кейсов»), нумерация стабильна для
  ссылок в скриптах.
