# Design — add-deterministic-flow (срез 1, Флоу 4)

## Research (альтернативы до решения)

1. **Внешний движок (LangGraph/Temporal)** — отвергнуто ТЗ (00-README, огр. 1) и практикой: зависимость, несоизмеримая с ~1.3К строк фабрики.
2. **Один State(Enum) для репозитория** — отвергнуто ТЗ 01 (треб. 4): состояние обязано быть по scope (project+change+task), у change одновременно несколько task-стадий.
3. **YAML-язык правил** — отвергнуто: правила на Python тестируемы таблично и отлаживаются стек-трейсом; YAML — еще один интерпретатор.
4. **Выбрано: Python stdlib, чистые функции + тонкий CLI** (ТЗ 01/02/03 дословно), переиспользование парсеров flow_check импортом.

## Decisions

- **D1. Модульная структура:** `flow_state.py` (снимок) и `flow_transition.py` (решение) — два файла, контракт по `contracts/flow_control_contract.md`; общий словарь кодов причин — в `flow_transition.py`, импортируется состоянием при необходимости.
- **D2. Decision-модель:** dataclass-совместимый dict со стабильными ключами; `status` — единственный арбитр (ALLOW исполняем, DENY/UNKNOWN нет); `next_candidates` вычисляется только по запросу (`next`), т.к. перебор действий дороже одного `check`.
- **D3. Правила флоу — таблицы фактов, не if-лес:** для каждого флоу — упорядоченный список этапов (этап = требуемые факты + роль + gates); `check_action` находит этап действия и сверяет факты snapshot; отсутствующий критерий правила = UNKNOWN (честно), а не DENY (ложный запрет).
- **D4. Совместимость:** flow_check/pm_bounds_check не изменяются; их роль в срезе 1 — `required_gates` как ссылки (исполнение gates — поставка 05); provenance-зависимые переходы (accept_review/merge) — UNKNOWN с кодом STALE_EVIDENCE-совместимости (спека, Requirement «Provenance review»).
- **D5. Этапные ворота:** источник — файл плана задачи со строкой «Флоу: N» (ОВ-2 дефолт) + зафиксированные решения Заказчика (в срезе 1 — цитата/коммит в PLAN/BACKLOG, ссылка передается в action.approval_ref; строгая верификация формата — сfollow-up).
- **D6. Тест-стратегия:** табличные тесты (fixture-snapshot × действие × ожидаемый status/код) — без subprocess; CLI-тесты — отдельно, exit 0/1/2.

## Risks

- Правила AGENTS.md частично текстовые → машина будет давать UNKNOWN чаще, чем хотелось; принято: UNKNOWN честнее выдуманного правила (спека). Shadow-прогон покажет долю UNKNOWN — данные для решения о срезе 2.
- Дублирование парсинга с flow_check → минимизируем импортом (D1), полное устранение — только после тестов старого поведения (контракт, раздел «Совместимость»).
