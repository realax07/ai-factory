## Общее описание

Инцидент-протокол для Флоу 3 (хотфикс прода): формализует реакцию на прод-инциденты — severity-классификация S1/S2/S3, initial response в окне 0–15 минут, обязательный post-mortem для S1/S2 с воротами перехода архивации (flow_transition, check архивации Флоу 3; design D2). Закрывает дефект «протокол реагирования не формализован» (прецедент — инцидент 2026-10-05, J25, разобран ad hoc). Источник практик: engineering-team/skills incident-commander + incident-response (SRE: severity classification, initial response 0–15 min, post-incident review).

Граница: протокол применяется ТОЛЬКО в Флоу 3 (хотфикс). Флоу 1 (полный), 2 (багфикс), 4 (обслуживание), 5 (экспресс) не меняются.

## Аудитория

- devops/dev-сабагенты: классификация severity, initial-response протокол, post-mortem.
- ПМ: контроль ворот архивации Флоу 3.
- Скрипты контроля: flow_transition (severity в маркере, ворота post-mortem при архивации).
- Заказчик: уведомление в initial response (что случилось, что делаем, ETA).

## Функциональные требования

### FR-1: Severity-матрица Флоу 3

Каждый инцидент Флоу 3 MUST классифицироваться до начала реакции по матрице:

- **S1** — прод недоступен или потеря данных. Реакция: немедленный откат по RUNBOOK (deploy_rollback); разбор — только после стабилизации.
- **S2** — деградация части функций (прод доступен, функции работают не полностью/неверно). Реакция: хотфикс-PR в приоритете.
- **S3** — некритично/косметика. Протокол Флоу 3 НЕ применяется: задача уходит в обычный Флоу 2 (багфикс).

Почему: состав реакции определяется классом инцидента; без классификации реакция выбирается ad hoc (дефект J48).

#### Scenario: S1 — немедленный откат

- **GIVEN** инцидент классифицирован S1 (прод недоступен/потеря данных)
- **WHEN** initial response начат
- **THEN** первым действием выполняется откат по RUNBOOK, а разбор причин не начинается до стабилизации

#### Scenario: S2 — приоритетный хотфикс-PR

- **GIVEN** инцидент классифицирован S2 (деградация части функций)
- **WHEN** стабилизация достигнута без потери функциональности
- **THEN** реакция — хотфикс-PR в приоритетном порядке (не откат как первый выбор)

#### Scenario: S3 — перевод в Флоу 2

- **GIVEN** дефект классифицирован S3 (некритично/косметика)
- **WHEN** задача регистрируется
- **THEN** она исполняется по обычному Флоу 2 и инцидент-протокол к ней не применяется

### FR-2: Initial response 0–15 минут

Initial response инцидента S1/S2 MUST укладываться в 15 минут от старта реакции и следовать порядку: (1) откат/стабилизация; (2) уведомление Заказчика — что случилось, что делаем, ETA; (3) фиксация incident_ref; (4) разбор причин — только после стабилизации. Фактические timestamps начала/окончания initial response MUST фиксироваться в таймлайне post-mortem (проверяемость порога).

Почему: «кто/что в первые минуты» не был формализован; первый инцидент разбирался раньше, чем стабилизирован прод.

#### Scenario: Порядок действий соблюден

- **GIVEN** инцидент S1/S2, реакция начата в момент T
- **WHEN** фиксируется initial response
- **THEN** порядок откат/стабилизация → уведомление Заказчика → incident_ref соблюден и завершен не позже T+15 мин; разбор не предшествует стабилизации

#### Scenario: Разбор до стабилизации заблокирован

- **GIVEN** прод не стабилизирован
- **WHEN** исполнитель переходит к разбору причин
- **THEN** это фиксируется как нарушение протокола (в post-mortem/ревью)

### FR-3: Post-mortem обязателен для S1/S2 — ворота архивации

Для каждого инцидента S1/S2 MUST быть написан post-mortem, содержащий: таймлайн (включая timestamps initial response), root cause, action items (каждый — в change-пакет или бэклог), без обвинений. Post-mortem хранится в `test-model/incidents/`, режим append-only. Архивация Флоу 3-задачи с инцидентом S1/S2 MUST блокироваться воротами перехода (flow_transition, check архивации Флоу 3; design D2) при отсутствии post-mortem. Для S3 post-mortem не требуется.

Почему: без ворот post-mortem пропадает (прецедент J25: ad hoc-разбор не оставил артефакта).

#### Scenario: Архивация S1 без post-mortem блокируется

- **GIVEN** Флоу 3-задача с incident_ref severity S1, post-mortem в test-model/incidents/ отсутствует
- **WHEN** запрошен переход архивации (flow_transition, check архивации Флоу 3)
- **THEN** результат — нарушение (DENY, ненулевой exit), архивация не проходит

#### Scenario: Архивация S2 с post-mortem проходит

- **GIVEN** Флоу 3-задача с incident_ref severity S2, post-mortem (таймлайн, root cause, action items) существует в test-model/incidents/
- **WHEN** запрошен переход архивации (flow_transition, check архивации Флоу 3)
- **THEN** нарушение по воротам post-mortem отсутствует

#### Scenario: Post-mortem append-only

- **GIVEN** post-mortem инцидента существует в test-model/incidents/
- **WHEN** любой агент работает с каталогом
- **THEN** существующие файлы не удаляются и не переписываются (только новые записи)

### FR-4: Severity в маркере делегации

Поле incident_ref в маркере делегации (уже существующее) дополняется severity. Выбранный формат: **`incident_ref=S1-<краткий-ид>`** — severity как префикс внутри incident_ref (альтернатива `incident_ref=X + severity=S1` отдельным полем отклонена: два поля могут рассинхронизироваться, а отдельное поле ломает существующих потребителей incident_ref). Новые инциденты S1/S2 MUST маркироваться этим форматом; severity в incident_ref MUST совпадать с классификацией по FR-1.

Почему: severity неотделим от инцидента — один атом, а не пара полей; префикс машинно-различим (S1-/S2-/S3-) и не ломает существующую семантику поля.

#### Scenario: Маркер S1 распознается

- **GIVEN** маркер делегации содержит incident_ref=S1-prod-down
- **WHEN** flow_transition разбирает маркер
- **THEN** severity S1 извлечен из префикса, задача требует post-mortem-ворота при архивации

#### Scenario: Инцидент без severity в маркере

- **GIVEN** Флоу 3-задача с incident_ref без S1-/S2-/S3-префикса
- **WHEN** flow_transition разбирает маркер
- **THEN** классификация отсутствует — состояние трактуется как неклассифицированный инцидент (не разрешает архивацию по FR-3-семантике)

## Нефункциональные требования

- **NFR-1:** Ворота post-mortem детерминированы: проверка по файлам (наличие post-mortem в test-model/incidents/, разбор префикса incident_ref), без LLM; UNKNOWN не разрешает архивацию.
- **NFR-2:** Append-only хранилища: существующие файлы в test-model/incidents/ не удаляются и не изменяются.
- **NFR-3:** Прогон регресса фабрики (pytest tests/) зеленый после изменений; поведение flow_check/flow_transition для Флоу 1/2/4/5 не меняется.

## Приоритеты

- MoSCoW Must: FR-1, FR-2, FR-3, FR-4, NFR-1, NFR-2, NFR-3.
- Should: нет (требования Заказчика дословны, обходных путей нет).
- Won't (этот change): изменения Флоу 1/2/4/5; промпты devops/dev вне initial-response; ретроспективная маркировка старых инцидентов.

## Ограничения

- Протокол применяется ТОЛЬКО в Флоу 3 (хотфикс); Флоу 1/2/4/5 не меняются (санкция Заказчика, план PLAN-J48).
- Пост-мортем — в `test-model/incidents/` (не docs/incidents/): append-only, смежно с QA-контуром test-model.
- Порог «0–15 минут» проверяем через timestamps в таймлайне post-mortem, а не настенный контроль.
- Не путать цифры: Флоу работы (1 — этот change-пакет) и Флоу, который усиливаем (3 — хотфикс), — источник путаницы 2026-10-14.
