# Incident Protocol Specification (Флоу 3 — хотфикс прода)

## Purpose

Формализованная реакция на прод-инциденты Флоу 3: обязательная severity-классификация
(S1/S2/S3) до начала реакции, initial response в окне 0–15 минут, обязательный
post-mortem для S1/S2 с машиной-воротами архивации. Закрывает дефект «протокол
реагирования не формализован» (прецедент — инцидент 2026-10-05, J25, ad hoc).
Граница: протокол применяется ТОЛЬКО в Флоу 3; Флоу 1/2/4/5 не меняются.

## ADDED Requirements

### Requirement: Severity-классификация инцидентов Флоу 3

Каждый инцидент Флоу 3 MUST классифицироваться до начала реакции по матрице:
S1 — прод недоступен или потеря данных; S2 — деградация части функций при
доступном проде; S3 — некритично/косметика. Для S1 первым действием MUST
выполняться откат по RUNBOOK, разбор причин не начинается до стабилизации.
Для S2 реакция — хотфикс-PR в приоритетном порядке (не откат как первый
выбор). Для S3 инцидент-протокол НЕ применяется: задача исполняется по
обычному Флоу 2.

#### Scenario: S1 — немедленный откат

- **GIVEN** инцидент классифицирован S1 (прод недоступен/потеря данных)
- **WHEN** initial response начат
- **THEN** первым действием выполняется откат по RUNBOOK, а разбор причин не начинается до стабилизации

#### Scenario: S2 — приоритетный хотфикс-PR

- **GIVEN** инцидент классифицирован S2 (деградация части функций)
- **WHEN** стабилизация достигнута без потери функциональности
- **THEN** реакция — хотфикс-PR в приоритетном порядке (не откат как первый выбор)

#### Scenario: S3 — перевод в Флоу 2

- **GIVEN** дефект классифицирован S3 (некритично/косметика)
- **WHEN** задача регистрируется
- **THEN** она исполняется по обычному Флоу 2 и инцидент-протокол к ней не применяется

### Requirement: Initial response 0–15 минут

Initial response инцидента S1/S2 MUST укладываться в 15 минут от старта реакции
и следовать порядку: (1) откат/стабилизация; (2) уведомление Заказчика — что
случилось, что делаем, ETA; (3) фиксация incident_ref; (4) разбор причин —
только после стабилизации. Фактические timestamps начала/окончания initial
response MUST фиксироваться в таймлайне post-mortem (проверяемость порога).
Переход к разбору причин до стабилизации MUST фиксироваться как нарушение
протокола.

#### Scenario: Порядок действий соблюден

- **GIVEN** инцидент S1/S2, реакция начата в момент T
- **WHEN** фиксируется initial response
- **THEN** порядок откат/стабилизация → уведомление Заказчика → incident_ref соблюден и завершен не позже T+15 мин; разбор не предшествует стабилизации

#### Scenario: Разбор до стабилизации заблокирован

- **GIVEN** прод не стабилизирован
- **WHEN** исполнитель переходит к разбору причин
- **THEN** это фиксируется как нарушение протокола (в post-mortem/ревью)

### Requirement: Post-mortem для S1/S2 и ворота архивации

Для каждого инцидента S1/S2 MUST существовать post-mortem в `test-model/incidents/`:
таймлайн (с timestamps initial response), root cause, action items (каждый —
в change-пакет или бэклог), без обвинений. Хранение append-only: существующие
файлы не удаляются и не переписываются. Переход архивации Флоу 3-задачи с
incident_ref S1/S2 MUST возвращать DENY (ненулевой exit) при отсутствии
post-mortem; неклассифицированный incident_ref архивацию не разрешает.
Для S3 post-mortem не требуется.

#### Scenario: Архивация S1 без post-mortem блокируется

- **GIVEN** Флоу 3-задача с incident_ref severity S1, post-mortem в test-model/incidents/ отсутствует
- **WHEN** запрошен переход архивации (flow_transition, check архивации Флоу 3)
- **THEN** результат — нарушение (DENY, ненулевой exit), архивация не проходит

#### Scenario: Архивация S2 с post-mortem проходит

- **GIVEN** Флоу 3-задача с incident_ref severity S2, post-mortem (таймлайн, root cause, action items) существует в test-model/incidents/
- **WHEN** запрошен переход архивации (flow_transition, check архивации Флоу 3)
- **THEN** нарушение по воротам post-mortem отсутствует

#### Scenario: Post-mortem append-only

- **GIVEN** post-mortem инцидента существует в test-model/incidents/
- **WHEN** любой агент работает с каталогом
- **THEN** существующие файлы не удаляются и не переписываются (только новые записи)

### Requirement: Severity в маркере делегации

Поле incident_ref в маркере делегации (уже существующее) MUST маркироваться
форматом `incident_ref=S1-<краткий-ид>`: severity как префикс внутри incident_ref
(машиночитаемые префиксы S1-/S2-/S3-). Severity в incident_ref MUST совпадать
с классификацией по матрице severity. incident_ref Флоу 3-задачи без префикса
S1-/S2-/S3- трактуется как неклассифицированный инцидент и архивацию по
семантике post-mortem-ворот не разрешает.

#### Scenario: Маркер S1 распознается

- **GIVEN** маркер делегации содержит incident_ref=S1-prod-down
- **WHEN** flow_transition разбирает маркер
- **THEN** severity S1 извлечен из префикса, задача требует post-mortem-ворота при архивации

#### Scenario: Инцидент без severity в маркере

- **GIVEN** Флоу 3-задача с incident_ref без S1-/S2-/S3-префикса
- **WHEN** flow_transition разбирает маркер
- **THEN** классификация отсутствует — состояние трактуется как неклассифицированный инцидент (не разрешает архивацию по семантике post-mortem-ворот)
