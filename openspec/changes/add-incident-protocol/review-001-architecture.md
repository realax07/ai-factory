## Решение по арбитражу D2 (ворота post-mortem: flow_transition, не flow_check)

**Согласен с СА, переноса/дублирования не требую.**

1. Довод D2.1 подтвержден фактически (см. выше): у flow_check нет ни incident_ref, ни контекста действия — корреляцию «инцидент → post-mortem» он строить не из чего; потребовалась бы эвристика «это Флоу 3», что противоречит NFR-1 (детерминизм, без LLM).
2. Семантика ворот — условие ПЕРЕХОДА (DENY + blocking_reason + MISSING_INPUT + ненулевой exit CLI) — нативна для flow_transition (Decision/Findings); flow_check — постфактум-аудит, ворота там дали бы аудит, а не запрет архивации.
3. Дублирование правила в обоих местах — две точки одной логики (риск расхождения), против «одного места»; NFR-3 изолируется и так: правило в check-функции STAGE_TABLE[3] физически не достижимо из Флоу 1/2/4/5.
4. Размещение по образцу `_hotfix_debt_findings` корректно: тот же слой (check_action Флоу 3), тот же доступ к Action.incident_ref и ctx.

Единственное требование к реализации — см. I-2: check_archive_flow3 обязан перепарсивать severity-префикс из `action.incident_ref` самостоятельно (CLI-вызов архивации — отдельный процесс, ctx от emergency_stabilize не переносится). Design это подразумевает («независимо перепроверяет»), но в tasks 2.2 сформулировано неявно.
