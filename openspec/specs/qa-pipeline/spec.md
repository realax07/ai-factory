# QA Pipeline Specification

## Purpose
Правила QA-контура: последовательность сабагентов (тест-кейсы → ревью → автотесты), итерационный цикл ревью, стек и раскладка автотестов.

## Requirements

### Requirement: Последовательность QA-этапов
QA-работа MUST выполняться в порядке: автор тест-кейсов → ревьюер → автоматизатор (при MODIFIED/REMOVED дельтах — перед автором impact-аналитик). Этап чеклистов упразднен: автор тест-кейсов MUST читать спеку (Requirements + Scenarios) напрямую и MUST NOT требовать чеклист как вход. Каждый этап MUST NOT начинаться до завершения предыдущего.

#### Scenario: Кейсы пишутся без чеклиста
- **GIVEN** спека change-пакета содержит Requirements и Scenarios
- **WHEN** автор тест-кейсов получает задачу
- **THEN** работа начинается по спеке напрямую
- **AND** отсутствие чеклиста в test-model/checklists/ не является нарушением

#### Scenario: Автоматизатор получает задачу до ревью
- **GIVEN** тест-кейсы не перенесены в test-model/approved/
- **WHEN** автоматизатор проверяет вход
- **THEN** работа не начинается
- **AND** автоматизатор уведомляет проектного менеджера

### Requirement: Цикл ревью тест-кейсов
Ревьюер MUST проверять все кейсы и выносить вердикт «одобрить» или «вернуть». При вердикте «вернуть» автор MUST исправить кейсы, после чего ревьюер MUST провести повторное ревью. Вердикт «одобрить» допустим только при отсутствии замечаний серьезности blocker и major.

#### Scenario: Ревью выявило blocker
- **GIVEN** при ревью найдено замечание серьезности blocker
- **WHEN** ревьюер формирует вердикт
- **THEN** вердикт «вернуть на доработку»
- **AND** кейсы остаются в test-model/new/ до исправления

#### Scenario: Кейс исправлен после замечаний
- **GIVEN** автор обновил кейсы по замечаниям ревью
- **WHEN** ревьюер проверяет исправленную версию
- **THEN** создается новая итерация ревью (review-NNN+1)

#### Scenario: Одобрение кейсов
- **GIVEN** ревью не выявило blocker и major замечаний
- **WHEN** ревьюер выносит вердикт «одобрить»
- **THEN** кейсы переносятся в test-model/approved/<change-id>/

### Requirement: Трассировка автотестов
Каждый приемочный автотест (tests/api/, tests/web/, tests/integration/, tests/smoke_cross/) MUST ссылаться на ID тест-кейса в docstring. Приемочный тест без ссылки на кейс MUST NOT приниматься. Матрица кейс → тест MUST находиться в tests/README.md. Unit-тесты разработчика (tests/unit/) пишутся без тест-кейсов: ссылка на TC-ID для них MUST NOT требоваться, ссылка на FR-N или задачу tasks.md SHOULD присутствовать.

#### Scenario: Тест без трассировки
- **GIVEN** автотест не содержит ID кейса в docstring
- **WHEN** ревью кода тестов
- **THEN** тест помечается дефектом трассировки

### Requirement: Стек автотестов
API-тесты MUST быть написаны на Python с pytest и requests. Web-тесты MUST быть написаны на Python с pytest и playwright. Unit- и integration-тесты MUST быть написаны на Python с pytest и MUST NOT использовать сеть (requests) и браузер (playwright). Автотесты MUST быть изолированы (независимость от порядка запуска) и детерминированы (запрет sleep вместо ожиданий).

#### Scenario: Sleep вместо ожидания
- **GIVEN** в коде теста используется time.sleep для ожидания условия
- **WHEN** ревью кода тестов
- **THEN** тест помечается дефектом (для web — автожидания Playwright, для API — poll-цикл с таймаутом)

### Requirement: Раскладка автотестов
Автотесты MUST лежать по уровню: tests/unit/ — unit-тесты разработчика; tests/api/ — приемка через HTTP API; tests/web/ — приемка через браузер (сьют против стенда — tests/web/e2e/); tests/integration/ — приемка через сервисный слой без HTTP и браузера. Смоук регресса MUST лежать в tests/smoke_cross/, архивные тесты — в tests/archive/. Запись в tests/unit/ MUST принадлежать роли dev, в остальные каталоги — роли qa_automation.

#### Scenario: Приемочный тест бота без HTTP API
- **GIVEN** проект не имеет HTTP API и UI
- **WHEN** автоматизатор пишет тест по одобренному кейсу
- **THEN** тест кладется в tests/integration/ с TC-ID в docstring

### Requirement: Проверка раскладки автотестов
Тестовый файл вне каталогов раскладки (в том числе в корне tests/) MUST считаться нарушением раскладки. Строгость проверки задает проект файлом test-model/test-layout.json: режим warn — предупреждение, strict — ошибка ворот. При отсутствии файла MUST применяться warn; нечитаемый файл MUST давать ошибку ворот.

#### Scenario: Тест в корне tests/ при строгой раскладке
- **GIVEN** test-model/test-layout.json задает режим strict
- **WHEN** в корне tests/ появляется файл test_*.py
- **THEN** проверка порядка артефактов завершается ошибкой раскладки

#### Scenario: Проект до миграции раскладки
- **GIVEN** файла test-model/test-layout.json нет
- **WHEN** тестовые файлы лежат вне каталогов раскладки
- **THEN** проверка выдает предупреждение и не блокирует мерж

#### Scenario: Unit-тест обращается к сети
- **GIVEN** файл в tests/unit/ импортирует requests или playwright
- **WHEN** проверка порядка артефактов
- **THEN** фиксируется нарушение стека по режиму раскладки

### Requirement: Красный тест как баг-репорт
При падении теста на корректном коде теста автоматизатор MUST оформить баг-репорт в test-model/bugs/. Автоматизатор MUST NOT изменять тест или ассерты для получения зеленого прогона без изменения одобренного кейса.

#### Scenario: Падение из-за дефекта продукта
- **GIVEN** тест падает, код теста соответствует одобренному кейсу
- **WHEN** автоматизатор анализирует падение
- **THEN** создается баг-репорт в test-model/bugs/
- **AND** код теста остается без изменений
