### Блок H: Тюнинг QA-агентов (Заказчик, 2026-09-19)

> Контекст: ревью 18 E2E-кейсов заняло 49 минут (43 tool-вызова) — ревьюер читает один большой файл и деградирует к концу. Причина: все кейсы в одном файле.

- [ ] **H1. 1 кейс = 1 файл.** qa_case_author создает каждый тест-кейс отдельным файлом `test-model/new/<change-id>/TC-<domain>-NNN.md` вместо одного большого `<domain>-01.md`. → Изменения: qa_case_author_agent.md (формат выхода), контракт 5 (пути: файл на кейс), возможно flow_check (трассировка по файлам). Экономика: ревьюер грузит только кейс, контекст чище, доработки точечные (один файл = одно замечание = один диф).
- [ ] **H2. Ревьюер работает поэтапно — файл за файлом.** qa_case_reviewer при ревью обрабатывает кейсы последовательно: прочитал кейс → сверил со спекой/кодом → записал замечание в review-файл → выгрузил кейс из контекста → следующий. Промежуточные замечания пишутся append-only в review-NNN.md в процессе, вердикт — в конце. → Изменения: qa_case_reviewer_agent.md (процедура), скилл case-review (шаг ревью). Цель: избежать деградации на больших партиях (случай 49 мин) и держать контекст ревьюера стабильным независимо от числа кейсов.
- [ ] **H3. Партионный лимит ревью.** Если кейсов >N (ориентир 10–12), ревьюер работает партиями: вердикт по партии, ПМ запускает следующую. → В контракт 5: партионная механика + как считать вердикт (approve всех партий = approve пакета). Зависит от H1/H2.
- [x] **H4. Линтеры в ворота (вместо Sonar — решение 2026-09-19).** Sonar для проекта — перебор (инфраструктура >> пользы на ~1.2К строк); 90% пользы дают линтеры: `ruff check` (Python: ошибки+сложность+стиль) и `eslint` (JS: ошибки+лучшие практики) — по одной строке в flow.yml, вывод в лог CI, контекст агентов не отжирает (запускаются только в CI/локально по запросу, НЕ в контексте каждой сессии). → Изменения: flow.yml (+2 шага), requirements/пакет-джсон для пинов версий, базовые конфиги. Порог: новые ошибки линтера = красные ворота; существующий код — базлайн-подавление или правка одним dev-циклом (оценить объем при внедрении). Условие усложнения до Sonar: >10К строк или командная разработка. (Внедрено 2026-09-21: ruff 0.8.4 + eslint 8.57 в flow.yml, базлайн-фиксы: unused imports/vars, noqa BLE001 с обоснованием; ruff config в backend/pyproject.toml, eslint в frontend/.eslintrc.cjs. Baseline: 8 ошибок Python — 2 auto-fix, 1 noqa, ESLint — 2 dead vars удалены. Прогоны: RUFF CLEAN, ESLINT CLEAN, тесты web 21/21, api 85/5.

- [ ] **H5. qa_impact_analyst — impact-анализ регресса при изменении спеки.** Тесты устаревают при доработках (поведение меняется) — постфактум при фейле = ложный пожар на релизном прогоне. → (решение 2026-09-19): отдельная роль (вход/выход qa_checklist не тронуты — роли разные). Запускается после СА при MODIFIED/REMOVED дельтах, до qa_checklist. Вход: дельты + манифест регресса + трассировка TC↔Requirement. Выход: `test-model/impact/<change-id>.md` — вердикт по каждому затронутому тесту: keep / revalidate (pending_update, исключен из прогона, кейс обновляется) / retire (в архив). Требования «обновить кейс X» попадают в чеклист. Промпт создается при первом change с MODIFIED-дельтами. Частично скриптуется: сверка Requirement↔TC по файлам — кандидат в flow_check. Отражено в README (агент №9) и agents/README (таблица зон).

### Блок A: Эскалации и режимы

- [x] **A1. Проверка «эскалация vs самостоятельное решение» в контрактах.** Заказчик делегировал ОВ-14 ПМ («сам решай») — ни один контракт не описывает делегированные решения: кто решает, как фиксируется, кто валидирует. → (сделано 2026-09-19, проход по бэклогу с Заказчиком): контракт 1 дополнен таблицей «Уровни решений по эскалациям» (3 типа: Заказчик / делегированное ПМ «интерпретация ПМ» / технические детали исполнителя) + 3 правила (ПМ не переписывает спеку; пределы делегирования — финансы/сроки/MoSCoW/Must обратно Заказчику; сомнение → тип «Заказчик»).
