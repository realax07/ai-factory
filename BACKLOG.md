# Гарантии соблюдения флоу — анализ и план (2026-09-20, по случаю R1.3)

> Случай: P4 (Флоу 1 — новое поведение/эндпоинт) был запущен ПМ сразу в dev, минуя БА/СА. Уточнение Заказчика поймано steer'ом на лету. Вопрос Заказчика: «какие гарантии соблюдения флоу?».

## Слепая зона: почему ворота не сработали

flow_check проверяет артефакты ПОСЛЕ их появления (кейсы без чеклиста и т.д.), но не проверяет «требовался ли БА/СА вообще». Флоу 2 (баги) легален без БА/СА — значит, и их отсутствие в Флоу 1 ворота не отличат: нет ни файла requirements, ни спеки-дельты, а проверять «должна ли была быть дельта» скрипт не может (это семантика).

## Какие гарантии возможны (по нарастающей силы)

### Уровень 1: Инструкция ПМ (уже есть, слабая)
README Флоу 1/2/4 + сводная таблица. Работает, пока ПМ дисциплинирован. Плюс этого случая: правило «экспресс-режим (Флоу 5) разрешен только при: S-объем, одна зона, поведение очевидно Заказчику; ОБЯЗАТЕЛЬНА ретроспективная документация (requirements + спека-дельта + кейсы) в том же цикле» — формализовать в README.

### Уровень 2: Метка флоу в задачах делегации (дешево, ввести сразу)
В goal делегации ПМ обязан указывать: **«Флоу: N (1/2/3/4/5)»** + обоснование выбора одной строкой. flow_check не проверяет (это в диалоге), но журнал делегаций PLAN.md хранит — аудит возможен пост-фактум, нарушения видны и разбираются в ретро.

### Уровень 3: Скриптовая эвристика в flow_check (средне)
Добавить проверку: «в репо появился новый API-эндпоинт (маршрут в коде), но в openspec нет ни дельты, ни упоминания в master-specs, и нет test-model/impact записи» → WARNING/ERROR. Технически: парс FastAPI-роутов (через import app.main) vs grep по спекам. Ложные срабатывания возможны (внутренние маршруты) — настраиваемый allowlist. Это детерминированная ловушка «новое поведение без спеки».

### Уровень 4: CI-контракт на PR (сильно, требует процесса)
Branch protection правило: PR с изменениями backend/ или frontend/ ОБЯЗАН иметь в описании ссылку на артефакт (BUG-NNN / change-id / impact-файл). GitHub не умеет проверять семантику описания, но умеет требовать статус-чек; можно завязать на легкий лямбда-скрипт или GitHub Action, который парсит тело PR и валидирует наличие маркера. Реализуемо Action'ом в flow.yml (~30 строк).

## Решение для внедрения (предложение ПМ)

Сразу: Уровень 1 (Флоу 5 в README + правило) и Уровень 2 (обязательная метка флоу в goal/журнале).
Следующий тюнинг-проход: Уровень 3 (эвристика в flow_check) — как H6.
Уровень 4 — при росте команды/агентов (сейчас избыточно: единственный создатель PR — dev, его дисциплина уже проверяется на приемке).

## Прецедент этого случая (честная фиксация)

R1.3: Флоу 5 (экспресс) применен БЕЗ формализации — ПМ начал сразу с dev. Спасло: steer-уточнение Заказчика на лету + обязательность ретроспективной документации. Урок: экспресс-режим без формализованных границ деградирует в «сразу код». После внедрения: Флоу 5 легален только при выполнении трех условий (S-объем / одна зона / очевидное поведение) + ретроспектива в том же цикле.
