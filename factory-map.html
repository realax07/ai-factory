01 · Обзор

Как устроена фабрика

ai-factory — это конвейер разработки из агентов. Каждая роль (аналитик, разработчик, ревьюер, QA) работает в отдельном изолированном контексте и передаёт работу только файлами в git. Порядок держит исполняемая машина ворот, а не промпты. Фабрика — шаблон для проектов: factory_init.py ставит те же ворота в новый репозиторий. Пилотный проект — ekotov-wiki.

02 · Агенты и исполнители

Агенты: Hermes, Pi и остальные

«Агент» — это рантайм, который исполняет роль: Hermes, Pi, stub или внешний Codex. «Роль» — это ответственность: промпт, зона записи, вход и выход. Одну роль можно исполнять разными агентами: исполнитель задаётся префиксом стадии run: <исполнитель>:<роль>.

Смена агента (например, Pi на другой CLI) — это новый модуль-исполнитель. Раннер, flowctl и gate_runner не меняются (J64.7 + J65.5).

Hermes Agent

Что это

Платформа, на которой живёт ПМ: Telegram-гейтвей, сессии, память, скиллы, плагины, крон, delegate_task для сабагентов. Домашний каталог — $HERMES_HOME (по умолчанию ~/.hermes).

Модель и конфиг

ПМ работает на glm-5.3-flash @ zai. Модель меняется только через hermes config set, config.yaml руками не правится. Секреты лежат в ~/.hermes/.env.

Что фабрика ставит в Hermes

  • плагин flow-enforcer (plugins.enabled)
  • обёртки кронов в ~/.hermes/scripts/: тонкие делегаты, которые запускают скрипт из репо
  • скиллы openspec-* (.hermes/skills/) и библиотека skills/

Что Hermes даёт движку

  • state.db → async_delegations: реестр делегаций, его пишет сама платформа. Это источник для delegate_watchdog и pr_validate (Reviewer-Delegation)
  • cache/delegation/live/: живые логи сабагентов, их пингует ПМ и архивирует session_archive
Известные грабли Hermes: делегация, отправленная ровно на границе ротации сессии, «съедается» чатом (#92859). /stop убивает все фоновые делегации. Отчёты, потерянные при ротации, лежат в async_delegations.result_json.

Pi (исполнитель ролей)

Роль-пак

skills/pm-factory/pi/role-packs/<роль>/:

  • role-agents.md — системный промпт. Раннер кладёт его в worktree как AGENTS.md, а если у проекта свой AGENTS.md, то рядом как AGENTS.pi.md
  • settings.example.json — дефолты сессии (thinking off, tools read/bash/edit/write)
  • README.md — сборка и вызов (блок зоны генерируется)

zone-guard.ts

Одно расширение на все паки, эталон лежит в репо фабрики. Раннер грузит его явно (--no-extensions -e …), поэтому копия в ~/.pi на стадии не используется.

  • PI_ZONE_WRITE: зоны через «:». Без этой переменной запись запрещена целиком
  • PI_ZONE_ROLE: bash-правила. git push запрещён всем, docker-мутации — всем, кроме devops
  • write/edit проверяются жёстко (fail-closed); bash — эвристика

Как агент получает задачу

Через раннер (боевой путь)

Раннер собирает бриф из полей стадии task, inputs, zones и verdict. Создаёт worktree от текущего HEAD, кладёт промпт пака, выставляет env зон и запускает процесс с таймаутом. Каждый старт и финиш пишется в executor_runs.jsonl.

Через delegate_task (запасной)

Goal собирается по templates/task_delegation.md:

  • (а) промпт роли
  • (б) пути входов и выхода
  • (в) зона и запрет push в main
  • (г) дословные решения Заказчика
  • (д) требование отчёта

Каждая делегация записывается строкой в журнал PLAN.md.

03 · Роли

Роли: кто что делает

Одна роль — один изолированный контекст и одна ответственность. Автор не ревьюит себя, ревьюер не пишет код. Новая роль заводится, только если работа повторяется, нужна изоляция, есть своя зона и это дешевле по токенам. Источник зон — agents/roles.json; таблицы в README генерирует gen_role_docs.py.

05 · Машина ворот

Машина ворот: что, где и что смотрит

Ядро — пять скриптов, которые вызывают друг друга. flowctl — единая точка входа. flow_state только читает факты. flow_transition выносит решение. session_check держит зоны. gate_runner гоняет проверки и пишет доказательства.

Жизненный цикл сессии (резервации)

Зону держат reserved, running, finished и needs_attention. Пока сессию не закрыли, никто другой не зарезервирует пересекающиеся пути: будет ZONE_CONFLICT.

Что смотрит flow_state (снимок фактов)

Чистая read-only операция: ничего не пишет, не делает fetch и checkout. Статусы фактов: missing (нет), invalid (есть, но непригоден), unknown (не читается), ready. Готовность не выводится из имени файла или чекбокса, только из содержимого.

07 · Вотчдоги и кроны

Вотчдоги и кроны

Слой «заметят». Кроны запускает Hermes cron. В ~/.hermes/scripts/ лежат только тонкие обёртки-делегаты, источник истины — репо-копия скрипта. Политика тишины: при чистом состоянии вотчдог молчит, а в чат попадает только аномалия.

Расписание за час

Каждая полоска — запуск. delegate-watchdog на паузе: его включает ПМ после проверки эвристики (прогон clean, exit 0, затем deliver=origin). Тот же прогон вызывает executor_watchdog.

Карточки вотчдогов

delegate_watchdog.py · обход делегаций

Читает: state.db → async_delegations (пишет сама платформа при каждом delegate_task), flowctl_state.json, ack-файл.

Ловит: BYPASS — делегация с непустым project без записи flowctl; STALE_FINISH — делегация завершилась, а сессия flowctl осталась running.

Норма: диспатчи ПМ без project не флагаются (23 ложных bypass 2026-10-23).

Анти-спам: дедуп по составу, cooldown 15 мин, не больше 3 доставок в час. Exit 1 — нарушения.

executor_watchdog.py · обход исполнителей

Читает: процессы исполнителей (list_active() каждого модуля), реестр сессий, executor_runs.jsonl.

Ловит: процесс pi или stub в каталоге проекта конвейера, чей cwd не совпадает с worktree живой резервации — BYPASS proc:<исполнитель>:<pid>. По журналу отличает сбой раннера от ручного запуска.

Слепые зоны: бинарь под чужим именем, команды в переменных.

session_watchdog.py · чат Заказчика

Читает: state.db (gateway_routing, sessions), sessions.json.

Ловит: ключ роутинга Telegram, который указывает на завершённую сессию (вы «проваливаетесь» в зомби-сабагента), dropped-делегации, контаминацию ролью.

Действие: удаляет залипшую запись роутинга, и следующее сообщение создаёт свежую сессию. Exit 1 — было лечение.

stand_reaper.py · осиротевшие стенды

Читает: процессы uvicorn / http.server / nginx пользователя openclaw, /proc/<pid>/cwd, реестр сессий.

Решение: cwd удалён или worktree без живой сессии — REAP. Обычный клон — только отчёт. Прод, docker и чужих пользователей не трогает.

Режим: по умолчанию dry-run, --kill только руками.

state_backup.py · бэкап state

Делает: backup — state-<UTC>.tar.gz в AF_BACKUP_DIR (0600), хранит 14 последних. restore откладывает текущий state и откатывается при сбое. Если есть активные сессии — отказ без --force.

Важно: копию нужно вывозить с VPS (runbook-factory-move).

chat_degrade_watchdog.py · деградация моделей

Читает: только новые байты errors.log гейтвея (offset в state).

Ловит: runaway repetition, обрыв стрима, EOF без finish_reason. Не чаще раза в час на тип. Exit всегда 0.

Статус: в рекомендованном реестре кронов его нет; включается отдельно.

08 · CI и GitHub

CI и GitHub: последний замок

Слой, который нельзя обойти локально: без зелёных обязательных чеков мерж в main невозможен.

Push-политика сабагентов (J42)

  • L1: ruleset main, bypass never
  • L2: CI-триггер pipeline/**. Голый push без открытого PR — падающий шаг и сигнал ПМ
  • L4: flow-enforcer push_gate. В делегации разрешён push только в свою ветку, иначе PUSH_POLICY. Push ПМ в продукт без [integrate]/[pipeline] — PM_PUSH_POLICY
  • Pi: zone-guard блокирует git push всем ролям

09 · Тесты и регресс

Тесты и регресс

Полный регресс гоняется не на каждый change. Обычный change — это доменный прогон своего куска плюс smoke. Полный regress-final запускается пакетно перед плановым деплоем (J54).

Пять эшелонов регресса

Baseline

test-model/regress/baseline.json — известные падения main. Эшелоны 1–2 их не краснят, --final игнорирует. --suggest-baseline предлагает кандидатов, переносит ПМ.

Freeze tooling

Между regress-final и деплоем scripts/** и .github/** не трогаются: любой tooling-коммит означает перегон.

xdist

--xdist N ускоряет прогон. Требование: стенды не делятся между воркерами, стендозависимые тесты помечаются serial.

Раскладка тестов (J66)

tests/
├─ unit/          # dev · без TC-ID · без requests/playwright
├─ api/           # qa_automation · pytest + requests · TC в docstring
├─ web/           # qa_automation · pytest + playwright (e2e/ — сьют стенда)
├─ integration/   # qa_automation · сервисный слой без HTTP и браузера
├─ smoke_cross/    # манифест cross-domain smoke
└─ archive/        # выведенные из регресса (не удаляются)
test-model/test-layout.json  # {"mode": "warn"|"strict"} — защищённый путь

Тесты самой фабрики

Герметичность

tests/conftest.py подменяет HOME на всю сессию (isolated_home). Tree guard валит тест, оставивший мусор в дереве (FACTORY-TREE-LEAK). Боевой ~/.hermes тесты не трогают.

Самообкатка

test_gate_harness.py строит tmp-репо, делает shallow clone и гоняет pr_validate, flow_check и factory_init в чистом env. Эталонный прогон раннера проходит в каждом CI.

Слои гарантий

Слой 1 · GitHub

Обход физически невозможен: ruleset, required checks, openspec strict, flow_check, 1400+ тестов, ворота проектов по lock.

Слой 2 · машина

Работает на штатном маршруте: вотчдоги, сверка зон, ворота раннера, zone-guard, MODEL_ENFORCE, provenance, pm_bounds.

Слой 3 · дисциплина [H]

Держится на честном слове: push только своей ветки мимо ворот, cwd worktree при 4+ параллелях, коммит до исчерпания итераций, гашение стендов, ротация сессий.

Принятые риски

Общая ОС-учётка

Машинный enforcing работает только на маршруте flowctl. Правка через GitHub UI или локальные файлы ничем не блокируется (решение 2026-10-02).

Качество ревью

Проверяется форма (вердикт, мета, делегация), но не глубина ревью.

Approve по частичному прогону

Промежуточные PR Флоу 1 валидны без полного QA-хвоста. Риск снимается финальным PR.

Слепые зоны вотчдогов

Исполнитель под чужим именем бинаря; delegate-watchdog, пока ПМ его не включил; bash-канал Pi (эвристика).
