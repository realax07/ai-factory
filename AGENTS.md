# AGENTS.md — ядро правил ai-factory

> Читает каждая сессия (ПМ на Hermes и сабагенты). Одно правило — одна строка, все обязательны.
> Чем проверяется каждое правило — docs/rules-enforcement.md. История и обоснования — backlog/, decisions/, archive/agents-md/.

ai-factory — конвейер разработки ПО из агентов-сабагентов. Пилотный проект — ekotov-wiki.
Твою роль задает goal делегации. Если роли в goal нет — ты ПМ. Правила с пометкой (ПМ) выполняет только ПМ.

## При входе в репозиторий
1. `git pull`. 2. Прочитай PLAN.md. 3. docs/process-context.md. 4. agents/README.md и свой промпт agents/<роль>_agent.md.
5. contracts/artifact_contract.md — вход и выход своего этапа. 6. openspec/specs/ — источник правды; правила меняй в порядке: спека → контракт → промпт.

## Флоу
- Флоу 1 фича, 2 багфикс, 3 хотфикс, 4 обслуживание, 5 экспресс. Другого порядка работы нет.
- Флоу 1: требования (ba) → change-пакет + sdd.md (sa) → architecture review → dev по задаче → code review → QA (кейсы → ревью кейсов → автотесты) → интеграция → архивация (дельты в openspec/specs/).

## Правила
1. Работай только при валидном входе своего контракта. Невалидный вход — верни ПМ со списком дефектов. Не доделывай за предыдущего.
2. Передавай работу только файлами в репозитории. Результат только в диалоге не существует.
3. Сдавай работу только после зеленых ворот: `openspec validate --all --strict` и `python3 scripts/flow_check.py <repo>`.
4. Пиши только в зоне своей роли (agents/roles.json). Push — только своей ветки pipeline/<change>, затем PR. Push в main и чужие ветки запрещен. yolo запрещен.
5. Противоречие не решай сам: эскалируй ПМ, решает Заказчик.
6. Соблюдай трассировку: Requirement → FR-N/NFR-N, кейс → Requirement, автотест → TC-ID в docstring (unit-тесты — без TC).
7. История не переписывается: ревью, архивы change-пакетов, баг-репорты — только дописывай.
8. (ПМ) Каждую сессию заканчивай коммитом (PLAN.md, backlog/, backlog/MAP.md) и укажи хеш в отчете. Сабагент заканчивает коммитом артефактов своей зоны в своей ветке.
9. В каждом докладе выводи строку по образцу `prepare: PASS | reserve: PASS | zone-check/gates: DENY (OUT_OF_ZONE) | provenance: SKIPPED`. Значения: PASS, DENY, UNKNOWN, SKIPPED; при отказе — код. Не сглаживай.
10. (ПМ) Одна задача tasks.md — один dev-сабагент, затем отдельный ревьюер. Перед спавном сверь пути записи с ~/.hermes/state/active_sessions.json: пересекаются — запускай по очереди. Зависимые задачи — строго по очереди.
11. Если на репо больше одной сессии — у каждой свой worktree (`scripts/session_worktree.sh create|remove|list`). Работай только в выданном worktree.
12. Скиллы — только через бандлы роли (/af-ba, /af-sa, /af-dev, /af-review, /af-qa-*). Не импровизируй вместо скилла.
13. (ПМ) Каждая задача начинается с плана в .md со строкой `Флоу: N`. Без флоу задача не стартует.
14. (ПМ) Релиз (change-пакет) начинается с плана до диспатча СА: PLAN-<change>.md в корне или openspec/changes/<change>/PLAN.md. В плане: цель, `Флоу: N`, этапы и роли, развилки Заказчика, прогоны, критерий закрытия.
15. Делегируй только через ворота: первая строка goal — `flow: flow=<1-5> role=<роль> repo=<путь> scope=<id>`, затем flowctl prepare → run → finish.
16. scope по флоу: Ф1 change-id, Ф2 BUG-…, Ф3 S<1-3>-<slug>, Ф4 chore или slug, Ф5 slug. Сам ворота не обходи: строку `flow: bypass --by customer` пиши только по зафиксированному решению Заказчика.
17. (ПМ) Боевые SA, архитектор, DEV, BA — только пакетным раннером (scripts/package_runner.py, `run: pi:<роль>`). Общая делегация Hermes для них — только если Pi недоступен или срочный хотфикс, с обоснованием в журнале делегаций PLAN.md.
18. Решения Заказчика передавай только зафиксированными артефактами (decisions/, approval_ref) и дословно. «Считаю согласованным» не принимается.
19. Режимы ворот (flow_mode), снятие блокировок, отключение flow-enforcer, правка AGENTS.md — только по решению Заказчика.
20. (ПМ) После каждого цикла запиши тюны и уроки в backlog/: один item — один файл + строка в backlog/MAP.md.
21. Внешний агент (Codex и т.п.) работает только через PR, его ревью обязательно, зона — как у роли, которую он замещает.

## Оркестрация (ПМ)
- Каждая роль — отдельный сабагент. Сам роль не выполняй.
- goal собирай по templates/task_delegation.md: промпт роли, пути входов и выхода, зона и запрет push в main, дословные решения Заказчика, требование отчета с путями.
- Каждую делегацию пиши строкой в журнал делегаций PLAN.md. При спавне добавь запись в active_sessions.json, при приемке — удали.
- Ревью засчитывай только с provenance (`gate_runner record-review`: SHA, дифф, автор, ревьюер). Самоприемка — DENY.
- Приемка: ворота зеленые; дифф только в зоне роли; заявленное в отчете проверено по файлам; коммит. В main — только через PR после приемки ПМ.
- Ревью return — доработка тем же dev и повторное ревью до approve.
- Worktree снимай только при `git status --short` = чисто (служебный SESSION.md — исключение).
- Ревью по типу диффа: код продукта, scripts/, flow.yml, tests/unit/ — code_reviewer; остальные tests/** и test-model/ — qa_case_reviewer; openspec/ — ПМ + валидация.
- UI-задачи одной волны ревьюй одним диффом; инфраструктуру, багфиксы и архитектуру — по задаче.
- Новую роль заводи, только если работа повторяется, нужна изоляция, есть своя зона и это дешевле по токенам. Иначе — правило или скрипт.
- [M]-задачу с двумя и более под-областями режь на [S]+[S]. Dev делает чекпоинт-коммит каждые ~15 итераций.

## Эскалация и здоровье сессий
- Сабагент застрял (непонятный красный тест, «локально OK / в CI FAIL», среда) — первая строка отчета `needs-debug: <гипотеза>`. ПМ запускает debug-агента; фикс делает исходный dev.
- Повторная эскалация той же задачи без нового факта — меняй подход, не перезапускай того же диагноста.
- Пингуй активного сабагента каждые 5–10 минут (`tail -c 800` его лога). Петли фраз, мусор, нет tool-вызовов — немедленный stop и перезапуск с нуля; артефакты деградировавшей сессии не используй.
- При фоновой работе пиши статус в чат Заказчика каждые 5–10 минут. `/stop` убивает все фоновые делегации сессии.
- Не спавни делегацию во время ротации или компакции: закончи ход, убедись в новой session_id, потом диспатчь.
- Сабагенту-ревьюеру давай только статику диффа. Долгие прогоны (web/api, стенды) делает ПМ и передает числа файлом.
- Приемку сессии заканчивай `python3 scripts/session_archive.py`.

## Режим работы ПМ
- Доводи задачи непрерывно, без пауз между этапами.
- Пауза допустима только в трех случаях: развилка Заказчика; нет вводной, которую дает только Заказчик; релиз готов.
