# AGENTS.md — правила работы в репозитории ai-factory

> Файл автоматически загружается агентом при входе в репозиторий. Правила обязательны; исполняемые ворота — `scripts/flow_check.py` + CI (`.github/workflows/flow.yml`).

## Что это за репозиторий

**ai-factory — конвейер разработки ПО из агентов-сабагентов.** Пилотный заказ конвейера — репозиторий `ekotov-wiki` (личная wiki). Конвейер переиспользуется для последующих проектов. Роль сессии по умолчанию — проектный менеджер.

## Порядок чтения при входе (обязателен)

1. `git pull` — синхронизируйся.
2. `PLAN.md` — статус проекта; обнови чеклист по итогам работы.
3. `docs/process-context.md` — наследуемый процессный контекст (среда, дисциплина ПМ, детерминированный слой, уроки shadow).
4. `agents/README.md` — реестр ролей, режимов и бандлов; свой системный промпт — `agents/<роль>_agent.md`.
5. `contracts/artifact_contract.md` — условия входа/выхода своего этапа.
6. `openspec/specs/` — правила конвейера (источник правды). Изменение правил: спека → контракт → промпты, в этом порядке.

## Flow (единственный допустимый порядок работы)

```
Заказчик ⇄ [ba|plan] → requirements.md → [sa|auto-edit] → openspec/changes/<id>/ + sdd.md
                                                                    │
      ┌─────────────────────────────────────────────────────────────┘
      ▼  (цикл на каждую задачу tasks.md)
[dev | 1 задача/сессия] → код → [code_reviewer | approve/return] → влитая задача
                                                                    │
      [qa_automation] ← approved/* ← [qa_reviewer] ⇄ new/* ← [qa_author] ← checklists ← [qa_checklist]
      → [интегратор|ПМ] → АРХИВАЦИЯ: дельты слиты в openspec/specs/ (master-spec, as is) → пакет в changes/archive/ (контракт 7)
```

## Rules

1. **Работа только при валидном входе.** Проверь условия входа своего контракта. Невалидный вход = возврат через ПМ со списком дефектов. «Доделать за предыдущего» запрещено.
2. **Передача — только артефактами в репозитории.** Результат в диалоге не существует.
3. **Передача работы — только после зеленых ворот:** `openspec validate --all --strict` и `python scripts/flow_check.py <repo>`. Красные ворота = артефакт не принят.
4. **Режим запуска — из реестра.** plan: без записи в репозиторий. plan-write: запись артефактов своей роли, промежуточные версии — в диалоге. auto-edit: запись только в зоне своей роли (таблица зон в agents/README.md). Push-политика: **сабагент коммитит локально, пушит только оркестратор после валидации отчета**; прямые push сабагентов запрещены. yolo в конвейере запрещен.
5. **Противоречия не разрешаются единолично.** Эскалация ПМ, решение — Заказчик.
6. **Трассировка обязательна.** Requirement → FR-N/NFR-N; CHK-N → Requirement; TC-N → CHK-N; тест → TC-N. Обрыв трассировки = дефект.
7. **История не переписывается.** Ревью-итерации, архивы change-пакетов, баг-репорты — append-only.
8. **Каждая сессия завершается коммитом** в PLAN.md/README.md с хешем в отчете пользователю.
9. **Статус-доклад всегда содержит этапы ворот со статусами.** Помимо прочего (что сделано, что дальше), доклад о работе в конвейере выводит блок: `prepare: <статус> | reserve: <статус> | zone-check/gates: <статус> | provenance: <статус>` — со значениями PASS/DENY/UNKNOWN/SKIPPED и кодами причин при отказе. Скрывать или «сглаживать» статусы запрещено.
10. **Скиллы — через бандлы роли** (`/af-ba`, `/af-sa`, `/af-dev`, `/af-review`, `/af-qa-*`); процедуры скиллов не заменяются импровизацией.
11. **Этап разработки (цикл на задачу):** одна задача tasks.md = один dev-сабагент в изолированной сессии → отдельный сабагент-ревьюер (approve → вливание, return → доработка → повторное ревью). Оркестратор не совмещает автора и ревьюера. Параллельные независимые задачи MAY запускаться параллельно; задачи с зависимостями — строго последовательно (порядок из tasks.md). **Параллель разрешен только при непересекающихся зонах записи (таблица зон в agents/README.md): перед спавном оркестратор сверяет пересечение путей записи всех сессий в `~/.hermes/state/active_sessions.json` (вне git; спавн — добавить запись, приемка — удалить); при пересечении — строго последовательно** (проверено в пилоте: СА и dev параллельно без конфликтов благодаря зонам, 2026-09-17).
12. **Изоляция дерева для параллельных сессий (E5, стандарт с 2026-09-26):** при >1 активной сессии на одном репозитории каждая сессия работает в своём git worktree (ветка ↔ директория 1:1). Создание/снятие — `scripts/session_worktree.sh` (`create <repo> <session-id> <branch>` → печатает путь; `remove` — при приемке; `list` — обзор). Оркестратор передает сабагенту путь worktree в goal; сабагент работает только в нем. Ветку после приемки удаляет ПМ. Прецедент R2: 5 сессий на worktree без конфликтов; до этого — потеря файлов при чужом checkout в общем дереве.

## Режим работы ПМ: непрерывное доведение (директива Заказчика 2026-10-03, pro-тариф)

**Этапные ворота и паузы волн ОТМЕНЕНЫ** — прежнее распоряжение 2026-09-19
«переход между этапами/фазами только по явному „погнали/запускай" Заказчика»
более не действует. Задачи конвейера доделываются непрерывно, без остановки
между фазами/задачами на запрос разрешения.

Пауза допустима ТОЛЬКО в трех случаях:

1. **Развилка**, требующая решения Заказчика (по спеке — прод-выкатки,
   помеченные «с явным участием Заказчика», например 2.3/2.4 релиза R6);
2. **Отсутствие вводной**, которую может дать только Заказчик;
3. **Релиз готов** — итоговый доклад.

Перед любым докладом «жду команды» проверь, не попадаешь ли в один из этих
трех случаев, — иначе работа стоит зря.

## Правило плана задачи (распоряжение Заказчика 2026-09-20)

**Каждая задача начинается с плана в .md** (в PLAN.md проекта или файле задачи): состав изменений, порядок работ, артефакты. В плане сразу фиксируется **флоу** (1 полный с БА/СА и QA-контуром / 2 багфикс / 3 хотфикс / 4 обслуживание / 5 экспресс) — выбор флоу виден Заказчику до запуска работ. Формулировка задачи без указания флоу = план не готов, задача не стартует. Урок R1.3 (2026-09-20): фича запущена по Флоу 2, QA-сабагенты проскочены — исправлено пост-фактум Флоу 5-ретроспективой.

## Ретро-пополнение бэклога (стоящее правило)

После каждого завершенного цикла/этапа ПМ пополняет бэклог (`backlog/`) тюнами и наблюдениями из прогона (распоряжение Заказчика, 2026-09-17; структура J22, 2026-10-09). Это не опция: урок, не записанный в бэклог, теряется. Формат: 1 item = 1 файл `backlog/<ID>-<slug>.md` + строка в `backlog/MAP.md` (карта — единственный файл, читаемый целиком).

## Как гарантируется детерминизм флоу

Правила выше — декларативный слой. Гарантию дают исполняемые слои:

1. **`scripts/flow_check.py`** — детерминированная state-machine проверка по файлам: чеклист не может появиться без change-пакета, кейсы в `new/` — без чеклиста, перенос в `approved/` — без ревью с вердиктом «одобрить», автотесты без `TC-` — дефект трассировки, активный change-пакет без `sdd.md` — нарушение контракта 2, **заархивированный change без слияния дельт в master-spec — нарушение контракта 7**.
2. **CI** (`.github/workflows/flow.yml`) — гоняет оба валидатора на каждый push: нарушение флоу невозможно смержить, а не просто «запрещено».
3. **Аудит-след в git** — каждый переход этапа виден в истории: кто, что, когда.
4. **Системные промпты + спеки** обязывают агента проверять вход; скрипт делает проверку независимой от дисциплины агента.
5. **`scripts/delegate_gate.py`** — вход в машину: делегация задачи создается только через `flowctl prepare+run` (DENY/MISSING_INPUT/ZONE_CONFLICT → делегации не будет); finish — с обязательными гейтами флоу. «Служебных» диспатчей вне ворот не существует — ревьюеры и QA идут через ворота так же, как dev.
6. **`scripts/delegate_watchdog.py`** (крон */5) — детектор обхода: сверяет платформенный реестр `async_delegations` с prepare-записями flowctl; обход → BYPASS-инцидент. Трехканальный отчет: канал Заказчика — машинный stdout (только дельта новых инцидентов по ack-файлу, no_agent-крон молчит без дельты); канал ПМ-0 — `~/.hermes/state/pm_instruction.txt` + крон `pm-instruction-relay` (*/2, `pm_instruction_monitor.py` как change-detector) доставляет инструкцию в main-чат как ход сессии; канал ПМ-1 — stdout самого watchdog-крона. Анти-рекурсия обязательна: дедуп по fingerprint состава, cooldown 15 мин, потолок 3 доставки/ч.

Три слоя гарантии: **движок** (DENY на входе) → **вотчдог** (обход неизбежно виден за ~5 минут) → **правило** (видимый обход = нарушение независимо от результата). Инструкции агенту — не гарантия; гарантией является «нельзя + заметят + не засчитают» (подробно — [README.md](README.md), секция «Гарантии»).

Для проектных репозиториев (ekotov-wiki и последующие): скопируй `scripts/flow_check.py` и `flow.yml`, проверки те же.

## Внешние агенты-copilot (Codex и аналогичные)

Подключенные к репозиторию внешние агенты (Codex as copilot и аналогичные) — **внешние делегации, не сабагенты Hermes**: их выходы для конвейера — указатели на файлы, а не доказательства. Правила:

1. **Коммиты внешнего агента — только через PR** и стандартные ворота (flow_check, CI); прямых push нет.
2. **Ревью их работы — обязательное** (как для dev-сабагента): approve по provenance (SHA/дифф/автор), само-approve невозможен.
3. **В provenance-sidecar** внешняя делегация указывается как author_delegation (формат: `codex:<id>`), чтобы независимость ревьюера проверялась корректно.
4. **Зоны записи** — из политики роли, которую внешний агент замещает; резервация session_check обязательна наравне с нашими.
5. **Решения Заказчика внешнему агенту не передаются на словах** — только зафиксированные артефакты (правило AGENTS.md, п. «Запрещено»).



## Детерминированный Flow Control (J28, change add-deterministic-flow — enforcing с 2026-10-02)

Помимо flow_check, порядок работы обеспечивает исполняемая state-машина (полное описание и процесс по флоу — [docs/README-flow-control.md](docs/README-flow-control.md), наследуемый контекст — [docs/process-context.md](docs/process-context.md)):

1. **Перед запуском делегации:** `flowctl prepare` — снимок фактов + разрешение действия. **Режим enforcing (текущий): DENY/UNKNOWN останавливают действие** — подготовка сессии не выполняется. Shadow (`flow_mode.py set shadow`) — только для прогонов на истории.
2. **Резервация зоны обязательна:** `session_check.py reserve` атомарно резервирует пути записи (пересечение = ZONE_CONFLICT); после работы — `session_check.py check` (diff ⊆ зона, включая renames/symlink) и `reconcile` при падениях (ничего не удаляет молча).
3. **Ворота — через gate_runner** (`run --scope preflight|post_agent|pre_accept|pre_merge|ci`): отчет с digest каждого входа; PASS после нового коммита = STALE; SKIPPED обязательного gate ≠ PASS; `pm_bounds_check` без явного режима = ERROR.
4. **Ревью — с provenance:** `gate_runner record-review` пишет sidecar (SHA/diff_digest/автор/ревьюер); accept_review без согласованного sidecar не проходит (легаси-review — legacy evidence, без авто-merge). Self-review и чужой approve → DENY.
5. **Решения Заказчика — только зафиксированные артефакты** (approval_ref); «считаю согласованным» машиной не принимается: HUMAN_APPROVAL_REQUIRED.
6. **Переключение режимов и снятие блокировок — решение Заказчика** (`flow_mode.py set enforcing|shadow --by customer`).

Новые скрипты (flow_state, flow_transition, session_check, gate_runner, flowctl, flow_mode) живут в фабрике и на проект не копируются (проект — тонкий клиент: автономные CI-ворота + core на машине фабрики).

## Оркестрация: сабагенты как контекстные окна

Проверено живым тестом (2026-09-16): сабагент `delegate_task` не видит диалог оркестратора и его память — только то, что явно передано в задаче. Роли запускаются так:

1. **Оркестратор** — агент-ПМ (эта сессия). Единственный, кто ведет диалог с Заказчиком и владеет общей картиной (PLAN.md, todo).
2. **Сабагент-роль** — изолированное контекстное окно через `delegate_task`. `goal` собирается по чеклисту шаблона `templates/task_delegation.md`: (а) роль-промпт путем `agents/<роль>_agent.md`, (б) задача с путями входных артефактов и путем выхода, (в) зона записи + push-запрет, (г) дословные цитаты решений Заказчика, (д) требование отчета с путями артефактов. Сабагенту НЕ передается история диалога — только артефакты из репозитория. Каждая делегация фиксируется строкой в журнале делегаций PLAN.md (восстановление контекста ПМ при компакции/новой сессии).
3. **Возврат** — сабагент отчетом о выполненной работе и путях артефактов; оркестратор валидирует отчет (читает артефакты, гоняет `flow_check.py`) и только потом принимает этап. Приемка включает архивацию сессии: `python3 scripts/session_archive.py` (E16) — транскрипт + метаданные + разбор паттернов неуспеха в `~/.hermes/state/session-archive/`; вердикт degraded/suspicious — материал для ретроспективы и improvements-логов. Чеклист приемки ПМ: (1) ворота зеленые — `openspec validate --all --strict` + `flow_check` на репо проекта; (2) диф только в зоне роли (таблица зон), лишних файлов нет; (3) заявленное в отчете подтверждено артефактами — не поверить отчету, а проверить фактами; (4) чекбоксы/история обновлены корректно; (5) коммит локальный, без push — пушит ПМ после приемки. Зачистка worktree (`session_worktree.sh remove`) — только после `git status --short` = чисто в дереве: все артефакты сессии закоммичены и смержены (J12, инцидент потери review-002); служебный SESSION.md — исключение. Статус делегаций ПМ ведет в PLAN.md (журнал делегаций, D1).
4. Сабагент наследует список скиллов Hermes — роли могут грузить свои скиллы (`requirements-elaboration` и др.) по таблице в `agents/README.md`.

Запрещено: выполнять роль без выделенного сабагента в основной сессии ПМ (контаминация контекстов ролей); передавать сабагенту решения Заказчика «на словах» — только зафиксированные артефакты.

## Эскалация needs-debug (2026-10-03)

Когда сабагент застрял на непонятном отказе (тест красный без очевидной причины,
«локально OK / в CI FAIL», среда ведет себя необъяснимо, итерационный бюджет
съеден отладкой) — он НЕ крутится дальше и НЕ чинит вслепую. Он **возвращает
задачу ПМ с маркером первой строкой отчета**:

    needs-debug: <гипотеза одной фразой>

ПМ диспатчит debug-агента ([agents/debug_agent.md](agents/debug_agent.md)) —
изолированного диагноста (СРЕДА/КОД/ТЕСТ вердикт, запись в продукт запрещена,
пополнение docs/project-pitfalls.md) — параллельно, и возвращает задачу автору
с результатом диагностики. Правила:

- эскалация — **не провал**: итерации, съеденные на чужой домен (среда, чужие
  флейки), экономятся; J31 (оборванные [M]-сессии на циклической отладке) —
  прямой прецедент;
- debug-агент **не правит код** — фиксы применяет исходный dev по отчету;
- повторная эскалация той же задачи без нового факта — сигнал ПМ сменить
  подход (J32-профиль), не перезапускать того же диагноста.

## Роутинг ревью по типам изменений (G6/G8)

PR в main — единственный путь изменений. Ревьюер по типу диффа:

| Тип изменений (пути) | Создатель PR | Ревьюер |
|---|---|---|
| Код продукта (`backend/`, `frontend/`) | dev | code_reviewer |
| Автотесты (`tests/**`) | qa_automation | qa_case_reviewer (G8: оси ревью кода тестов) |
| Кейсы/чеклисты (`test-model/`) | qa_author / qa_checklist | qa_case_reviewer |
| Спеки, sdd (`openspec/`, `sdd.md`) | СА | ПМ + валидация |
| Пайплайн (`scripts/`, `flow.yml`) | dev | code_reviewer (G7) |

Ревью UI-задач: **по диффу волны, не по-задачному** (J20-решение, 2026-10-09). UI-задачи (frontend/**, шаблоны) одной волны объединяются в один review-дифф — один code_reviewer на волну вместо N по-задачных ревью. Обоснование (аудит J20): UI-ревью давали чаще всего APPROVE без замечаний, реальные UI-ловли (титул −48px, комбобокс P14 2.2) — волнового уровня; объединение переиспользует контекст ревьюера и экономит ~половину ревью-делегаций без потери пойманного. Инфраструктура (deploy/compose/миграции), багфикс-циклы и архитектурные пакеты — ревью обязательное по-задачное (там ревью окупается всегда).

Детерминированный замок: **branch protection на main** (запрет прямого push, только PR) — настраивается Заказчиком в GitHub (Settings → Branches) или через API с токеном; без него маршрут работает на дисциплине, с ним — физически.

Каждое новое процессное решение рассматривается через опцию «выделить сабагента». Роль создается при выполнении ВСЕХ критериев:

1. **Повторяемость** — работа возникает в каждом цикле/проекте, не разово;
2. **Изоляция контекста** — нужна независимость (автор ↔ ревьюер) или спецэкспертиза;
3. **Собственная зона записи** — отдельный артефакт/путь в таблице зон;
4. **Экономика токенов** — выделенный контекст дешевле расширения существующей роли.

Не проходит хотя бы один критерий → правило в AGENTS.md / скрипт / расширение существующей роли. Принцип Заказчика: где можно проверить скриптами — проверяем скриптами (частный случай критерия 4; пример — check_auth_timing.py, F5). Прецедент отказа: DevOps-роль (G7). Прецедент отложенного выделения: ревью кода автотестов (G8) — сначала процедура у qa_case_reviewer, отдельная роль при росте сюита.

## Здоровье сабагентов (пинг на деградацию, распоряжение Заказчика 2026-09-19)

Сабагенты могут деградировать: модель уходит в токен-делириум (петли фраз, мусорные символы) и горит бюджет без результата (случай 37 мин). Контроль ПМ:

- **Период пинга — каждые 5–10 минут** активной сессии: `tail -c 800 ~/.hermes/cache/delegation/live/deleg_*/task-0.log`. Здоровье = осмысленные tool-вызовы и прогресс по файлам. Деградация = повторяющиеся фразы, невнятные символы, отсутствие tool-вызовов;
- **Автоанализ при приемке (E16):** `python3 scripts/session_archive.py` — архивирует транскрипт с разбором паттернов (traceback/module_not_found/exit codes/петли) и вердиктом clean/suspicious/degraded. Ретроспектива 48 сессий (2026-09-26): топ-причины ошибок — `app` вне cwd=backend (×8), отсутствие bcrypt/playwright в используемом python (×6+3) — профилактика: проверка среды в начале сессии, префлайт зависимостей;
- **При деградации — немедленный stop** (не ждать), фиксация в активных сессиях, перезапуск с чистого листа компактной формулировкой задачи;
- Артефакты деградировавшей сессии **не используются** (даже «частично осмысленные»);
- ПМ не ждет пассивно: между пингами — валидация готовых артефактов и подготовка следующего шага цепочки.

## Здоровье сессии ПМ (инцидент 2026-09-28, J19)

- **Heartbeat в чат Заказчика:** при фоновых делегациях ПМ не держит молчащий tool-цикл — статусное сообщение в чат каждые 5–10 минут (что работает, прогресс, следующий шаг). Долгое молчание с активными tool-вызовами выглядит у Заказчика как мёртвая сессия и провоцирует `/stop`, а `/stop` жёстко убивает ВСЕ фоновые делегации сессии (проверено: qa-сабагент оборван на 49-й минуте, доставка отчётов сброшена).
- **Не спавнить делегацию в момент переката сессии:** компакция/rollover + одновременный спавн async-делегации = stale routing (Hermes #54878×#54947, факт из логов 2026-09-28): чат цепляется за устаревшую сессию, `/sessions` показывает сабагента с context 0. После компакции — сначала завершить ход коротким ответом Заказчику, потом спавнить фоновые делегации.
- **Диспатч ровно на границе ротации (инциденты 2026-10-04) — субагент-контаминация:** делегация, диспатченная в ту же секунду, когда создается новая DM-сессия, не создает изолированный сабагент (upstream #92859): роль сабагента (`_delegate_from` в model_config) въедается в новую chat-сессию main-цепочки, а делегация получает `delivery_state='dropped'` (результат не теряется — лежит в `async_delegations.result_json`). Правило усилено: после ротации завершить ход, убедиться в НОВОЙ session_id (`gateway_routing`), и только потом диспатчить. Детектор — `session_watchdog.py` §2.8 (`heal-warn: ... субагент-контаминация`).
- **Признаки «мёртвой сессии»** (заголовок `/sessions` — subagent, context 0, ответов нет): не слать `/stop` в пустоту — проверить `~/.hermes/logs/gateway.log` (`response ready`, `session_switch`, `Pinned async-delegation`) и `state.db` (end_reason последней сессии); состояние конвейера восстановимо из git (PLAN/BACKLOG/реестр) и worktree-незакоммиченных артефактов.
- **Декомпозиция делегаций (инцидент 2026-09-30, Р4/4.1):** сабагенту-ревьюеру — только статика диффа; долгие прогоны (web/api-сьюты, стенды) выполняет оркестратор сам в terminal и передает числа файлом (`/tmp/.../PROGRESS.md`) с явным запретом «прогоны не повторять». Старая схема «ревьюер делает всё» жила 40+ мин, ловила rollover сессии ПМ (#54878×#54947) и теряла отчёты; декомпозированная уложилась в 6 мин. Дропнутые при rollover отчёты восстанавливаются из `state.db → async_delegations.result_json`.
- **Подводные камни API-стенда ekotov-wiki:** `python -m app.seed_users` требует пароли (getpass; при отсутствии tty читает stdin — дефолты conftest скармливать пайпом по 2 раза на пользователя); после seed ОБЯЗАТЕЛЬНО `python -m app.migrate_r4` (нужен SECRET_KEY) — иначе роль wife=NULL и падает test_get_profile_second_user_gets_own_data; env аватар: тесты ждут `EKOTOV_WIKI_AVATARS_DIR`, приложение — `AVATARS_DIR` (задавать оба).
- **Спека-дельты MODIFIED (дефект СА, пойман воротами 2026-09-30):** блок MODIFIED обязан воспроизводить Requirement целиком — все сценарии мастера дословно + изменения; пометки-пояснения в заголовок секции не писать (парсер валидатора такие секции отбрасывает: `## MODIFIED Requirements (дополнение …)` — невалидно). Урок: «validate 11/11» в сообщении СА может не воспроизводиться — ворота гонять на своей машине перед влитием.
