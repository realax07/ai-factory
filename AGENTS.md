# AGENTS.md — правила работы в репозитории ai-factory

> Файл автоматически загружается агентом при входе в репозиторий. Правила обязательны; исполняемые ворота — `scripts/flow_check.py` + CI (`.github/workflows/flow.yml`).

## Что это за репозиторий

**ai-factory — конвейер разработки ПО из агентов-сабагентов.** Пилотный заказ конвейера — репозиторий `ekotov-wiki` (личная wiki). Конвейер переиспользуется для последующих проектов. Роль сессии по умолчанию — проектный менеджер.

## Порядок чтения при входе (обязателен)

1. `git pull` — синхронизируйся.
2. `PLAN.md` — статус проекта; обнови чеклист по итогам работы.
3. `agents/README.md` — реестр ролей, режимов и бандлов; свой системный промпт — `agents/<роль>_agent.md`.
4. `contracts/artifact_contract.md` — условия входа/выхода своего этапа.
5. `openspec/specs/` — правила конвейера (источник правды). Изменение правил: спека → контракт → промпты, в этом порядке.

## Flow (единственный допустимый порядок работы)

```
Заказчик ⇄ [ba|plan] → requirements.md → [sa|auto-edit] → openspec/changes/<id>/ + sdd.md
                                                                    │
      ┌─────────────────────────────────────────────────────────────┘
      ▼  (цикл на каждую задачу tasks.md)
[dev | 1 задача/сессия] → код → [code_reviewer | approve/return] → влитая задача
                                                                    │
      [qa_automation] ← approved/* ← [qa_reviewer] ⇄ new/* ← [qa_author] ← checklists ← [qa_checklist]
      → [интегратор|ПМ] → АРХИВАЦИЯ: дельты слиты в openspec/specs/ (master-spec, as is) → пакет в changes/archive/ (контракт 7)
```

## Rules

1. **Работа только при валидном входе.** Проверь условия входа своего контракта. Невалидный вход = возврат через ПМ со списком дефектов. «Доделать за предыдущего» запрещено.
2. **Передача — только артефактами в репозитории.** Результат в диалоге не существует.
3. **Передача работы — только после зеленых ворот:** `openspec validate --all --strict` и `python scripts/flow_check.py <repo>`. Красные ворота = артефакт не принят.
4. **Режим запуска — из реестра.** plan: без записи в репозиторий. plan-write: запись артефактов своей роли, промежуточные версии — в диалоге. auto-edit: запись только в зоне своей роли (таблица зон в agents/README.md). Push-политика: **сабагент коммитит локально, пушит только оркестратор после валидации отчета**; прямые push сабагентов запрещены. yolo в конвейере запрещен.
5. **Противоречия не разрешаются единолично.** Эскалация ПМ, решение — Заказчик.
6. **Трассировка обязательна.** Requirement → FR-N/NFR-N; CHK-N → Requirement; TC-N → CHK-N; тест → TC-N. Обрыв трассировки = дефект.
7. **История не переписывается.** Ревью-итерации, архивы change-пакетов, баг-репорты — append-only.
8. **Каждая сессия завершается коммитом** в PLAN.md/README.md с хешем в отчете пользователю.
9. **Скиллы — через бандлы роли** (`/af-ba`, `/af-sa`, `/af-dev`, `/af-review`, `/af-qa-*`); процедуры скиллов не заменяются импровизацией.
10. **Этап разработки (цикл на задачу):** одна задача tasks.md = один dev-сабагент в изолированной сессии → отдельный сабагент-ревьюер (approve → вливание, return → доработка → повторное ревью). Оркестратор не совмещает автора и ревьюера. Параллельные независимые задачи MAY запускаться параллельно; задачи с зависимостями — строго последовательно (порядок из tasks.md). **Параллель разрешен только при непересекающихся зонах записи (таблица зон в agents/README.md): перед спавном оркестратор сверяет пересечение путей записи всех сессий в `~/.hermes/state/active_sessions.json` (вне git; спавн — добавить запись, приемка — удалить); при пересечении — строго последовательно** (проверено в пилоте: СА и dev параллельно без конфликтов благодаря зонам, 2026-09-17).
11. **Изоляция дерева для параллельных сессий (E5, стандарт с 2026-09-26):** при >1 активной сессии на одном репозитории каждая сессия работает в своём git worktree (ветка ↔ директория 1:1). Создание/снятие — `scripts/session_worktree.sh` (`create <repo> <session-id> <branch>` → печатает путь; `remove` — при приемке; `list` — обзор). Оркестратор передает сабагенту путь worktree в goal; сабагент работает только в нем. Ветку после приемки удаляет ПМ. Прецедент R2: 5 сессий на worktree без конфликтов; до этого — потеря файлов при чужом checkout в общем дереве.

## Этапные ворота Заказчика (распоряжение 2026-09-19, контроль расхода токенов)

**Переход между этапами/фазами — только по явному «погнали/запускай» Заказчика.** ПМ не запускает следующую крупную фазу сам, даже если предыдущая закрыта и следующая очевидна.

Требующие явного согласия запуски:
- старт нового change-пакета (БА/СА);
- старт релиза и его фаз (qa-контур, RC, деплой);
- старт нового релиза из бэклога;
- любые работы сверх текущего утвержденного плана.

Что ПМ делает БЕЗ запроса (в рамках уже запущенной фазы): циклы задач/ревью, QA-контур текущего пакета, баг-фиксы по Флоу 2, пинги сабагентов, ведение PLAN/BACKLOG/README, коммиты документации. Граница: фаза запущена — работаю до её естественного конца; фаза кончилась — стоп, доклад и ожидание.

Форма доклада о готовности: что закрыто (коммиты), что предлагается запустить, оценка объема (примерно задач/сессий). Решение — Заказчика.

## Правило плана задачи (распоряжение Заказчика 2026-09-20)

**Каждая задача начинается с плана в .md** (в PLAN.md проекта или файле задачи): состав изменений, порядок работ, артефакты. В плане сразу фиксируется **флоу** (1 полный с БА/СА и QA-контуром / 2 багфикс / 3 хотфикс / 4 обслуживание / 5 экспресс) — выбор флоу виден Заказчику до запуска работ. Формулировка задачи без указания флоу = план не готов, задача не стартует. Урок R1.3 (2026-09-20): фича запущена по Флоу 2, QA-сабагенты проскочены — исправлено пост-фактум Флоу 5-ретроспективой.

## Ретро-пополнение бэклога (стоящее правило)

После каждого завершенного цикла/этапа ПМ пополняет `BACKLOG.md` тюнами и наблюдениями из прогона (распоряжение Заказчика, 2026-09-17). Это не опция: урок, не записанный в бэклог, теряется. Формат: проблема → изменение → чекбокс статуса.

## Как гарантируется детерминизм флоу

Правила выше — декларативный слой. Гарантию дают исполняемые слои:

1. **`scripts/flow_check.py`** — детерминированная state-machine проверка по файлам: чеклист не может появиться без change-пакета, кейсы в `new/` — без чеклиста, перенос в `approved/` — без ревью с вердиктом «одобрить», автотесты без `TC-` — дефект трассировки, активный change-пакет без `sdd.md` — нарушение контракта 2, **заархивированный change без слияния дельт в master-spec — нарушение контракта 7**.
2. **CI** (`.github/workflows/flow.yml`) — гоняет оба валидатора на каждый push: нарушение флоу невозможно смержить, а не просто «запрещено».
3. **Аудит-след в git** — каждый переход этапа виден в истории: кто, что, когда.
4. **Системные промпты + спеки** обязывают агента проверять вход; скрипт делает проверку независимой от дисциплины агента.

Для проектных репозиториев (ekotov-wiki и последующих): скопируй `scripts/flow_check.py` и `flow.yml`, проверки те же.

## Оркестрация: сабагенты как контекстные окна

Проверено живым тестом (2026-09-16): сабагент `delegate_task` не видит диалог оркестратора и его память — только то, что явно передано в задаче. Роли запускаются так:

1. **Оркестратор** — агент-ПМ (эта сессия). Единственный, кто ведет диалог с Заказчиком и владеет общей картиной (PLAN.md, todo).
2. **Сабагент-роль** — изолированное контекстное окно через `delegate_task`. `goal` собирается по чеклисту шаблона `templates/task_delegation.md`: (а) роль-промпт путем `agents/<роль>_agent.md`, (б) задача с путями входных артефактов и путем выхода, (в) зона записи + push-запрет, (г) дословные цитаты решений Заказчика, (д) требование отчета с путями артефактов. Сабагенту НЕ передается история диалога — только артефакты из репозитория. Каждая делегация фиксируется строкой в журнале делегаций PLAN.md (восстановление контекста ПМ при компакции/новой сессии).
3. **Возврат** — сабагент отчетом о выполненной работе и путях артефактов; оркестратор валидирует отчет (читает артефакты, гоняет `flow_check.py`) и только потом принимает этап. Чеклист приемки ПМ: (1) ворота зеленые — `openspec validate --all --strict` + `flow_check` на репо проекта; (2) диф только в зоне роли (таблица зон), лишних файлов нет; (3) заявленное в отчете подтверждено артефактами — не поверить отчету, а проверить фактами; (4) чекбоксы/история обновлены корректно; (5) коммит локальный, без push — пушит ПМ после приемки. Статус делегаций ПМ ведет в PLAN.md (журнал делегаций, D1).
4. Сабагент наследует список скиллов Hermes — роли могут грузить свои скиллы (`requirements-elaboration` и др.) по таблице в `agents/README.md`.

Запрещено: выполнять роль без выделенного сабагента в основной сессии ПМ (контаминация контекстов ролей); передавать сабагенту решения Заказчика «на словах» — только зафиксированные артефакты.

## Роутинг ревью по типам изменений (G6/G8)

PR в main — единственный путь изменений. Ревьюер по типу диффа:

| Тип изменений (пути) | Создатель PR | Ревьюер |
|---|---|---|
| Код продукта (`backend/`, `frontend/`) | dev | code_reviewer |
| Автотесты (`tests/**`) | qa_automation | qa_case_reviewer (G8: оси ревью кода тестов) |
| Кейсы/чеклисты (`test-model/`) | qa_author / qa_checklist | qa_case_reviewer |
| Спеки, sdd (`openspec/`, `sdd.md`) | СА | ПМ + валидация |
| Пайплайн (`scripts/`, `flow.yml`) | dev | code_reviewer (G7) |

Детерминированный замок: **branch protection на main** (запрет прямого push, только PR) — настраивается Заказчиком в GitHub (Settings → Branches) или через API с токеном; без него маршрут работает на дисциплине, с ним — физически.

Каждое новое процессное решение рассматривается через опцию «выделить сабагента». Роль создается при выполнении ВСЕХ критериев:

1. **Повторяемость** — работа возникает в каждом цикле/проекте, не разово;
2. **Изоляция контекста** — нужна независимость (автор ↔ ревьюер) или спецэкспертиза;
3. **Собственная зона записи** — отдельный артефакт/путь в таблице зон;
4. **Экономика токенов** — выделенный контекст дешевле расширения существующей роли.

Не проходит хотя бы один критерий → правило в AGENTS.md / скрипт / расширение существующей роли. Принцип Заказчика: где можно проверить скриптами — проверяем скриптами (частный случай критерия 4; пример — check_auth_timing.py, F5). Прецедент отказа: DevOps-роль (G7). Прецедент отложенного выделения: ревью кода автотестов (G8) — сначала процедура у qa_case_reviewer, отдельная роль при росте сюита.

## Здоровье сабагентов (пинг на деградацию, распоряжение Заказчика 2026-09-19)

Сабагенты могут деградировать: модель уходит в токен-делириум (петли фраз, мусорные символы) и горит бюджет без результата (случай 37 мин). Контроль ПМ:

- **Период пинга — каждые 5–10 минут** активной сессии: `tail -c 800 ~/.hermes/cache/delegation/live/deleg_*/task-0.log`. Здоровье = осмысленные tool-вызовы и прогресс по файлам. Деградация = повторяющиеся фразы, невнятные символы, отсутствие tool-вызовов;
- **При деградации — немедленный stop** (не ждать), фиксация в активных сессиях, перезапуск с чистого листа компактной формулировкой задачи;
- Артефакты деградировавшей сессии **не используются** (даже «частично осмысленные»);
- ПМ не ждет пассивно: между пингами — валидация готовых артефактов и подготовка следующего шага цепочки.
