# J37: Открытые вопросы конвейера/гейтов (накоплено за ЭТАП A релиза R6, 2026-10-04 — на обсуждение с Заказчиком).

- **Статус:** ОТКРЫТО
- **Карта:** backlog/MAP.md (строка item'а)

(1) **Required checks не принудительны**: PR двадцать восемь смержился с красным flow-чеком (flow не в required status checks ветки main фабрики; rulesets посмотреть не смог — нет прав на branch protection). Вопрос: добавить flow + test-flow-control в required? Список чеков подготовлю. (2) **Reviewer-Delegation: реестр vs платформенные id**: меты ревью-файлов должны нести реальные платформенные delegation-id (сверка с async_delegations), но ТЗ ревьюеру не должно задавать литеральные id — как ПМ должен передавать ревьюеру «твой id для меты» без ручных шагов? Кандидат: pr_validate подсказывает ожидаемый id при FAIL / delegate_gate выдает id при диспатче и ПМ включает его в ТЗ автоматически. (3) **Автозаполнение review-mapping.json**: J10-связка review-файл↔задачи требует ручной строки от ПМ (review-002 кейс) — кандидат: delegate_gate finish автоматически дописывает mapping при approve-вердикте делегации ревьюера. (4) **Файловые тесты требуют стенд**: pytest-base-url плагин тянет base_url-фикстуру для всех тестов tests/api/ — тест, читающий только файлы, падает без живого приложения (ЭТАП A, test_openapi_search_service). Кандидаты: conftest-разделение (unit-каталог без стендовой фикстуры) / ленивая фиксстура / маркер. Адресат: QA-инфра, sync в wiki. (5) **Полный PR-набор только на merge-стадии**: pr_validate (impact H5, чеклист, approved-кейсы) валится на промежуточных стадиях Флоу 1 — это норма (полный набор = ЭТАП C), но ворота промежуточных стадий (flow_check) и финального PR (pr_validate) стоит развести явно в доке «что проверяется когда». (6) **Обязательность [docs]/[ops] чекеров**: env-конвенция PR_CHANGED_SPECS/CODE зависит от честности CI-скрипта — рассмотреть вычисление диффа внутри pr_validate (subprocess git) вместо env. Каждое — с решением Заказчика при проработке; кандидаты 2–4 идут в J34/J35-класс (детерминизация).
