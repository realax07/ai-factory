# J43 — pre_tool_call-энфорсер делегаций (Заказчик, 2026-10-11)

**Флоу: 2** (изменение исполняемого контура по решению Заказчика). Статус:
**НА ОБДУМАНИЕ** — реализации нет, план ниже черновой. Родословная: J39
(bypass-делегации) → J41 (план релиза как артефакт, реализован 2026-10-11) →
J42 (CI на пушах сабагентов) → этот item — недостающий слой «неизбежности».

## Проблема (честная формулировка)

J41 дал воротам зубы (flowctl prepare требует план релиза), но ворота
**опциональны для ПМ**: оркестратор может диспатчить delegate_task напрямую,
мимо flowctl (прецеденты — весь P15). Watchdog (J41/2b) детектит обход
пост-фактум и не доставляет результат, но делегация уже отработала — бюджет
потрачен, зоны не резервированы.

## Идея Заказчика (дословно)

«У тебя есть инструмент pre tool calling или как-то так. Можно ли при помощи
него валидировать, планируется ли делегация мимо нашего питон-флоу?»

## Механика (проверено по docs Hermes, hooks.md §pre_tool_call)

`pre_tool_call` — платформенный хук Hermes: срабатывает перед КАЖДЫМ вызовом
инструмента (включая delegate_task), может вернуть:
- `{"action": "block", "message": ...}` — вызов НЕ состоится, текст ошибки
  возвращается оркестратору (ПМ видит DENY с кодом сразу);
- `{"action": "approve", ...}` — эскалация в human-approval gate (Заказчик);
- без директивы — идет как шло.

Регистрация: Python-плагин (`ctx.register_hook("pre_tool_call", ...)`) или
shell-хук в config.yaml. Fail-closed на таймаут (30s default) и на падение
колбэка — молчаливый обход невозможен: сломанный энфорсер БЛОКИРУЕТ
делегации, а не пропускает их.

## Черновой дизайн (flow_enforcer)

Триггер: `tool_name == "delegate_task"`. Из args.goal/context парсятся
маркеры (контракт формата goal — см. Риски): роль, repo, change-id.
Валидация: subprocess `flowctl prepare --role R --repo P --change C`
(переиспользует flow_transition/state: план релиза J41, requirements
approved, session_check reserve — зоны, policy).
Вердикт: ALLOW → пропуск; DENY → block с machine-кодом
(PLAN_RELEASE_MISSING, ZONE_CONFLICT, REQUIREMENTS_NOT_APPROVED, ...).
Метки-исключения: `flow: bypass --by customer` в goal — явное распоряжение
Заказчика (HUMAN_APPROVAL_REQUIRED-семантика, логируется в incident-файл).

## Что это закрывает

- Дыра «ПМ сам обходит ворота»: обход требует ОТКЛЮЧИТЬ плагин — действие
  видно (защищенный файл, git/логи), требует согласия Заказчика.
- Обратная связь мгновенная: DENY на спавне, а не пост-фактум от watchdog.
- Watchdog J41 остается вторым контуром (defence in depth).

## Риски / открытые вопросы

1. **Контракт маркеров**: false-block на делегациях без внятных
   роль/repo/change (мелкие внутренние задачи). Нужен явный header-формат
   goal (см. templates/task_delegation.md) + allowlist «не конвейерные»
   делегации (doc/бэклог-правки).
2. **Латентность**: prepare на каждый спавн (секунды) — терпимо, но
   измерить.
3. **Кто сторожит сторожа**: плагин живет в защищенной зоне профиля; правка
   = согласие Заказчика (как AGENTS.md). Считаем достаточным.
4. **Shell-хук vs плагин**: плагин богатее (structured args), shell проще в
   аудите. Решить при реализации.
5. **Взаимодействие с J42**: независимые контуры (спавн vs пуш), не
   дублируют друг друга.

## Критерий закрытия (когда решим делать)

- Делегация без prepare → block с кодом; с валидным prepare → проходит.
- bypass-маркер с "--by customer" → проходит + incident-запись.
- Отключение плагина невозможно без видимого действия (защищенный файл).
- Тесты: fixture-реестр, все ветки вердиктов; замер латентности спавна.
