# J57 — Возврат к J9: сабагент в своей ветке, сбор — dev-lead, ПМ без git

**Заявлено:** 2026-10-19 (переработано по решению Заказчика: «уже есть dev-lead,
просто не используем; при делегации сабагент создает свою фича-ветку, при
множественных делегациях собирает коммиты и ветки девлид; детерминированно,
но можно и на семантике»).
**Статус:** OPEN.

## Диагноз
Роль Dev-lead существует (agents/README №14, J9): «merge только через dev-lead,
ПМ git продукта не трогает (pm_bounds_check --product-commits)». Дрейф ПМ:
роль семантическая, триггеров нет — pm_bounds_check НЕ вмонтирован в push_gate
(проверено: enforcer его не вызывает), flowctl prepare (ветка из cid) при
делегациях не обязателен. Итог: ПМ жонглировал ветками, два сноса работы dev.

## Схема (детерминированный каркас + семантика)
1. ДЕЛЕГАЦИЯ → flowctl prepare ОБЯЗАТЕЛЕН (ветка из cid в worktree) — уже есть,
   сделать безусловным правилом диспетчеризации (ПМ не создает сабагенту ветку руками).
2. СБОРКА → `flowctl integrate` (НОВОЕ, механика): по repo/change показывает
   ветки пакета из реестра, проверяет отсутствие активных сессий, создает
   интеграционную ветку — передает dev-lead'у. Разрешение конфликтов — семантика
   dev-lead (канон J9, узкий бриф).
3. ЗАЩИТА ПМ → pm_bounds_check --product-commits вмонтировать в push_gate
   (enforcer): ПМ-push в продуктовое репо без dev-lead-маркера интеграции = DENY.
4. Ветка на роль: ревьюеры/фиксеры коммитят в свои ветки (уже так); результат
   собирает dev-lead.

## Скоап
Фабрика: flowctl integrate + push_gate-хук + docs (Режимы/agents) + тесты.
Зеркала — стандартно (flowctl/session_check/pr_validate).
