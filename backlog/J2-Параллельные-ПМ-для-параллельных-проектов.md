# J2: Параллельные ПМ для параллельных проектов.

- **Статус:** ЗАКРЫТО (решение Заказчика 2026-10-09)
- **Карта:** backlog/MAP.md (строка item'а)

Следствие J1: несколько изолированных ПМ-контекстов = параллельные проекты без смешивания. Каждый ПМ ведет свой PLAN.md и реестр сессий. → **ДИЗАЙН ГОТОВ 2026-09-26:** схема `active_sessions.json` дополнена обязательными полями `project` + `owner_pm` (миграция выполнена, существующие записи помечены `project: ai-factory`); ворота `scripts/pm_bounds_check.py --sessions` ловят отсутствующие поля и повторение пары project/owner_pm; правило «один ПМ = один проект», ПМ трогает только записи своего project (чужие — только как чужие зоны при проверке пересечений). Этап внедрения — 3 плана в pm_launch.md (после смены дефолта).

**РЕШЕНИЕ Заказчика 2026-10-09 (закрытие J1–J3):**

ПМ-сабагент НЕ внедряется. Аргументы Заказчика:
1. Сабагент ПМ вызывал бы своих сабагентов = сабсабагенты (лишний уровень
   потери доставки и сложности оркестрации).
2. Параллельные проекты решаются **отдельным инстансом Hermes на другой VPS**
   (вторая VPS + второй Hermes уже есть; межэкземплярное общение настраивается
   при необходимости) — изоляция проектов платформенная, не контекстная.
3. Контекст проекта живет во внешней памяти (папки backlog/, PLAN.md, agents/,
   memory). Новый проект = новая директория + сброс контекста сессии — дешево,
   без отдельного сабагента.

Дизайн pm_agent.md + pm_launch.md + pm_bounds_check сохранены в репозитории
как артефакт проработки (J28-класс: детерминированный флоу может переиспользовать
bounds-проверки). Триггеры J4 (деградация/второй проект/запрос) — покрыты
пунктом 2: второй проект = второй Hermes.
