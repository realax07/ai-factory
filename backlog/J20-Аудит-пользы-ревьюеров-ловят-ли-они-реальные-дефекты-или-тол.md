# J20: Аудит пользы ревьюеров: ловят ли они реальные дефекты, или только жгут токены (Заказчик, 2026-09-29).

- **Статус:** ОТКРЫТО
- **Карта:** backlog/MAP.md (строка item'а)

Вопрос: каждый dev-коммит проходит отдельного сабагента-ревьюера (полный контекст роли + независимые прогоны тестов) — какова фактическая отдача? Гипотеза Заказчика: значительная часть ревью завершается «APPROVE, 0–3 minor» без находок, влияющих на продукт → токены на ритуал. План анализа (по транскриптам и review-файлам Р1–Р4, данные уже есть — session-archive + code-reviews/): (1) реестр всех ревью: вердикт, число/серьезность замечаний, были ли RETURN и что именно поймано (классификация: реальный баг продукта / дефект теста / расхождение со спекой / оформление); (2) стоимость: токены/время каждой ревью-сессии (метаданные делегаций); (3) доля дефектов, пойманных ревью vs пропущенных до QA/прода (сверить с баг-репортами и регрессами — ловит ли QA то, что проспало ревью, и наоборот); (4) контрпримеры-ценность: ревью, поймавшие серьезное (пример Р4: architect RETURN с blocker C-1 — rsync стирал бы аватары прода; это архитектурное ревью, не code_review — в анализ включить отдельно по типам ревьюеров); (5) альтернативы: ревью только по-trigger (сложные зоны/миграции/безопасность), дешевая модель на ревью, скриптовые ворота вместо части ревью, ревью объединенного диффа волны вместо по-задачного. Выход: отчет с числами (средняя цена ревью, % ревью с находками major+, % дефектов продукта, пойманных именно ревью) + решение Заказчика: оставить как есть / дифференцировать / резать. Связь: J8 (общий токен-аудит), J10–J11 (ворота J10 требуют ревью — при резке менять flow_check), J14 (какая доля гарантии «каждый коммит отревьюен» реально работает).
