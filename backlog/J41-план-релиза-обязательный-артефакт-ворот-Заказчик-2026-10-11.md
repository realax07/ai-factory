# PLAN-J41 — план релиза как обязательный артефакт ворот (Заказчик, 2026-10-11)

**Флоу: 2** (изменение исполняемых ворот по прямому распоряжению Заказчика;
requirements = дословная фиксация решений в диалоге 2026-10-11). Ревью:
code_reviewer (зоны пайплайна). QA-контур Флоу 1 не тянем — изменение
детерминированных скриптов покрывается их юнит/смоук-прогонами в приемке ПМ.

## Проблема (урок P15 add-wiki)

Релиз стартовал без PLAN-файла: план существовал только в tasks.md (детализация
СА) и в переписке ПМ. Правило «каждая задача стартует с плана в .md» соблюдено
по сути, но не по форме — план релиза (кто/что/этапы/воркфлоу) не был
артефактом, и ворота не могли его требовать.

## Решения Заказчика (дословная фиксация)

- «Мы перед релизом должны план набрасывать. SA лишь детализацию»
- «На будущее можем как то гарантировать что работа по задаче начинается с
  plan.md?»
- Двухконтурная схема согласована: старт-ворота + блокировка доставки
  bypass-результатов, мердж — только аудит.

## Изменения

### Фабрика (ai-factory)

1. **flow_transition.py**:
   - `check_create_change` (Флоу 1): обязателен артефакт
     `PLAN-<change-id>.md` (корень проекта или каталог change-пакета):
     существует, содержит объявленный воркфлоу (строка `**Флоу: N**`),
     отсутствует → DENY с кодом `PLAN_RELEASE_MISSING` / `PLAN_FLOW_UNDECLARED`.
   - `check_dev_task` (транзитивно, все флоу с change-пакетом): та же проверка —
     dev не стартует без плана релиза, даже если СА-этап проскочили.
2. **delegate_watchdog.py** (кандидат 2b из J39): bypass-делегация (нет
   валидной flowctl-записи prepare для своей роли/зоны) — результат НЕ
   доставляется оркестратору: incident-запись + пометка `undelivered_bypass` в
   реестре; результат остается в кэше делегации для ручного разбора Заказчиком.
3. **AGENTS.md** (фабрика): правило «Релиз стартует с PLAN-<change>.md; пишет
   ПМ до запуска СА; SA детализирует в tasks.md, план не переписывает».

### Проект (ekotov-wiki, тонкий клиент)

4. **scripts/flow_check.py** (копия проекта): контракт «активный change-пакет →
   PLAN-<change>.md существует» (аудит на мердже).
5. **AGENTS.md** (проект): тот же правило-абзац, ссылка на фабрику.

## Порядок работ

1. ПМ: этот план + коммит (выполнено этим коммитом).
2. dev-сабагент A (фабрика): пп.1–2 + юнит-тесты flow_transition (fixture:
   change без плана → DENY; с планом и флоу → ALLOW; dev_task транзитивно).
3. dev-сабагент B (проект): пп.4–5 (зоны не пересекаются с A — параллель).
4. ПМ: AGENTS.md обеих реп (пп.3/5 — документация, зона ПМ), PR, приемка:
   юнит-прогоны flow_transition, smoke flow_check обоих реп, watchdog dry-проба.

## Критерий закрытия

- `flowctl prepare --flow 1 --action create_change` без PLAN-файла → DENY
  (PLAN_RELEASE_MISSING); с файлом без «Флоу:» → DENY (PLAN_FLOW_UNDECLARED).
- `flow_check` проекта на активном change без плана → FAIL.
- Watchdog на bypass-делегации ставит undelivered_bypass (тест на фикстуре).
- Оба AGENTS.md содержат правило; CI обоих реп зеленый.
