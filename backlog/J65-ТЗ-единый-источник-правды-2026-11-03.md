# J65 — ТЗ: единый источник правды и стабилизация ядра (2026-11-03)

Статус: **открыт**. Источник — разбор работы внешнего агента Claude Code по
фабрике (сессия «Аудит персонального проекта», 2026-11-02/03: J63, J64.1–3,
J64.5, J64.18). Дополняет J64: пересекающиеся задачи J64 здесь уточняются,
а не дублируются (ссылки у каждой задачи).

## Наблюдение, из которого выросло ТЗ

Ядро «ворота + независимое ревью» на практике окупилось: ревью и ворота
поймали ошибки исполнителя (снимок prepare из основного клона вместо ветки
пакета; зависимость памяти движка от `HERMES_HOME` с риском молча снять
enforcing; падение копий `flow_check`/`pr_validate` в проектах без
`factory_paths.py`; тесты без TC-трассировки; тест digest, проходивший только
с полной историей).

Почти все STOP-ы и дефекты по ходу работы возникли **на стыках, где один и
тот же факт хранится в нескольких местах** и эти места расходятся:

| Факт | Где хранится сейчас |
|---|---|
| Зона записи роли | таблица `agents/README.md`, `ROLE_ZONE_POLICY`, `POLICY_TABLE_DIGEST` (пин коммита), `POLICY_VERSION`, `PI_ZONE_WRITE` в README паков, `zone:` стадий в примерах манифеста |
| Список ролей | `role_zone_policy.py`, `flow_transition.py`, `plugins/flow-enforcer/enforcer.py` |
| Грамматика scope флоу | `flow_state.py` (`CHORE_RE` и др.), `flowctl.py:184`, энфорсер |
| Вердикт ревью | подстрока в `package_runner.py` (`contains: "Одобрить"`), формат J52 (`## Вердикт: approve`), `pr_validate` |
| Пути машины | `factory_paths.py`, копия в энфорсере, запасные блоки в `flow_check`/`pr_validate`/`flow_mode` |

**Принцип J65:** каждый факт — в одном машиночитаемом месте; остальные места
генерируются из него или сверяются с ним тестом.

## J65.2 `ZONE_POLICY_MISMATCH` — по зоне своей роли — Флоу 4

Проблема: любая правка политики меняет `POLICY_VERSION`, и все активные
сессии на `finish` получают `ZONE_POLICY_MISMATCH`. Отсюда условие «мержить
правки политики только при отсутствии активных сессий на VPS» (J64.18).

Сделать: в резервацию писать хэш зоны своей роли; на `finish` сверять его, а
не версию политики целиком. Расширение зоны чужой роли сессию не задевает;
сужение своей — `ZONE_POLICY_MISMATCH`, как сейчас.

Зависимость: J65.1. Приемка: тест — правка зоны devops не ломает finish
активной сессии dev; сужение зоны dev — ломает.

## J65.4 Вердикт ревью: блок раунда + provenance — Флоу 4

Уточняет J64.12; закрывает расхождение форматов из резолюции J64.3
(`Вердикт: Одобрить` раннера ≠ `## Вердикт: approve` J52).

Сделать:
1. Каждый раунд ревью — блок append-only с фиксированной шапкой:
   ```
   ## Ревью N
   verdict: approve | return
   commit: <sha>
   reviewer: <роль/исполнитель>
   ```
2. Действующий вердикт — последний блок; его `commit` обязан совпадать с HEAD
   проверяемой ветки, иначе STALE (как PASS после нового коммита в
   `gate_runner`).
3. Один парсер `scripts/review_verdict.py` для раннера, `pr_validate`,
   `gate_runner`; `verdict: {contains: …}` в манифесте снимается.
4. Раннер после review-стадии сам вызывает `gate_runner record-review`
   (sidecar: SHA, digest диффа, автор, ревьюер).

Приемка: STOP на «Не одобрить», на шаблоне с обоими словами, на отсутствии
блока, на `commit` ≠ HEAD; approve в последнем блоке при «return» в первом —
проходит; sidecar создается без участия ПМ.
