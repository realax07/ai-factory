# J25: Живой дизайн-макет проекта в репо + обязательный дизайн-проход UI-изменений (Заказчик, 2026-09-30: «что-то мне подсказывает, что словим шляпу на проде с дизайном новых отображений»).

- **Статус:** ОТКРЫТО
- **Карта:** backlog/MAP.md (строка item'а)

Проблема: дизайн-макеты (ekotov-wiki/design/form-style-v3.html и др.) — статичные снимки на момент релиза; живые UI-изменения (4.1 view-модалка, 5.1 ряды assigned/creator на карточках, tooltip'ы) в них НЕ отражаются — макет и продукт дрейфуют. Риск: новое отображение на проде выглядит не так, как ожидал Заказчик (свежий пример — волна 5: hotfix кнопок view-модалки, Classы .btn/.btn-primary без CSS; DEF-004 — кнопки без стилей ушли в Р3). Кандидат-решение: (а) «живой макет» — html-страница в репо проекта (design/), отражающая АКТУАЛЬНЫЙ UI (все формы/карточки/модалки/tooltip'ы), обновляемая как артефакт каждой UI-задачи (DoD: макет обновлен в том же коммите); (б) процессный гейт: любое изменение UI проходит через дизайнера (ui_designer/design_validator) ДО merge — design_check как обязательный ревьюер UI-диффов (сейчас design_validator E13 запускается пост-фактум на QA-этапе, и не на каждую задачу); (в) скриптовая проверка «макет ↔ код» (токены/классы из макета присутствуют в css — частично уже есть в design_validator). Связь: E13 (design_validator — пост-фактум), DEF-004/DEF-005 (уроки), 4.2 (форма V3 pixel-consistent). Триггер решения: следующий UI-релиз или первый инцидент «дизайн на проде не такой» — что раньше. До решения: минимално — держать form-style-v3.html актуальным при касании форм (правило в DoD UI-задач).
