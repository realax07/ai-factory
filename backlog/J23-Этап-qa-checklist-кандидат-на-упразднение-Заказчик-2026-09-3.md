Предмет: в QA-контуре (impact → чеклист → кейсы → ревью → автотесты) этап чеклиста — промежуточный артефакт: CHK-пункты пишутся по дельтам, затем кейсы пишутся по CHK с обязательной трассировкой CHK→Requirement и TC→CHK (правило 6). Гипотеза Заказчика: чеклист дублирует дельты спеки (те же сценарии, пересказанные) и добавляет один полный проход сабагента (контекст: чтение пакета + запись 60-80 CHK) без пропорциональной отдачи — покрытие кейсов можно проверять напрямую по сценариям дельт (TC → Requirement/сценарий), минуя CHK-прослойку. Контраргументы для разбора (факты Р2/Р3): чеклист ловил дефекты спеки до кейсов (4 CHK без FR-источника — красный flow_check, пойман ревьюером кейсов); revalidate-таблицы impact-анализа материализуются в CHK-пунктах; сквозная нумерация CHK дает дешевую проверку полноты покрытия. План решения (Флоу 4, связь J8/J20 — токен-аудиты): (1) замерить стоимость этапа чеклиста по архивам делегаций (r2-qa-checklist, Р3) — токены/длительность; (2) оценить, что теряется: прямую трассировку TC→сценарий дельты flow_check проверять умеет (формат кейсов меняется), проверку полноты — заменить скриптом «каждый сценарий дельты покрыт ≥1 TC» (принцип «проверять скриптами»); (3) варианты: (а) упразднить этап, кейсы пишутся по дельтам напрямую; (б) слить checklist в impact-анализ (одна делегация вместо двух); (в) оставить.
