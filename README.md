# AI Factory — конвейер разработки ПО из агентов

> Детальный документ о процессе: кто что делает, как гарантируется, зачем, какие артефакты и где лежат. Оперативные правила — [AGENTS.md](AGENTS.md), статус проекта — [PLAN.md](PLAN.md), уроки — [BACKLOG.md](BACKLOG.md).

## Зачем это существует

Обычная разработка с LLM-агентами страдает тремя болезнями: контаминация ролей (один «универсальный» агент пишет, тестирует и ревьюит сам себя), потеря решений (устные договоренности исчезают), отсутствие детерминизма (процесс зависит от дисциплины конкретного запуска). Конвейер решает их: **каждая роль — изолированный сабагент**, **передача — только артефактами в репозитории**, **порядок проверяется скриптом и CI**, **решения фиксируются дословно**.

## Роли (кто что делает)

Все роли выполняются выделенными сабагентами (изолированные контекстные окна через delegate_task). Оркестратор — агент-ПМ — единственный контакт с Заказчиком и владелец общей картины.

| Роль | Промпт | Что делает | Зона записи | Вход → Выход |
|---|---|---|---|---|
| **БА** (бизнес-аналитик) | [agents/ba_agent.md](agents/ba_agent.md) | Диалог с Заказчиком, формулирование требований (не придумывает их — только фиксирует слова Заказчика) | `requirements.md`, `docs/ba/answers_roundN.md` | диалог → УТВЕРЖДЕННОЕ ТЗ |
| **СА** (системный аналитик) | [agents/sa_agent.md](agents/sa_agent.md) | ТЗ → формальная спека OpenSpec + SDD: домены, Requirement + Scenario, API-контракты, задачи | `openspec/changes/<id>/**`, `sdd.md` | ТЗ → change-пакет |
| **qa_impact_analyst** | (создается при первом change с MODIFIED-дельтами, H5) | Impact-анализ: дельты vs существующий регресс → вердикт по каждому затронутому тесту (keep/revalidate/retire) | `test-model/impact/<change-id>.md` | дельты → вердикты по тестам |
| **dev** (разработчик) | [agents/dev_agent.md](agents/dev_agent.md) | Реализация одной задачи tasks.md; ветка + PR | своя ветка `feature/*` | задача → код + PR |
| **code_reviewer** | [agents/code_reviewer_agent.md](agents/code_reviewer_agent.md) | Ревью диффа по 3 кругам (спека как закон / практики / интеграция) + регресс-прогон | `code-reviews/`, review PR | PR → approve / return |
| **qa_checklist** | [agents/qa_checklist_agent.md](agents/qa_checklist_agent.md) | Спека → чеклист проверок (CHK-N), техники границ/негатива, дефекты спеки | `test-model/checklists/` | спека → чеклист |
| **qa_case_author** | [agents/qa_case_author_agent.md](agents/qa_case_author_agent.md) | Чеклист → тест-кейсы (TC-N): предусловия, атомарные шаги, проверяемые ожидания, данные | `test-model/new/<id>/` | чеклист → кейсы |
| **qa_case_reviewer** | [agents/qa_case_reviewer_agent.md](agents/qa_case_reviewer_agent.md) | Ревью кейсов (6 осей) + ревью кода автотестов (G8); approve = перенос в approved | `test-model/reviews/`, `test-model/approved/` | кейсы → approve / return |
| **qa_automation** | [agents/qa_automation_agent.md](agents/qa_automation_agent.md) | Approved-кейсы → автотесты (pytest+requests API, Playwright UI); баг-репорты при падениях | `tests/**`, `test-model/bugs/` | кейсы → сьют |
| **qa_regression_analyst** | (создается при первом релизе, G5) | Пост-релизно: валидация меток keep/archive на тестах → манифест регресса | `test-model/regression/manifest.md` | метки → манифест |
| **ПМ** (оркестратор) | эта сессия | Диалог с Заказчиком, сборка задач сабагентам, приемка (чеклист), пуш, PLAN/BACKLOG | `PLAN.md`, `BACKLOG.md`, push | — |

Режимы запуска и полная таблица зон записи: [agents/README.md](agents/README.md).

## Флоу (порядок работы)

### Флоу 1: Новый функционал (полный цикл) — основной

```
Заказчик ⇄ БА → requirements.md (УТВЕРЖДЕН) → СА → change-пакет + sdd.md
                                                       │
                                     (MODIFIED/REMOVED дельты? → qa_impact_analyst → вердикты по регрессу)
                                                       │
     ┌─────────────────────────────────────────────────┘
     ▼  цикл на каждую задачу tasks.md (G6: ветка + PR)
 dev → PR → code_reviewer (approve → ПМ merge | return → доработка → повторное ревью)
     │
     ▼  после всех задач
 qa_checklist → чеклист → qa_case_author → кейсы → qa_case_reviewer (approve)
     │
     ▼
 qa_automation → сьют (pytest tests/) → ревью кода тестов (G8)
     │
     ▼  релизный контур (G9, G5)
 feature/* → PR → release-candidate → предрелизный регресс (pytest tests/) → PR → main
     │
     ▼  контракт 7
 АРХИВАЦИЯ: дельты слиты в openspec/specs/ (master-spec as-is), пакет → changes/archive/
     │
     ▼  пост-релизно (G5)
 qa_regression_analyst → манифест регресса (keep/archive)
```

Когда применять: новое поведение, изменение существующего поведения, новые сущности (справочники, разделы) — всё, что меняет спеку.

### Флоу 2: Баг-фикс (быстрый цикл) — без БА и СА

Баг — это расхождение **реализованного** поведения со **спекой**. Спека уже существует и не меняется, поэтому БА и СА не участвуют: некогда формулировать требования и нечего проектировать.

```
Источник бага (пользователь, автотест, ревью) → ПМ валидирует: баг-репорт BUG-NNN
   в test-model/bugs/ (кейс-источник, ожидание из спеки, факт, окружение)
   → ПМ проверяет: спека ДЕЙСТВИТЕЛЬНО требует иного? (если нет — это не баг,
     а фича-запрос → Флоу 1 или отказ)
→ dev: ветка feature/bug-NNN → фикс → PR (ссылка на BUG-NNN)
→ code_reviewer: ревью диффа (спека = арбитр, как всегда)
→ ПМ merge → regression-тест бага помечается regression: keep
```

Когда применять: поведение противоречит существующей спеке/кейсам. Граница: если «фикс» меняет поведение, которого спека не описывает, — это не баг, а изменение спеки → Флоу 1 (пусть и мини). Порог обратного: баг-фиксы, требующие изменения схемы БД или API-контрактов — привлекается СА (мини-дельта), потому что это уже дизайн-решение.

**Прецедент:** BUG-001 (2026-09-19) — первый проход Флоу 2. Выявленная слепая зона: BUG-001 формально требует дельты спеки navigation (клик-поведение карточки из поиска не описано Requirement'ом) — правило «баг без СА» справедливо только когда ожидание выводимо из существующих Requirements. Если выводимо — фикс легален; если нет — мини-дельта СА обязательна даже для бага. ПМ обязан проверить это при валидации баг-репорта.

### Флоу 3: Горячий фикс на проде (hotfix)

Резерв для инцидентов на production (сейчас прод — ekotov-wiki на этой машине). Отличие от Флоу 2: скорость важнее формальностей.

```
Инцидент → ПМ: откат деплоя (предыдущий артефакт/main) → остывание
→ фикс по Флоу 2, но параллельно: уведомление Заказчика немедленно, полный PR-цикл после стабилизации
```

Когда применять: продукт недоступен/теряет данные. Не применять: косметика, неудобства. Состояние: контур описан, не обкатан (прод не падал) — первый инцидент уточнит детали.

### Флоу 4: Обслуживание конвейера и продукта без функционала

Чистка, линтеры, обновление зависимостей, докрутка тестов — изменения без нового поведения.

```
ПМ (или инициатива роли) → мини-ТЗ прямо в задаче делегации (без БА)
→ если меняет спеку — СА мини-дельта; иначе — сразу dev/qa_automation
→ стандартный PR-цикл + регресс
```

Когда применять: рефакторинг (P6), чистка (G9-шаг), подключение линтеров (H4), обновление зависимостей. Прецедент: задачи P6/H4 релиза 1 пойдут этим флоу.

### Сводная таблица выбора флоу

| Ситуация | Флоу | БА | СА | Основное отличие |
|---|---|---|---|---|
| Новое поведение/сущность | 1 | да | да | полный цикл с change-пакетом |
| Поведение ≠ спеке (баг) | 2 | нет | нет* | фикс по существующей спеке (*мини-дельта СА, если затронуты API/схема) |
| Прод сломан | 3 | нет | нет* | откат → стабилизация → потом Флоу 2 |
| Без изменения поведения (чистка/линтеры/рефакторинг) | 4 | нет | нет* | мини-ТЗ в делегации (*СА не нужен, спека не меняется) |

Слепые зоны, выявленные при описании (2026-09-19): (1) «баг vs фича» — граница проходила интуицией ПМ, теперь правило: выводимость ожидания из существующей спеки; (2) Флоу 2 не требует impact-анализ (H5), но фикс может ломать существующие тесты — ревьюер обязан гонять полный регресс (уже в G3-правиле); (3) Флоу 3 никогда не обкатан.

## Гарантии (как детерминизм обеспечен)

Три независимых слоя — правила «на бумаге» + исполняемые ворота + физические замки:

1. **`scripts/flow_check.py`** — state-machine по файлам: чеклист без change-пакета, кейсы без чеклиста, approved без ревью, автотесты без TC-трассировки, заархивированный change без слияния дельт — все это exit 1. Также валидирует ТЗ (7 разделов, уникальность FR/NFR, преамбула ответственности, TBD/TODO, оценочные формулировки).
2. **CI (`.github/workflows/flow.yml`)** — оба валидатора на каждый push/PR: нарушение невозможно смержить, а не просто «запрещено».
3. **Branch protection на main** — прямые push отклонены GitHub'ом (проверено живым тестом GH013): любое изменение — только через PR с ревью.
4. **`scripts/check_auth_timing.py`** — AST-проверка auth-модулей (bcrypt, dummy-логины, токены через secrets, нет `==` на секретах).
5. **Аудит-след git** — каждый переход этапа виден: кто, что, когда, почему (коммиты + review-файлы append-only).
6. **Изоляция контекстов** — сабагент физически не видит диалог ПМ (проверено живым тестом 2026-09-16): решение не может «просочиться» на словах.

## Контракты (интерфейсы этапов)

Полностью — [contracts/artifact_contract.md](contracts/artifact_contract.md). Кратко:

1. **Заказчик → БА → СА** (requirements.md): 7 разделов, FR-N/NFR-N, MoSCoW, преамбула, статусная модель (ЧЕРНОВИК → ГОТОВ К УТВЕРЖДЕНИЮ → УТВЕРЖДЕН — только Заказчик), decision rights (Заказчик / интерпретация ПМ / технические детали), answers_roundN обязателен.
2. **СА → Разработка** (change-пакет + sdd): Must покрыт, каждый Requirement со Scenario, без реализации в спеке, tasks атомарны. Вход: ТЗ УТВЕРЖДЕН + answers-артефакты.
2a. **СА → qa_impact_analyst** (H5, при MODIFIED/REMOVED дельтах): дельты + существующий регресс → вердикт по каждому затронутому тесту (keep / revalidate=pending_update / retire) в `test-model/impact/<change-id>.md`; запускается до qa_checklist, его вердикты добавляют в чеклист требования «обновить кейс».
3. **СА → QA-чеклисты**: спека доступна, change-id проставлен.
4. **Чеклисты → кейсы**: полное покрытие CHK, негативные/граничные для валидаций, дефекты спеки эскалированы.
5. **Автор ⇄ Ревьюер кейсов**: цикл new/ → reviews/ → approved/; ревью 6 осей + G8-оси кода тестов; approve без blocker/major.
6. **Автотесты только по approved-кейсам**, TC-трассировка обязательна.
7. **Архивация**: триггер (все tasks [x] + зеленый QA + разрешение ПМ) → дельты в master-spec → пакет в archive. Архив без слияния ловится flow_check.

## Решающие принципы

- **Скриптами, не агентами** — где проверка автоматизируема, она не доверяется агенту (flow_check, check_auth_timing; AST-анализ чистых функций G2).
- **Линза «сабагент vs правило»** — новая роль только при: повторяемость + изоляция контекста + своя зона + экономика токенов. Иначе правило/скрипт. (Прецеденты: DevOps — отказ G7; регресс-аналитик — создание G5.)
- **Спека — арбитр.** Расхождение кода со спекой = эскалация, никогда не молчаливая правка под код. Делегированное решение («интерпретация ПМ») не переписывает спеку.
- **Не поверить отчету, а проверить фактами** — приемка ПМ: ворота + диф в зоне + артефакты + история + коммит без push.
- **Здоровье сабагентов** — пинг транскриптов каждые 5–10 мин; деградация (петли фраз, мусор) → stop, перезапуск компактной формулировкой; артефакты деградировавшей сессии не используются.
- **Экономия контекста** — goal ≤2500 симв., ссылки вместо пересказа, дословные цитаты только значимых решений, ревью поэтапно файл за файлом (блок H при внедрении), PLAN.md как внешняя память ПМ.

## Релизный контур

1. Предрелизный регресс: `pytest tests/` (все тесты текущего + keep прошлых релизов) на release-candidate.
2. Шаг «свернуть промежуточные» (G9): PR очистки new-дублей, временных смоков; аудит-след не трогается.
3. PR release-candidate → main (только зеленый + решение Заказчика о релизе).
4. Деплой из main (ekotov-wiki: systemd + nginx, `deploy/README.md`).
5. Пост-релизно: qa_regression_analyst актуализирует манифест (G5); эскалации спеки → следующий change.
