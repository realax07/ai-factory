# AI Factory — Harness-as-a-Service: конвейер разработки ПО из агентов

**AI Factory — это harness: исполняемая обвязка вокруг LLM-агентов, которая
превращает их в конвейер разработки.** Работу делают агенты-роли (аналитик,
разработчик, ревьюер, QA…), а порядок, границы и приемку обеспечивают
скрипты и CI. Агент может ошибиться, забыть правило или переоценить свой
результат, и harness это ловит: шаг не в том порядке отклоняется, запись вне
зоны роли не принимается, PR без ревью и зеленых ворот не вливается.

**As-a-service** — фабрика ставится на машину один раз и обслуживает любые
проекты. Проект получает ворота одной командой и остается тонким клиентом:
в нем код, спеки и артефакты, а исполняемое ядро живет в фабрике.

Фабрика не привязана к модели: роли работают на дешевых моделях (GLM-5.3 и
GLM-5.3-flash), потому что проверку делает не модель, а ворота.

## 1. Как это работает

```
 Заказчик (человек)
    │  требования, решения на развилках, утверждения
    ▼
 ПМ — агент-оркестратор (Hermes, Claude Code или другой кодагент)
    │  план пакета: флоу + стадии с ролями и зонами
    ▼
 Пакетный раннер ──► стадия pi:<роль> ──► роль-агент (Pi, свой worktree, своя модель)
    │                    │                     │ пишет только в зону роли
    │                    ▼                     ▼
    │               ворота flowctl  ◄──── артефакты в git (спеки, код, кейсы, ревью)
    │               до и после стадии
    ▼
 PR → CI (openspec, flow_check, полный сьют) → ruleset main → merge
```

Три принципа, на которых всё держится:

1. **Одна роль — один изолированный агент.** Роль не видит диалог ПМ и чужие
   контексты, только файлы репозитория и свой бриф. Автор не ревьюит себя.
2. **Передача — только артефактами в git.** Что не закоммичено, того не
   существует: следующая роль и ворота читают файлы, а не чат.
3. **Правило проверяет скрипт, а не дисциплина агента.** Инструкции в
   промптах — подсказка; гарантию дают ворота, которые нельзя пропустить.

<details>
<summary>Словарь терминов</summary>

- **Hermes** — агент-оркестратор, в котором обычно работает ПМ (диалог с
  Заказчиком в мессенджере, делегации `delegate_task`). **Pi** — CLI-агент, в
  котором исполняются роли.
- **Пакет** — единица работы с одним планом и одним PR (фича, багфикс,
  обслуживание). **scope** — его идентификатор (`add-widget`, `BUG-042`…).
- **Change-пакет** — пакет флоу 1 в OpenSpec: `openspec/changes/<id>/`
  с предложением, дельтами спек, дизайном и задачами `tasks.md`.
- **Дельта / master-spec** — изменение спеки внутри change-пакета / общая
  спека проекта в `openspec/specs/`; при архивации дельты сливаются в
  master-spec.
- **Зона** — пути, в которые роль имеет право писать; **резервация** —
  захват зоны на время сессии, чтобы две сессии не писали в одно место.
- **Ворота (gate)** — проверка, без прохождения которой шаг не принимается.
- **Provenance** — запись о ревью, привязанная к SHA и отпечатку диффа:
  кто автор, кто ревьюер, на каком коммите вердикт. **STALE** — вердикт
  или прогон ворот относится к старому коммиту и не засчитывается.

</details>

## 2. Кто что делает

### Участники

| Кто | Что делает | Чего не делает |
|---|---|---|
| **Заказчик** | Ставит задачу, утверждает требования, решает развилки (зафиксированные решения — в репозитории) | Не управляет агентами вручную |
| **ПМ** (агент-оркестратор) | Общается с Заказчиком, пишет план пакета с флоу, запускает раннер, принимает этапы по фактам, ведет PLAN и бэклог | Не пишет продуктовый код и не ревьюит сам себя |
| **Роли** (агенты-исполнители) | Делают одну работу своей роли в своем worktree и своей зоне записи | Не выходят за зону, не пушат в main |
| **Машина фабрики** (скрипты) | Решает ALLOW/DENY по фактам, резервирует зоны, сверяет дифф, гоняет ворота, пишет аудит | Не судит о качестве по существу — это ревьюеры |
| **GitHub** | Ruleset на main (только PR, без обхода) + обязательные проверки CI | — |

### Роли конвейера

Каждая роль — системный промпт в [`agents/`](agents/README.md); у ролей,
которые исполняет Pi, есть еще роль-пак в
[`skills/pm-factory/pi/role-packs/`](skills/pm-factory/pi/role-packs/README.md)
с моделью своего яруса. Зоны записи всех ролей — таблица в
[agents/README.md](agents/README.md#таблица-зон-записи-норма-для-всех-ролей).

| Роль | Результат | Модель |
|---|---|---|
| ba — бизнес-аналитик | `requirements.md` (FR/NFR, дословные решения Заказчика) | glm-5.3 |
| sa — системный аналитик | change-пакет OpenSpec + `sdd.md`, задачи `tasks.md` | glm-5.3 |
| architect | ревью пакета до разработки, `architecture/map.md` | glm-5.3 |
| dev | код одной задачи + unit-тесты `tests/unit/` | glm-5.3 |
| dev_lead | сборка веток параллельных задач пакета в интеграционную ветку | — (вне роль-паков) |
| code_reviewer | ревью диффа: approve / return | glm-5.3-flash |
| qa_impact_analyst | что из регресса затронуто дельтами спек | glm-5.3-flash |
| qa_case_author → qa_case_reviewer | тест-кейсы по спеке → их ревью | glm-5.3-flash |
| qa_automation | приемочные автотесты по кейсам: `tests/api` (requests), `tests/web` (playwright), `tests/integration` (без HTTP и браузера) | glm-5.3-flash |
| regress_runner | прогон и разбор регресса, артефакт прогона | glm-5.3-flash |
| ui_designer / design_validator | мокапы / сверка UI с мокапами | glm-5.3-flash |
| devops | RUNBOOK и деплой-инфраструктура (боевой деплой — по утверждению) | glm-5.3-flash |
| debug | диагностика по эскалации `needs-debug:`, без правки продукта | glm-5.3-flash |

Аудитор (Kimi K3.1, только чтение) вызывается вручную вне конвейера.

## 3. Установка

### Требования

| Компонент | Версия | Зачем |
|---|---|---|
| git | ≥ 2.40 | версии, PR, аудит-след |
| Python | ≥ 3.10 (CI — 3.12), скрипты — только stdlib | ворота и утилиты |
| pytest | актуальный | сьют фабрики |
| [OpenSpec CLI](https://github.com/Fission-AI/OpenSpec) | 1.14.0 (`npm i -g @fission-ai/openspec@1.14.0`) | формат спек и `validate --strict` |
| Node.js + npm | для OpenSpec CLI и Pi | проверяется bootstrap |
| [Pi](https://pi.dev) | `npm i -g @earendil-works/pi-coding-agent` + ключ провайдера | исполнитель ролей |
| Оркестратор ПМ | Hermes Agent или другой кодагент | диалог с Заказчиком, запуск раннера |
| GitHub с Actions | — | CI и ruleset |

### Шаг 1. Фабрика на машину

```bash
git clone https://github.com/realax07/ai-factory ~/ai-factory && cd ~/ai-factory
python3 scripts/factory_bootstrap.py
```

Bootstrap проверяет окружение (python, git, node/npm, OpenSpec CLI, pytest в
том же python; нет `pi` — предупреждение), создает каталог состояния движка
(`AF_STATE_DIR`, по умолчанию `~/.hermes/state/`) с файлом режима
`flow_mode.json` (реестр сессий появится там при первой резервации), ставит
zone-guard исполнителя Pi (см. «Шаг 2») и — если на машине есть Hermes — обертки
кронов вотчдогов, затем прогоняет полный сьют фабрики как приемку. Системный
crontab bootstrap не правит. Режим ворот нового файла — **shadow** (решения
считаются, но не блокируют), повторный запуск режим не меняет; боевой режим
включает Заказчик: `python3 scripts/flow_mode.py set enforcing --by customer`.
Секреты не переносятся — ключи кладутся вручную (`~/.hermes/.env`,
`~/.pi/agent/models.json`). Флаги: `--skip-pi`, `--skip-cron`, `--skip-tests`,
`--flow-mode`.

State движка резервируется кроном `state-backup` (`scripts/state_backup.py`,
архивы в `AF_BACKUP_DIR`); восстановление и перенос на новую машину —
[docs/runbook-factory-move.md](docs/runbook-factory-move.md).

Пути машины не прошиты в коде: каждый задается переменной окружения
(`AF_STATE_DIR`, `HERMES_HOME`, `AI_FACTORY_HOME`, `AF_PROJECTS_ROOT`,
`PI_AGENT_DIR`, `AF_BACKUP_DIR`). Текущие значения: `python3 scripts/factory_paths.py`.

### Шаг 2. Исполнитель Pi

Сам Pi ставится через npm (таблица требований). Zone-guard —
копия эталона `skills/pm-factory/pi/zone-guard.ts` в `~/.pi/agent/extensions/zone-guard.ts` для ручных
запусков pi (пакетный раннер берет эталон из репо) — ставит bootstrap (шаг 1); если там
уже лежит отличающаяся копия, bootstrap ее не перезаписывает и предупреждает.
Вручную:

```bash
mkdir -p ~/.pi/agent/extensions
cp skills/pm-factory/pi/zone-guard.ts ~/.pi/agent/extensions/
```

Ключ провайдера — в `~/.pi/agent/models.json` (chmod 600, не в git). Состав
паков, модели и зоны — [role-packs/README.md](skills/pm-factory/pi/role-packs/README.md).

### Шаг 3. GitHub (один раз на репозиторий)

Settings → Rules → Rulesets → ruleset на `main`: **Active**, bypass —
**никому**, правила: только через PR, без force-push, обязательные проверки
`test-flow-control` и `flow` (чек появляется в списке только после первого
прогона CI в репозитории — сначала откройте любой PR). Проверка: `gh api repos/<owner>/<repo>/rules/branches/main`
возвращает `pull_request` и `required_status_checks`, прямой push в main
отклоняется; то же одной командой — `python3 scripts/ruleset_check.py`.
Если сломан сам CI и починку нельзя влить — аварийный merge по
[docs/runbook-emergency-merge.md](docs/runbook-emergency-merge.md) (выполняет
только админ репозитория).

### Шаг 4. Конвейер в проект

```bash
python3 ~/ai-factory/scripts/factory_init.py --target /path/to/repo --name "My Project"
```

Создает структуру каталогов (openspec, test-model, docs…), копирует ворота,
CI-workflow, контракты, шаблоны, промпты ролей и скиллы, `CONSTITUTION.md` и
скелет глоссария, шаблон impact-карты `templates/impact.template.md`,
smoke-тест `tests/unit/test_smoke.py` и режим раскладки
тестов `test-model/test-layout.json` (`strict`, если тестов вне раскладки нет,
иначе `warn`), затем проверяет, что `flow_check` на пустом проекте проходит. Если на машине есть Hermes, заодно ставит плагин flow-enforcer в
`~/.hermes/plugins/` (`--skip-plugin`) и обертки кронов в `~/.hermes/scripts/`
(`--skip-crons`); без Hermes оба шага пропускаются сами.

Заодно пишет `factory.lock` — HEAD фабрики, влитый в `origin/main`, чьи ворота
будет гонять CI проекта (J65.7); существующий lock без `--force` не трогается.

Повторный запуск без `--force` докопирует только недостающее. `--force`
перезаписывает копируемые файлы — ворота, `flow.yml`, промпты `agents/`, а
также `CONSTITUTION.md` и `docs/glossary.md` проекта (уже существующие
каталоги скиллов не перекопируются) — после него
сверьте required-checks и верните проектные правки.

## 4. Как пользоваться

### 4.1. Выбрать флоу

Каждая задача начинается с выбора флоу. Флоу определяет, какие роли нужны и
какие ворота проверяются.

| Флоу | Когда | Цепочка | scope |
|---|---|---|---|
| **1** полный | новое поведение, меняется спека | ba → sa → architect → [dev → review] на каждую задачу → QA-контур → архивация дельт в master-spec | `add-widget` (change-id) |
| **2** багфикс | реализация расходится со спекой | баг-репорт → dev → [qa_automation] → review → merge | `BUG-042` (имя репорта) |
| **3** хотфикс | прод сломан | severity S1–S3 → стабилизация → [qa_automation] → обязательный PR-цикл → post-mortem | `S1-prod-down` |
| **4** обслуживание | поведение продукта не меняется (инфра, ворота, доки) | план → работа → [qa_automation] → review → merge | `chore` или `repo-cleanup` |
| **5** экспресс | малая правка, артефакты оформляются после | работа → [qa_automation] → ретро-артефакты → закрытие | `fix-typo` |

`[qa_automation]` — этап по необходимости: dev пишет только `tests/unit/`,
поэтому регрессионный приемочный тест к багу и адаптацию сломанных приемочных
тестов делает автоматизатор.

Формат scope проверяет `python3 scripts/flow_ids.py <флоу> <scope>`. Подробно
по каждому флоу, с развилками и кодами отказов, —
[docs/README-flow-control.md](docs/README-flow-control.md).

### 4.2. Написать план пакета

План — обязательный артефакт для флоу 1, 2 и 4: `PLAN-<scope>.md` в корне
проекта или `PLAN.md` внутри change-пакета `openspec/changes/<id>/` (флоу 3
вместо плана несет incident-ref, флоу 5 план не требует). В плане цель,
строка `Флоу: N`, решения Заказчика, критерий закрытия и манифест стадий для
раннера. Пример — обслуживание (флоу 4):

````markdown
# PLAN-log-cleanup: убрать отладочный вывод из backend

**Флоу: 4** — поведение продукта не меняется.

```yaml
pipeline:
  package: log-cleanup
  flow: 4
  stages:
    - id: impl
      run: pi:dev
      zones: [backend/**, tests/unit/**]
      task: заменить print на logging в backend/, поведение не меняется, тесты зеленые
    - id: check
      run: gate:python3 scripts/flow_check.py .
    - id: review
      run: pi:code-reviewer
      zones: [code-reviews/log-cleanup/review-001.md]
      verdict:
        file: code-reviews/log-cleanup/review-001.md
```
````

Виды стадий: `pi:<роль>` — роль-агент, `gate:<команда>` — ворота,
`stand:<команда>` — подъем тестового стенда, `hermes:<роль>` — стоп-точка
для ПМ. Во флоу 1 стадии ролей идут по задачам `tasks.md` (поле `task_id`), а
движок пустит их только при утвержденных требованиях и готовом
change-пакете. Все поля и пример флоу 1 —
[docs/guides/pipeline-manifest.md](docs/guides/pipeline-manifest.md).

### 4.3. Запустить раннер

```bash
python3 ~/ai-factory/scripts/package_runner.py PLAN-log-cleanup.md --dry-run   # только разобрать манифест
python3 ~/ai-factory/scripts/package_runner.py PLAN-log-cleanup.md             # исполнить
```

Что происходит на каждой стадии `pi:<роль>`:

```
flowctl prepare   — снимок фактов → можно ли этой роли этот шаг сейчас? (ALLOW/DENY)
  └─ резервация зоны (две сессии не пишут в одни пути)
flowctl run       — переснимок перед стартом
pi <роль>         — агент работает в своем worktree; zone-guard режет write/edit вне зоны
flowctl finish    — реальный git diff ⊆ зона (ловит и запись через bash)? ворота этапа зеленые?
коммит стадии в ветку пакета → резервация закрыта → следующая стадия
```

Любой отказ — **STOP** с кодом и диагностикой: `DENY` (шаг не по флоу, нет
плана или утвержденных требований), `ZONE_CONFLICT` (зону держит другая
сессия), `ZONE_OUTSIDE_POLICY` (зона шире политики роли), `OUT_OF_ZONE`
(агент записал лишнее), красный гейт. Ретраев нет: ПМ разбирает причину,
повторный запуск продолжает с той же стадии (состояние — рядом с планом).

### 4.4. Принять результат и влить

ПМ не верит отчету агента, а проверяет факты: ворота зеленые, дифф только в
зоне роли, заявленное подтверждено артефактами. Затем — PR в main. CI
проверяет спеки (`openspec validate --strict`), порядок артефактов
(`flow_check`), полный сьют и PR-ворота (маркер PR, обязательные артефакты,
ревью независимой ролью). Ruleset пускает merge только при зеленых
проверках.

До push полезно прогнать то же, что увидит CI: `python3 scripts/ci_local.py`
(закоммиченный HEAD в клоне глубины 1, пустой HOME — ловит «локально
зеленое, в CI красное»; незакоммиченные правки в прогон не попадают).

### 4.5. Как работает с harness сам агент-ПМ

Оркестратор — тоже агент, и harness ведет его так же жестко:

1. **Вход в репозиторий** — чтение по порядку: [AGENTS.md](AGENTS.md)
   (правила), [PLAN.md](PLAN.md) (статус), [docs/process-context.md](docs/process-context.md)
   (среда и дисциплина), [agents/README.md](agents/README.md) (роли и зоны),
   контракт своего этапа.
2. **План до работы.** Без плана с объявленным флоу движок отвечает
   `PLAN_RELEASE_MISSING` / `PLAN_FLOW_UNDECLARED`.
3. **Решения Заказчика — только зафиксированными.** «Считаю согласованным»
   машина не принимает (`HUMAN_APPROVAL_REQUIRED`).
4. **Работа ролей — через раннер.** Если оркестратор — Hermes, его
   `delegate_task` проверяет плагин flow-enforcer: заголовок
   `flow: flow=N role=… repo=… scope=…` с невалидным scope или отказом движка
   блокируется на спавне. Делегация вовсе без заголовка в режиме по
   умолчанию (`permissive`) проходит с записью в лог, в `strict` —
   блокируется. Боевые SA/архитектор/DEV/BA с маркером `[hermes:<роль>]`
   получают отказ с подсказкой «используй Pi» (без маркера исполнителя —
   предупреждение в лог).
5. **Доклад Заказчику** всегда содержит статусы ворот:
   `prepare | reserve | zone-check/gates | provenance` — PASS/DENY/UNKNOWN/SKIPPED,
   без «сглаживания».
6. **Застрял на непонятном отказе** — не чинит вслепую, а эскалирует
   `needs-debug:` диагносту.

## 5. Что гарантировано и чем

Гарантия — это то, что нельзя обойти незаметно. Остальное честно отнесено к
дисциплине. Полный реестр «гарантировано / на честном слове» —
[docs/guarantees.md](docs/guarantees.md).

| Слой | Что обеспечивает | Чем | Граница |
|---|---|---|---|
| **GitHub** — обойти нельзя | merge в main только через PR с зелеными проверками | ruleset (bypass — никому) + CI: `openspec validate`, `flow_check`, полный сьют, `pr_validate` | — |
| **Движок** — блокирует на входе | шаг по флоу, правильная роль, план и утвержденные требования, непересекающиеся зоны | `flowctl` → `flow_state` (факты) → `flow_transition` (решение) → `session_check` (зоны) | работает на штатном маршруте; общая учетка ОС — граница доверия |
| **Приемка стадии** — блокирует на выходе | дифф только в зоне роли, ворота этапа, вердикт ревью (заголовок `## Вердикт: approve\|return`, решает последний; на стадии Pi — аудит-запись: SHA проверявшегося коммита, дифф, авторы и ревьюер) | `session_check check`, `gate_runner`, единый парсер вердикта `flow_check` | содержательное качество ревью не проверяется — только форма и привязка |
| **Вотчдоги** — замечают обход | делегация Hermes мимо движка видна за ~5 минут | `delegate_watchdog` (крон) | запуск Pi вручную мимо раннера не ловит |
| **Правила** — дисциплина | то, что механизировать нельзя или не окупается | AGENTS.md, промпты ролей, контракты | нарушение видно только ревью и аудиту |

Итог: **нельзя** (движок и GitHub) + **заметят** (вотчдог, аудит-след в git) +
**не засчитают** (видимый обход = нарушение независимо от результата).

Харнесс проверяет и сам себя: сьют фабрики (более 1200 тестов, включая
негативные сценарии ворот) обязателен на каждом PR и герметичен — не пишет
в реальный HOME и в дерево репозитория.

### Как связаны части

```
openspec/specs (правила)  ──►  contracts (вход/выход этапов)  ──►  agents/*.md (промпты ролей)
        │                               │                               │
        ▼                               ▼                               ▼
 flow_transition (графы флоу)    flow_check / pr_validate         role-packs (промпт → модель Pi)
        │                               │                               │
        └──────────► flowctl ◄──────────┴──── package_runner ◄──────────┘
                        │
                 реестр сессий, аудит  (~/.hermes/state, вне git)
```

- **Изменение правил идет сверху вниз:** спека → контракт → промпты. Код
  ворот проверяет то, что записано в спеках и контрактах.
- **Реестр ролей** `agents/roles.json` — единый источник зон записи (политика
  ворот), строк таблицы зон в `agents/README.md` и оглавления роль-паков:
  таблицы генерирует `scripts/gen_role_docs.py`, тест сверяет их с реестром.
  Версия политики — sha256 реестра (аудит) и отпечаток зоны своей роли
  пишутся в каждую резервацию; `finish` сверяет отпечаток роли, поэтому
  правка зоны одной роли не роняет активные сессии других (J65.2).
- **Фабрика ↔ проект.** Проект хранит код, спеки и артефакты. CI-ворота
  проекта — по закрепленной версии фабрики (J65.7): `factory.lock` в корне
  (`repo=` и `sha=` коммита фабрики), `flow.yml` делает checkout фабрики на
  этот SHA в `.factory/` и гоняет ее `flow_check` и `pr_validate` против
  проекта. Обновить ворота в проекте — PR с одной строкой:
  `python3 scripts/factory_lock.py update --target <проект>`. Без
  `factory.lock` CI берет копии `scripts/` проекта (как раньше). Ядро
  работает экземпляром фабрики (`--repo` проекта — параметр); копии ядра
  `factory_init` пока тоже кладет в проект (снимаются после перевода всех
  проектов на lock), сверка копий — `check_mirrors.py`.
- **Раскладка тестов** (спека qa-pipeline): `tests/unit/` — dev,
  `tests/api/`, `tests/web/` (сьют стенда — `tests/web/e2e/`),
  `tests/integration/` — qa_automation; плюс `tests/smoke_cross/` и
  `tests/archive/`. TC-ID в docstring обязателен везде, кроме `tests/unit/`.
  `flow_check` проверяет раскладку и стек уровня (в unit и integration нет
  `requests` и `playwright`) в режиме проекта `test-model/test-layout.json`:
  `warn` (по умолчанию) или `strict`.
